> 这是隐性漂移源——它不违反任何显式规则，但会让文档与代码对不上。

## 缓存术语（**极易混用，且面试必问**）

| 术语 | 代码标识 | 定义 | **不要叫** |
|---|---|---|---|
| 命中 | cache hit | L1/L2 缓存命中 | 缓存成功 |
| 回源 | fallback to DB | 缓存未命中后查 MySQL | **穿透**（那是另一回事） |
| **击穿** | cache stampede | **热点 key 失效的瞬间**，大量并发请求同时回源 DB | 穿透、雪崩 |
| **穿透** | cache penetration | 查询**不存在的数据**，每次都绕过缓存打到 DB | 击穿 |
| **雪崩** | cache avalanche | **大量 key 同时失效**，DB 被整体打垮 | 击穿、穿透 |

> 三者的区别在**触发条件**：击穿是"单个热点 key + 高并发"，穿透是"查不存在的数据"，雪崩是"大批 key 同时过期"。答错这个，面试官立刻知道你没真做过。

## 秒杀与一致性术语

| 术语 | 定义 |
|---|---|
| **超卖** | 卖出数量超过库存。秒杀的**第一号敌人** |
| **少卖** | 库存有剩余但用户抢不到（如扣减成功却下单失败未回补）——比超卖隐蔽，靠对账发现 |
| **削峰** | 用 MQ 把瞬时高并发请求转成平稳的异步消费 |
| **幂等** | 同一操作执行多次，结果与执行一次相同 |
| **库存回补** | 扣减成功但下单失败时，把库存加回去（最终一致的兜底手段） |
| **对账** | 定时比对两侧数据（如 Redis 库存 vs DB 订单数），修正差异。**把"最终一致"从口号变成可运行的检查** |
| **本地消息表** | 业务操作与"待发送消息"写在同一本地事务中，保证消息最终一定发出 |

## 架构术语

| 术语 | 定义 |
|---|---|
| **逻辑态** | M0–M8：一个进程，但模块边界已按三个服务划好，由 ArchUnit 强制 |
| **物理态** | M9 起：三个独立进程 + 网关 |
| **故障域** | 一处故障的影响范围。**本项目拆分的唯一理由**就是不让秒杀的故障波及交易 |
| **机制 vs 策略** | 边界线：`wt-infra` 管机制（连接、序列化、Key 规范），业务模块管策略（缓存存多久、哪些事件幂等） |
| **防腐层** | 模块/服务间只能通过 `wt-domain` 的接口通信，不碰对方内部实现 |

## 过程术语

| 术语 | 定义 |
|---|---|
| **证据等级** | `[REAL]` 真实链路跑过 / `[SYNTHETIC]` 仅单测或造数 / `[UNVERIFIED]` 只写完 / `[BLOCKED]` 卡住 |
| **Step 0** | 每个任务动手前向用户说清「做什么/为什么现在/几种做法与代价」的确认闸门 |
| **验证剧场** | 用自己造的假数据跑通测试就宣称成功。**本项目头号反模式** |
| **单边数据** | 只给优化后的数据、没有优化前的对照。**不算证据** |
