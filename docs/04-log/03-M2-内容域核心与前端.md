## 一句话总结

**把「内容」这条链路从数据库打通到了浏览器**——帖子、评论、标签、点赞收藏、后台治理，
配一个 4 个页面的 Vue3 前端。M2 的验收闸门「真实 HTTP 走通 `发帖 → 评论 → 列表`」已达成。

**但 M2 真正的价值不在这些功能本身，而在于它是 M3–M6 四个亮点的数据基础**：
缓存要缓存帖子、Kafka 要异步写评论点赞、ES 要索引帖子正文、深翻页要有一张能塞 10w 行的表。
**没有 M2，那四个亮点就没有对象可讲。**

## 关键决策与理由

> **完整的推理在 ADR 与设计稿里，这里只列结论**（单一事实源，协作协议 §4）。
> 设计稿：[`docs/03-design/m2-content-core.md`](../03-design/m2-content-core.md)（10 个决策点的完整取舍表）

| 决策 | 为什么 | 备选与被否决的理由 | 记录 |
|---|---|---|---|
| 跨域取用户信息走契约，**不冗余作者快照** | 快照的代价是"用户改昵称后历史帖子永远停在旧昵称"，而**没有机制会去修它** | 判据是"这个值描述当前状态还是历史事实"——订单的收货地址快照**反过来是对的**（M7 会用） | ADR-0015 |
| 计数**冗余在内容表**，不实时 COUNT | 列表页是最高频的读，实时 COUNT 把成本压在最贵的地方；而且**它就是 M3 要缓存的东西** | 诚实代价：允许短暂不一致，且热点帖会争同一行 | ADR-0016 |
| 点赞收藏用**两张专用表**，不做通用 action 表 | 唯一约束表达了"这个人赞过这个帖"的完整语义；通用表要拼四列，漏带一个条件不报错只查错 | 判据是"查询会不会跨类型"，不是"结构像不像" | ADR-0017 |
| 评论**两级**（`parent_id` + `root_id`） | `root_id` 让"取第 2 页的顶层评论"变成普通索引查询，不必递归 | 树形在技术社区用不上；升级路径（加 `depth`）已留 | ADR-0018 |
| 帖子正文**与主表同表** | MySQL 的 TEXT 本来就行外存储，**只要查询不 SELECT 它就不读**；拆表换不来收益 | 真正要立的是"列表查询禁止 `SELECT *`"这条规范 | 设计稿 §2.6 |
| 后台**只做接口不做页面** | M2 的重点是链路，不是管理界面 | 用户 2026-10-05 定的 | — |
| 限流规则**支持按方法区分**，键也带上方法 | 同一条路径的读与写需要两套阈值；**键不带方法的话它们会共用一个计数器** | Task 4 时为此把这件事挪到了 Task 9 | ADR-0014 |

## 你可以怎么验证

### 1. 不启动任何东西（最快）

```
mvn -B test
```

末尾出现 **`BUILD SUCCESS`** 就是全过（151 个，不连数据库）。
里面包含架构测试——**跨域依赖那条线一旦被踩，这里就红**。

### 2. 真实 HTTP（需要 MySQL + Redis 起着）

按 [`docs/06-runbook/api-smoke.http`](../06-runbook/api-smoke.http) 从第 1 条往下跑。
**每条都写了期望值，而且自带反面对照**：

| 看什么 | 期望 |
|---|---|
| 发帖 → 评论 → 列表 | 都 200 |
| **不带令牌**发帖 / 改帖 | 401 |
| **改 / 删别人的**帖子 | 403（改自己的 200） |
| 重复点赞 3 次 | 三次都 200，但**计数只加 1** |
| 跨帖回复 | 400 |
| 同一用户名连登 6 次 | 前 5 次 401、**第 6 次 429**；换个用户名仍 401 |
| 发帖 11 次 → 再看列表 | 第 11 次 429，但**列表仍然 200**（读与写各自一个计数器） |

### 3. 前端

```
npm --prefix frontend run dev
```

打开 `http://localhost:5173`，走一遍：注册 → 登录 → 列表 → 发帖 → 详情 → 评论 → 点赞。

## 踩过的坑

**这一节只记真实的，不编。M2 期间踩到的坑按性质分四类：**

### 一、我自己写错、又被测试逮住的

| 坑 | 表现 | 怎么发现的 |
|---|---|---|
| **限流的规则匹配拆成了两步** | `GET /api/posts` 撞上发帖那条规则，因方法不符**径直放行**——**这条接口完全不受限流，而配置看起来完全正确** | `RateLimitInterceptorTest` |
| **用 UPDATE 的返回行数判断"帖子存在"** | MySQL 返回的是"**改变了的**行数"，所以用户打开帖子、什么都不改、点保存 → 被判成"帖子不存在" | 写接口层时想到，补了回归测试 |
| **权限规则只做了一半** | 定了"下架的帖子作者仍能打开"，但详情响应里**没有状态字段**——作者打开了，看到的和正常帖子一模一样 | 写链路讲解的子 agent 交叉核对时发现注释与代码对不上 |
| **测试断言越界** | 在 `PostService` 那层断言"没调过互动服务"，可那一层它是替身，**调用确实发生** | 跑测试直接红 |

### 二、环境的坑（都不是代码的问题，但会伪装成代码的问题）

| 坑 | 表现 | 出处 |
|---|---|---|
| **`curl` 发带中文的 JSON 一律失败** | 返回 `400 请求体格式不正确`——**第一反应是"接口写错了"**，实际是命令行把中文按 GBK 发出去了 | `troubleshooting.md` 2026-10-05 那条 |
| **`redis-cli --scan` 在这个 Redis 版本上不生效** | 我用它清限流计数，报"清空成功"**是假的**（好在计数 60 秒自己过期） | 本次执行时发现 |
| **`npm init` 不认 `--prefix`** | 它在**仓库根目录**生成了一个 `package.json`，而我是想建到别处 | 已删除；`git log` 确认它从未入库 |

### 三、设计层面的、值得单独记住的

- **"设计稿先于代码"有终点**：提交设计稿时 `check-doc-refs` 报了 1 处漂移
  （`UserQueryService` 还不存在），当时写明"Task 1 完成后即消失"——
  **它确实消失了**。这件事值得记：那个状态是有尽头的，不是长期的债。
- **注释与代码对不上，暴露的往往是功能缺了一半**（见上面第三行）。
  这类"曾经想过、但没落地"的缺口，靠读代码很难发现，**靠对账才看得见**。

### 四、协作机制上的

- **改一半比不改更糟**：交接测试查出「专栏来源写错」后，我第一轮只改了 §2.7，
  同一份文档的 §1/§9/§10 还留着旧说法——**文档自己内部矛盾，接手人无从判断该信哪个**。
  第二轮测试才把它们全揪出来。
- **提交信息里的反引号会被 shell 当成命令替换**：一条提交信息的两个代码标识
  被替换成了空、从信息里消失。**教训：提交信息一律走 `-F 文件`，不要内联在命令行里。**

## 遗留与风险

| 项 | 说明 | 何时处理 |
|---|---|---|
| **列表搜索走的是 `LIKE`** | M2 的权宜之计，代码注释里标了"M5 会用 ES 替换" | M5 |
| **浏览量用直接 `UPDATE +1`** | 每次读详情都写一次库；M3 会换成 Redis 累加 | M3 |
| **热度排序的系数是拍出来的** | `评论×3 + 点赞×2 + 收藏×1`——初始值，注释里写明要用真实数据与 EXPLAIN 校准 | M6 |
| **计数的短暂不一致** | 冗余计数在极端情况下会偏（ADR-0016 的后果一节写明） | M3 |
| **前端只存访问令牌、不接续期** | 30 分钟后需要重新登录。刷新令牌后端是现成的，接上它是十几行 | 不阻塞；记在 `12-前端工程与页面.md` |
| **后台没有页面** | 只有接口（用户定的）；管理界面若要做，是独立的一块 | 未排期 |
| **`forum-content` 的测试不连库** | 这一层只守业务规则；SQL 本身由冒烟用例与本地集成测试覆盖 | 已有分工 |

### ✍️ 几件"后端做了、前端没露出"的事（2026-10-06 用户看过前端后提出）

用户点开前端之后问：头像、个人资料修改、点作者进他的主页、关注/粉丝……这些是后续要做还是没规划？
查下来分三类，**结论是"排期而不现在做"**：

| 项 | 实情 | 处置 |
|---|---|---|
| 改个人资料、看别人的主页与他的帖子、头像**显示** | **后端接口全都已经做了**（M1 的改资料与主页、M2 的按作者查帖子），**只是前端没接**。一个接口都不用新写 | **排期到 M10**（它本来就是"交付质量"那一档）。见 spec §6.2 的指针 |
| 头像**上传** | 卡在"存储方案未定"上——本地目录，还是第三方对象存储？后者与 ADR-0006「本地可复现」冲突 | 记入 **spec §12 开放问题 #15**，做之前再定 |
| **关注 / 粉丝** | **全项目文档里只出现过一次**——ADR-0017 把它当作"通用表的好处"举例、然后连同那个方案一起被否决。**没有任何里程碑把它列为内容**，所以它当前既不是"要做"也不是"不做"，而是**从未决策** | 记入 **spec §12 开放问题 #14**，**M10 交付前定稿**。倾向不做：五个亮点全挂在"帖子"上，而关注关系不参与任何一个 |

> **这一节值得留着的原因**：用户问的那几个功能，**有两个根本不是"没做"，而是"没被决策过"**。
> 这类缺口靠读代码是看不出来的（代码里没有它们，看起来就像还没轮到），
> 只有把"说要做/说不做"两边都翻一遍才看得见。

## 回滚记录

**分支内没有做过回滚**（没有 `revert` 提交）。

M2 已经合并进 `main`（PR [#5](https://github.com/Wingtisky20/wingtisky-forum/pull/5)，
Merge commit `c70579b`，tag `m2-done`）。要整体回退有两条路：

| 做法 | 效果 | 注意 |
|---|---|---|
| `git revert c70579b -m 1` | 生成一个**反向提交**，历史完整保留 | 这是 `main` 上的标准做法——**永不 force push** |
| `git checkout m1-done` | 回到 M1 结束时的状态 | 用于对照、排查，不是"撤销" |

**回滚原因要写在这里**（现在是"无"）——回滚记录本身就是面试素材：
"我做过一次回滚，因为 X，回滚后改成了 Y"比"一路顺利"可信得多。
