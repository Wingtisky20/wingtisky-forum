## 关键决策与理由

| 决策 | 为什么 | 记录 |
|---|---|---|
| 业务域从纯论坛扩展为「技术社区 + 付费内容」 | 判据是**域之间有无真实数据流转**，不是技术含量高不高 | ADR-0009 |
| 拆 3 个服务，且**先画逻辑边界后做物理拆分** | 拆分理由是**故障域隔离**（不依赖流量大小，可实测）；不在未经验证的判断上押注 | ADR-0010 |
| 跨服务一致性用本地消息表 + 最终一致，**不用 Seata** | Seata 的同步阻塞与秒杀削峰目标直接冲突。**选型看场景，不看组件名气** | ADR-0011 |
| 合并方式用 **Merge commit 而非 Squash** | 你要的是"靠 commit 一步步看迭代"，Squash 会把过程压没 | ADR-0008 |
| `wip:` 提交**允许进 `main`**，但必须可编译 | 若要求"合并前整理掉"，等于把刚为保留过程而放弃的压平手工再做一遍——自相矛盾 | ADR-0008 |
| 防漂移脚本**只扫活文档**，不扫计划书与规格 | 计划书描述的是"将要写的代码"，扫它必然报假阳性；**一个天天报红的检查等于没有检查** | `tools/README.md` |
| 域边界有**两道闸门**：Maven 管"能不能看到"，ArchUnit 管"该不该看到" | Maven 拦得住编译错误，但拦不住"为了让代码编过，顺手在 POM 里加一条依赖"——后者才是真实会发生的事 | `ArchitectureTest.java` 类注释 |
| 前端走 **Element Plus 默认视觉**，不大量 AI 生图 | 省下的时间投给后端亮点 | spec §12 |
| **协作基建提前到 M0 第一步** | 新对话能否接手依赖它——它应该是第一步，不是第四步 | 本文件 |

## 踩过的坑

| 坑 | 根因 | 记录 |
|---|---|---|
| `gh` 能建仓库但 `git push` 连不上 | `api.github.com` 通、`github.com` 不通；git 未配代理 | troubleshooting.md |
| `mvn -pl app -am spring-boot:run` 跑不起来 | `-am` 把无 main class 的根聚合 POM 拽进 reactor | 计划全球约束 |
| `mvn clean compile` 后 `ls */target/*.jar` 失败 | **compile 不产 jar** | 计划全球约束 |
| 两个改动挤进同一个提交 | 同一文件的多处改动被一次 `git add` 全部暂存 | collaboration.md §5.3 |
| **决策改了，5 份文档没跟上** | 合并方式改 Merge commit 时只改了 spec §10.2，**每次对话自动加载的 `CLAUDE.md` 和必读的 `collaboration.md` 都还写着 Squash** | ADR-0008、commit `b990672` |
| **计划书给的脚本按原样抄会误报** | `grep '<version>' \| grep -v xxx` 按行过滤，而父 POM 的 `<version>` 与 `artifactId` 不在同一行 | 计划书 Task 6、commit `5ede1f6` |
| **计划书写的"预期输出"本身是错的** | 它说脚本会报 `CLAUDE.md` 引用的 `ArchitectureTest`——实际那名字只在计划书自己里，CLAUDE.md 根本没有 | 计划书 Task 6、commit `8307089` |
| **计划书的"违规实验"验错了对象** | 它想在 trade-order 里 import forum-user 触发 ArchUnit 报错，但 **Maven 会先拦下编译**——证明的是第一道闸门。要验第二道，必须**先把第一道人为打开**（临时加 POM 依赖） | 计划书 Task 7 Step 3 |
| **`-am` 第三次咬人** | `-Dtest=XxxTest` + `-am` 时，上游无匹配测试的模块会让 surefire 直接失败；要加 `-Dsurefire.failIfNoSpecifiedTests=false` | 计划书 Task 7 Step 2 |
| **`.bat` 里写中文注释会让脚本崩** | cmd 按 GBK 解码文件，而文件在 git 里是 UTF-8，行结构被拆散；`chcp 65001` 也救不了 | troubleshooting.md、commit `e0c8df0` |
| **`call xxx.bat` 报"不是内部或外部命令"** | Git Bash 设置了 `NoDefaultCurrentDirectoryInExePath=1` 并传给子进程，cmd 不再从当前目录找程序；加 `.\` 前缀解决 | troubleshooting.md |
| **Kafka 格式化落到了 `D:\tmp`** | 默认 `log.dirs=/tmp/kraft-combined-logs` 在 Windows 上是**盘相对路径**；配置必须排在格式化之前 | local-setup.md §6.2、troubleshooting.md |
| **Kafka 3.9.1 下载极慢**（8~16 KB/s） | 3.9.x 已是归档版本，国内镜像只留最新版，全 404；只能走 archive.apache.org + 代理 + 断点续传，**丢后台别阻塞其他工作** | troubleshooting.md |
| **"本地绿、CI 红"：check-deps 一直在靠本机残留状态通过** | 内部模块坐标只由 reactor 提供，而 reactor 看的是**本次 Maven 会话**；本机装过 SNAPSHOT 所以看不出来，空仓库必然失败。**这就是 CI 存在的意义** | troubleshooting.md、commit `3e73707` |

> **其中两条值得单说：**
>
> **① "决策改了，5 份文档没跟上"**——决策落地时改的是"设计文档"，而真正会被下一个对话读到的是"入口文档"。两者不是同一批文件：`CLAUDE.md` 自动加载、`collaboration.md` 是会话协议必读，它们比 spec 更早被看到。**改决策时要顺着"谁会读到它"倒推一遍该改哪些文件**，而不是只改做出决策的那一处。
>
> **② "本地绿、CI 红"**——`check-deps.sh` 写完后在本地跑过多次都是绿的，CI 第一次跑就挂了。根因是它依赖了本机仓库里的残留状态。**它验证的不是"依赖是否真实存在"，而是"我的机器上恰好装过"。** 这条是 M0 最值钱的坑：本地通过从来不是充分证据。
