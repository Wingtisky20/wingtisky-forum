## Global Constraints

贯穿全篇，每个 Task 都适用：

1. **每一步都必须可编译。** 进入 `main` 的提交必须可编译（ADR-0008）；做不到的用 `wip:` 留在功能分支。
2. **不改 M2 已有的 HTTP 契约。** `GET /api/posts/{id}` 的请求参数与响应字段**一个都不变**——
   缓存是内部实现。唯一的对外可见变化是**浏览数的含义**：从"精确"变成"最终一致"（见 Task 9），
   这一条要写进 README 与讲解文档，不藏着。
3. **Redis 必须起着。** M3 全程依赖它。`cd /d/aaaSoftware/redis && ./redis-server.exe &`
4. **提交粒度**：一个 Task 拆 1~3 个提交，按「契约 → 实现 → 装配 → 测试」分层。
   **修复独立成条**，不混进功能提交。
5. **闸门 5（高危区点名）**：Redisson 与 Caffeine 都是**首次接入**。
   接入后第一关**不是**业务功能，而是**启动验证 + 已有功能回归**（Task 1 的验证清单）。
6. **闸门 3（依赖防幻觉）**：新依赖必须 `mvn dependency:tree` 真实可解析；
   版本号只写在父 POM 的 `dependencyManagement`，子模块不写版本。
7. **闸门 6**：每次提交前跑 `bash tools/check-doc-refs.sh`。
8. **Step 0**：每个 Task 动手前，按协作协议 §2 向用户说清「做什么 / 为什么现在做 / 几种做法与代价」，**等回应才动手**。
9. **集成测试不进 CI**（ADR-0007）：`@Tag("integration")` 的测试连本机中间件，只在本地跑。

**这是 M3 的高危区，验证比实现重要。**

| 步 | 做什么 |
|---|---|
| 1.1 | `wt-infra/pom.xml` 加 `redisson-spring-boot-starter`；**改掉那段冲突注释** |
| 1.2 | 先靠 starter 的自动装配拿 `RedissonClient`（不写配置类）；**若不兼容再手动装配** |

**1.2 的两种做法与代价**（Step 0 会再确认一次）：

| 做法 | 好处 | 代价 |

## Task 2: `TwoLevelCache`（L1 + L2，先不含锁）

> **本节的契约与验证方式在 2026-10-06 施工时修正过，三处**（原文留档在下方引用块）：
> ① 接口签名漏了**类型**参数；② 四种过期时间应打包成策略对象；
> ③ **测试分层写错了**——"读真实 TTL"那两条用假 Redis 证明不了，必须放集成测试。

| 内容 | 说明 |
|---|---|
| 契约 | `<V> V get(String key, Class<V> type, CachePolicy policy, Supplier<V> loader)`、`void evict(String key)` |
| 为什么要有 `type` | 值在 Redis 里是 JSON 字符串，**还原时必须知道还原成什么类**；`loader` 只在回源时用到，靠它推断不出类型（Java 泛型运行时被擦掉） |
| 策略 | `record CachePolicy(l1Ttl, l2Ttl, l2Jitter, nullTtl)` —— 四种时间**一起变**，散着传会让每个调用点变成四个参数 |
| 序列化 | **JSON 字符串**（注入 Spring 的 `ObjectMapper`）；不用 JDK 序列化 |
| L1 | Caffeine，**开启 `recordStats()`**（闸门实验要读命中率）；**按条目设 TTL** |
| L2 | `StringRedisTemplate` |
| **墓碑** | 哨兵字符串 `"__NULL__"` + `nullTtl` |
| **抖动** | 实际 TTL = `l2Ttl + random(0, l2Jitter)` |
| **回源计数** | 一个 `AtomicLong`，对外有 getter（闸门实验要用它证伪） |

**施工时踩到的两个坑，已固化进注释与测试**：

1. **两个构造器 + 没标 `@Autowired` = 启动时才炸**。类里有一个给测试用的第二个构造器时，
   Spring 不再猜、直接去找无参构造器，报 `No default constructor found`。
   **单测发现不了**——它压根不起 Spring 上下文。
2. **测"L1 按条目过期"时必须先把 L2 清掉**。不清的话，L1 过期后会由 L2 供数，
   返回值不变 → "L1 到底有没有过期"根本观察不到（第一版测试就是这么写错的）。
   `expireVariably` 配错时会**静默退回兜底时长**，表面一切正常。

**测试分两层**（这是修正后的第三条）：

```bash
# 第一层：纯逻辑，假 Redis（内存 Map 冒充 L2），不连中间件 → wt-infra
mvn -B test -pl wt-infra -am
# 期望：Tests run: 8。覆盖：
#   ① 未命中 → 回源一次 → 值进两层；再取两次 → 回源计数仍是 1
#   ② L1 空但 L2 有 → 由 L2 供给并回填 L1
#   ③ loader 返回 null → 写墓碑；再取 → **不再回源**（防穿透）
#   ④ 墓碑请求的 TTL 是 nullTtl 那一档，不是 l2Ttl
#   ⑤ evict 之后 → 重新回源
#   ⑥ 连写 20 个 key，**请求的** TTL 不完全相同（抖动的算法在跑）
#   ⑦ L1 返回的是同一个对象引用（固化"缓存对象必须不可变"这条约定）
#   ⑧ L2 里是坏数据时 → 记 WARN、删掉、回源，**读不失败**

# 第二层：真实 Redis，读真实的 TTL → app 的集成测试
mvn -B test -pl app -am -Dexcluded.groups=__none__ -Dgroups=integration \
    -Dtest=TwoLevelCacheRedisIntegrationTest -Dsurefire.failIfNoSpecifiedTests=false
# 期望：Tests run: 5。覆盖：
#   ① 值以 JSON **明文**存进 Redis（StringRedisTemplate 直接读得到）
#   ② 正常值的 TTL 落在 [l2Ttl, l2Ttl + jitter]
#   ③ 【防雪崩】连写 20 个键，**Redis 里真实的** TTL 不完全相同
#   ④ 【防穿透】墓碑真实的 TTL 明显短于正常值
#   ⑤ L1 真的按条目 TTL 过期（先清 L2 隔离出来，否则观察不到）
```

> 为什么第二层非做不可：第 ③④⑤ 条问的是"**Redis / Caffeine 里实际发生了什么**"。
> 用假 Redis 断言"我传了 30 秒进去"只证明参数传对了，不证明行为对了——
> 而"按条目设过期时间"配错时不会报错，只会默默用兜底时长。

| 内容 | 说明 |
|---|---|
| 契约 | `V get(K key, Duration ttl, Supplier<V> loader)`、`void evict(K key)` |
| **墓碑** | 值为哨兵字符串 `"__NULL__"`，**过期时间取短** |
| **抖动** | 实际 TTL = `ttl + random(0, jitter)` |

## Task 3: 防击穿（Redisson 锁 + 锁内 double-check）

| 内容 | 说明 |
|---|---|
| 锁 | `RedissonClient.getLock("wt:lock:cache:post:{id}")` |
| **double-check** | 拿到锁之后**必须再查一次 L2**——不查的话，排队的请求会依次各回源一次，锁白加 |
| 抢不到锁 | 自旋等待 L2 出现（默认 50ms × 最多 10 次 = 500ms）；等不到则**降级回源**（宁可多查一次库，也不能卡死请求） |

```bash
mvn -B test -pl wt-infra
# 期望：
#   ① 单线程：第一次取 → 1 次回源；第二次取 → 仍 1 次
#   ② 【反面】把 double-check 去掉（测试里用可注入的开关模拟），
#      并发 20 个请求 → **回源次数 > 1**   ← 证明 double-check 不是可选项
```

## Task 4: 跨节点失效（发布订阅）

| 内容 | 说明 |
|---|---|
| 通道 | `wt:cache:evict` |
| 消息 | 失效的 key + **发送方实例标识** |
| 订阅 | 收到别人的消息 → 删本机 L1；收到自己的 → 跳过 |

**这个 Task 的验收方式是本设计的特色**（设计 §3.5）：M0–M8 是单进程，
真实部署下"跨节点"无法验证。所以：

```bash
mvn -B test -pl wt-infra -Dtest=CacheEvictionBroadcasterTest
# 期望：
#   ① 造两个互相独立的 Caffeine 实例（模拟两个节点），都订阅同一通道
#   ② 往实例 A 的 L1 塞一个 key，往实例 B 的 L1 也塞同名 key
#   ③ 触发一次广播
#   ④ 断言：**A 与 B 的 L1 都被清空**
#   ⑤ 【反面】把订阅关掉，重复 ③ → B 的 L1 里那个 key **仍在**（证明是广播清的，不是自然过期）
```

> 第 ⑤ 条是必须的。没有它，第 ④ 条可能只是"缓存碰巧过期了"。

## Task 5: `CachedPostDetail` + `PostDetailCache`（策略层）

**`CachedPostDetail` 放什么**（设计 §2.1 的结论）：

- **放**：`id`、`title`、`content`、`authorId`、`author`、`tags`、`top`、`featured`、
  `offline`、`likeCount`、`collectCount`、`commentCount`、`createTime`、`updateTime`
- **不放**：`viewCount`（走计数器，Task 9）、`liked` / `collected`（因人而异）
- **必须放**：判定可见性所需的字段（`deleted`、下架状态）——**否则命中缓存时没法做鉴权**

两个硬要求（设计 §7）：

1. 用 `record`，**不可变**
2. `List` 字段在构造时 `List.copyOf(...)` 拷一份——缓存里存的是**引用**，
   不拷的话调用方一改，缓存就被静默改掉了

```bash
mvn -B test -pl forum/forum-content -Dtest=PostDetailCacheTest
# 期望：
#   ① 序列化再反序列化，字段与对象相等（JSON 往返不丢字段）
#   ② 改传入的 tags 列表，缓存里的对象**不受影响**（证明拷了）
#   ③ key 的生成规则符合 RedisKey 的格式（`wt:cache:post:detail:<id>`）
```

## Task 6: `PostService.getDetail` 接上三级缓存

读路径见设计 §3.1。**两个不能省的点**：

1. **可见性判定必须照做**——缓存的是**数据**，不是**权限判定的结果**。
   命中缓存也要重新判，否则已下架的帖子被缓存后，匿名用户也能拿到（越权，不是缓存问题）。
2. 浏览数改走计数器（本 Task 先留原样，Task 9 换）。

```bash
mvn -B test
# 期望：M2 的 PostServiceTest 全部仍通过（接口契约未变）

# 启动后走真实 HTTP：
#   1) 发一帖 → 200
#   2) 读它的详情两次 → 都 200；【查 Redis】应存在 wt:cache:post:detail:<id>
#   3) 作者本人读自己**已下架**的帖 → 200（仍能看见）
#   4) 【反面】匿名读同一帖（该帖已在缓存里）→ **404**   ← 证明缓存没绕过鉴权
```

**第 4 条是本 Task 的安全断言，只有"必须成立"这一种结果。**

## Task 7: 失效清单逐条接上（最容易漏的一步）

照设计 §3.3 的表，一处一处改：

| 方法 | 加什么 |
|---|---|
| `PostService.update` | evict |
| `PostService.delete` | evict |
| `PostService.administrate` | evict |
| `InteractionService.like` / `unlike` | evict（**注意：只在真的写入了才 evict**——M2 已用 `INSERT IGNORE` 保证幂等，要接在"真的改了"那个分支上） |
| `InteractionService.collect` / `uncollect` | 同上 |
| `CommentService.create` / `delete` | evict |

> **`TagService` 不在清单里**——M2 的标签没有改名/合并（只有新增与关联）。
> 将来若加了"标签改名"，这张表**必须加一行**，否则页面上的标签名会永远是旧的，且不报错。

```bash
mvn -B test
# 期望：全绿

# 真实 HTTP：逐条走一遍，每条都"改完再读，读到的是新值"
#   1) 改帖标题 → 再读详情 → 标题是新的        ← 若还是旧的，说明 update 漏了 evict
#   2) 点赞     → 再读详情 → likeCount +1      ← 漏了 like 的 evict 就会读到旧计数
#   3) 连点 3 次赞 → 计数仍只 +1（M2 的幂等仍成立），且**不会**多删几次缓存
#   4) 发评论   → 再读详情 → commentCount +1
#   5) 删评论   → 再读详情 → commentCount -1
#   6) 下架     → 作者读 → offline=true；匿名读 → 404
```

## Task 8: 浏览数改成 Redis 计数器 + 定时回写

收 M2 在 `PostService.java:141` 埋的伏笔。

| 内容 | 说明 |
|---|---|
| key | `wt:cache:post:view:{id}`，存**绝对值** |
| 每次读 | Lua 原子：key 不存在 → 先装载种子（查一次库取当前值）→ `INCR` → 返回新值 |
| 回写 | `@Scheduled`，默认 30 秒，把绝对值 `UPDATE` 回 `t_post.view_count` |
| 一致性 | **弱一致，有意接受**（architecture.md §2.1 明写"浏览数"属最终一致可接受） |

```bash
mvn -B test
# 期望：全绿

# 真实 HTTP：
#   1) 读一篇详情 5 次 → 响应里的 viewCount 依次 +1（不是每次都一样）
#   2) 【查 Redis】wt:cache:post:view:<id> 的值在涨
#   3) 等 30 秒（或临时把间隔调成 5 秒）→ 【查库】t_post.view_count 被更新了
#   4) **正面确认它不再每次 UPDATE**：读 100 次详情，期间查库，
#      确认 t_post.view_count 在两次回写之间**不变**（M2 时它每次都变）
```

**要写进文档的**：浏览数从此是**最终一致**的，Redis 挂掉会丢最近一段增量。
这条写进 README 与讲解文档，不藏着。

## Task 10: 闸门实验（本里程碑的交付核心）

闸门见 spec §6.2：**命中率 / 延迟对比** 与 **100 并发仅 1 次回源**。

### 10.1 命中率与延迟对比

| 组 | 做法 |
|---|---|
| 对照组「纯 MySQL」 | `wt.cache.post-detail.enabled=false` —— **同一份代码，只翻开关** |
| 实验组「三级缓存」 | 同上，开关打开 |

要记录：**L1 命中率 / L2 命中率 / 回源率 / P99 延迟**。

> **为什么必须用同一个开关**：两组只能差一个变量。拿"改前改后的两份代码"比，
> 差值里混着重构的影响，说明不了缓存的作用。

### 10.2 100 并发仅 1 次回源（含反面对照）

```bash
mvn -B test -Dexcluded.groups=__none__ -Dgroups=integration -Dtest=PostDetailCacheConcurrencyTest
# 期望：
#   ① 清空 L1 与 L2 → 100 线程同时请求同一帖 → 全部 200
#   ② 回源次数 **恰好 1**
#   ③ 【反面】去掉锁（或去掉锁内的 double-check）→ 回源次数 **远大于 1**
```

**第 ③ 步是本设计的证据核心。** 只报第 ② 步，只能证明"数字是 1"；
加上反面，才证明**是那把锁让它变成 1**（spec §9 闸门 2：单边数据不算证据）。

### 10.3 设计 §9.3 的六个反面对照，逐个跑完

| # | 正面 | 反面 |
|---|---|---|
| 1 | 命中缓存时**不查帖子主体** | 关掉缓存后每次都查 |
| 2 | 100 并发 → **1 次回源** | 去掉锁 → **> 1 次** |
| 3 | 查不存在的 id → **只回源 1 次** | 去掉墓碑 → 每次都回源 |
| 4 | 广播一发，**另一个 L1 实例被清空** | 不订阅 → 另一个实例仍是旧值 |
| 5 | 改帖后再读 → **读到新内容** | 手工跳过 evict → 读到旧内容 |
| 6 | 未登录读已下架帖 → **404**（即使该帖已在缓存里） | ——（安全断言，只有"必须成立"） |
