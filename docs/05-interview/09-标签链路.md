# 链路讲解 · 标签

> 对着 M2 的真实代码讲一遍：一个标签从"用户在发帖框里敲下 `Redis`"到"点标签能筛出帖子"。
> 只讲代码实际怎么走；设计上的"为什么"指向已有文档，不在这里复述第二遍。
> 帖子本身的读写见 `07-帖子读写链路.md`，本文不重复。

---

## 一句话

标签**不是先建好再用的资源**——用户打什么就是什么，后端在发帖那一刻替他"取用或创建"：先查，查不到就插，并发下插重了就撞 `t_tag.name` 的唯一索引，**而那不是错误，是别人替我建好了**，回头重查一次接着用；之所以能这么做，是因为"`Redis` 和 `redis` 算不算一个标签"这件事 Java 和数据库两头用的**是同一条判据**（大小写不敏感）；挂上标签时同步 +1 计数，删帖 -1、改帖旧的 -1 新的 +1——这三处漏一处都不报错，只让标签页的数字慢慢变假；而按标签筛帖子用的是 `EXISTS`，因为 `JOIN` 现在不出错，但**要在支持多标签筛选的那天**才变成重复行。

## 数据怎么走

### 写一：发帖顺手带标签 `POST /api/posts`

```
PostController.create(userId, CreatePostRequest)
      │  request.tags() 原样传给 Service —— DTO 上没有任何标签校验注解（见下）
      ▼
PostService.create(authorId, title, content, tags)
      │
      ├─ post.setSummary(summarize(content))
      ├─ postMapper.insert(post)              ← 主键回填到 post.id
      ├─ tagService.attachTags(post.getId(), tags)   ← 标签与帖子在同一个事务里
      └─ 返回 post.getId()
               │
               ▼
          TagService.attachTags(postId, rawNames)
               │
               ├─ normalize(rawNames)         ← 去空白、去空串、大小写不敏感去重、判长度与数量
               │
               └─ 对每个名字：
                    ├─ findOrCreate(name)     ← 查到就用，查不到就插，插重了就重查
                    ├─ tagMapper.insertPostTag(postId, tag.getId())
                    └─ tagMapper.addPostCount(tag.getId(), 1)
```

### 写二：改帖整体换标签 `PATCH /api/posts/{id}`

```
PostService.update(id, title, content, tags)
      │  tags == null → 什么都不做（"不改标签"）
      │  tags == []   → 走下面这条，"把标签全去掉"
      │
      └─ tagService.replaceTags(id, tags)
               │
               ├─ detachAll(id)           ← 先把带过的标签计数各 -1，再删关联
               └─ attachTags(id, tags)    ← 再挂新的
```

### 写三：删帖摘标签 `DELETE /api/posts/{id}`

```
PostService.delete(id)
      ├─ selectById(id) == null → 报"帖子不存在"（防重复调用把计数减第二遍）
      ├─ tagService.detachAll(id)     ← 计数各 -1，再删关联
      └─ postMapper.softDelete(id)
```

### 读一：热门标签 `GET /api/tags`

```
TagController.list(limit)          ← 公开接口（SecurityConfig 里放行 GET /api/tags）
      ▼
TagService.listTop(limit)          ← 把 limit 夹到 [1, 100]
      ▼
tagMapper.selectTop(limit)
      SELECT id, name, post_count, create_time FROM t_tag
      ORDER BY post_count DESC, id DESC LIMIT ?
      ▼
TagView.from(tag)                  ← 只暴露 id / name / postCount
```

### 读二：按标签筛帖子 `GET /api/posts?tagId=`

```
PostController.list(page, size, sort, tagId)
      ▼
PostQuery(page, size, sort, tagId) → PostService.page(query)
      ├─ countList(null, tagId)
      └─ selectPage(null, tagId, sort, offset, size)
               └─ WHERE deleted = 0 AND status = 0
                       AND EXISTS (SELECT 1 FROM t_post_tag pt
                                   WHERE pt.post_id = t_post.id AND pt.tag_id = ?)
```

**注意这里没有"新建标签"接口。** `TagController` 只有 `GET`。标签只在发帖 / 改帖时顺带产生（`TagController` 类注释）。

## 逐段讲代码

### 1. 取用或创建：`findOrCreate`，并发下插重了不是错误

```java
private Tag findOrCreate(String name) {
    Tag existing = tagMapper.selectByName(name);
    if (existing != null) {
        return existing;
    }

    Tag created = new Tag();
    created.setName(name);
    try {
        tagMapper.insert(created);
        return created;
    } catch (DuplicateKeyException e) {
        Tag createdBySomeoneElse = tagMapper.selectByName(name);
        if (createdBySomeoneElse == null) {
            // 唯一索引冲突了、却又查不到这个名字——说明冲突来自别的约束
            // （比如将来加了别的唯一键）。**不能把这种情况吞掉**，
            // 否则真正的数据问题会变成一个安静的 200。
            throw e;
        }
        return createdBySomeoneElse;
    }
}
```

三段，每一段都在处理一个具体情形：

① **查到就用。** 绝大多数请求走这里，一次查询结束。

② **查不到就插。** 走到这说明"这个名字此前没人用过"。

③ **插的时候撞了 `DuplicateKeyException`，回头重查。** 这条分支只在一种时序下触发：两个请求几乎同时第一次用同一个新标签——两边都查不到，两边都插，数据库的唯一索引拦下第二个。**这不是错误**，是"别人替我建好了"，把别人插进去的那一行重查出来用即可。注释里那句"这不是错误"是这段代码最容易被人改坏的地方：后来的人看到 `catch` 往往第一反应是"这里出错了，要报给用户"。

中间那句 `if (createdBySomeoneElse == null) { throw e; }` 是**反向的**：唯一索引冲突了、却按这个名字查不到东西——这说明冲突来自别的约束（比如将来的某个新唯一键），不是"标签重复"。这种情况**必须原样抛出去**。吞掉的后果是一次真正的数据问题变成接口上一个安静的 200。

这条分支也解释了为什么 `name` 上的唯一索引不只是"防止重名"。`db/V2__init_content.sql` 里 `t_tag` 的注释写得很直白：

```sql
-- 唯一索引不只是"防止重名"——并发下两个请求同时第一次用同一个新标签时，
-- 靠它拦下第二条，应用层捕获唯一键冲突后回头重查即可。
-- 换成"先查再插"在并发下有窗口：两个请求都查到"没有"，然后都插入。
UNIQUE KEY uk_name (name)
```

`TagMapper.insert` 的 Javadoc 也在同一条线上拦了一次：**"调用方必须处理 `DuplicateKeyException`"**——把这个契约写在接口上，而不是只写在实现里。

### 2. 大小写不敏感：判据 Java 侧和数据库必须一致

数据库那一侧，`selectByName` 的 SQL 里**没有 `LOWER()`，也没有 `BINARY`**：

```xml
<!-- 按名字查。**不写 LOWER() 也不写 BINARY**：
     比较大小写敏不敏感由列的排序规则决定，而 t_tag.name 用的是
     utf8mb4 的默认排序规则（utf8mb4_0900_ai_ci，`ci` = 大小写不敏感）。
     在这里自己加 LOWER() 反而会让 name 上的索引失效。
     这条依赖是**实测过**的（见 db/V2__init_content.sql 的文件头）。 -->
<select id="selectByName" resultType="com.wingtisky.forum.forum.content.entity.Tag">
    SELECT id, name, post_count, create_time
    FROM t_tag
    WHERE name = #{name}
</select>
```

也就是说：数据库眼里，`Redis` 和 `redis` **是同一个标签**。`V2__init_content.sql` 的文件头记了这条依赖是实测出来的，不是靠注释保证的。**那么 Java 侧的去重判据就必须跟它一样**，否则会在两个地方对不上。

Java 侧在 `normalize` 里：

```java
static List<String> normalize(List<String> rawNames) {
    if (rawNames == null || rawNames.isEmpty()) {
        return List.of();
    }

    Map<String, String> byLowerName = new LinkedHashMap<>();
    for (String raw : rawNames) {
        if (raw == null) {
            continue;
        }
        String trimmed = raw.trim();
        if (trimmed.isEmpty()) {
            continue;
        }
        // 按**码点**数长度，与数据库的 varchar(32) 一致：
        // 一个 emoji 在 Java 里占两个 char，用 length() 会把它算成两个字符
        if (trimmed.codePointCount(0, trimmed.length()) > MAX_NAME_LENGTH) {
            throw new BizException(ErrorCode.PARAM_INVALID,
                    "单个标签最长 " + MAX_NAME_LENGTH + " 个字符");
        }
        byLowerName.putIfAbsent(trimmed.toLowerCase(Locale.ROOT), trimmed);
    }

    if (byLowerName.size() > MAX_TAGS_PER_POST) {
        throw new BizException(ErrorCode.TOO_MANY_TAGS);
    }
    return List.copyOf(byLowerName.values());
}
```

关键是这一行的**两个方向**：

```java
byLowerName.putIfAbsent(trimmed.toLowerCase(Locale.ROOT), trimmed);
```

- **键**是 `toLowerCase(...)`——用它做去重判据，与数据库的 `ai_ci` 一致；
- **值**是 `trimmed`，**原始写法**——最后 `return List.copyOf(byLowerName.values())` 吐出去的是原样，**不转小写**。所以库里存的还是 `Redis`，不是 `redis`。

假设 Java 侧偷懒、按原样去重会怎样：`["Redis", "redis"]` 两条都会通过，然后 `attachTags` 里两条都要 `insertPostTag`，一起写进 `t_post_tag`——而 `t_post_tag` 的主键是 `(post_id, tag_id)`，两条其实指向**同一个 tag**（第二次 `findOrCreate` 会查回同一个），于是撞联合主键。**那条异常长得完全不像"标签重复"**，排查时会往别处找。这就是为什么去重判据非得跟数据库一致不可。

`Locale.ROOT` 那个参数也不是装饰。用默认 Locale 的话，在土耳其语环境下 `"I".toLowerCase()` 得到的**不是** `"i"`，去重结果会随机器而变。

同一段里还有两处与数据库列长对齐的地方：单个名字按**码点**数长度对 `MAX_NAME_LENGTH = 32`（对应 `t_tag.name` 的 `varchar(32)`），数量对 `MAX_TAGS_PER_POST = 5`（超了抛 `TOO_MANY_TAGS`，即 `A0203`）。

**这些规则全部集中在 `normalize` 一处**，DTO 上一个校验注解都没加——`CreatePostRequest.tags` 的注释说明了原因：绑在数据库列长上的规则分两处写，迟早出现"接口说可以、数据库说不行"。

### 3. 计数三处维护：漏一处不报错，只是数字变假

`t_tag.post_count` 是冗余计数（为什么冗余见 `ADR-0016`）。它的维护散在三个地方，**每一处都要记得**：

| 时机 | 代码 | 计数动作 |
|---|---|---|
| 发帖 | `attachTags` 里 `tagMapper.addPostCount(tag.getId(), 1)` | +1 |
| 删帖 | `detachAll` 里 `tagMapper.addPostCount(tag.getId(), -1)` | -1 |
| 改帖换标签 | `replaceTags` = `detachAll`（旧的 -1）+ `attachTags`（新的 +1） | -1 / +1 |

`addPostCount` 的 SQL 带一层下限保护：

```xml
<update id="addPostCount">
    UPDATE t_tag
    SET post_count = GREATEST(post_count + #{delta}, 0)
    WHERE id = #{tagId}
</update>
```

`GREATEST(..., 0)` 是防计数变成负数——界面上出现一个没法解释的数字，排查时又很难判断它从哪来。`Tag` 实体的 `postCount` 注释把这三处点名列了出来，顺带写了下漏掉的**症状**：标签页上写着"12 篇"、点进去只有 9 篇，而且**不会自己恢复**。

顺带看 `attachTags` 的形状——它是"一个一个来"的：

```java
@Transactional
public void attachTags(Long postId, List<String> rawNames) {
    for (String name : normalize(rawNames)) {
        Tag tag = findOrCreate(name);
        tagMapper.insertPostTag(postId, tag.getId());
        tagMapper.addPostCount(tag.getId(), 1);
    }
}
```

`PostService.create` 用 `@Transactional` 把它和 `postMapper.insert` 圈在一起。分开的话，中间断掉就会出现"帖子发了但没有标签"或者"标签指向一条不存在的帖子"（`PostService.create` 的注释）。

### 4. `detachAll`：顺序不能反

```java
/**
 * 摘掉帖子的全部标签：**先把每个标签的使用次数减 1，再删关联**。
 *
 * <p>顺序不能反：关联删了之后就查不到"这篇帖子原来带了哪些标签"，
 * 那些标签的计数就永远减不回去了——标签页上会一直多着几篇。
 */
@Transactional
public void detachAll(Long postId) {
    List<Tag> attached = tagMapper.selectByPostId(postId);
    if (attached.isEmpty()) {
        return;
    }
    for (Tag tag : attached) {
        tagMapper.addPostCount(tag.getId(), -1);
    }
    tagMapper.deletePostTags(postId);
}
```

要减哪些标签的计数，得先知道"这篇帖子原来带了哪些标签"——就是那句 `selectByPostId`。关联一旦删了，这个信息就没了。所以顺序只能是**先减、再删**；反过来的话，那些标签的计数永远减不回去，而且**下一个删帖请求也修不好**（关联已经不在了，`selectByPostId` 返回空）。开头那句 `if (attached.isEmpty()) return;` 让"没带标签的帖子"直接返回，连循环和 DELETE 都不发。

`selectByPostId` 的 SQL 是从关联表反查回标签：

```xml
<select id="selectByPostId" resultType="com.wingtisky.forum.forum.content.entity.Tag">
    SELECT t.id, t.name, t.post_count, t.create_time
    FROM t_post_tag pt
             JOIN t_tag t ON t.id = pt.tag_id
    WHERE pt.post_id = #{postId}
</select>
```

再往上一层看 `replaceTags` 为什么"整体替换"而不是"算差异增删"：

```java
@Transactional
public void replaceTags(Long postId, List<String> rawNames) {
    detachAll(postId);
    attachTags(postId, rawNames);
}
```

原因是差异法要处理"旧的有新的没有""都有""都没有"三种情况，而这段代码唯一的收益是省几次数据库写入——换来的是三类分支的测试（`replaceTags` 的注释）。

对应地在 DTO 那一层，"传了才改"和"传空列表 = 全去掉"是两个不同的语义，靠**给没给**来分，不靠列表空不空：

```java
/**
 * 新的标签列表。{@code null} 表示**不改标签**；给了就**整体替换**
 * ...
 * <p>传空列表是合法的，表示"把这篇帖子的标签全去掉"——这和"不改"是两件事，
 * 所以不能用"列表是否为空"来判断要不要处理。
 */
List<String> tags
```

落到 `PostService.update` 里就是 `if (tags != null) { tagService.replaceTags(id, tags); }`——`null` 跳过，`[]` 走进去、把关联全清掉。

### 5. 按标签筛帖子用 `EXISTS`，不用 `JOIN`

```xml
<!-- 按标签筛用 EXISTS 而不是 JOIN：
       · 现在只筛一个标签，JOIN 也不会重复（一篇帖子最多匹配一行）
       · 但**只要将来支持"同时筛多个标签"，JOIN 就会让同一篇帖子出现多行**——
         列表里同一篇帖子出现两次、总数也跟着偏大，而这两个现象
         都很难让人联想到是 JOIN 的问题
       EXISTS 是半连接语义："存在一条关联指向这个标签"，从写法上就不会重复。 -->
<sql id="List_Filter">
    deleted = 0 AND status = 0
    <if test="authorId != null">
        AND author_id = #{authorId}
    </if>
    <if test="tagId != null">
        AND EXISTS (SELECT 1
                    FROM t_post_tag pt
                    WHERE pt.post_id = t_post.id
                      AND pt.tag_id = #{tagId})
    </if>
</sql>
```

现在只筛一个标签，`JOIN t_post_tag` 也不会重复：一篇帖子在这个标签下最多一行关联，`JOIN` 出来就最多一行。所以**代码今天不出问题**——这正是这段写法容易被改回去的原因。

但把条件往前推一步：`tagId` 从"一个"变成"一组"（多标签筛选），`JOIN` 就会为命中的每个标签各出一行，同一篇帖子在结果里出现多次。表现出来是列表里看到重复的帖子、`COUNT(*)` 也跟着偏大——而这两个现象**都很难让人联想到是 JOIN 写的**。`EXISTS` 是半连接语义："存在一条关联指向这个标签"，从写法上就限死了每个帖子最多贡献一行。

`List_Filter` 是**取数据和数总数共用的一段**（`selectPage` 和 `countList` 都 `<include refid="List_Filter"/>`），所以"筛标签"这个条件在两边天然一致——那种"总数说有 100 条、翻到第 3 页就空了"的不一致从源头就没机会发生。

### 6. 两处"不做"：不给 `t_post_tag` 建实体、不给 `selectTop` 加过滤

`TagMapper` 的类注释：

```java
/**
 * <p><b>没有 {@code PostTag} 实体</b>：关联表是两列的主键，没有自己的状态。
 * 为它建一个实体类只会多一个没人真正需要的类型——所有操作都用
 * {@code (postId, tagId)} 两个标量就够了。
 */
```

`selectTop` 不过滤 `post_count = 0` 的标签：

```xml
<!-- 热门标签。按使用次数倒序——不过滤 post_count = 0 的标签：
     刚建出来还没挂上帖子的标签是瞬间状态，为它加一个条件反而让
     "为什么我刚建的标签不见了"变成一个需要解释的问题。 -->
```

顺带，`insertPostTag` 的契约是"**调用方必须保证这一对是新的**"（联合主键会拦重复插入）。正常情况下不会重复——改帖是先清空再建立——但万一调用方漏了"先清空"，表现会是一条主键冲突异常，而**它长得不像"标签重复"**，排查时容易跑偏。这条契约写在 `TagMapper.insertPostTag` 的 Javadoc 上。

## 走一遍场景

**场景一：两篇帖子分别打 `Redis` 和 `redis`**

1. 用户 A 发帖，标签 `["Redis"]`。`POST /api/posts` → `PostService.create` → `tagService.attachTags(postId1, ["Redis"])`。
2. `normalize(["Redis"])` 返回 `["Redis"]`。`findOrCreate("Redis")`：`selectByName("Redis")` 返回 null → `insert` → `t_tag` 多一行 `(1, 'Redis', 0)`，主键回填到 `created.id`。
3. `insertPostTag(postId1, 1)`；`addPostCount(1, 1)` → `post_count = 1`。
4. 用户 B 发帖，标签 `["redis"]`。`normalize(["redis"])` 返回 `["redis"]`（**去重是在单个请求内部做的，跨请求不去重**）。
5. `findOrCreate("redis")`：`selectByName("redis")` —— 这条 SQL 是 `WHERE name = 'redis'`，但列是 `utf8mb4_0900_ai_ci`，**它会命中刚插进去的 `Redis` 那一行**。返回 `(1, 'Redis', 1)`。
6. 于是走的是"已有，直接用"这条分支，**不会再插一行**。`insertPostTag(postId2, 1)`，`addPostCount(1, 1)` → `post_count = 2`。
7. 结果：`t_tag` 只有一行、名字是首次写入的 `Redis`（好看的那个），两篇帖子都通过 tag_id = 1 关联到它。这条"只有一行"的断言由测试钉住（`V2__init_content.sql` 文件头写明），服务器排序规则哪天换了会先炸测试。

**场景二：两个人同时第一次用同一个新标签 `Kafka`**

1. 请求甲和请求乙几乎同时进 `findOrCreate("Kafka")`，两边 `selectByName` 都返回 null。
2. 两边都调 `insert`。数据库的唯一索引 `uk_name` 拦下一个：甲成功，拿到 id；乙抛 `DuplicateKeyException`。
3. 乙进 `catch`：**再查一次** `selectByName("Kafka")` —— 这次甲已经插好了，查得到，于是返回甲建的那一行。
4. 两边各自 `insertPostTag` + `addPostCount`，两个帖子都挂在同一个标签上。**没有任何一行因为并发而丢失或报错。**

如果第 3 步那次重查也查不到（`createdBySomeoneElse == null`），说明冲突不是来自 `name`——那就要把异常原样抛出去（见"逐段讲代码"第 1 段）。

**场景三：改帖把标签从 `["Redis", "Kafka"]` 换成 `["Java"]`**

1. `PATCH /api/posts/7`，body 里 `tags: ["Java"]`。过 `@postAuthz.isOwner(#id)`，进 `PostService.update`。
2. `tags != null` → `tagService.replaceTags(7, ["Java"])`。
3. `detachAll(7)`：`selectByPostId(7)` 拿回 `[Redis, Kafka]` 两行 → 各自 `addPostCount(id, -1)` → 再 `deletePostTags(7)`，把 `t_post_tag` 里 post_id = 7 的两行删掉。**先减计数、后删关联**，顺序不能反。
4. `attachTags(7, ["Java"])`：`findOrCreate("Java")`（没有就当场建）→ `insertPostTag(7, javaId)` → `addPostCount(javaId, 1)`。
5. 净效果：Redis 和 Kafka 的 `post_count` 各 -1，Java 的 +1。

如果 body 里是 `tags: []`，第 3 步照走、第 4 步什么都不挂——帖子变成没有标签。如果 body 里**根本没有 `tags` 字段**（`null`），整个 `replaceTags` 都不会被调用，标签原样不动。这三种是三个不同的结果。

**场景四：点标签筛帖子**

1. `GET /api/posts?tagId=1`（公开接口，`SecurityConfig` 里 `GET /api/posts` 已放行；注意只放行 GET，同一路径的 POST 发帖仍要认证）。
2. `PostQuery(..., tagId=1)` → `PostService.page`。先 `countList(null, 1)`，SQL 里带上 `AND EXISTS (SELECT 1 FROM t_post_tag pt WHERE pt.post_id = t_post.id AND pt.tag_id = 1)`。
3. 总数不为 0 → `selectPage(null, 1, sort, offset, size)`，**同一段 `List_Filter`**，所以总数和列表的筛选条件一定一致。
4. `EXISTS` 只判断"有没有这样一条关联"，每篇帖子最多贡献一行——不管这篇帖子在 `t_post_tag` 里有多少行。

## 面试会追问

**Q：两个请求同时第一次用同一个新标签，会怎样？**
两边都 `selectByName` 查不到、都 `insert`，数据库的唯一索引 `uk_name` 拦下第二个，抛 `DuplicateKeyException`。`findOrCreate` 捕获它、回头重查一次，拿到别人建好的那一行继续用。**这不是错误分支，是正常分支**——`TagMapper.insert` 的 Javadoc 直接把"调用方必须处理 `DuplicateKeyException`"写成了契约。

**Q：那为什么不干脆"先查出没有就插"，加个锁？**
锁会让所有创建标签的请求排队，而重复创建是极低频的事件；用唯一索引兜底是成本最低的。而且"先查再插"中间本来就有窗口——锁只是把窗口关掉，索引是让窗口开着也不出错。

**Q：冲突了、回头重查却查不到这个名字，为什么不直接返回 null 或吞掉？**
那说明冲突来自**别的约束**，不是标签重名。吞掉就把一次真正的数据问题变成一个安静的 200（注释原话）。所以这种情况 `throw e`，把原始异常原样抛出去。

**Q：`Redis` 和 `redis` 会变成两个标签吗？**
不会。`t_tag.name` 用的是 `utf8mb4_0900_ai_ci`，`ci` 是大小写不敏感，`Redis` 会撞 `redis` 的唯一索引——数据库眼里它们是一个标签。所以 `selectByName("redis")` 会命中已存在的 `Redis` 那一行，第二次根本不插。（这条依赖是**实测**的，见 `V2__init_content.sql` 文件头，不是"应该如此"。）

**Q：那 Java 侧为什么还要自己去重？数据库不是已经会拦了吗？**
拦是拦得住，但拦出来的**是一条联合主键冲突**，长得完全不像"标签重复"——同一次发帖里 `["Redis","redis"]` 两条都通过了 Java 去重，两条都要写进 `t_post_tag`、指向同一个 tag，撞的是 `(post_id, tag_id)` 主键。所以 Java 侧的判据必须和数据库一致（大小写不敏感），把这种情况在进库之前就压成一条。`normalize` 的注释把这条因果链写全了。

**Q：为什么不干脆统一转成小写存？**
设计上刻意不转（设计稿 §2.3 决策点 ③）：技术标签里 `Redis` 比 `redis` 好看，小写化会把这个信息**永久丢掉**。保留原始大小写、靠排序规则去重，两头的便宜都占。——所以 `normalize` 里键是 `toLowerCase(...)` 做判据、值是原始写法往后传。

**Q：`toLowerCase` 为什么要带 `Locale.ROOT`？**
用默认 Locale 的话，土耳其语环境下 `"I".toLowerCase()` 得到的不是 `"i"`，去重结果会随部署机器的区域设置而变。`Locale.ROOT` 固定用中性规则。

**Q：标签的 `post_count` 在哪里维护？漏一处会怎样？**
三处：发帖 `attachTags` 里 +1、删帖 `detachAll` 里 -1、改帖换标签时旧的 -1（`detachAll`）新的 +1（`attachTags`）。漏一处**不会报错**，只让标签页的数字变假——写着"12 篇"点进去只有 9 篇，而且**不会自己恢复**（冗余计数只能重算，理由见 `ADR-0016`）。`Tag` 实体的 `postCount` 注释把这三处和这个症状都点出来了。

**Q：`detachAll` 为什么要先减计数、再删关联，反过来行不行？**
不行。要减哪些标签的计数，得先知道"这篇帖子原来带了哪些标签"（`selectByPostId`）。关联删了这信息就没了，那些计数永远减不回去——而且**下一个删帖请求也修不好**，因为关联已经不在了。所以顺序只能是先减后删。

**Q：改帖为什么整体替换，不算差异？**
算差异要处理"旧的有新的没有""都有""都没有"三种情况，而这段代码唯一的收益是省几次数据库写入——换来的是三类分支的测试（`replaceTags` 的注释）。整体替换的代价是这几次写，对发帖/改帖这种低频操作可以接受。

**Q：改帖传空列表和根本不传，结果一样吗？**
不一样。`tags == null` 表示"不改标签"，`replaceTags` 根本不会被调用；`tags == []` 表示"把标签全去掉"，会走 `detachAll` 把关联清空。所以判断用 `tags != null`，**不能用"列表是否为空"**（`PostService.update` 与 `UpdatePostRequest` 的注释）。

**Q：按标签筛帖子为什么用 `EXISTS` 不用 `JOIN`？**
现在只筛一个标签，`JOIN` 也不会重复——所以今天用了也不出错。但将来支持多标签筛选时，`JOIN` 会让同一篇帖子每个命中的标签各出一行：列表里出现重复帖子、总数偏大，而这两个现象都很难让人联想到是 `JOIN` 写的。`EXISTS` 是半连接语义，从写法上就限死每个帖子最多一行（`PostMapper.xml` 的 `List_Filter` 注释）。

**Q：为什么没有"新建标签"的接口？**
标签不是先建好再用的资源，它**在发帖时顺带产生**。单独开一个新建接口会让前端多一步，而用户根本不知道自己的标签是否已存在。所以 `TagController` 只有 `GET`（类注释）。

**Q：为什么没有 `PostTag` 实体？**
关联表是两列的主键，没有自己的状态。为它建实体只会多一个没人真正需要的类型——所有操作都用 `(postId, tagId)` 两个标量就够了（`TagMapper` 类注释）。

**Q：热门标签为什么不把 `post_count = 0` 的过滤掉？**
刚建出来还没挂上帖子的标签是瞬间状态。为它加一个条件，反而让"为什么我刚建的标签不见了"变成一个需要解释的问题（`selectTop` 的注释）。

**Q：为什么 `TagView` 不直接返回 `Tag` 实体？**
和帖子、用户同一个理由：实体是持久层对象，它加一个字段不该自动变成对外契约。`TagView` 只暴露 `id` / `name` / `postCount`。

**Q：为什么标签的长度和数量规则写在 Service 不在 DTO？**
因为这两条规则**绑在数据库列长上**（`t_tag.name` 是 `varchar(32)`、单帖最多 5 个）。规则和列长绑在一起，就必须和列长在同一处维护——全部放 `TagService.normalize` 一处。分两处写，迟早出现"接口说可以、数据库说不行"（`CreatePostRequest.tags` 的注释）。
