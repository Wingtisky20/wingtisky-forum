# 链路讲解 · 帖子读写

> 对着 M2 的真实代码讲一遍：一篇帖子从"发出去"到"被别人翻到"。
> 只讲代码实际怎么走；设计上的"为什么"指向已有文档，不在这里复述第二遍。

---

## 一句话

发帖时把正文压成一行、按码点截 200 存进 `summary`；列表页的 SQL **根本不 SELECT `content` 那一列**，所以它永远不碰正文那个大字段；作者昵称头像不在帖子表里，是拿这一页 20 篇的 `author_id` **一次性**去用户域的契约里批量换回来的——四件事凑在一起，让"翻列表"这条最高频的读只做该做的事。

---

## 数据怎么走

### 写：`POST /api/posts`

```
PostController.create(@AuthenticationPrincipal Long userId, CreatePostRequest)
      │  能走到这里说明认证已过（anyRequest().authenticated()），userId 不会是 null
      ▼
PostService.create(userId, title, content)
      │
      ├─ new Post()；setAuthorId / setTitle / setContent
      ├─ post.setSummary(summarize(content))   ← 摘要在这里生成一次（见下）
      │
      └─ postMapper.insert(post)
               │
               ▼
          INSERT INTO t_post (author_id, title, content, summary)
          VALUES (?, ?, ?, ?)
               ← useGeneratedKeys 把自增主键回填到 post.id
      返回 post.getId()
```

Controller 返回的是**新帖子的 ID**，不是整个帖子——前端紧接着要跳到详情页，它要的就是这个 ID，把帖子再查一遍传回去是多余的一次查询。

### 读：`GET /api/posts`

```
PostController.list(page, size, sort)
      │  sort 声明成 PostSort 枚举；外部传进来的字符串到不了 SQL
      ▼
new PostQuery(page, size, sort)     ← 分页参数的夹紧在 record 的紧凑构造器里
      ▼
PostService.page(query) → page(null, query)
      │
      ├─ postMapper.countList(null)                ← 先 COUNT
      │        total == 0 就直接返回空页（连列表都不查，也就不会去查作者）
      │
      ├─ postMapper.selectPage(null, sort, offset, size)
      │        SELECT <List_Columns>               ← 这里没有 content
      │        FROM t_post
      │        WHERE <List_Filter>
      │        ORDER BY ... LIMIT ? OFFSET ?
      │        ← 拿到这一页的 List<Post>（content 是 null）
      │
      ├─ findAuthors(posts)                        ← 一次批量查作者
      │        收集本页的 author_id 去重 → userQueryService.findBriefs(ids)
      │        ← Map<Long, UserBrief>，一次查询，不是 20 次
      │
      └─ posts.stream().map(p -> PostListItem.from(p, authors.get(p.getAuthorId())))
         返回 PageResult<PostListItem>
```

详情页走的是另一条：`selectById` **带 content**，顺手 `incrementViewCount`，作者用 `findBrief`（单个）拿。

## 逐段讲代码

### 1. 列表页不读正文：`List_Columns` 里没有 `content`

```xml
<!-- 列表用的列。**注意这里没有 content**：
     正文是 MEDIUMTEXT，列表页永远不读它——这是 M6 那个"大字段拖慢分页"
     的性能优化能够成立的前提。想加 content 进来之前，先回去看设计稿 §2.6。
     另外也刻意不写 SELECT *：它会把 content 一起捞出来，让这条约束失效。 -->
<sql id="List_Columns">
    id, author_id, title, summary, status, top_flag, featured_flag,
    view_count, like_count, comment_count, collect_count, create_time
</sql>
```

这条 SQL 是**显式列名**，不是一个 `SELECT *`。为什么这件事值得单独拎出来讲：MySQL 的 `TEXT` / `MEDIUMTEXT` 本来就是**行外存储**——正文超过一定长度后，数据放在溢出页里，主表行只剩一个 20 字节左右的指针。所以"不查这一列"就等于"根本不读那块数据"。**但 `SELECT *` 会把这个优势当场抹掉**，它会把 `content` 一起捞出来。设计稿 §2.6 里立的就是这条规范：列表 / 分页查询必须显式列出需要的列。M6 要演示的"大字段拖慢分页 + Deferred Join"就靠它当前置。

对应地，实体的类注释也把这件事钉住了——从列表查询拿到的 `Post`，它的 `content` 是 `null`，别拿去读。

### 2. 取数据和数总数共用一段筛选条件：`List_Filter`

```xml
<!-- 列表的筛选条件。**取数据和数总数共用这一段**——
     两边各写一遍的话，改了一处忘了另一处，表现是"总数说有 100 条、
     翻到第 3 页就空了"，而这类不一致极难联想到是 SQL 写岔了。 -->
<sql id="List_Filter">
    deleted = 0 AND status = 0
    <if test="authorId != null">
        AND author_id = #{authorId}
    </if>
</sql>
```

`selectPage` 和 `countList` 都 `<include refid="List_Filter"/>`。这也解释了为什么 `PostMapper.selectPage` 收的是一个可空的 `authorId`：全站列表传 `null`，个人主页传具体的值，同一个方法加可选条件——为的就是让"筛选"和"统计"走同一段 SQL。`deleted = 0 AND status = 0` 是两个恒定的等值条件，正好都进 `idx_status_top_create`（`db/V2__init_content.sql`），过滤和排序能全靠索引完成、不必回表。

### 3. 排序值不拼进 SQL：`<choose>` 里两种排法都写死

```xml
<select id="selectPage" resultType="com.wingtisky.forum.forum.content.entity.Post">
    SELECT <include refid="List_Columns"/>
    FROM t_post
    WHERE <include refid="List_Filter"/>
    <choose>
        <when test="sort == 'HOT'">
            ORDER BY top_flag DESC,
                     (comment_count * 3 + like_count * 2 + collect_count) DESC,
                     id DESC
        </when>
        <otherwise>
            ORDER BY top_flag DESC, create_time DESC, id DESC
        </otherwise>
    </choose>
    LIMIT #{size} OFFSET #{offset}
</select>
```

`sort` 参数是 `"LATEST"` 或 `"HOT"`，但它**只用来在两条写死的分支之间选**，不会成为 SQL 的一部分。原因是 `ORDER BY` 的列名不能用 `#{}` 占位符（占位符只能填值），那就只剩 `${}` 拼接一条路——而那是注入入口。用枚举 + `<choose>`，外部传进来的字符串根本到不了 SQL（`PostSort` 的类注释写了同一件事）。

末尾的 `id DESC` 不是多余的：`create_time` 只精确到秒，同一秒发的帖子排序不稳定，翻页时同一行可能两页都出现、或者一页都不出现。加一个唯一的列兜底，顺序才是确定的。`HOT` 分支里那个“几个计数相乘相加”的表达式 MySQL 用不了索引、必然走 `filesort`——注释里写明这是**已知的现状不是遗漏**，M6 拿它当对照物。

### 4. 跨域取作者：一次批量，不是 N 次

```java
private Map<Long, UserBrief> findAuthors(List<Post> posts) {
    Set<Long> authorIds = posts.stream()
            .map(Post::getAuthorId)
            .collect(Collectors.toSet());
    return userQueryService.findBriefs(authorIds);
}
```

帖子表里只存了作者的**数字 ID**，昵称和头像在用户域的 `t_user` 里。内容域不能直接依赖用户域（`ArchitectureTest` 的规则 2 会拦），所以它只认 `wt-domain` 这个契约接口 `UserQueryService`：

```java
public interface UserQueryService {
    Map<Long, UserBrief> findBriefs(Collection<Long> userIds);
    Optional<UserBrief> findBrief(Long userId);
}
```

契约里**直接放的是批量方法**，而不是只给一个 `findBrief(Long id)`。这不是提前优化——分页列表天然就是这个形状：一页 N 条就是 N 个作者。给单条查询的接口，调用方必然写成循环，那就是 N+1；而 N+1 最麻烦的地方是**它不会报错**，只在数据量上来之后表现为“列表越来越慢”（理由见 ADR-0015 §二）。把 `findBriefs` 放在契约上，是让正确的用法成为最省事的用法。

实现落在用户域这一侧（`UserQueryServiceImpl`），两个细节值得看：

```java
@Override
public Map<Long, UserBrief> findBriefs(Collection<Long> userIds) {
    // 空集合必须在这里短路：传下去会拼出 `IN ()` 这种非法 SQL，
    // 而它只在"这一页恰好一个作者都没有"时才会炸——正是最容易漏测的那一类。
    if (userIds == null || userIds.isEmpty()) {
        return Map.of();
    }

    return userMapper.selectBriefsByIds(userIds).stream()
            .collect(Collectors.toMap(User::getId, UserQueryServiceImpl::toBrief));
}
```

① **空集合短路**。空集合传下去会拼出 `IN ()`，非法 SQL——而它只在“这一页一个作者都没有”时才炸，最难测到。顺带，`PostService.page` 里“`total == 0` 就直接返回”也少走了一遍这里。② `selectBriefsByIds` 查回来的 `User` **只填了 id / nickname / avatar 三个字段**，Service 再转成不可变的 `UserBrief` record（转换是个纯函数，可以单测）。查不到的 id **不补位**——`Map` 里没有这个键，调用方自己决定怎么显示。

拿到 `Map` 之后，`PostListItem.from(post, authors.get(post.getAuthorId()))`：作者是被逻辑删除（注销）时 `get` 返回 `null`，`PostListItem.author` 就是 `null`，前端显示“已注销用户”而不是崩掉（DTO 的 `@param author` 写了这条）。

### 5. 摘要：发帖时生成一次，按**码点**截 200

```java
static String summarize(String content) {
    if (content == null || content.isBlank()) {
        return "";
    }
    String flat = content.replaceAll("\\s+", " ").trim();
    if (flat.codePointCount(0, flat.length()) <= SUMMARY_MAX_CODE_POINTS) {
        return flat;
    }
    return flat.substring(0, flat.offsetByCodePoints(0, SUMMARY_MAX_CODE_POINTS));
}
```

三步：先把所有空白（含换行）压成一个空格——列表卡片只有一两行的位置，正文里的换行会把卡片撑变形；再按**码点**判断长度；超了才截。

用码点而不是 `String.length()` 是个具体的坑：`String.length()` 数的是 `char`，而一个 emoji 在 Java 里占**两个** char。按 char 截断会把最后一个 emoji 切成半个代理对，存进库就是非法字符，显示出来是乱码或问号，**而且不会报错**。`SUMMARY_MAX_CODE_POINTS = 200`，对应 `t_post.summary` 是 `varchar(255)`（按字符计，放得下）。

摘要在 `create` 里生成一次落库，列表页因此**永远不用碰正文列**——这就是第 1 段那条“不含 content 的 SQL”能成立的原因。它和“计数冗余存表”是同一个思路（ADR-0016）：把代价花在写得少的那一侧。改帖时摘要跟着正文走：

```xml
<if test="content != null">content = #{content}, summary = #{summary},</if>
```

`summary` 挂在 `content` 这个分支里，只有正文变了才重算；放在外面的话，只改标题也会把摘要冲掉。

### 6. 归属校验为什么不能用现成的 `@authz.isOwner`

帖子接口的“只有作者能改”，用的是内容域自己的 `PostAuthzService`（Bean 名 `postAuthz`）：

```java
@PatchMapping("/posts/{id}")
@PreAuthorize("@postAuthz.isOwner(#id)")
public Result<Void> update(@PathVariable Long id, @Valid @RequestBody UpdatePostRequest request) {
```

用户域另有一个看起来一样的 `@authz.isOwner`，但它的入参语义是**用户 ID**：

```java
// AuthzService（用户域）——入参是"用户 ID"，比的是"当前登录用户是不是这个人"
public boolean isOwner(Long ownerId) {
    Long currentUserId = CurrentUser.id();
    return currentUserId != null && currentUserId.equals(ownerId);
}
```

而帖子接口里的 `#id` 是**帖子 ID**。照抄过来，比的就是“帖子 ID 是否等于我的用户 ID”，后果有两层：几乎永远为假——**作者改自己的帖子也会被拒**（一眼能发现的坏）；更麻烦的是，某个用户的 ID 恰好等于某个帖子的 ID 时**会错误放行**，这个不报错，只在特定数据下悄悄发生。内容域的实现拿帖子 ID 先去把帖子的真实作者查出来，再和当前登录用户比：

```java
public boolean isOwner(Long postId) {
    Long currentUserId = CurrentUser.id();
    if (currentUserId == null || postId == null) {
        return false;
    }
    Post post = postMapper.selectById(postId);
    // post 为 null 说明帖子不存在或已删除——此时不认为是"你的"
    return post != null && currentUserId.equals(post.getAuthorId());
}
```

为什么不干脆把这个方法塞进用户域的 `AuthzService`：那需要用户域去读帖子表，也就是让 `forum-user` 依赖 `forum-content`，直接踩碎“三个业务域互不依赖”这条边界。**判断“这个东西是不是你的”，必须由拥有这个数据的域来做**（`PostAuthzService` 类注释）。

删帖那条更值得看，它把 RBAC 与资源归属**并排放在同一行**：

```java
@DeleteMapping("/posts/{id}")
@PreAuthorize("@postAuthz.isOwner(#id) or hasAnyRole('MODERATOR', 'ADMIN')")
```

`@postAuthz.isOwner(#id)` 回答“这是不是你发的”，`hasAnyRole(...)` 回答“你有没有治理权限”，两者是“或”——满足任一个就能删。混成一个判断就表达不出这种关系。注意**改帖没有给版主留口子**：版主改别人的帖等于篡改作者原意，治理动作应该是“下架”（`status`），不是“替他改写”。

### 7. 改帖：不能拿 UPDATE 的返回行数判断“帖子不存在”

```java
public void update(Long id, String title, String content) {
    if (title == null && content == null) {
        throw new BizException(ErrorCode.PARAM_INVALID, "至少要修改标题或正文中的一项");
    }
    if (postMapper.selectById(id) == null) {
        throw new BizException(ErrorCode.POST_NOT_FOUND);
    }

    postMapper.updateContent(id, title, content,
            content == null ? null : summarize(content));
}
```

两个防御。第一，两个字段都不给时直接拒——不然是一次“静默的无操作成功”，比报错更难查。第二，**先查一次确认存在**，而不是靠 `updateContent` 的返回行数：MySQL 的 `UPDATE` 默认返回的是“**实际改变了的行数**”，不是“匹配到的行数”，用户打开帖子、什么都没改、直接点保存时返回是 0，按返回行数判断会误报“帖子不存在”。多这一次查询换来的是不会误报。

### 8. 分页参数的夹紧在 DTO 里，不在 Controller

```java
public record PostQuery(int page, int size, PostSort sort) {
    public static final int MAX_SIZE = 50;

    public PostQuery {
        page = Math.max(page, 1);
        size = Math.min(Math.max(size, 1), MAX_SIZE);
        sort = sort == null ? PostSort.LATEST : sort;
    }

    public int offset() {
        return (page - 1) * size;
    }
}
```

夹紧放在 record 的紧凑构造器里，而不是 Controller 的参数校验上。理由：Service 可能被别的地方调用（M3 的缓存预热、M10 的压测脚本），放在 Controller 就等于“只有走 HTTP 的那条路才安全”；放在数据结构的构造处，**无论谁构造它都安全**。上限 50 的理由很直接——不加的话，一个 `size=100000` 的请求就是一次免费的资源消耗，而它看起来完全合法。

## 走一遍场景

**场景一：登录用户发一篇带换行的长帖**

1. `POST /api/posts`，请求体经 `CreatePostRequest` 校验：标题非空白且 ≤100、正文非空白且 ≤10 万字（上限不是防手滑，正文存 MEDIUMTEXT，不设限的话一个 10MB 请求就够服务难受）。
2. 进 `PostService.create`，`summarize(content)` 把正文里的换行压成空格、按码点截到 200，set 进 `post.summary`。
3. `postMapper.insert(post)` → `INSERT INTO t_post (author_id, title, content, summary) VALUES (?, ?, ?, ?)`；`useGeneratedKeys` 把自增主键回填到 `post.id`。
4. 返回这个 ID。前端拿它跳详情页。

**场景二：匿名用户翻首页**

1. `GET /api/posts?page=1&size=20`。这是公开接口——`SecurityConfig` 里只放行了 GET：

   ```java
   .requestMatchers(HttpMethod.GET, "/api/posts", "/api/posts/*").permitAll()
   ```

   注意只放行 GET，同一个 `/api/posts` 路径上的 POST（发帖）仍然要认证。之所以用“只放行 GET”而不是把整个 `/api/posts` 敞开：漏列一个接口的表现是它完全敞开，不会报错；而漏放行一个公开接口的表现是匿名访问 401，一眼能发现——后者比前者安全（设计稿 §4 的说明②）。

2. Controller 把参数包成 `PostQuery`（越界的 page / size 在这一步被夹紧），调 `postService.page`。
3. **先 `countList(null)`**。总数为 0 就直接返回空页——连列表查询都不发，顺带也不会去查作者（空集合的批量查询本该被短路，但这里连调用都省了）。
4. `selectPage(null, "LATEST", 0, 20)`：`SELECT id, author_id, title, summary, ...`（**没有 content**）`FROM t_post WHERE deleted = 0 AND status = 0 ORDER BY top_flag DESC, create_time DESC, id DESC LIMIT 20 OFFSET 0`。拿回 20 个 `Post`，它们的 `content` 都是 `null`。
5. `findAuthors`：把这 20 条的 `author_id` 收进一个 `Set`（同一作者发多条会去重），一次 `findBriefs(ids)` 换回 `Map<Long, UserBrief>`。**这是 1 次查询，不是 20 次。**
6. 每条 `PostListItem.from(post, authors.get(...))`，作者查不到（已注销）时 `author` 为 `null`。返回 `PageResult{items, total, page, size}`。

**场景三：另一个用户改这篇帖**

1. `PATCH /api/posts/7`，`@PreAuthorize("@postAuthz.isOwner(#id)")` 先跑。
2. `PostAuthzService.isOwner(7L)`：拿当前登录用户 ID，`postMapper.selectById(7L)` 取出帖子，比对 `post.getAuthorId()`。
   - 不是作者 → 返回 false → Spring Security 抛 `AccessDeniedException` → `AccessDeniedHandler` 写回统一错误体 `FORBIDDEN`（403）。
   - 帖子不存在或已删除 → 也返回 false。对不存在的帖子，“是不是你的”无从谈起，返回 403 是合理的。
3. 是作者 → 进 `PostService.update`：先查存在、再 `updateContent`，正文没给就不动 `summary`。

## 面试会追问

**Q：列表页为什么可以不查正文？**
MySQL 的 `TEXT` / `MEDIUMTEXT` 本来就行外存储，主表行只留一个指针；**只要不 SELECT 那一列，就不会读出来**。所以内容域立的规范是“列表 / 分页查询显式列列名，禁止 `SELECT *`”——`SELECT *` 会把 `content` 一起捞出来，前一句的便宜当场失效。真要不小心加了 `content`，`PostListItem` 里根本没有这个字段，这层“类型不让带正文”也会先挡一下（设计稿 §2.6 是这条的出处）。

**Q：为什么列表页摘要而不是正文？**
摘要发帖时从正文生成一次落库（压成一行 + 按码点截 200），列表页读 `summary` 这一列就行，不必碰正文。这和“计数冗余存表”是同一个思路：把代价花在写得少的那一侧（ADR-0016）。

**Q：摘要为什么按“码点”截，不按 `String.length()`？**
一个 emoji 在 Java 里占两个 `char`，按 char 截会把最后一个 emoji 切成半个代理对——存库非法、显示乱码，**且不报错**。`codePointCount` / `offsetByCodePoints` 数的是真正的字符。

**Q：作者昵称为什么不做快照存进 `t_post`？**
理由见 `ADR-0015 §理由`。一句话版：快照省一次查询的代价，是**用户改昵称之后历史帖子永远停在旧昵称，没有任何机制去修它**——这不是缓存（缓存可以失效，快照不能）。判据是“这个值描述的是当前状态还是历史事实”，不是“哪个更快”。同一份 ADR 里也写了快照在**订单收货地址**上是对的（M7 会那么做）。

**Q：一页 20 篇，是不是查了 20 次用户？**
不是，是一次：`findAuthors` 把本页的 `author_id` 去重后丢给 `findBriefs(Collection)`，契约上直接放的就是批量方法。给单条查询的接口，调用方必然写成 N+1，而 N+1 不报错、只在数据量上来后表现为列表变慢（ADR-0015 §二）。

**Q：空集合会不会拼出非法的 `IN ()`？**
会，所以 `UserQueryServiceImpl.findBriefs` 在**进 mapper 之前**短路空集合，直接返回 `Map.of()`。这一条只在“这一页一个作者都没有”时才可能踩到，最难测，所以有专门的用例钉它（`verify(userMapper, never())`，断言的是“根本没查库”而不是“返回了空”）。

**Q：`@authz.isOwner(#id)` 为什么不能用在帖子接口上？**
它的入参是**用户 ID**，语义是“当前登录用户是不是这个人”；而帖子接口的 `#id` 是**帖子 ID**。照抄比的是“帖子 ID == 我的用户 ID”——作者改自己的帖会被拒，而且两者恰好相等时**会错误放行**（静默）。帖子这类资源由内容域的 `PostAuthzService` 判断，它拿帖子 ID 查出真实作者再比（`AuthzService` 的类注释也写了这条对照）。

**Q：为什么版主能删帖却不能改帖？**
删是治理动作（下架是“不让它被看见”，可撤销，见 `status` 字段）；改是**替作者改写原意**。所以改帖只留给作者本人，删帖给作者或版主 / 管理员——`@PreAuthorize("@postAuthz.isOwner(#id) or hasAnyRole('MODERATOR', 'ADMIN')")` 这一行把两种判断用“或”连起来，也正好说明 RBAC 与资源归属是两件必须分开的事。

**Q：改帖为什么先查一次再更新，不直接看 UPDATE 的影响行数？**
MySQL 的 `UPDATE` 默认返回**实际改变的行数**，不是匹配的行数。用户什么都没改就点保存，返回 0，按它判断会误报“帖子不存在”。多一次查询换“不会误报”（`PostMapper.updateContent` 的注释写了完整原因，还提到这取决于驱动的 `useAffectedRows`，与其赌它不如不依赖）。

**Q：`sort` 参数是怎么防注入的？**
`sort` 是 `PostSort` 枚举，外部传不认识的值在参数转换阶段就报错了；就算到了 XML，它也只用于 `<choose>` 在两条**写死**的 `ORDER BY` 之间选，**不会拼进 SQL**。根本原因是 `ORDER BY` 的列名不能用 `#{}` 占位符，只剩 `${}` 拼接这条路——而那是注入入口，所以干脆不拼。

**Q：翻页为什么 `ORDER BY` 末尾要带 `id DESC`？**
`create_time` 只精确到秒，同一秒发的帖子排序不稳定，翻页时同一行可能两页都有或都没有。`id` 是唯一的，拿它兜底顺序才确定。（M6 的 keyset 分页会把这个“兜底列”变成主角。）

**Q：详情页那个“读接口里带写”的浏览数 +1 回事？**
`getDetail` 里 `selectById` 之后调 `incrementViewCount`，是一条 `UPDATE ... SET view_count = view_count + 1`——**单条语句**，并发安全，换成“先查再写”会丢更新。这是有意接受的现状，**M3 会换成 Redis 累加 + 定期回写**，那时只改这一行（`PostService.getDetail` 与 `PostMapper.incrementViewCount` 的注释都标了）。返回值里也把本次访问算上，否则响应里的数字比库里差 1，排查时会怀疑“更新是不是没生效”。
