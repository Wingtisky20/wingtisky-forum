# 链路讲解 · 请求生命周期与公共设施

## 一句话

一次请求进来，先由一个全局过滤器给它发一个 `traceId` 塞进日志上下文；再经过 Spring Security
过滤器链（认证 + 授权），最后到 Controller 执行业务；无论在哪一层成功或失败，吐出去的
JSON 都是同一个 `Result` 形状——**Controller 层的异常由 `GlobalExceptionHandler` 收敛，
过滤器链层的 401/403 由 `RestAuthErrorWriter` 手写，两条路殊途同归**。

---

## 数据怎么走

按时间顺序，一次请求依次穿过这些东西（括号里是所在位置）：

```
HTTP 请求
  │
  ├─ 1. TraceIdFilter                （Servlet Filter，order = HIGHEST_PRECEDENCE）
  │      取/造 traceId → 写进 MDC → 写进响应头 X-Trace-Id
  │
  ├─ 2. Spring Security 过滤器链      （DelegatingFilterProxy，order = -100 起）
  │      ├─ JwtAuthenticationFilter   有 Bearer 就验，验通则填 SecurityContext；
  │      │                            验不通什么都不做（不在这里拒绝）
  │      └─ AuthorizationFilter       按 SecurityConfig 的规则判定
  │            ✗ 不通过 → AuthenticationEntryPoint / AccessDeniedHandler
  │                       → RestAuthErrorWriter 直接写响应，链路到此结束
  │
  ├─ 3. DispatcherServlet
  │      └─ RateLimitInterceptor.preHandle（MVC HandlerInterceptor）
  │            超限 → throw BizException(TOO_MANY_REQUESTS)
  │
  ├─ 4. Controller 方法
  │      @Valid 失败 / @PreAuthorize 拒绝 / 业务抛 BizException
  │
  ├─ 5. 正常返回 → Result.success(data)
  │           异常 → GlobalExceptionHandler 映射成 Result.error(errorCode)
  │
  └─ 6. 回到 TraceIdFilter 的 finally → TraceIdHolder.clear()
```

两个关键的顺序事实：

- **第 1 步必须早于第 2 步**。否则 Security 链里产生的 401/403 会拿不到 traceId，
  响应体里的 `traceId` 是空的——`RestAuthErrorWriter` 的注释专门写了这一点。
- **第 3、4 步在 DispatcherServlet 内部**，所以这里的异常能走到 `@RestControllerAdvice`；
  而第 2 步在 DispatcherServlet **之前**，异常根本冒不到 advice 那里。这是全文最要紧的一句话。

## 逐段讲代码

### 1. TraceIdFilter —— 给请求发一张身份证

`wt-common/.../trace/TraceIdFilter.java`

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID_HEADER = "X-Trace-Id";
    private static final Pattern SAFE_TRACE_ID = Pattern.compile("^[A-Za-z0-9-]{8,64}$");
```

`Ordered.HIGHEST_PRECEDENCE` 是整型最小值，Spring Security 的过滤器链是 `-100` 起，
所以它排在最前面。三个动作：

```java
String traceId = resolveTraceId(request);
TraceIdHolder.set(traceId);
response.setHeader(TRACE_ID_HEADER, traceId);
try {
    filterChain.doFilter(request, response);
} finally {
    // 必须清理：线程是复用的，不清理会让下一个请求沿用上一个的 traceId
    TraceIdHolder.clear();
}
```

`resolveTraceId` 允许客户端带 traceId（链路从上游传下来时用得上），但**必须过白名单正则**：

```java
String incoming = request.getHeader(TRACE_ID_HEADER);
if (incoming != null && SAFE_TRACE_ID.matcher(incoming).matches()) {
    return incoming;
}
return UUID.randomUUID().toString().replace("-", "");
```

为什么不能原样接受任意输入——`SAFE_TRACE_ID` 上面的注释给了答案：这个值要进日志，
不校验的话攻击者能塞换行符伪造整行日志（日志注入）。限制字符集与长度后它只能是标识符。

`finally` 里的 `clear()` 是最容易漏的：Tomcat 复用线程，不清理就会沿用上一个请求的 traceId，
日志串成一片。`OncePerRequestFilter` 保证一次请求只走一遍。

### 2. TraceIdHolder —— 只暴露"拿 traceId"，不暴露"怎么存"

`wt-common/.../trace/TraceIdHolder.java`

```java
public static final String MDC_KEY = "traceId";

public static String current() {
    return MDC.get(MDC_KEY);
}

static void set(String traceId) {
    MDC.put(MDC_KEY, traceId);
}

static void clear() {
    MDC.remove(MDC_KEY);
}
```

底层是 SLF4J 的 `MDC`（把值绑在当前线程上）。注意 `set` / `clear` 是**包级私有**的——
只有同包的 `TraceIdFilter` 能改，业务代码只能 `current()` 读。这样"traceId 由谁写入"只有一处，
将来换成别的传播机制（比如跨服务链路追踪）只改这个类，见类注释里的理由。

### 3. Result —— 唯一的响应形状

`wt-common/.../result/Result.java`

```java
public static final String SUCCESS_CODE = "0";

private String code;
private String message;
private T data;
private String traceId;
```

```java
private Result(String code, String message, T data) {
    this.code = code;
    this.message = message;
    this.data = data;
    // 从日志上下文取，保证"响应里的 traceId"和"日志里的 traceId"是同一个
    this.traceId = TraceIdHolder.current();
}
```

traceId 不是调用方传进来的，而是在构造时**从 MDC 现取**。所以只要 `TraceIdFilter` 跑过，
响应体里就一定带着与日志同源的那个 id。用户截个图把 traceId 报过来，直接在日志里 `grep` 就能定位。

工厂方法只有四个：`success(data)` / `success()`（`data` 为 `null`，文案 `"ok"`）、
`error(errorCode)`、`error(errorCode, message)`（自定义文案覆盖默认）。
`code` 用 `String` 而不是 `int`，理由见 `docs/03-design/m1-user-and-security.md §6.1`。

### 4. ErrorCode —— 错误码把 HTTP 状态也捎带上了

`wt-common/.../result/ErrorCode.java`

```java
PARAM_INVALID("A0001", "参数不合法", HttpStatus.BAD_REQUEST),
UNAUTHORIZED("A0002", "未登录或登录已过期", HttpStatus.UNAUTHORIZED),
FORBIDDEN("A0003", "没有权限", HttpStatus.FORBIDDEN),
TOO_MANY_REQUESTS("A0004", "请求过于频繁，请稍后再试", HttpStatus.TOO_MANY_REQUESTS),
SYSTEM_ERROR("A0005", "系统繁忙，请稍后再试", HttpStatus.INTERNAL_SERVER_ERROR),
```

用户域 `A01xx`：`USERNAME_EXISTS` / `LOGIN_FAILED` / `USER_NOT_FOUND` / `ACCOUNT_DISABLED`。
分段规则见 `docs/03-design/m1-user-and-security.md §6.2`。

每个枚举项都握着一个 `HttpStatus`，`getHttpStatus()` 供异常处理时设状态码。
把"HTTP 状态"和"业务码"绑在一处，而不是散在各处的 if 里——散着写迟早漏一个，
漏掉的表现是"该 403 的返回了 500"（见类注释）。
另外 `LOGIN_FAILED` 同时用于"用户名不存在"和"密码错误"是有意的，理由见
`ErrorCode.LOGIN_FAILED` 的 javadoc：否则接口会变成用户名探测器。

### 5. BizException —— "预期之内"的失败

`wt-common/.../exception/BizException.java`

```java
public class BizException extends RuntimeException {
    private final ErrorCode errorCode;

    public BizException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }
```

只多带了一个 `ErrorCode`。"预期之内"与"系统故障"的区分见类注释——前者给用户看文案、
日志记 WARN 不打堆栈，后者给开发者看堆栈、给用户只说"系统繁忙"。

### 6. GlobalExceptionHandler —— Controller 层异常的收敛口

`wt-common/.../exception/GlobalExceptionHandler.java`，注解是 `@RestControllerAdvice`。
五个 handler，各自做的事不一样：

| 捕获 | 记什么日志 | 返回 |
|---|---|---|
| `BizException` | WARN，不打堆栈 | 状态码/文案取 `e.getErrorCode()`（含自定义文案） |
| `HttpMessageNotReadableException` | WARN | 400 + `PARAM_INVALID`，文案固定"请求体格式不正确" |
| `MethodArgumentNotValidException` | WARN | 400 + `PARAM_INVALID`，文案拼出出错字段名 |
| `AccessDeniedException` | WARN | 403 + `FORBIDDEN` |
| `Exception`（兜底） | ERROR + 完整堆栈 | 500 + `SYSTEM_ERROR` |

```java
@ExceptionHandler(BizException.class)
public ResponseEntity<Result<Void>> handleBizException(BizException e) {
    ErrorCode errorCode = e.getErrorCode();
    log.warn("业务异常: code={}, message={}", errorCode.getCode(), e.getMessage());
    return ResponseEntity.status(errorCode.getHttpStatus())
            .body(Result.error(errorCode, e.getMessage()));
}
```

业务异常走 `e.getMessage()`（可被 `BizException(errorCode, message)` 覆盖），
所以同一个码可以有更具体的文案。参数校验那条则把字段名拼进文案：

```java
String detail = e.getBindingResult().getFieldErrors().stream()
        .map(fe -> fe.getField() + ": " + defaultMessageOf(fe))
        .collect(Collectors.joining("; "));
```

两个 handler 值得单独说：

- `handleUnreadableBody` —— 畸形 JSON 必须单独接，否则掉进兜底报 500。它是**调用方的问题**，
  报 500 会把"有人发了畸形请求"统计成"服务端出错"。但响应里不说具体哪里错，细节只进日志。
- `handleAccessDenied` —— `@PreAuthorize` 拒绝时抛的就是 `AccessDeniedException`，
  它发生在 DispatcherServlet **内部**（方法安全是 Controller 方法上的 AOP 切面），
  所以能走到这里。这里必须映射成 403，否则会被兜底的 `Exception` 分支吞掉报成 500。

兜底 handler 的不对称也写得很清楚：日志里完整堆栈，响应里只有 `SYSTEM_ERROR` + traceId。

### 7. RestAuthErrorWriter —— 过滤器链层的 401/403

`forum/forum-user/.../security/RestAuthErrorWriter.java`

```java
final class RestAuthErrorWriter {

    private RestAuthErrorWriter() {
    }

    static void write(HttpServletResponse response, ObjectMapper objectMapper, ErrorCode errorCode)
            throws IOException {
        response.setStatus(errorCode.getHttpStatus().value());
        response.setContentType(MediaType.APPLICATION_JSON_VALUE);
        response.setCharacterEncoding(StandardCharsets.UTF_8.name());
        response.getWriter().write(objectMapper.writeValueAsString(Result.error(errorCode)));
    }
}
```

它为什么必须存在，类注释一句话点破：**认证失败发生在过滤器链里，早于 DispatcherServlet，
`@RestControllerAdvice` 根本拦不到**——不写它，返回的是 Spring Security 的默认响应（空 body 或 HTML）。

它复用的还是 `Result.error(errorCode)` 这个工厂方法，因此 traceId 依然在构造时从 MDC 取。
此时 MDC 里有值，靠的是 `TraceIdFilter` 的 order 排在 Security 链之前（`RestAuthErrorWriter` 的
注释里明确写了这条依赖）。

两个细节：`charset` 必须显式设 `UTF-8`（不带字符集时某些客户端按 ISO-8859-1 解析，
中文文案变乱码）；`ObjectMapper` 是从 Spring 容器注入的，不是 new 出来的。

### 8. SecurityConfig —— 把两个 handler 接上

`forum/forum-user/.../security/SecurityConfig.java`

```java
AuthenticationEntryPoint entryPoint =
        (request, response, authException) ->
                RestAuthErrorWriter.write(response, objectMapper, ErrorCode.UNAUTHORIZED);

AccessDeniedHandler deniedHandler =
        (request, response, accessDeniedException) ->
                RestAuthErrorWriter.write(response, objectMapper, ErrorCode.FORBIDDEN);
```

```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers(PUBLIC_ENDPOINTS).permitAll()
        .requestMatchers(HttpMethod.GET, "/api/users/*").permitAll()
        .anyRequest().authenticated())

.exceptionHandling(ex -> ex
        .authenticationEntryPoint(entryPoint)
        .accessDeniedHandler(deniedHandler))
```

- `authenticationEntryPoint`：**未认证**时触发（没有令牌、令牌过期/被篡改）→ 401 `A0002`。
- `accessDeniedHandler`：**已认证但没通过授权规则**时触发 → 403 `A0003`。

注意 `JwtAuthenticationFilter` 本身**不拒绝任何请求**——它只负责"能验通就填 SecurityContext"，
至于是不是放行交给上面的授权规则。理由见该类的类注释：两处都判会迟早不一致。

### 9. 日志格式 —— traceId 真正起作用的地方

`app/src/main/resources/application.yml`

```yaml
logging:
  charset:
    console: UTF-8
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [%X{traceId:-}] %logger{36} - %msg%n"
```

`%X{traceId:-}` 从 MDC 取 traceId，取不到留空。没有这一行，`TraceIdHolder.set()` 写进去的值
就只是个摆设。`console: UTF-8` 也不能省——中文 Windows 默认 GBK，日志里的中文会 grep 不到。

## 走一遍场景

用 `docs/06-runbook/api-smoke.http` 里的真实请求，看三种结局分别走哪条路。

### 场景 A：重复注册（走 advice，409）

请求 2 重复注册同一个用户名。`AuthService` 里撞到唯一索引/查到重名，抛
`BizException(ErrorCode.USERNAME_EXISTS)`。异常从 Controller 冒出来，
被 `handleBizException` 接住 → `ResponseEntity.status(CONFLICT).body(Result.error(...))`。

响应：`409`，`code=A0101`，`message="用户名已被占用"`，`traceId` 与日志同一份。
在此之前 `RateLimitInterceptor` 那步已经跑过（普通接口按用户 100/分钟）。

### 场景 B：不带令牌访问受保护接口（走 RestAuthErrorWriter，401）

请求 9 `POST /api/auth/logout` 不带 `Authorization`。请求进到 Security 链，
`JwtAuthenticationFilter` 没找到 Bearer 头，什么都不做；`AuthorizationFilter` 按规则判定
`/api/auth/logout` 不在公开名单里、且没认证 → 抛 `AuthenticationException` →
`ExceptionTranslationFilter` 调 `entryPoint` → `RestAuthErrorWriter` 写出
`401 + code=A0002`。**这条路径根本到不了 DispatcherServlet，也就到不了
`GlobalExceptionHandler`**——这正是 api-smoke.http 第 9 条注释和本文件想讲清的点。

### 场景 C：不带令牌、但响应体格式和场景 A 一模一样

这是最值得强调的效果：场景 A 由 advice 生成、场景 B 由 `RestAuthErrorWriter` 生成，
前端拿到的却是一个形状的 JSON。因为两条路都调 `Result.error(...)`，
traceId 又都来自同一个 MDC。前端只写一次"失败处理"就够了。

### 另外两条，顺带串起来

- 请求 15 触发限流：`RateLimitInterceptor.preHandle` 抛 `BizException(TOO_MANY_REQUESTS)`
  → 落到 `handleBizException` → 429 `A0004`。**它走的是 advice，不是 Security**，
  因为 MVC 拦截器在 DispatcherServlet 内部、Security 链之后。
- 请求 14 畸形 JSON：`HttpMessageNotReadableException` → `handleUnreadableBody` → 400 `A0001`
  （文案"请求体格式不正确"），而不是 500。

## 面试会追问

**Q：为什么 401/403 要单独写一个 `RestAuthErrorWriter`，不能靠全局异常处理？**

因为拦截层不同。`@RestControllerAdvice` 是 DispatcherServlet 的组件，**只能在请求已经进入
Spring MVC 之后**才起作用；而认证/授权失败发生在 Security 过滤器链里，位置在 DispatcherServlet
**之前**，异常根本走不到 advice。不写它，返回的就是 Security 的默认响应（空 body 或 HTML 页），
"统一响应体"这个契约恰好在最常见的场景（没登录）上失效。

**Q：那什么时候 403 走 advice，什么时候走 `RestAuthErrorWriter`？**

看拒绝发生在哪一层。`SecurityConfig` 里 `authorizeHttpRequests` 的规则拒绝，发生在过滤器链
（`AuthorizationFilter`），走 `accessDeniedHandler` → `RestAuthErrorWriter`；
`@PreAuthorize`（如 `UserController.updateProfile` 上的 `@authz.isOwner(#id) or hasRole('ADMIN')`）
是 Controller 方法上的 AOP，发生在 DispatcherServlet 内部，抛出的 `AccessDeniedException`
由 `handleAccessDenied` 接住。两条路最后都是 `403 + A0003`，但代码路径完全不同。

**Q：怎么保证两条路的 traceId 是同一个？**

`TraceIdFilter` 的 `@Order(Ordered.HIGHEST_PRECEDENCE)` 排在 Security 链（-100）之前，
所以 `RestAuthErrorWriter` 执行时 MDC 里已经有 traceId。`Result` 的构造函数从
`TraceIdHolder.current()` 现取，两条路都经过这个构造函数，因此同一个 traceId 既在
响应头 `X-Trace-Id` 里、也在响应体 `traceId` 字段里、还在日志行 `[%X{traceId:-}]` 里。

**Q：为什么不直接把异常的堆栈返回给前端？**

安全问题（暴露包名、类名、SQL 片段），也是体验问题（用户看到一屏 Java 堆栈）。
兜底 handler 的处理是：日志里 `log.error("未预期的异常", e)` 打完整堆栈，响应里只给
`SYSTEM_ERROR` + traceId。调用方拿 traceId 报障，开发者在日志里精确定位。

**Q：`Result` 里的 traceId 为什么不在 Controller 里手动塞？**

那样每个接口都要重复一遍，且容易漏。放在构造函数里现取 MDC，只要过滤器跑过就一定有，
不给业务代码留下"忘了塞"的机会。

**Q：限流的 429 为什么不是异常处理链？**

它**是**——`RateLimitInterceptor` 抛 `BizException(TOO_MANY_REQUESTS)`，正是走
`GlobalExceptionHandler`。它和 401/403 的区别在于拦截位置：MVC 拦截器在 DispatcherServlet
内部、Security 链之后，所以能享受 advice；Security 链在 DispatcherServlet 之前，享受不到。

**Q：`TraceIdHolder.set/clear` 为什么是包级私有？**

只有同包的 `TraceIdFilter` 能写，业务代码只能 `current()` 读。这保证"谁写 traceId"只有一处，
边界清晰；将来换传播机制（比如接入跨服务链路追踪）只改这一个类。
