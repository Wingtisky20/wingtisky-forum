# 链路讲解 · 后台治理

> 对着 M2 的真实代码讲一遍：版主/管理员怎么把一条帖子置顶、加精、下架。
> 只讲代码实际怎么走；设计上的"为什么"指向已有文档，不在这里复述第二遍。
> 鉴权本身的两层划分见 `04-鉴权-RBAC与资源归属.md`，本文不重复，只引它；
> 帖子本身的读写见 `07-帖子读写链路.md`。

---

## 一句话

后台治理这条链路里有**两个完全不同的判断**，混起来就出事：第一个是"**你能不能调这个接口**"，写在 `AdminPostController` 的**类上**（`@PreAuthorize("hasAnyRole('MODERATOR', 'ADMIN')")`）——写类上而不是每个方法上，是因为漏写的失败模式是静默的，新加一个治理接口忘了写注解，它就对外面所有人敞开了；第二个是"**同一条数据，不同人看到的不一样**"，藏在详情接口里：被下架的帖子公开列表和匿名详情都看不到，**但作者本人和版主还能打开**——帖子突然从作者眼前消失、没有任何提示，他只会以为网站坏了；别人来访问给的是 **404 而不是 403**（403 等于替对方确认"这个 id 是存在的"）。另外，下架要**连带把标签的使用次数减 1**，而且只有"状态真的变了"才动——重复下架一次不该把数字减第二遍。

## 数据怎么走

### 写一：版主下架一条帖子 `PATCH /api/admin/posts/{id}`

```
HTTP  PATCH /api/admin/posts/1   Authorization: Bearer <版主的 access>
      body: { "status": 1 }
  │
  ▼
JwtAuthenticationFilter                    ← 只验签，不拒绝任何请求
  │  principal=9（版主 id）、authorities=[ROLE_MODERATOR, ROLE_USER]
  ▼
SecurityConfig 的 authorizeHttpRequests    ← 配置级闸门
  │  /api/admin/posts/1 **不在 PUBLIC_ENDPOINTS** 里 → 落到 anyRequest().authenticated()
  │  上下文里有认证 → 放行
  ▼
AdminPostController 类上的 @PreAuthorize("hasAnyRole('MODERATOR', 'ADMIN')")  ← 方法级闸门
  │  有 ROLE_MODERATOR → 放行；只有 ROLE_USER 的话在这里抛 AccessDeniedException → 403
  ▼
AdminPostController.update(id=1, operatorId=9, request)
  ▼
PostService.administrate(1, 9, null, null, 1)
   ├─ 三个字段都是 null？→ 抛 A0001（400，不能静默返回成功）
   ├─ postMapper.selectById(1) == null？→ 抛 A0201
   ├─ postMapper.updateAttributes(1, null, null, 1)      ← UPDATE t_post SET status = 1 WHERE id = 1 AND deleted = 0
   ├─ status(1) 与查出来的 post.getStatus()(0) 不同 → tagService.adjustPostCountForTagsOf(1, -1)
   │        └─ 这条帖子带的每个标签：UPDATE t_tag SET post_count = GREATEST(post_count - 1, 0) WHERE id = ?
   └─ log.info("帖子治理: postId=1, ..., 操作人=9")
  ▼
HTTP 200  Result<Void>（data 为 null）
```

`administrate` 上有 `@Transactional`，所以"改帖子"与"改标签计数"要么一起成功，要么一起回滚——这两件事本来就是一体的。

### 读一：四种人打开同一条**已下架**的帖子 `GET /api/posts/{id}`

四个请求走的是**同一个接口、同一份代码**，差别只在 `viewerId` 和 `viewerIsModerator` 两个入参：

```
GET /api/posts/1
  │
  ▼
PostController.detail(id=1, viewerId=@AuthenticationPrincipal)
  │  最后一个实参是 CurrentUser.hasAnyRole("MODERATOR", "ADMIN")  ← **在这里算，传下去**
  ▼
PostService.getDetail(1, viewerId, viewerIsModerator)
  ├─ postMapper.selectById(1)              ← 注意它只排除 deleted = 1，**能查得到已下架的帖子**
  ├─ visibleTo(post, viewerId, viewerIsModerator) 为 false → 抛 A0201（404 = 当作不存在）
  └─ 为 true → incrementViewCount + 拼 PostDetail 返回
```

| 谁 | `viewerId` | `viewerIsModerator` | `visibleTo` 走哪条分支 | 结果 |
|---|---|---|---|---|
| 匿名访客 | `null` | `false` | 不是 `isVisible()`，`viewerId == null` → `false` | **404 A0201** |
| 别人（普通登录用户） | 999 | `false` | 不是作者、不是版主 → `false` | **404 A0201** |
| 作者本人 | 10 | `false` | `viewerId.equals(post.getAuthorId())` → `true` | **200** |
| 版主 / 管理员 | 9 | `true` | `viewerIsModerator` → `true` | **200** |

公开列表（`GET /api/posts` 与 `GET /api/users/{id}/posts`）不参与这张表——它连"来看的人是谁"都不问，SQL 的过滤条件里恒有 `status = 0`。

## 逐段讲代码

### 1. 单独一个 Controller，权限的范围一目了然

```java
@RestController
@RequestMapping("/api/admin/posts")
@PreAuthorize("hasAnyRole('MODERATOR', 'ADMIN')")
public class AdminPostController {
```

为什么不是塞进 `PostController` 加个方法，类注释里写得很直白：后台接口集中在一处，将来加治理动作（删评论、封账号…）不用去业务接口那个类里翻；**更重要的是这个类里每一个接口都是同一个门槛**。

### 2. 注解写在**类上**，不写在每个方法上

这是本文最该记住的一点。同一个类注释：

> `@PreAuthorize` 写在**类上**而不是每个方法上：这一整个类都是后台接口，逐个方法写注解的失败模式是"新加一个方法时忘了写"，而那种漏洞不会报错，只会让一个治理接口对所有人敞开。写在类上就不存在"忘了"。

对照着看 `PostController`：那里一个类里混着公开接口（列表、详情）、登录接口（发帖、点赞）和带归属校验的接口（改帖、删帖），所以只能逐方法写 `@PreAuthorize`——每个方法的门槛都不一样，写类上表达不了。**两种写法的取舍依据是"这个类里的门槛是不是同一个"**，不是风格偏好。

`@PreAuthorize` 能生效还有一个前提：`SecurityConfig` 上的 `@EnableMethodSecurity`。它被删掉的话注解会被静默忽略——`04-鉴权-RBAC与资源归属.md` §3 讲过这一条，本文不重复。

### 3. 一个 `PATCH`，三个可选字段

```java
@PatchMapping("/{id}")
public Result<Void> update(@PathVariable Long id,
                           @AuthenticationPrincipal Long operatorId,
                           @Valid @RequestBody AdminPostUpdateRequest request) {
    postService.administrate(id, operatorId,
            request.topFlag(), request.featuredFlag(), request.status());
    return Result.success();
}
```

用 `PATCH` 而不是 `/top`、`/feature`、`/offline` 三个接口，注释里的理由是"同时置顶并加精"会变成两次请求，两次之间可能失败，留下一个不想要的中间状态。

`AdminPostUpdateRequest` 三个字段都是可空的（给哪个就改哪个），但 `status` 有范围限制：

```java
@Min(value = 0, message = "状态只能是 0（正常）或 1（下架）")
@Max(value = 1, message = "状态只能是 0（正常）或 1（下架）")
Integer status
```

它限制的不只是"别乱传"，而是"**别让调用方把状态改成 7**"——那会让这条帖子既不在正常列表里、也不在任何"已下架"的处理路径上，变成一条谁都说不清该不该显示的数据。DTO 的注释还解释了为什么用 `0/1` 而不是 `offline: true`：它和数据库列是同一个东西，多加一层"接口说 true、库里存 1"的对应关系要维护。

### 4. `administrate`：入口校验 → 改属性 → 视情况动标签计数

```java
@Transactional
public void administrate(Long id, Long operatorId,
                         Boolean topFlag, Boolean featuredFlag, Integer status) {
    if (topFlag == null && featuredFlag == null && status == null) {
        throw new BizException(ErrorCode.PARAM_INVALID, "至少要修改置顶、加精或上下架中的一项");
    }

    Post post = postMapper.selectById(id);
    if (post == null) {
        throw new BizException(ErrorCode.POST_NOT_FOUND);
    }

    postMapper.updateAttributes(id, topFlag, featuredFlag, status);

    // 只有"状态真的变了"才动标签计数——重复把已下架的帖子再下架一次，
    // 不该把标签的数字减第二遍
    if (status != null && !status.equals(post.getStatus())) {
        tagService.adjustPostCountForTagsOf(id,
                status == Post.STATUS_PUBLISHED ? 1 : -1);
    }

    log.info("帖子治理: postId={}, topFlag={}, featuredFlag={}, status={}, 操作人={}",
            id, topFlag, featuredFlag, status, operatorId);
}
```

三处细节：

- **先 `selectById` 再更新，而不是拿 `UPDATE` 的返回行数判断**。这一次查询是那个"状态有没有真的变"的判断所必需的（`updateAttributes` 自己不知道原来是什么状态）。
- **`!status.equals(post.getStatus())` 用的是 `equals` 而不是 `==`**。`status` 和 `post.getStatus()` 都是 `Integer`（包装类型），`==` 比的是引用，两个值都是 0 的两个不同对象也能是不相等。这里的比较必须按值。
- **`operatorId` 只进日志**。方法注释写得很清楚："权限在接口层用 `@PreAuthorize` 判过，这里不再判"。这一条和 `PostService` 的类注释是同一件事：**这里不放鉴权**——多一个调用入口（定时任务、内部接口）就要重写一遍鉴权，而那种遗漏不会报错。

### 5. `updateAttributes` 的 `WHERE`：只排除已删除的，**不排除已下架的**

```xml
<update id="updateAttributes">
    UPDATE t_post
    <set>
        <if test="topFlag != null">top_flag = #{topFlag},</if>
        <if test="featuredFlag != null">featured_flag = #{featuredFlag},</if>
        <if test="status != null">status = #{status},</if>
    </set>
    WHERE id = #{id} AND deleted = 0
</update>
```

`WHERE` 只有 `deleted = 0`，没有 `status = 0`。XML 的注释写了原因：

> ⚠️ WHERE 只排除 deleted = 1，**不排除已下架的**——否则一条帖子被下架之后就再也恢复不了了（它自己把自己锁在外面）。

这是本文里最容易写错、又最不容易被测试发现的一处：如果加上了 `status = 0`，正常的"下架"测试照过不误，只有"**先下架、再恢复上架**"那条路径会静默地什么都不改——`UPDATE` 影响 0 行**不报错**，而 Service 那边照样会去加标签计数，于是数字和真实状态对不上。

### 6. 下架要带动标签计数，而且只在状态真的变了时

`TagService.adjustPostCountForTagsOf`：

```java
@Transactional
public void adjustPostCountForTagsOf(Long postId, int delta) {
    tagMapper.selectByPostId(postId)
            .forEach(tag -> tagMapper.addPostCount(tag.getId(), delta));
}
```

它的注释把两件事讲清了：

> 用在"上下架"上：帖子从公开列表消失时，它给各标签贡献的那一篇也该消失——否则标签页写着"12 篇"、点进去只有 9 篇（差的那几篇被下架了），**而这正是当初为删帖做减计数时的那条理由**，两者是同一件事。
>
> 与 `detachAll` 的区别：那个还删关联（改帖换标签、删帖时用），这个只动计数（帖子还在，只是不再公开）。

底层的 `TagMapper.addPostCount` 里带了下限保护，和点赞、评论计数同一套路：

```xml
UPDATE t_tag
SET post_count = GREATEST(post_count + #{delta}, 0)
WHERE id = #{tagId}
```

计数为什么要冗余存表（而不是实时 `COUNT`）见 ADR-0016；"漏一处不会报错、只会让数字慢慢变假"这个代价同样在那份 ADR 里。

### 7. 可见性：`isVisible()` 管"正常吗"，`visibleTo` 管"这个人能看吗"

两个状态常量（`Post`）：

```java
/** 正常可见。 */
public static final int STATUS_PUBLISHED = 0;

/** 被版主下架。与"删除"是两件事——下架可恢复，且记录还在。 */
public static final int STATUS_OFFLINE = 1;
```

```java
/** 是否正常可见（未被下架、未被删除）。 */
public boolean isVisible() {
    return status != null && status == STATUS_PUBLISHED
            && (deleted == null || deleted == 0);
}
```

`isVisible()` **只看数据本身**，不知道"现在是谁在看"。补上"谁在看"的是 `PostService` 里那个私有静态方法：

```java
private static boolean visibleTo(Post post, Long viewerId, boolean viewerIsModerator) {
    if (post.isVisible()) {
        return true;
    }
    if (viewerId == null) {
        return false;
    }
    return viewerId.equals(post.getAuthorId()) || viewerIsModerator;
}
```

读的顺序就是注释里的三句话：正常帖子谁都能看；被下架的、又没登录 → 看不到；登录了就再问两个问题——**你是不是作者**、**你是不是版主**，满足任一个就能看。

它的注释补了一个容易被漏掉的边界：

> **注意列表那边不适用这条规则**：列表是公开视图，下架的帖子对谁都不显示，包括作者自己的个人主页。作者要看到它，走详情页的直链。

### 8. "是不是版主"在**接口层**算好，Service 不读安全上下文

`PostController.detail` 那两行是整个设计的落点：

```java
@GetMapping("/posts/{id}")
public Result<PostDetail> detail(@PathVariable Long id,
                                 @AuthenticationPrincipal Long viewerId) {
    // "你是不是版主"在这里问、传下去——Service 不去读安全上下文。
    // 被下架的帖子：作者与版主仍能打开，别人当作不存在。
    return Result.success(postService.getDetail(id, viewerId,
            CurrentUser.hasAnyRole("MODERATOR", "ADMIN")));
}
```

用的是 `CurrentUser.hasAnyRole`，它的类注释正好解释了和 `@PreAuthorize` 的分工：

> **它与 `@PreAuthorize("hasRole(...)")` 的分工**：后者用于"这个接口只有某角色能调"；前者用于"同一条数据，不同角色看到的内容不同"（比如下架的帖子，作者和版主能看、别人不能）。

`visibleTo` 被声明成 `private static`，也是这条分工的体现——它**只依赖传进来的三个参数**，不碰 `SecurityContextHolder`。所以它能被当成纯函数直接单测（`PostServiceTest` 里那几条可见性测试就是靠 `getDetail(id, viewerId, viewerIsModerator)` 的第三个参数来演的）。

角色名传的是**不带 `ROLE_` 前缀**的写法，前缀在 `CurrentUser` 内部补上：

```java
for (String role : roles) {
    if (owned.contains("ROLE_" + role)) {
        return true;
    }
}
```

注释里说了为什么：让调用方不必记住那个前缀，也避免有人写 `hasAnyRole("ROLE_ADMIN")` 而它永远为假。`hasAnyRole` 也不查库——角色来自 JWT 载荷（ADR-0013）。

### 9. 给 404，不给 403

```java
Post post = postMapper.selectById(id);
if (post == null || !visibleTo(post, viewerId, viewerIsModerator)) {
    // 已删**或已下架**且你没资格看时，对外一律当作"不存在"。
    // 用 403 会告诉对方"这个 id 是存在的"——那本身就是一种信息泄漏。
    throw new BizException(ErrorCode.POST_NOT_FOUND);
}
```

注意 `selectById` 的 SQL（`PostMapper.xml`）只有 `WHERE id = #{id} AND deleted = 0`——**已下架的帖子查得出来**，是靠上面这个 Java 判断把它挡在外面的，不是靠 SQL。这一点很关键：如果改成在 SQL 里加 `status = 0`，作者和版主就一起看不到了，1、5、7 三节的设计全部失效。

404 而不是 403 这个选择不是这里独有，`m2-content-core.md` §3.3 和 M1 的 `A0103`（用户不存在）是同一条规则。

### 10. 列表侧用的是另一套办法

`PostMapper.xml` 里列表的筛选条件是一段共用的 SQL：

```xml
<sql id="List_Filter">
    deleted = 0 AND status = 0
    <if test="authorId != null">
        AND author_id = #{authorId}
    </if>
    ...
</sql>
```

`selectPage` 与 `countList` 都 `<include refid="List_Filter"/>`——**取数据和数总数用的是同一套条件**，否则会出现"总数说有 5 条、实际只翻出 1 条"。`deleted` 与 `status` 两个等值条件都在 `idx_status_top_create` 索引里，过滤不走回表（见 `V2__init_content.sql`）。

## 走一遍场景

下面四条都在 `PostServiceTest` 的 `后台治理与可见性` 这一组里（11 条测试）被钉住。它们用的是 mock 的 `postMapper` / `tagService`，所以断言方式分两种：**能查库的一律 `verify(...)` 看 SQL 有没有发出去**，不能查库的用 `assertThatThrownBy` 看错误码。

**① 版主下架一条正常帖子 —— 顺手把标签计数减 1**

```java
@Test
@DisplayName("★ 下架：状态真的变了，标签的帖子数要减 1")
void takingOfflineDecrementsTagCount() {
    when(postMapper.selectById(1L)).thenReturn(post(1L, 10L, "正常帖子"));

    postService.administrate(1L, 99L, null, null, Post.STATUS_OFFLINE);

    verify(postMapper).updateAttributes(1L, null, null, Post.STATUS_OFFLINE);
    // 不减的话，标签页写着"12 篇"、点进去只有 9 篇
    verify(tagService).adjustPostCountForTagsOf(1L, -1);
}
```

**② 对一条已经下架的帖子再下架一次 —— 计数不许动**

```java
@Test
@DisplayName("★ 重复下架：状态没变，**不能把标签计数减第二遍**")
void repeatedOfflineDoesNotDecrementTwice() {
    when(postMapper.selectById(1L)).thenReturn(offlinePost(1L, 10L));

    postService.administrate(1L, 99L, null, null, Post.STATUS_OFFLINE);

    verify(postMapper).updateAttributes(1L, null, null, Post.STATUS_OFFLINE);
    verify(tagService, never()).adjustPostCountForTagsOf(anyLong(), anyInt());
}
```

注意 `updateAttributes` 仍然被调了一次（SQL 照发，只是值本来就是这个），**只有标签计数那条分支被跳过**——这正是 `!status.equals(post.getStatus())` 那行判断的作用。同一组里还有 `restoringIncrementsTagCount`（从 `STATUS_OFFLINE` 改回 `STATUS_PUBLISHED` → `+1`）和 `toppingDoesNotTouchTagCount`（只改置顶/加精时 `status` 为 null → 完全不碰计数），两个方向都覆盖到了。

**③ 一条被下架的帖子，四种人分别打开**

同组四条第名字就说明了问题：

- `offlinePostIsHiddenFromAnonymous` —— 匿名 → 抛 `POST_NOT_FOUND`；并且 `verify(postMapper, never()).incrementViewCount(anyLong())`，**看不到的帖子连浏览数都不加**（拒绝发生在 `incrementViewCount` 之前）。
- `offlinePostIsHiddenFromOthers` —— 别人 → 同样抛 `POST_NOT_FOUND`。
- `offlinePostIsVisibleToItsAuthor` —— 作者 → 正常拿到标题（`getDetail(1L, 10L, false)`）。
- `offlinePostIsVisibleToModerator` —— 版主 → 正常拿到标题（`getDetail(1L, 999L, true)`，注意第三个参数是 `true`）。

这几条必须成对看：只证明"匿名看不到"证明不了任何东西——一条谁都看不到的帖子也能过；必须同时证明**作者和版主确实看得到**。

**④ 反面对照：普通用户调治理接口 → 403**

这条是 `plan` Task 8 明确要求的反面用例（"普通用户 token 调 `PATCH /api/admin/posts/{id}` → 期望 403"）：普通用户带着有效令牌进来，`anyRequest().authenticated()` 那一关**会放他过**（他确实登录了），拦住他的是类上那行 `@PreAuthorize` → `AccessDeniedException` → `AccessDeniedHandler` → **403 A0003**。这和"完全不带令牌 → 401 A0002"是两条不同的路，区别见 `04-鉴权-RBAC与资源归属.md` §「数据怎么走」。

Task 8 的验证命令同时要求用 `mysql` 复查落库结果：

```bash
mysql -u wingtisky -p -e "SELECT top_flag, featured_flag, status FROM t_post WHERE id={id}" wingtisky_forum
```

理由写在那份计划里——"不能只看 HTTP 200——它可能什么都没干"。这条对本文第 5 节（`WHERE` 漏写 `status = 0` 时会静默地 0 行）正好是唯一的兜底。

## 面试会追问

**Q1：`@PreAuthorize` 为什么写在类上，不写在每个方法上？**
因为这个类里每个接口的门槛是同一个。逐方法写的话，失败模式是"新加一个方法忘了写"——不报错、不告警，只让一个治理接口对所有人敞开。写类上就不存在"忘了"。反过来，`PostController` 那种一个类里混着公开接口和归属校验接口的，就只能逐方法写，因为门槛不一样（见 `AdminPostController` 与 `PostController` 的类注释）。

**Q2：被下架的帖子，作者本人为什么还能打开？直接给所有人 404 不是更省事？**
那是"治理要能解释得清"的问题。帖子突然从作者眼前消失、又没有任何提示，他只会以为网站坏了，然后反复刷新或者干脆重发一遍。所以 `visibleTo` 里留了两个例外：作者与版主。版主那个例外还有一个用途——**他要能复核自己刚才的治理动作**。

**Q3：为什么返回 404 而不是 403？**
403（`A0003`）等于替对方确认"这个 id 是存在的"，这本身就是一种信息泄漏——拿 id 一个个试就能摸出哪些帖子存在过。所以不可见的资源一律当作不存在（`A0201`，404）。内容和用户两个域用的是同一条规则（`m2-content-core.md` §3.3）。

**Q4：`visibleTo` 为什么不放进 Service 里读 `SecurityContext`？反正都在后端。**
因为它一旦读了安全上下文，就变成一个依赖全局状态的隐式输入：测试要先把 `SecurityContextHolder` 填好，换个入口（内部接口、定时任务）就可能读到上一个请求残留的认证信息。现在它是个 `private static` 方法，只认三个参数；"是不是版主"由接口层的 `CurrentUser.hasAnyRole(...)` 算好传进来。这条分工在 `CurrentUser` 的类注释、`PostService.visibleTo` 的注释、`PostController.detail` 的行内注释里各写了一遍。

**Q5：为什么下架要连带改标签的 `post_count`？**
因为标签页的数字要能对得上点进去的列表。帖子从公开列表消失，它给各标签贡献的那一篇也该消失，否则标签页写着"12 篇"、点进去只有 9 篇。这和删帖减计数是同一件事（`TagService.adjustPostCountForTagsOf` 的注释），而这个数字**不会自己恢复**——所以每一条改变可见性的路径都得记着动它，漏一处就永久偏了。

**Q6：那重复下架一次，是不是要把数字减第二遍？**
不会，也不该。`administrate` 里判断 `status != null && !status.equals(post.getStatus())`——只有状态真的从 0 变成 1 才动计数。测试 `repeatedOfflineDoesNotDecrementTwice` 专门对着这一点：`UPDATE` 照发，但标签计数一条也不发。

**Q7：为什么 `updateAttributes` 的 `WHERE` 不排除 `status = 1`？**
排除了的话，一条帖子被下架之后就再也恢复不了了——它把自己锁在了外面。`WHERE` 只排除 `deleted = 1`，因为"已删除"是真的不该再改。这个差异的源头是 `status` 与 `deleted` 是两个字段（下节）。

**Q8：下架和删帖有什么区别？看起来都是"看不见了"。**
两件事，两个字段：`deleted` 管"这条记录还在不在"（作者删帖），`status` 管"这条记录能不能被看见"（版主下架，**可撤销**）。`V2__init_content.sql` 里那段注释写得很直接："合成一个字段省不了多少事，代价是'版主误下架'和'作者删帖'再也分不开——恢复路径不同"。合并了还会顺带毁掉一件事：删掉的帖子不该能被"恢复上架"找回来，而它恰恰共用同一条 `updateAttributes`。

**Q9：为什么用 `status = 0/1` 而不是 `offline: true`？**
因为它和数据库列、实体常量是同一个东西，多加一层映射就多一处要维护的对应关系。真正有价值的不是布尔语义，而是 `@Min(0) @Max(1)` 那道范围限制——防止有人把状态改成 7，让帖子落在一个既不在正常列表、也不在任何"已下架"处理路径上的状态里。

**Q10：版主既然能下架，为什么不能顺手替作者改正文？**
因为那是两回事。作者改的是**内容**（`PATCH /api/posts/{id}`，要归属校验），版主改的是**属性**（`PATCH /api/admin/posts/{id}`，要角色）。版主改别人的正文等于篡改作者原意；治理动作应该是"下架"，而不是"替他改写"。这也是两个请求形状分开的原因之一（`AdminPostUpdateRequest` 的类注释）。

**Q11：`operatorId` 传进 `administrate` 干什么？**
只用于那行 `log.info`。权限在接口层判过了，Service 不再判——`PostService` 的类注释写的是"这里不放鉴权"，理由是将来多一个调用入口就会绕过鉴权，而这种遗漏不会报错。
