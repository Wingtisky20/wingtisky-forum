# 链路讲解 · 帖子详情多级缓存

> 对着 M3（分支 `feature/m3-cache`）的真实代码讲一遍：一次 `GET /api/posts/{id}`
> 从进入接口到把详情返回，中间经过哪几层、哪一层在什么时候被跳过。
> 只讲代码实际怎么走；设计上的"为什么"指向设计稿与 ADR，不在这里复述第二遍。
> 帖子本身的字段与列表读写见 `07-帖子读写链路.md`；详情里 `liked` / `collected`
> 的含义见 `10-点赞与收藏链路.md`。本文只讲 M3 新加的那一段：两级缓存与浏览数计数器。

---

## 一句话

M3 之前，一次详情要查三次库（帖子、作者、标签）再写一次库（浏览数 +1）；
现在**公共内容由两级缓存供给、浏览数由 Redis 计数器供给，读路径上一次数据库写都没有了**。

缓存只装"公共内容"：`viewCount` 和 `liked` / `collected` 刻意**不在**里面——
前一个每次读都在变（进缓存就永远是脏的），后两个因人而异（塞进公共缓存，
下一个命中缓存的用户就会看到你点过的赞）。回源函数只回答"**这条帖子在不在**"，
不回答"**你能不能看**"；可见性判定单独一步，**命中缓存也要重做**，
而且必须排在浏览数自增的**前面**。写路径那一半是"先更新库、再删缓存"，
而删的时机**排在事务提交之后**。

代价放在明处：浏览数变成**最终一致**（Redis 重启会丢最近一段增量），
内容最多脏一个 L1 的存活时间（失效广播丢消息时的兜底）。

## 数据怎么走

### 读：`GET /api/posts/{id}`

```
PostController.detail(id, viewerId)
      │  viewerId 来自 @AuthenticationPrincipal —— 匿名访问时是 null
      │  "你是不是版主"在这里现算（CurrentUser.hasAnyRole），Service 不读安全上下文
      ▼
PostService.getDetail(id, viewerId, viewerIsModerator)
      │
      ├─ ① postDetailCache.get(id, () -> loadForCache(id))
      │        │   总开关关掉 → 直接执行回源、一个 Redis key 都不碰
      │        ▼
      │     TwoLevelCache.get(key, CachedPostDetail.class, policy, loader)
      │        ① L1：本进程 Caffeine，命中即返回（最快的一档）
      │        ② L2：Redis，命中 → 回填 L1 → 返回
      │           命中的是"墓碑" → 直接返回 null（防穿透）
      │        ③ 都没有 → 抢 Redisson 锁（锁键由缓存键推导出来）
      │        ④ 抢到锁 → double-check 再查一次 L2 → 仍没有才回源，回填两层
      │        ⑤ 没抢到 → 分小段轮询 L2 等一会儿（最多 lockWait = 500ms）
      │        ⑥ 等不到 → 降级直接回源（宁可多查一次库，也不能把请求卡死）
      │
      ├─ ② 可见性：post == null || !visibleTo(post, viewerId, viewerIsModerator)
      │        不通过 → 抛 A0201 帖子不存在
      │        （已删、已下架且你没资格看，对外一律"不存在"——用 403 等于
      │          告诉对方"这个 id 是存在的"）
      │
      ├─ ③ postViewCounter.increment(id, () -> postMapper.selectViewCount(id))
      │        Redis 里 EXISTS？→ Lua 里 SADD 脏集合 + INCR，一次库都不查
      │        不存在 → 才执行第二个参数，去库里取一个基准值，
      │                 Lua 里"播种 + 自增"一步完成
      │
      └─ ④ interactionService.liked(id, viewerId) / collected(id, viewerId)
               未登录 → 直接 false 且不查库；登录了才在唯一索引上各查一次
                    ▼
            PostDetail.from(post, viewCount, liked, collected)
```

### 写：任何会改动缓存内容的操作

```
写操作（改帖 / 删帖 / 后台治理 / 点赞 / 取消赞 / 收藏 / 取消收藏 / 发评论 / 删评论）
      │  都在 @Transactional 里
      ├─ 更新 MySQL
      └─ postDetailCache.evictAfterCommit(id)
             ├─ 有事务同步在跑 → 登记一个 afterCommit 回调，**提交之后**才删
             └─ 没有事务在跑 → 立刻删
                    ▼
             evict：删本机 L1 → DEL 掉 L2 → 广播 wt:cache:evict
                    ▼
             别的节点收到广播 → 清它自己进程里的 L1（自己发的消息跳过）
```

### 回写：浏览数定时落库

```
@Scheduled(fixedDelay = wt.cache.view-count.flush-interval，默认 30s)
PostViewCounter.flushToDatabase()
      └─ 读脏集合 wt:cache:post:view:dirty
           对每个 id：取值 → UPDATE t_post SET view_count = <绝对值> → 从脏集合移除
           顺序不能反：先移除再写库，失败一次这条帖子的浏览数就永远停在旧值上
```

## 逐段讲代码

### 1. 回源的 SQL 带着 `deleted = 0`

`PostMapper.xml` 的 `selectById`：

```xml
<select id="selectById" resultType="com.wingtisky.forum.forum.content.entity.Post">
    SELECT id, author_id, title, content, summary, status, top_flag, featured_flag,
           view_count, like_count, comment_count, collect_count, create_time, update_time
    FROM t_post
    WHERE id = #{id} AND deleted = 0
</select>
```

两个细节：它**带 `content`**（详情页要正文，这一点与列表查询正好相反，见
`07-帖子读写链路.md`）；`deleted = 0` 是本项目的逻辑删除过滤条件——
所谓"删除"是把 `deleted` 置 1，行还在。所以回源函数拿到的 `null` 里，
**"没发过"和"已被作者删除"是同一件事**，对外都表现为帖子不存在。

### 2. 缓存对象是 `PostDetail` 的真子集

`CachedPostDetail` 是缓存里存的东西，形状上它是 `PostDetail` 去掉三个字段之后的样子
（另外多了一个 `visible`，那是判定用的、不是展示用的）。

切法只有一句判据（设计稿 §2.1）：

> 这个值会不会因为一次**读**而改变？<br>
> 会 → 不能进缓存，得走计数器。不会 → 能进缓存，由**写**负责删。

按这句话，`PostDetail` 的 17 个字段分成四堆：

| 哪一堆 | 字段 | 去哪 |
|---|---|---|
| 几乎不变 | 标题、正文、作者、标签、置顶 / 加精、创建与更新时间 | **进缓存**（只有编辑与治理会动） |
| 变得比较多 | `likeCount` / `collectCount` / `commentCount` / `offline` | **也进缓存**（点赞评论会动，但仍远低于读的频率） |
| 每次读都在变 | `viewCount` | **不进**，走 Redis 计数器 |
| 因人而异 | `liked` / `collected` | **不进**，每次现查 |

`CachedPostDetail` 是个 `record`（`record` 天生不可变），紧凑构造器里对唯一的可变字段做了拷贝：

```java
public CachedPostDetail {
    tags = tags == null ? List.of() : List.copyOf(tags);
}
```

为什么必须拷：L1 里存的是**对象引用**而不是副本。不拷的话，"从缓存取出来的对象"
和"缓存里存着的对象"是同一个，调用方一改它就跟着变——而且**没有任何代码删过这个 key**，
日志里也查不出来（设计稿 §7）。

### 3. 回源函数只回答"在不在"，不回答"你能不能看"

```java
private CachedPostDetail loadForCache(Long id) {
    Post post = postMapper.selectById(id);
    if (post == null) {
        return null;   // 真的不存在 → 缓存会写下一枚短命的墓碑
    }
    UserBrief author = userQueryService.findBrief(post.getAuthorId()).orElse(null);
    return CachedPostDetail.from(post, author, tagService.listByPost(id));
}
```

注意它**不看 `viewerId`、也不看 `status`**：一篇被版主下架的帖子，照样进缓存。

按可见性返回 `null` 的话有两个后果，性质完全不同（设计稿 §3.1；执行记录里有实测）：

- **会被当场发现的**：被下架的帖子对**作者本人**也变成 404。而 M2 明确定过
  "作者与版主仍能打开"——帖子从作者眼前突然消失、没有任何提示，他只会以为是 bug。
- **不会被发现的**：缓存里存下的就成了"**某个人的权限判定结果**"。换个人命中同一个 key，
  读到的就是**别人**的可见性结论——这是一条静默的越权，不报错，日志里也查不出，
  只会在很久以后以"数据莫名其妙不对"的形式出现。

所以判定留给下一步。那一步是纯内存判断，比再查一次库便宜得多。

### 4. 可见性判定：命中缓存也要重做，且排在浏览数前面

```java
public PostDetail getDetail(Long id, Long viewerId, boolean viewerIsModerator) {
    CachedPostDetail post = postDetailCache.get(id, () -> loadForCache(id));

    if (post == null || !visibleTo(post, viewerId, viewerIsModerator)) {
        throw new BizException(ErrorCode.POST_NOT_FOUND);
    }

    int viewCount = (int) postViewCounter.increment(id, () -> postMapper.selectViewCount(id));

    return PostDetail.from(post, viewCount,
            interactionService.liked(id, viewerId),
            interactionService.collected(id, viewerId));
}
```

```java
private static boolean visibleTo(CachedPostDetail post, Long viewerId, boolean viewerIsModerator) {
    if (post.visible()) {
        return true;
    }
    if (viewerId == null) {
        return false;
    }
    return viewerId.equals(post.authorId()) || viewerIsModerator;
}
```

两点：

- **判定收的是缓存对象，不是数据库实体**。所以 `CachedPostDetail` 里必须带着
  `visible`（未被下架、未被删除）和 `authorId`——判定所需的输入都在缓存里，
  命中缓存时一样能判。**缓存的是数据，不是权限判定的结果。**
- **它排在浏览数自增之前**。反过来写的话，一篇你根本看不见的帖子（匿名读已下架的）
  也会被计入浏览数——看不见的东西不该被计数。顺序换了不会报错，只是数字悄悄变脏。

`viewerIsModerator` 由**接口层**算好传进来（那里才知道当前用户有什么角色）。
Service 不去读安全上下文，"谁有资格"是接口层的问题。

### 5. `TwoLevelCache.get` 的六步

上面第 ① 步调到的就是它。这是一个泛型方法，**不知道缓存的是什么业务对象**——
缓存"什么、存多久"，由调用方通过 `CachePolicy` 和一个回源函数传进来。

```java
public <V> V get(String key, Class<V> type, CachePolicy policy, Supplier<V> loader) {
    // ① L1：进程内，最快的一档
    Object local = localCache.get(key);
    if (local != null) {
        return local == NULL_HOLDER ? null : type.cast(local);
    }

    // ② L2：Redis
    L2Hit<V> hit = readL2(key, type, policy);
    if (hit != null) {
        return hit.value();
    }

    // ③ 要回源了。先抢锁——这一步就是防击穿
    RLock lock = redisson.getLock(RedisKey.cacheLock(key));
    if (tryLock(lock, key, policy)) {
        try {
            // ④ double-check：这一步不能省
            L2Hit<V> again = readL2(key, type, policy);
            if (again != null) {
                return again.value();
            }
            return loadAndFill(key, policy, loader);
        } finally {
            unlock(lock, key);
        }
    }

    // ⑤ 没抢到锁：等一会儿，看拿到锁的那个人有没有把值写进去
    L2Hit<V> waited = waitForL2(key, type, policy);
    if (waited != null) {
        return waited.value();
    }

    // ⑥ 等不到就降级回源
    return loadAndFill(key, policy, loader);
}
```

每一步都在解决一个具体的坏情况：

| 步 | 解决什么 | 少了它会怎样 |
|---|---|---|
| ① L1 | 进程内那一份最快 | 每次都走一次 Redis 网络往返 |
| ② L2 | 跨进程共享一份 | 每个进程各回源一次 |
| ③ 锁 | **击穿**：热点 key 刚过期的一瞬间，并发请求同时发现"缓存没了"，一起冲到数据库上 | 缓存在最需要它的时候反而失效 |
| ④ double-check | 在你等锁的这段时间里，前一个拿到锁的线程**很可能已经把值写进去了** | 所有排队的请求依次各回源一次，锁等于白加 |
| ⑤ 轮询等待 | 没抢到锁的人不必立刻回源，先等等看 | 等锁的人直接压到数据库上 |
| ⑥ 降级回源 | 一次偶发的锁竞争不该变成用户可见的故障 | 锁竞争一发生就是一次报错 |

**回源返回 `null` 时会写一枚"墓碑"**，这一步是防穿透：

```java
V loaded = loader.get();
if (loaded == null) {
    redis.opsForValue().set(key, NULL_SENTINEL, policy.nullTtl());
    putL1(key, NULL_HOLDER, policy.nullTtl());
} else {
    redis.opsForValue().set(key, serialize(loaded), policy.nextL2Ttl());
    putL1(key, loaded, policy.l1Ttl());
}
```

Redis 里"这个 key 不存在"（`GET` 返回空）和"这个 key 的值是空"是两件事，
`NULL_SENTINEL`（字符串 `"__NULL__"`）把"确实不存在"变成一个**看得见**的值——
选它而不是包装类，是因为在 RedisInsight 里一眼能认出来。

墓碑的存活时间由 `nullTtl`（60 秒）单独给，比正常的 L2 短得多：正常的 5 分钟是
"值不太会变，可以放久一点"，而墓碑是"这个 id 现在没有，但它**随时可能被创建**"
——墓碑留久了，新发的帖子会被当成不存在。

**写 L2 用的是 `policy.nextL2Ttl()` 而不是 `policy.l2Ttl()`**，前者是
"基准 5 分钟 + 一个 `[0, 60s]` 的随机量"（防雪崩）。不加抖动的话，
同一批写进去的 key 会同时过期，那一刻所有请求一起回源。

### 6. 浏览数：Redis 里数，定时回写库

M2 的详情是"读接口里带写"——每看一次就 `UPDATE t_post SET view_count = view_count + 1`。
浏览数恰好是全站最频繁的写，流量一上来只会越来越慢。现在改成 Redis 里放一个
**绝对值**计数器，读的时候自增并返回，每 30 秒把脏的那些回写进库。

```java
private static final RedisScript<Long> SEED_AND_INCR = script("""
        if redis.call('EXISTS', KEYS[1]) == 0 then
            redis.call('SET', KEYS[1], ARGV[2])
        end
        redis.call('SADD', KEYS[2], ARGV[1])
        return redis.call('INCR', KEYS[1])
        """);
```

三件事值得说：

- **Lua 是为了原子**。"不存在就先播种、然后自增"这两步分开调的话，
  两个并发请求会各自播种一次（都以为键不存在），其中一次的播种会把另一次的增量
  覆盖掉——而"浏览数少了几次"没人查得出来。
- **第二个参数是惰性的**（`Supplier<Integer>` 而不是直接传一个 `int`）：
  只有计数器不存在时才被执行，去库里取一个基准值。正常路径（计数器在）
  **一次库都不查**——传值的话每次读详情都会白查一次，"搬去 Redis"就白搬了。
- **它是最终一致**，而且是有意接受的。Redis 重启会丢最近一段增量；
  两次回写之间库里的值是旧的。`docs/03-design/architecture.md` §2.1 明写这个域的
  一致性要求是"最终一致可接受（浏览数、热度）"。这条要如实说，不能假装它精确。

回写的顺序是"取值 → 写库 → 从脏集合移除"：

```java
postMapper.updateViewCount(postId, Integer.parseInt(value));
redis.opsForSet().remove(RedisKey.postViewDirtySet(), rawId);
```

反过来的话（先移除再写库），失败一次这条帖子的浏览数就**永远停在旧值上**了，
除非它再被看一次。回写本身是**幂等**的——SQL 写成绝对值
`SET view_count = #{viewCount}` 而不是 `+ 1`，重复执行结果一样。
这也是 Redis 里存绝对值而不是增量的理由。

### 7. 失效清单：9 处调用点，都在事务提交之后

`PostDetailCache.evictAfterCommit` 在业务代码里有 9 个调用点。它们不是分头拍的，
而是照同一条规则挑出来的（设计稿 §3.3）：

> **凡是能改变 `CachedPostDetail` 里任何一个字段的写操作，都必须删这个 key。**

| 写操作 | 为什么它要删 |
|---|---|
| `PostService.update` | 改了标题 / 正文 / 标签，三样都在缓存对象里 |
| `PostService.delete` | 逻辑删除，`deleted` 变了 → 可见性变了 |
| `PostService.administrate` | 置顶 / 加精 / 下架——`top`、`featured`、`offline` 都在缓存对象里 |
| `InteractionService.like` / `unlike` | `likeCount` 在缓存对象里 |
| `InteractionService.collect` / `uncollect` | `collectCount` 在缓存对象里 |
| `CommentService.create` / `delete` | `commentCount` 在缓存对象里 |

**注意点赞那一侧删在 `if` 里面**：

```java
@Transactional
public void like(Long postId, Long userId) {
    requirePostExists(postId);
    if (postLikeMapper.insertIgnore(userId, postId) > 0) {
        postMapper.addLikeCount(postId, 1);
        postDetailCache.evictAfterCommit(postId);
    }
}
```

计数没动，缓存里那份就还是对的；删了反而让下一次读白回源一次。
顺带拿到一个好处——**连点 3 次赞只删 1 次缓存**。`unlike` / `collect` / `uncollect`
是对称的写法。

**删的时机排在提交之后**，这是整条写路径上最容易写错的一处：

```java
public void evictAfterCommit(String key) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                evict(key);
            }
        });
    } else {
        evict(key);
    }
}
```

为什么必须等提交：失效只能排在"库里已经是新值"之后。在事务体里直接删的话，
"缓存被删"这个事实会**先于**"库被改"对外可见——中间那道窗口里进来的并发读
会发现缓存空了、于是回源，而它读到的仍是**还没提交的旧值**，转头就把旧值写回了缓存。
结果是缓存一直脏着，直到 TTL 到期。

换句话说，**在事务里删，等于把顺序做成了「先删缓存、再更新库」**——那正是设计稿 §4
否决掉的方案，而且它看起来跟正确写法只差一行，**不会报错**。

两个边界：**回滚时不删**（库里的值根本没变过，缓存本来就不脏；删了只是白让下一次读
多回源一次）；**不在事务里时立刻删**（这个方法不是"只对事务生效"，而是"**尽量**排到
提交后"——没有事务同步在跑时，等一个永远不会到来的提交就等于永远不删）。

### 8. 为什么 L1 的存活时间比 L2 短得多

`application.yml` 里这两档差一个数量级：

```yaml
l1-ttl: 45s            # 进程内那份。**必须短**：广播丢消息时靠它兜底
l2-ttl: 5m             # Redis 里那份的基准值
```

跨节点失效靠 Redis 的发布订阅广播，而发布订阅**不可靠**——订阅者掉线期间的消息直接丢，
没有任何重发机制。所以 L1 的过期时间本身就是兜底：即使那条"该失效了"的消息丢了，
脏数据最多活一个 `l1Ttl`。把它设成和 L2 一样长，这个兜底就等于没有。

还有一个配套的选择：`LocalCache` 里**读不续期**。

```java
@Override
public long expireAfterRead(String key, Object value,
                            long currentTime, long currentDuration) {
    return currentDuration;
}
```

访问频繁的 key 一直不回源看起来很划算，但那样它永远不会去拿新数据，
等于把缓存变成了事实上的权威副本。跨节点失效本来就不太可靠，再叠一个"读就续期"，
脏数据就可能永远留在那里。

### 9. `liked` / `collected` 为什么不进缓存

它们是"**这个人**点过赞没有"，因人而异。塞进公共缓存的话，下一个命中缓存的用户
会看到**别人**点过的赞——缓存串号就是越权。所以每次现查，而且和 M2 一样，
未登录时连查都不查：

```java
public boolean liked(Long postId, Long userId) {
    return userId != null && postLikeMapper.exists(userId, postId) > 0;
}
```

代价是详情命中缓存时仍有 2 次很轻的索引查询（在联合主键上查"有没有这一行"）；
未登录时一次都不查。另一种做法（整条详情都缓存、key 带上浏览者 id）的代价见
设计稿 §2.2：命中率会难看到没法交差，而且一次点赞要失效"所有人"的缓存——
失效只能按 key 删，你删不完。

## 走一遍场景

**场景一：这篇帖子谁都没读过（冷缓存）**

1. `GET /api/posts/7`。`postDetailCache.get(7, ...)` 进去，L1 没有、L2 也没有。
2. 抢 Redisson 锁（键是 `wt:lock:cache:post:detail:7`，由缓存键推导出来，
   不另起一套命名）。抢到 → double-check 再查一次 L2，还是没有 → 执行回源函数。
3. `loadForCache(7)`：`selectById(7)` 拿到帖子（没删）、`findBrief` 拿作者、
   `listByPost` 拿标签，组装成 `CachedPostDetail`。
4. 写回两层：L2 里放一份 JSON（TTL = 5 分钟 + 随机抖动），L1 里放一份（TTL 45 秒）。
5. 可见性判定 → 正常帖子直接过。
6. 浏览数计数器：Redis 里没有这个 key，于是执行第二个参数去库里取基准值（比如 3），
   Lua 里播种 + 自增，返回 4。
7. 查 `liked` / `collected`（未登录就都是 false，且不查库），组装 `PostDetail` 返回。
   响应里 `viewCount: 4`，而库里还是 3——**这个差是正常的**，要等 30 秒后回写才补上。

**场景二：紧接着另一个人读同一篇（命中）**

1. 同一个进程：L1 直接命中，返回缓存对象。**一次 Redis、一次数据库都没有**。
2. 另一个进程（M9 拆服务之后）：L1 没有、L2 命中，回填自己的 L1，同样不查库。
3. 但**可见性判定照做，浏览数计数器照走**（SADD 脏集合 + INCR），
   `liked` / `collected` 照查。读路径上唯一会写的东西就是那个计数器和脏集合，
   **数据库一次写都没有**。

**场景三：作者改标题**

1. `PATCH /api/posts/7`（`@PreAuthorize("@postAuthz.isOwner(#id)")`）。
2. `PostService.update` 在事务里改库，然后调 `postDetailCache.evictAfterCommit(7)`
   ——**此刻还没删**，只是登记了一个回调。
3. 事务提交，回调触发：删本机 L1 → `DEL` 掉 L2 → 广播 `wt:cache:evict`。
4. 下一次读 → 缓存空了 → 回源拿到新标题。

如果第 2 步是直接 `evict(7)`（不等提交）：删完之后、提交之前的那一小段里，
并发读会发现缓存空了、回源读到**还没提交的旧值**并写回缓存，
于是缓存一直脏到 TTL 到期。这条窗口**不会报错**，日志里也看不出来。

**场景四：版主下架一篇"已经在缓存里"的帖子**

1. 版主调治理接口 → `administrate` 改 `status` → `evictAfterCommit` → 缓存被删。
2. 作者读 → 200，`offline: true`（他要能看懂"我那篇去哪了"）。
   这一步把"已下架"的版本重新装进了缓存。
3. 匿名读同一帖 → 缓存**命中**（里面躺着的正是已下架的帖子），
   但第 ② 步的可见性判定重做：`visible` 是 false，`viewerId` 是 null → 抛 A0201 → **404**。
4. 这条是设计 §9.3 六条反面对照里唯一没有反面的一条——它是**安全性断言**，
   只有"必须成立"这一种结果：缓存不能绕过鉴权。

**场景五：同一篇被反复读，看库里什么时候才动**

1. 连读 5 次 → Redis 计数器的值一直涨（比如 4 → 9），
   **其间 `t_post.view_count` 一动不动**。
2. 等一次回写（默认 30 秒）→ 脏集合里那条被取出来，
   `UPDATE t_post SET view_count = 9`，然后才从脏集合移除。
3. 如果回写中途失败：那条 id **还留在脏集合里**，下一次定时任务会重试。
   这就是"先写库、后移除"这个顺序换来的东西。

## 面试会追问

**Q：缓存里到底存了什么、没存什么？**
存的是公共内容（标题、正文、作者、标签、置顶 / 加精、三个计数、创建与更新时间，
外加一个判定用的 `visible`）。没存两样：`viewCount` 和 `liked` / `collected`。
判据是"这个值会不会因为一次读而改变"，见设计稿 §2.1。

**Q：`viewCount` 为什么不能进缓存？**
它被**这一次读**改变——放进缓存的话，缓存从被存进去那一刻起就是脏的。
所以它走 Redis 计数器，每次读各自自增，根本不入缓存。`CachedPostDetail` 里
刻意没有这个字段（该类的注释写了这条）。

**Q：`liked` / `collected` 为什么不进缓存？**
它们回答的是"**你**点过没"，因人而异。塞进公共缓存就是缓存串号：
下一个人命中同一个 key，看到的是你点过的赞——这是越权，不是命中率问题。
而改成"key 带 userId"的话，100 个人看同一帖就是 100 份缓存，命中率没法看，
一次点赞还要失效所有人的缓存（失效只能按 key 删，删不完）。见设计稿 §2.2。

**Q：缓存没命中时，回源函数会不会判断"这个人能不能看"？**
不会，而且这是刻意的。`loadForCache` 只回答"这条帖子在不在"——它不看 `viewerId`、
也不看 `status`，**已下架的帖子照样进缓存**。可见性判定留给 `getDetail` 的下一步。
按可见性返回 `null` 的话，被下架的帖子会对作者本人也变成 404（M2 定过
"作者与版主仍能打开"）；更麻烦的是缓存里会存下"某个人的权限判定结果"，
换个人命中同一个 key 就读到别人的结论——一条不报错的越权。

**Q：命中缓存了还要不要做鉴权判定？**
要。缓存的是**数据**，不是**权限判定的结果**。判定所需的 `visible` 和 `authorId`
都在缓存对象里，所以命中时一样能判，而且是纯内存判断。
少了这一步，一篇被下架、又被缓存的帖子，匿名用户就能读到正文。

**Q：可见性判定为什么要排在浏览数自增的前面？**
因为**看不见的东西不该被计数**。顺序反过来的话，匿名读一篇已下架的帖子会先给
计数器 +1 再被判 404，浏览数就悄悄变脏了——不会报错，只是数字不对。

**Q：100 个并发请求同一篇冷缓存，会回源几次？为什么？**
1 次。抢到锁的那个去回源，其余的人没抢到锁 → 分小段轮询 L2，等它把值写进去就返回。
**锁内的 double-check 是这条能成立的关键**：不重查 L2 的话，所有排队的请求会
依次各回源一次，锁等于白加。实测的正面 / 反面读数和实验条件见
`docs/04-log/04-M3-多级缓存.md` 与 `docs/superpowers/plans/2026-10-06-m3-cache.md`。

**Q：抢锁失败之后会不会一直等？**
不会。等 `lockWait`（默认 500ms）就**降级直接回源**——宁可多查一次库，
也不能把请求卡死。若改成抛错或返回空，一次偶发的锁竞争就会变成用户可见的故障。

**Q：为什么会有"墓碑"这个东西？**
防穿透。缓存里"没有这个 key"和"这个 key 的值是空"必须分得开，分不开的话
每次查一个不存在的 id 都会回源，缓存对这类攻击完全无效。回源返回 `null` 时
往 Redis 写一个显式的哨兵字符串 `"__NULL__"`，并给它一个**短**的 TTL（60 秒）
——正常的 5 分钟是"值不太会变"，而墓碑是"这个 id 随时可能被创建"，
留久了新发的帖子会被当成不存在。

**Q：为什么会"雪崩"，怎么防？**
同一批 key 一起写进去、又一起过期，那一刻所有请求一起回源。防法是写 L2 时
**加一个 `[0, 60s]` 的随机量**（`CachePolicy.nextL2Ttl()`），让到期时刻散开。

**Q：浏览数为什么存的是"绝对值"而不是"增量"？**
回写因此是**幂等**的——重复写同一个值，结果一样。增量方案下，
"写进去了但没来得及标记完成"会在重试时又加一遍；而浏览数是只增不减的，
加错了没人会发现。

**Q：那个"播种 + 自增"为什么要写成 Lua？**
"不存在就先播种、然后自增"这两步必须原子。分成两次调用的话，两个并发请求会
各自播种一次（都以为键不存在），其中一次的播种把另一次的增量覆盖掉——
浏览数少了几次，没人查得出来。另外 `StringRedisTemplate` 发 Lua 是常规用法，
不需要额外配置。（M3 引入的 Redisson 与它在连接上的实际关系，见设计稿 §5 的实测更正。）

**Q：读一次详情，会查几次数据库？**
正常路径（缓存命中 + 未登录）**一次都不查**。登录了会多 2 次很轻的索引查询
（`liked` / `collected`）。计数器不存在时（Redis 冷启动、键过期、这篇第一次被看）
才会多一次单列查询取基准值。**数据库写是一次都没有的**——这正是 M3 的收益。

**Q：浏览数准不准？**
**最终一致，不保证精确**。Redis 重启会丢最近一段增量，两次回写之间库里是旧值。
这个域的一致性口径见 `docs/03-design/architecture.md` §2.1，设计稿 §2.3 也把
这条代价写在明处。交付说明里要如实讲，不能假装它精确。

**Q：写完之后为什么要"提交之后"才删缓存，而不是在事务里直接删？**
在事务里删等于把顺序做成了"先删缓存、再更新库"：删完之后、提交之前进来的并发读
会发现缓存空了，回源读到**还没提交的旧值**并把它写回缓存，于是缓存一直脏到 TTL 到期。
这个错**不会报错**，而且和正确写法只差一行。反过来，"先更新库再删缓存"也有它自己的
窗口，但那个窗口极窄，下一次写会纠正它——被否决的四个方案见设计稿 §4。

**Q：事务回滚了，缓存会被删掉吗？**
不会。库里的值根本没变过，缓存本来就不脏；删了不出错，只是白让下一次读多回源一次。

**Q：那如果这个写操作根本不在事务里呢？**
立刻删。`evictAfterCommit` 不是"只对事务生效"，而是"**尽量**排到提交后"——
没有事务同步在跑时（比如定时任务、测试直接调用），等一个永远不会到来的提交
就等于永远不删。宁可少一层保护，也不能让缓存永远不失效。

**Q：为什么"连点 3 次赞只删 1 次缓存"？**
因为删除调用写在 `if (insertIgnore(...) > 0)` 里面。第二次、第三次点赞时插入被忽略、
计数没动，缓存里那份就还是对的，没必要删。见 `InteractionService.like` 与设计稿 §3.3。

**Q：哪些写操作要删缓存？漏一个会怎样？**
看设计稿 §3.3 那张表（本文第 7 段照抄了它的目录）。漏掉任何一个都不会报错，
只会表现为"详情页显示旧内容"——比如漏了评论，页眉的评论数一直是旧的，
看着像统计坏了。

**Q：`TagService` 为什么不在失效清单里？**
M2 的标签只有"新增 / 关联"，没有改名或合并，`listByPost` 是只读的。
将来若加了"标签改名"，这张表就要加一行（设计稿 §3.3 专门记了这条，
因为"标签名变了但缓存没删"是典型的静默错误）。

**Q：为什么 L1 只活 45 秒，L2 活 5 分钟？**
L1 的失效靠 Redis 发布订阅广播，而发布订阅不可靠（订阅者掉线期间的消息直接丢）。
L1 的过期时间本身就是兜底：消息丢了，脏数据最多活一个 L1 TTL。
设成和 L2 一样长，这个兜底就等于没有。两档数字都在 `application.yml` 的 `wt.cache` 段。

**Q：为什么 L1 读的时候不续期？**
访问频繁的 key 一直不回源看起来很划算，但那样它永远不会去拿新数据，
等于把缓存变成了事实上的权威副本。跨节点失效本来就不太可靠，
再叠一个"读就续期"，脏数据就可能永远留在那里（`LocalCache` 的注释）。

**Q：只清 L2 的 key，为什么还是读到旧值？**
因为 **L1 还在供数**。删 L2 只影响进程外那一份，进程内那份要等它自己过期（45 秒）。
这不是 bug，而且顺带证明了"两级缓存确实在各自工作"——
执行记录「踩过的坑」第 2 条有实测。

**Q：这套缓存怎么验证的？**
两条闸门（spec §6.2）：命中率 / 延迟对比（同一份代码，缓存开 / 关两组，
只差一个总开关）和**100 并发仅 1 次回源**（含反面对照）。读数、实验条件，
以及"P99 反而比对照组慢"这条如实记录，都在 `docs/04-log/04-M3-多级缓存.md`
与 `docs/STATUS.md` 的 M3 两节里。这套集成测试要连真实的 MySQL 与 Redis，
**不在 CI 上跑**（ADR-0007），中间件也是本机装的（ADR-0004）。

**Q：为什么用这么薄的抽象，不上 `@Cacheable`？**
`@Cacheable` 把"什么时候删、删哪个 key"藏进注解里，而这个亮点恰恰靠
**把失效规则显式写出来**（设计稿 §3.3 那张清单就是交付物）。用注解等于把这个亮点删掉。
见设计稿 §1「不做什么」与 §6.3。
