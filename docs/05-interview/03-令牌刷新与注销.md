# 链路讲解 · 令牌刷新与注销

> 本文讲一条链路：**登录发出去的令牌，怎么续期、怎么撤销。**
> 代码在 `forum/forum-user` 模块，涉及 `AuthService`、`JwtTokenProvider`、
> `RefreshTokenStore` 三个类和一个 Redis Key。
> 设计的取舍不在这里复述——它们在 ADR 里，本文只把「代码实际怎么走」讲清。

---

## 一句话

访问令牌是一张**签出去就收不回来的**通行证，所以它**命很短**（30 分钟）；
真正能被撤销的是刷新令牌——它只在 Redis 里存了一个 `jti`，注销时 `DEL` 掉这个 Key，
用户就拿不到新令牌了，但手里那张访问令牌**最多再活 30 分钟**。这个窗口是明确接受的代价
（见 ADR-0013 §理由）。

---

## 数据怎么走

两个令牌完全是两种东西，先分清：

| | 访问令牌 access | 刷新令牌 refresh |
|---|---|---|
| 谁签的 | `JwtTokenProvider.issueAccessToken` | `JwtTokenProvider.issueRefreshToken` |
| 载荷里有什么 | `sub`(userId) / `username` / `roles` / `jti` | `sub`(userId) / `jti`（**不放角色**） |
| 有效期 | 30 分钟 | 7 天 |
| 服务端存不存 | **不存**，纯验签 | **存**，Redis 里一个 Key |
| 撤销 | 做不到 | `DEL` 即撤销 |

Redis 里的那条记录长这样：

```
key   = wt:auth:refresh:{userId}      ← RedisKey.refreshToken(userId)
value = 该用户当前有效的刷新令牌的 jti  ← 只存 jti，不存令牌串
ttl   = 7 天                          ← 跟刷新令牌同期
```

**注意 key 是按 `userId` 存的，不是按令牌本身。** 所以「一个用户同一时刻只有一张有效的刷新令牌」——
重复登录、刷新轮换，都是把同一个 Key 的值覆盖掉。

```
登录    ──> SET wt:auth:refresh:42 = jti-A  (ttl 7d)      发 access-A + refresh-A
刷新    ──> SET wt:auth:refresh:42 = jti-B  (ttl 7d)      发 access-B + refresh-B
            （值从 A 变成 B，jti-A 当场作废 —— 这就是轮换）
注销    ──> DEL wt:auth:refresh:42
            （拿不到新的了；但 access-B 本身还能用，直到它自己过期）
```

---

## 逐段讲代码

### 签发：`AuthService.issueTokens`

登录和刷新最后都汇到这个私有方法，两条路的令牌是同一套签发逻辑：

```java
private LoginResult issueTokens(User user, List<String> roles) {
    IssuedToken access = tokenProvider.issueAccessToken(user.getId(), user.getUsername(), roles);
    IssuedToken refresh = tokenProvider.issueRefreshToken(user.getId());
    refreshTokenStore.save(user.getId(), refresh.jti());

    return new LoginResult(
            access.token(), refresh.token(),
            access.expiresInSeconds(), refresh.expiresInSeconds());
}
```

关键在第三行：**签刷新令牌的同时，把它的 `jti` 写进 Redis**。
访问令牌签完就撒手（没有任何存储动作），刷新令牌签完必须落一条记录——
这是「可撤销」这三个字的全部来源。

### 撤销的记录：`RefreshTokenStore`

整个认证里唯一有状态的地方，三个方法都很短：

```java
public void save(Long userId, String jti) {
    redis.opsForValue().set(RedisKey.refreshToken(userId), jti, ttl);
}
```

```java
public boolean isCurrent(Long userId, String jti) {
    return Objects.equals(jti, redis.opsForValue().get(RedisKey.refreshToken(userId)));
}
```

```java
public void remove(Long userId) {
    redis.delete(RedisKey.refreshToken(userId));
}
```

- `save` 用 `set` 而不是 `setIfAbsent`——**后写的覆盖先写的**，这正好就是「轮换」和「后登录的顶掉先登录的」。
- `isCurrent` 是**比对**，不是「存在即有效」。这个区别不是洁癖：如果只判存在，
  用户注销后重新登录，**注销前泄露出去的那张刷新令牌仍然能被判为有效**，因为它对应的 `jti` 曾经存过。
- `remove` 就是 `DEL` 一个确定的 Key，不需要先查出令牌内容。

Key 的拼法在 `wt-infra` 的 `RedisKey`（机制层，只管 key 长什么样，不管活多久）：

```java
public static String refreshToken(Long userId) {
    return PREFIX + "auth:refresh:" + userId;
}
```

`PREFIX` 是 `"wt:"`，最终就是 `wt:auth:refresh:{userId}`。

### 换新的：`AuthService.refresh`

```java
public LoginResult refresh(String refreshToken) {
    Claims claims = parseRefreshToken(refreshToken);

    Long userId;
    try {
        userId = Long.valueOf(claims.getSubject());
    } catch (NumberFormatException e) {
        throw new BizException(ErrorCode.UNAUTHORIZED);
    }

    if (!refreshTokenStore.isCurrent(userId, claims.getId())) {
        log.debug("刷新令牌已失效: userId={}", userId);
        throw new BizException(ErrorCode.UNAUTHORIZED);
    }

    User user = userService.getById(userId);
    if (!user.isActive()) {
        refreshTokenStore.remove(userId);
        throw new BizException(ErrorCode.ACCOUNT_DISABLED);
    }

    List<String> roles = userService.getRoleCodes(userId);
    return issueTokens(user, roles);
}
```

四步，每步都有它的用意：

1. **`parseRefreshToken`** 验签 + 解析，签名不对／过期／格式坏都在这里转成 `UNAUTHORIZED`
   （`parseRefreshToken` 内部吞掉 jjwt 的异常，对外只给一句「未登录或登录已过期」）。
2. **`isCurrent`** 是这条链路的**闸门**：`jti` 不是该用户当前那个，直接 401。
   注销、被轮换掉、从没发过——三种情况在这里**合并成同一个响应**，不区分。
3. **重新查库拿角色**（`getRoleCodes`），不吃旧令牌里的信息。所以改角色、封号
   能在刷新时生效，不必等 7 天。顺带 `isActive()` 判一下封禁，封了顺手 `remove`。
4. **`issueTokens`** 再走一遍签发——`save` 会用新的 `jti` 覆盖旧的，
   **这就是轮换**：换新成功的瞬间，旧刷新令牌已经作废了（见 ADR-0013 §理由）。

### 注销：`AuthService.logout`

```java
public void logout(Long userId) {
    refreshTokenStore.remove(userId);
    log.info("用户注销: userId={}", userId);
}
```

一行。`userId` 从哪来？控制器上 `@AuthenticationPrincipal Long userId`——
是 `JwtAuthenticationFilter` 把访问令牌验通后放进 `SecurityContext` 的 principal
（见 `AuthController.logout`）。**能调到这个接口，说明访问令牌当时还是有效的。**

再看过滤器怎么「验」的，就明白为什么访问令牌撤不掉：

```java
Claims claims = tokenProvider.parse(token);

Long userId = Long.valueOf(claims.getSubject());
String username = claims.get("username", String.class);
List<String> roles = rolesOf(claims);
```

```java
public Claims parse(String token) throws JwtException {
    return Jwts.parser()
            .verifyWith(signingKey)
            .build()
            .parseSignedClaims(token)
            .getPayload();
}
```

**只有验签，没有任何存储访问。** 所以一个请求能不能通过，只取决于
「签名对不对、过没过期」，与 Redis 里那条刷新令牌记录毫无关系。
注销删掉的是刷新令牌，删不到访问令牌——这不是漏写，是访问令牌**根本没有**服务端记录可删。

### 有效期从哪来：`JwtProperties` + `application.yml`

```java
private Duration accessTtl = Duration.ofMinutes(30);
private Duration refreshTtl = Duration.ofDays(7);
```

```yaml
wt:
  jwt:
    secret: ${JWT_SECRET}
    access-ttl: 30m
    refresh-ttl: 7d
```

`JwtProperties` 绑 `wt.jwt.*`。`access-ttl` 这个数是**有含义的**：
它就是「注销后旧访问令牌最多还能用多久」的那 30 分钟。

## 走一遍场景

打开 `docs/06-runbook/api-smoke.http`，第 7、8、11 条就是这条链路的对照实验。
假设用户已登录，手上是 `access-A` + `refresh-A`（Redis 里存的是 A 的 jti）：

**第 7 步 · 刷新成功，发生轮换**
带 `refresh-A` 调 `/api/auth/refresh` →
`isCurrent` 通过（Redis 里就是 A）→ 重新查角色 → `issueTokens` 发 `access-B` + `refresh-B`，
并把 Redis 的值**覆盖**成 B 的 jti。
期望 200，**且返回的 `refreshToken` 与旧的不是同一个**——这就是轮换的证据。

**第 8 步 · 拿旧刷新令牌再试**
还带 `refresh-A` 调一次 →
`isCurrent` 比对：Redis 里现在是 B，来的还是 A → **401**。
这一条是第 7 步的**反面**：同一个令牌在第 7 步能用，第 8 步就不能用了，
说明「轮换真的让旧的失效了」，而不是「刷新接口一直返回 401」。

**第 11 步 · 注销之后**
带 `access-B` 调 `/api/auth/logout` → `DEL wt:auth:refresh:42`。
之后拿 `refresh-B` 调 `/api/auth/refresh` → Redis 里什么都没了 → **401**。

> 冒烟脚本开头特意写了「顺序有依赖」，原因就在这：注销会撤销刷新令牌，
> 所以「能刷新」必须排在「注销」之前。顺序不是随意的。

**那 `access-B` 呢？** 注销之后它**仍然能通过**——因为 `JwtAuthenticationFilter`
只验签、不查 Redis。它会一直有效到 `access-ttl` 走完（最长 30 分钟）。
这就是 ADR-0013 后果里写的那条负面：注销后旧访问令牌仍有效，窗口最长 30 分钟。

## 面试会追问

**Q：注销了为什么旧 token 还能用？你是不是没做撤销？**
撤销做了，做在刷新令牌上。访问令牌是自包含的，签出去服务端就没记录了，
**没有东西可以被删**——这不是疏漏，是 JWT 的固有性质。我把「可撤销」放在了
唯一能放的刷新令牌上：注销 = 删 Redis 里的 jti = 拿不到新令牌。
代价是手上那张访问令牌最多再活 30 分钟，这是明确接受的（ADR-0013 §后果）。
要压到零，就得每个请求查一次黑名单，那拆分服务时「本地验签」的好处就没了。

**Q：为什么刷新时要把旧的作废（轮换）？**
不作废的话，一张刷新令牌 7 天里能无限次用。一旦泄露，攻击者能一直续期，
而真正的用户毫无察觉。轮换后，被偷的那张在用户**下次刷新**时就失效了——
攻击者和用户谁能先用，谁就赢，至少不是攻击者稳赢。这里 `save` 覆盖旧 `jti` 就是轮换。

**Q：`isCurrent` 为什么不写成「key 存在就算有效」？**
因为那样注销后重新登录，注销前泄露出去的那张还能用——它的 jti 曾经存在过。
必须比对「是不是当前这一个」。这也顺带把「同一用户多端登录互相顶掉」变成了
自然结果：key 按 userId 只有一个。

**Q：为什么 Redis 里存 jti 而不是整串令牌？**
令牌串等于凭据。存进 Redis 会让「Redis 泄露」直接等于「账号被盗」。
存 jti 只用来比对，泄露了也伪造不出令牌。

**Q：改了用户角色，多久生效？**
下次刷新时生效，也就是最长 30 分钟（`access-ttl`）。
因为 `refresh` 里是重新查库拿角色的，不吃旧令牌里的信息。
