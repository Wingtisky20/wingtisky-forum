# 讲解 · 前端工程与页面

> 前面 11 份讲的都是「一次 HTTP 请求在后端怎么走完」。这一份讲**界面这一侧**。
>
> 重点不是「页面长什么样」，而是**几个很容易做错、做错了又很难查的决定**：
> 开发期用代理而不开 CORS、401 要按错误码分两种含义、登录后装会话的顺序、
> 以及为什么这里没有状态管理库。
>
> 本文只讲**代码实际怎么走**。「为什么这么设计」凡是设计稿写过的不复述，只指路——
> 复述会造出第二个事实源，改了代码忘了改文档时两个源就开始打架。

---

## 一句话

前端整套工程只有三个东西：**一个 HTTP 入口**（`src/api/client.js`，所有请求都从这里出）、
**一份登录态**（`src/composables/useAuth.js` 里两个模块级 `ref`）、**4 个页面**。

而它最容易出错的三个点，全都在「边界」上——**代理与同源**的边界、**两种 401** 的边界、
**令牌先存还是先用**的边界。这三处写错的共同特征是：不会报错，只会表现成
「页面怪怪的」，而那种现象离原因很远。

---

## 一次页面访问怎么走

分两段：**开发期**（Vite 开发服务器起在 5173）和**上线后**（构建产物与后端同源部署）。
两段里前端代码一模一样，差别只在 `/api` 这个前缀被谁接走。

**开发期：**

```
浏览器  GET http://localhost:5173/
  └─ Vite dev server 返回 index.html，按需编译 .vue
       └─ main.js 启动：
            createApp(App).use(ElementPlus, { locale: zhCn }).use(router).mount('#app')
       └─ App.vue 的 <router-view /> 渲染当前路由对应的页面组件
       └─ 页面 onMounted 里发起请求，例如 PostListView 调 postApi.page(...)
            └─ axios 实例 baseURL 是 '/api'
                 → 实际请求 http://localhost:5173/api/posts?page=1&size=10&sort=LATEST
                      └─ Vite 的 proxy 把 /api 开头的转发到 http://localhost:8080
                           └─ Spring Boot 处理，回 Result{ code, message, data, traceId }
                      └─ 响应拦截器把外层剥掉，调用方直接拿到 data
```

关键在 `baseURL` 写的是 **`/api`，不是后端的完整地址**：

```js
const client = axios.create({
  baseURL: '/api',
  timeout: 10000
})
```

`client.js` 的注释把这一步的动机写得很直接——写死 `http://localhost:8080` 的话，
「上线部署时这里要改一次，而『忘了改』的表现是请求全部 404」。
用 `/api` 之后，**开发期和上线后走的是同一份配置**：开发期由 Vite 转发，
上线后前端静态文件和后端在同一个源上，`/api` 直接命中后端。

而「为什么不干脆在后端开 CORS」写在 `vite.config.js` 里：

```js
    // 开发时把 /api 转发到后端，**前后端在浏览器看来是同源的**。
    //
    // 为什么不直接在后端开 CORS：开了之后开发期是一种跨域配置、
    // 上线后通常又变成同源部署——**两套东西**，而真正出问题（凭证不生效、
    // 预检请求被挡）往往只在其中一种环境下复现。
    // 用代理，开发期就复现了"同源"，这个问题从一开始就不存在。
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true
      }
    }
```

**上线后**没有代理这一步，`/api/posts` 直接落在同源的 Spring Boot 上。
**前端代码一个字都不用改**——这正是选 `/api` 这个 baseURL 的全部价值。

**入口 `main.js`** 只做三件事，其中一件容易漏：

```js
// 用 Element Plus 的**中文语言包**：默认是英文，分页控件会显示 "Go to"、
// 表单校验的默认文案也是英文——不设的话界面上会中英混杂。
createApp(App)
  .use(ElementPlus, { locale: zhCn })
  .use(router)
  .mount('#app')
```

不传 `locale: zhCn` 的话分页控件上会出现 `Go to`，跟周围的中文界面格格不入。

## 逐段讲代码

### 1. `src/api/client.js` —— 唯一的出口，两个拦截器

**它存在的理由**：`baseURL`、令牌怎么带、错误怎么弹、什么时候跳登录页——
这些如果散在 4 个页面里写，漏一处的表现是「这个页面的数据加载不出来」，
而它看起来像后端的问题。集中成一个文件之后，这些约定只有一份。

**请求拦截器：自动带令牌。**

```js
client.interceptors.request.use((config) => {
  const { token } = useAuth()
  if (token.value) {
    config.headers.Authorization = `Bearer ${token.value}`
  }
  return config
})
```

注释里那句话是这一段的重点：**放在这里而不是每个调用点写一遍——漏写一处的表现是
「这个页面的数据加载不出来」，而它看起来像后端的问题。**

注意它是**从 `useAuth()` 现取令牌**（而不是捕获某个值）。所以只要 `setToken` 一执行，
下一个请求就带上了新令牌。这条性质是下面「登录装会话顺序」能成立的前提。

**响应拦截器：剥掉统一响应体的外层。**

```js
client.interceptors.response.use(
  (response) => {
    const body = response.data
    if (body && body.code === '0') {
      return body.data
    }
    return Promise.reject(toError(body))
  },
  (error) => {
    const body = error.response?.data
    if (body && body.code) {
      redirectIfTokenInvalid(body)
      return Promise.reject(toError(body))
    }
    // 连响应体都没有：网络断了，或者后端没起来
    ElMessage.error('网络异常，请确认后端已启动')
    return Promise.reject(error)
  }
)
```

成功分支把 `backend 的 Result.data` 直接返回，所以页面里写的是
`const result = await postApi.page(...)`，而不是 `res.data.data`。
`PostListView`、`PostDetailView` 里都直接取 `result.items`、`result.total`——
可以对照 `src/api/index.js` 的注释：「返回的都是**已经剥掉统一响应体外层**的 `data`」。

失败分支分两种情况：**有响应体**（`body.code` 存在）就走错误码判断，
**没有响应体**（后端没起来 / 网断）才弹「网络异常，请确认后端已启动」。
区分这两种很重要——后端没起来时如果去读 `error.response.data.code`，会读到 `undefined`，
然后弹一句让人摸不着头脑的默认文案。

**⚠️ 401 有两种含义，所以按错误码判断、不按状态码。**

```js
/**
 * 令牌失效时清掉会话并回登录页。
 *
 * <p><b>⚠️ 这里按「错误码」判断，不按 HTTP 状态码。</b>
 * 401 在本项目里有两种含义：
 * <ul>
 *   <li>`A0002` 未登录 / 令牌过期 → 该去登录页</li>
 *   <li>`A0102` 用户名或密码错误 → **该留在登录页把错误显示出来**</li>
 * </ul>
 * 只看 401 就跳转的话，用户在登录页输错密码会被"刷新一下"，
 * 刚看到的错误提示当场消失——像是页面坏了。
 */
function redirectIfTokenInvalid(body) {
  if (body?.code !== 'A0002') {
    return
  }
  useAuth().clear()
  if (window.location.pathname !== '/login') {
    window.location.href = '/login'
  }
}
```

对照后端的 `ErrorCode`（`wt-common/.../result/ErrorCode.java`）就明白了：

```java
UNAUTHORIZED("A0002", "未登录或登录已过期", HttpStatus.UNAUTHORIZED),
...
LOGIN_FAILED("A0102", "用户名或密码错误", HttpStatus.UNAUTHORIZED),
```

**两个都返回 HTTP 401**。如果前端写成 `if (error.response.status === 401) 跳登录页`，
那么用户在登录页输错密码时，会先被弹一下「用户名或密码错误」，紧接着被跳到 `/login`
（本来就是 `/login`，看起来像刷新了一下），**那句提示当场消失**。用户只会觉得「这页面坏了」。

所以这里只认 `A0002`。`A0102` 会穿过拦截器，变成 `LoginView` 的 `catch` 里的
`showError(error)`，停在原地把「用户名或密码错误」显示出来。
**`A0102` 为什么必须同时表示「用户名不存在」和「密码错误」，见
`docs/05-interview/02-注册与登录.md` 的「防用户名枚举全在这里」一节**——那是后端的取舍，
前端要做的只是别把它的错误码当成「401 = 该跳走」。

另外注意它用 `window.location.href` 而不是 `router.push`，注释给了两个理由：
**`client` 被 router 间接依赖，反过来 import router 会形成循环依赖**；
而且这里也不需要无刷新跳转——令牌失效本来就该重新来一遍。

**`showError`：唯一的弹错口。**

```js
export function showError(error) {
  // 令牌失效那条已经在拦截器里处理了（跳登录页），这里再弹一次是噪音
  if (error?.code === 'A0002') {
    return
  }
  ElMessage.error(error?.message || '操作失败')
}
```

各页面调它，而不是各自 `ElMessage.error`——这样「要不要提示、提示什么」只有一处逻辑，
也避免了「同一个错误弹两次」。`A0002` 已经在拦截器里跳走了，这里再弹就是噪音，
所以第一行就把它挡掉。

### 2. `src/api/index.js` —— 接口清单

一个文件把「后端有哪些能力在前端被用上」列全了，分成认证 / 用户 / 帖子 / 评论 / 标签五组。
好处注释里写了：**接口路径一变，改一处**。

这里没有逻辑，但有一条值得记的对应关系——**路径里的层级是后端的设计，前端照搬不加戏**：

```js
  /** 按作者筛走的是子资源路径（见后端设计稿 §4） */
  pageByAuthor: (authorId, params) => client.get(`/users/${authorId}/posts`, { params }),
```

按作者筛走的是 `/users/{id}/posts`（用户下面的帖子子资源），而不是给 `/posts` 加一个
`authorId` 查询参数。**这个选择是后端定的，前端不重排**——重排会让两边的接口文档对不上。

### 3. `src/composables/useAuth.js` —— 登录态，没有状态管理库

**为什么不引 Pinia**，类注释里写得最清楚：

```js
/**
 * 登录态。
 *
 * <p>**刻意不引入 Pinia**：这里只有"令牌"和"当前用户"两个字段。
 * 为它装一个状态管理库，第一个要写的往往是"把 localStorage 包一层"——
 * 收益为负。真需要跨页面的复杂状态时再引入不迟。
 *
 * <p>模块级的 `ref` 让整个应用共享同一份状态（`useAuth()` 每次返回的是同一组 ref）。
 */
```

状态就两个，都是**模块级的 `ref`，在模块加载时初始化**：

```js
const token = ref(localStorage.getItem(TOKEN_KEY) || '')
const user = ref(readUser())
```

写在模块顶层（不是写在函数里）是这段的全部技巧：ES 模块只求值一次，
所以**不管多少个组件调 `useAuth()`，拿到的是同一组 ref**——
改一处，`App.vue` 顶栏和页面同时更新。这就是「共享状态」在 4 个页面规模下的全部需要。

`readUser` 还有个防御：本地存的东西坏了不该让整个应用起不来。

```js
function readUser() {
  try {
    return JSON.parse(localStorage.getItem(USER_KEY) || 'null')
  } catch {
    // 本地存的东西坏了不该让整个应用起不来
    return null
  }
}
```

**`setToken` 与 `setUser` 必须分开、而且先调 `setToken`**——这条注释直接解释了
下面 `LoginView` 里那个顺序，别把两者合成一个方法：

```js
  /**
   * 存令牌。**必须与 `setUser` 分开、而且先调它**——
   * 登录响应里只有令牌、没有用户资料，资料要另外请求 `GET /users/me`，
   * 而那个请求要靠请求拦截器带上令牌。合成一个方法是能省一次调用，
   * 但那会逼出一个顺序依赖（先存令牌才发得出下一个请求），
   * 而这个顺序在调用点上是看不见的。
   */
  function setToken(value) {
    token.value = value || ''
    localStorage.setItem(TOKEN_KEY, token.value)
  }
```

**M2 的已知简化**（写在类注释最末尾，免得看起来像漏了）：
只存访问令牌，**不接续期**。访问令牌 30 分钟过期，过期后会被拦到登录页重新登一次。
后端有现成的刷新令牌接口（`POST /api/auth/refresh`），前端接上它「是十几行的事」，
但那属于体验优化，不是 M2 要交付的东西。

### 4. `src/router/index.js` —— 路由与守卫

4 条路由，写法上有一个刻意的顺序：

```js
  {
    // ⚠️ 这条要写在 `/posts/:id` 前面：虽然 vue-router 4 会优先匹配静态段，
    // 但按"具体在前"的顺序写，读的人不必去回忆那条规则
    path: '/posts/new',
    name: 'post-create',
    component: () => import('../views/PostCreateView.vue'),
    meta: { requiresAuth: true }
  },
```

`/posts/new` 放在 `/posts/:id` 前面，是因为**读的人不需要知道 vue-router 4
有「静态段优先」这条规则**也能看懂这里不会匹配错。

`scrollBehavior: () => ({ top: 0 })` 是体验细节：「从列表翻到详情还停在页面中间的话，
会以为新页面没加载出来。」

**守卫只有一处，而且它自己声明了自己不是安全措施：**

```js
/**
 * 需要登录的页面在路由层拦一道。
 *
 * <p>**这只是体验，不是安全**——真正拦住越权的是后端的鉴权
 * （`@PreAuthorize` 与资源归属校验）。前端拦不住的场景很多：
 * 用户手改 localStorage、直接调接口、令牌过期而本地还没清。
 * 这里的价值是"别让用户填完一整篇帖子才告诉他没登录"。
 */
router.beforeEach((to) => {
  const { isLoggedIn } = useAuth()
  if (to.meta.requiresAuth && !isLoggedIn.value) {
    return { name: 'login', query: { redirect: to.fullPath } }
  }
})
```

三句话概括它的定位：**拦不住的场合列举在注释里**（手改 `localStorage`、
直接调接口、令牌过期但本地还没清）；**它拦得住的**是「还来得及」的那一类——
让用户在点进发帖页之前就知道要登录，而不是写完一整篇再被打回。
`isLoggedIn` 只看本地有没有令牌，**根本不验证令牌是否有效**——这也正是它只能算体验的原因。

`query: { redirect: to.fullPath }` 把「原本想去哪」记下来，登录成功后送回去。
这个 `redirect` 在 `LoginView` 的末尾被消费。

### 5. `App.vue` —— 顶栏在所有页面共用

顶栏只有一个组件，因为它是**唯一需要「跨页面知道自己登录没登录」的地方**：

```vue
          <template v-if="isLoggedIn">
            <el-button type="primary" @click="router.push('/posts/new')">发帖</el-button>
            <el-dropdown @command="onCommand">
              <span class="wt-user">
                {{ user?.nickname || user?.username }}
```

`isLoggedIn` 和 `user` 都是从 `useAuth()` 拿的模块级 ref，所以登录页一 `setToken`，
顶栏立刻从「登录 / 注册」变成「发帖 + 用户名」。

退出登录那段有个刻意的「不管失败也继续」：

```js
  try {
    // 后端会把这个用户的刷新令牌删掉。失败也继续清本地——
    // "退出登录"这个动作不该因为网络问题而失败
    await authApi.logout()
  } catch (error) {
    showError(error)
  }
  clear()
  ElMessage.success('已退出登录')
  router.push('/')
```

后端删的是刷新令牌（拿不到新令牌），本地 `clear()` 清的是令牌和用户。**本地这一半不能省**，
否则网络不好时用户会「退不出去」。

### 6. `LoginView.vue` —— 登录与注册共用一页

`mode` 一个 ref 在 `'login'` / `'register'` 之间切，字段高度重合所以不做两个页面。

**校验规则与后端保持一致，但只是体验**——这段注释值得原样读：

```js
/*
 * 前端校验规则**与后端保持一致**（用户名 3~32 且只含字母数字下划线连字符、
 * 密码 8~64）。
 *
 * ⚠️ 但它**只是体验，不是安全**：真正说了算的永远是后端——
 * 前端能拦住的只有"用正常界面提交"这一种情况，手改请求、直接调接口都绕得过去。
 * 之所以要把两边的规则写成一样，是为了**别让用户被两套说法搞糊涂**：
 * 前端说可以、后端说不行的话，用户会以为是 bug。
 */
```

「保持一致」的目的**不是拦住谁**（拦不住），而是**让用户不会被两套说法搞糊涂**。
对得上后端的 `RegisterRequest` 上的 `@Size(min = 3, max = 32)`、`@Pattern`、`@Size(min = 8, max = 64)`
（见 `02-注册与登录.md` §2）。注意登录**不校验密码长度**——前端只在注册模式显示昵称字段，
规则表里 `password` 的 `min: 8` 是跟着后端注册规则写的。

**装会话的顺序不能颠倒**——这是整个前端最值得记的一段：

```js
/**
 * 登录成功后把会话装好。
 *
 * <p>**顺序不能颠倒**：先存令牌，再请求当前用户资料——
 * 那个请求要靠请求拦截器从本地取令牌带上。反过来的话会拿到 401。
 */
async function establishSession(loginResult) {
  setToken(loginResult.accessToken)
  const profile = await userApi.me()
  setUser(profile)
}
```

`userApi.me()` 走的是 `client`，而 **`client` 的请求拦截器会从 `useAuth()` 现取 `token.value`
塞进 `Authorization` 头**（见 §1）。所以 `setToken` 必须**先**跑完——
反过来的话，`GET /users/me` 是个不带令牌的请求，后端回 `A0002`，
而拦截器又会顺手把用户踢回登录页。**表现是「登录成功了但立刻被弹回来」**，
光看代码顺序看不出来，因为这两行看起来只是「两个不相关的赋值」。

登录响应里只有 `accessToken` / `refreshToken` / 两个过期秒数，**没有用户资料**，
资料只能另外查——这就是为什么是两次调用，而不是一次。

提交那段把注册与登录串起来：

```js
    if (mode.value === 'register') {
      await authApi.register({
        username: form.username,
        password: form.password,
        nickname: form.nickname
      })
      ElMessage.success('注册成功，正在登录')
    }

    const result = await authApi.login({ username: form.username, password: form.password })
    await establishSession(result)

    ElMessage.success('登录成功')
    // 登录前想去哪，登录后回哪；直接进来的就回首页
    router.replace(route.query.redirect || '/')
```

**注册成功后紧接着自动登录一次**——后端注册接口刻意不发令牌
（`POST /api/auth/register` 只回一个 id，理由见 `02-注册与登录.md` §1），
所以前端在这边把「注册 → 登录」串成一个动作，用户只感觉按了一次按钮。
最后 `router.replace(route.query.redirect || '/')` 把路由守卫存下的 `redirect` 消费掉；
用 `replace` 不用 `push`，是为了别在历史里留一条「登录页」。

### 7. `PostListView.vue` —— 列表页，三态齐全

**筛选条件一变就重新拉数据，靠 `watch` 而不是每个交互里手动调：**

```js
// 筛选条件一变就重新拉数据。放在 watch 里而不是每个交互里手动调 loadPosts：
// 漏调一处就是"点了没反应"，而那种 bug 在页面上很难一眼看出
watch(query, loadPosts)
```

`query` 是个 `reactive({ page, size, sort, tagId })`，翻页 / 切排序 / 点标签
都只改这个对象——**改数据，不用记得去调加载函数**。`selectTag` 和 `changeSort` 里
都顺手把 `query.page = 1` 归位（换了筛选条件还停在第 3 页是常见的低级 bug）。

**`loading` 必须在 `finally` 里关：**

```js
  } finally {
    // 必须放在 finally：出错时不关掉的话，页面会一直转圈，
    // 而用户看到的是"加载中"，完全不知道已经失败了
    loading.value = false
  }
```

放 `try` 末尾的话，请求一失败就永远关不掉，界面永远转圈、底下却没有数据。
**「一直转圈」比「显示一句错误」更糟**——它不给用户任何判断依据。

**空状态是必须的，不是锦上添花：**

```vue
      <!-- 空状态：**没有数据时不能是一片白**，用户会以为是加载失败 -->
      <el-empty
        v-if="!loading && posts.length === 0"
        class="wt-empty"
        :description="query.tagId ? '这个标签下还没有帖子' : '还没有帖子，来发第一篇吧'"
      >
```

注意条件是 `!loading && posts.length === 0`——**「加载中」和「加载完了没数据」是两件事**。
少了 `!loading` 这一半，请求飞出去的一瞬间空状态就会闪一下，白屏闪烁比不显示还难受。
文案还分了两种：带标签时是「这个标签下还没有帖子」，不带时是「来发第一篇吧」——
**同一个空状态的文案指向不同的下一步**，用户才知道该不该换个标签。

标签加载失败**不牵连主列表**：

```js
    // 标签加载失败不该让整个首页崩掉：帖子列表才是主体
    showError(error)
```

页面主体是帖子列表，标签只是筛选项。为了一个附属请求失败而让整页显示错误，是把次要问题
放大成主要问题。

### 8. `PostDetailView.vue` —— 详情页，三类失败分别处理

**404 不是「出错」，是「不可见」：**

```js
  } catch (error) {
    // 404 要单独处理：它不是"出错"，而是"这条帖子对你不可见"，
    // 该给一个明确的空页面，而不是弹一个红色错误框
    if (error.code === 'A0201') {
      notFound.value = true
    } else {
      showError(error)
    }
  }
```

`A0201`（`POST_NOT_FOUND`）被单独拎出来，渲染成一个带「回首页」按钮的空页面
（模板里 `<el-empty v-if="notFound" description="帖子不存在，或已被删除 / 下架">`），
而不是弹红色错误框。**「这条内容不存在」是正常结果之一，不是系统故障**，
把它显示成故障会让人以为是自己网络的问题。

**未登录时统一走 `requireLogin`：**

```js
/** 未登录时提示并带去登录页；登录后能回到这里。 */
function requireLogin(action) {
  if (isLoggedIn.value) {
    return true
  }
  ElMessage.info(`登录后才能${action}`)
  router.push({ name: 'login', query: { redirect: route.fullPath } })
  return false
}
```

点赞、收藏、回复、发评论四处都先调它。**这里是「体验型拦截」的典型**：
和路由守卫一样，它拦不住直接调接口的人；它的价值是把「去登录」这件事
放在用户按下按钮的当口，而不是等他写完评论才告诉他。

**点赞与收藏：先请求成功再改本地状态。**

```js
/*
 * 点赞与收藏：**先请求成功再改本地状态**。
 *
 * 反过来（先改界面、失败再改回来）看着更"跟手"，但失败时用户会先看到
 * 数字跳了一下又跳回去——比起"点完等一下"，那个体验更让人困惑。
 */
```

「乐观更新」（先改界面，失败再回滚）在失败时会让数字**先跳一下再跳回去**。
用这段注释的话说，**那比「点完等一下」更让人困惑**。所以这里等接口回来才动 `post.liked`
和 `post.likeCount`，回滚那段 `Math.max(post.value.likeCount - 1, 0)` 也顺手兜住了 0 的下界。

**正文按纯文本显示，不引 Markdown 库：**

```vue
          <!-- 正文按 Markdown 文本存（设计稿 §6），这里**按纯文本显示**：
               不引 Markdown 渲染库，避免把用户输入当 HTML 注入 -->
          <div class="wt-post__content">{{ post.content }}</div>
```

正文按 Markdown **文本**存（设计稿 §6 的范围），但这一版**按纯文本渲染**。
用 `{{ }}` 插值而不是 `v-html`，浏览器自动转义——**把用户输入当 HTML 渲染
就是一个 XSS 洞**。配套的 `white-space: pre-wrap`（在 `<style scoped>` 里）
负责保留换行，不保留的话整篇会挤成一坨。

**评论是两级。** 模板里回复被缩进一级渲染（`.wt-comment__replies`），
注释里点了后端模型：**「后端是两级模型（ADR-0018）：回复的回复也会被拍平到这一层」**——
所以这里只有一层 `v-for` 嵌套，不做递归组件，因为后端不会给出三层。
发评论时 `parentId: replyTo.value?.id ?? null`：不回复任何人就是顶层评论。

### 9. `PostCreateView.vue` —— 发帖

标签选择器开了 `allow-create`：

```vue
          <el-select
            v-model="form.tags"
            multiple
            filterable
            allow-create
            default-first-option
            :multiple-limit="MAX_TAGS"
            placeholder="选已有的，或直接输入新的（回车创建）"
```

**候选项不限制只能选这些**——标签是自由输入的（设计稿 §2.3），下拉里列已有标签
只是方便，输入新词回车创建新标签。`MAX_TAGS = 5` 的注释点明了它跟后端的对应：
「标签上限与后端一致（`TagService.MAX_TAGS_PER_POST`）」，对应后端的 `A0203`。

提交成功后直接跳到详情页，而不是回列表：`router.replace(\`/posts/${id}\`)`。
`postApi.create` 返回的就是新帖 id（后端 `Result.success(id)`）。

### 10. `src/styles/global.css` —— 全站共用的那几个数字

```css
/*
 * 这里只放「所有页面都必须一致的东西」：容器宽度、页面底色、卡片间距。
 * 具体组件的样式留在各自的 .vue 里——**但数字从这里取**，
 * 否则页面一多，就会出现"这个页面边距 16px、那个 20px"的不一致，
 * 而单看每一页都不觉得有问题。
 */
:root {
  --wt-content-width: 960px;
  --wt-gap: 16px;
  --wt-gap-lg: 24px;
  --wt-bg: #f5f7fa;
}
```

各页面的 `<style scoped>` 里写的是 `var(--wt-gap)`，不是 `16px`——**数字只有一处**。
`App.vue` 的顶栏内层和页面的 `.wt-container` 都用 `max-width: var(--wt-content-width)`，
两者对齐，注释解释了不对齐的后果：「视觉上会有一条对不齐的竖线」。

### 11. `src/utils/format.js` —— 两个显示函数

```js
export function formatTime(value) {
  if (!value) {
    return ''

}
```

后端返回的时间是 `2026-10-06T00:01:58`（`LocalDateTime` 直接序列化），

## 走一遍场景

假设用户 `alice` 从空白浏览器开始，走一遍：登录 → 列表 → 详情 → 发帖。

**1. 打开 `http://localhost:5173/`。** Vite 返回 `index.html`，`main.js` 挂载应用。
本地 `localStorage` 里没有 `wt_access_token`，所以 `useAuth` 的 `token` 初值是 `''`、
`isLoggedIn` 是 `false`，`App.vue` 顶栏显示「登录 / 注册」。路由是 `/`，渲染 `PostListView`。

`PostListView` 的 `onMounted` 调 `loadTags()` 和 `loadPosts()`。两个请求都打到
`http://localhost:5173/api/...`，被 Vite 代理转到 `8080`。列表回 `{ items, total }`，
拦截器剥掉外层，`posts.value = result.items`。`loading` 在 `finally` 里关掉，
`v-loading` 的转圈消失。如果一条帖子都没有，`el-empty` 显示「还没有帖子，来发第一篇吧」。

**2. 点「登录 / 注册」。** `router.push('/login')`，渲染 `LoginView`，`mode` 默认 `'login'`。
`alice` 输入用户名 `alice` 和密码，但**打错了一个字母**，点登录。

`authApi.login` 打 `POST /api/auth/login`。后端 `UserService.authenticate` 比对失败，
抛 `LOGIN_FAILED`，响应是 `401 / A0102 / 用户名或密码错误`。

回到前端：响应拦截器的失败分支拿到 `body`（有 `code`），调 `redirectIfTokenInvalid(body)`
——**`body.code` 是 `A0102` 不是 `A0002`，函数第一行就 return 了，什么都没做**。
然后 `Promise.reject(toError(body))`。`LoginView` 的 `catch` 调 `showError(error)`，
`ElMessage.error('用户名或密码错误')`。

**用户停留在登录页，表单里的内容还在，上面弹着「用户名或密码错误」。**
这正是「按错误码判断」换来的结果——如果按 401 判断并跳转，此刻页面会被刷到 `/login`，
那句错误提示当场消失，用户只会以为按钮点了没反应。

**3. 改对密码，再点一次。** 这次后端返回 `{ accessToken, refreshToken, accessExpiresIn, refreshExpiresIn }`。
`onSubmit` 里走到 `await establishSession(result)`：

- `setToken(result.accessToken)` → 模块级 `token.value` 变成那串 JWT，
  同时写进 `localStorage['wt_access_token']`。
- `await userApi.me()` → 请求拦截器此刻 `token.value` 已经有值，
  于 `GET /api/users/me` 带上了 `Authorization: Bearer eyJ...`，后端返回用户资料。
- `setUser(profile)` → `user.value` 和 `localStorage['wt_user']` 一起更新。

顺序反过来会怎样前面讲过：`me()` 不带令牌，后端回 `A0002`，拦截器把用户踢回登录页——
**表现是「登录成功了但立刻被弹回来」**。

接着 `ElMessage.success('登录成功')`、`router.replace(route.query.redirect || '/')`。
**顶栏当场变了**——`isLoggedIn` 是模块级 ref，`App.vue` 里同样的 `isLoggedIn` 现在是 `true`，
「登录 / 注册」按钮换成「发帖 + `alice`」。

**4. 回列表点一条帖子。** 路由到 `/posts/7`，`PostDetailView` 的 `postId = Number(route.params.id)`
是 `7`。`onMounted` 先 `loadPost()`：`postApi.detail(7)` 成功，`post.value` 填上，
转圈消失。再 `loadComments()`（`!notFound` 才走）。

`alice` 点「点赞」。`requireLogin('点赞')` 返回 `true`（已登录），于是发
`PUT /api/posts/7/like`。**等接口回来**——成功后才 `post.value.liked = true`、
`post.value.likeCount += 1`，按钮变蓝、数字加一。再点一次是 `DELETE`，状态翻回去。

如果这时她换了个浏览器 / 清了 localStorage 再点，`requireLogin` 会 `ElMessage.info('登录后才能点赞')`
并 `router.push({ name: 'login', query: { redirect: '/posts/7' } })`——登录完会回到这条帖子。

**5. 点头像 → 发帖。** 路由到 `/posts/new`。进之前先过守卫：
`to.meta.requiresAuth` 是 `true`，`isLoggedIn` 是 `true`，放行。

`PostCreateView` 的 `onMounted` 拉一次标签候选（失败也不挡发帖）。
`alice` 填标题、正文，在标签框里输入 `Redis` 回车——`allow-create` 让它是新标签。
点发布，`postApi.create({ title, content, tags })` 打 `POST /api/posts`，
请求拦截器带上令牌。后端建帖成功，回新帖的 id，比如 `8`。
前端 `router.replace('/posts/8')`，直接停在新帖详情页上。

**6. 半个多小时后。** `alice` 回来再点赞。访问令牌早过期了，后端回 `401 / A0002`。
响应拦截器这次认出 `A0002`：`clear()` 清掉本地令牌和用户，顶栏变回「登录 / 注册」；
`window.location.href = '/login'` 把整页刷到登录页。**这就是 M2 的已知简化**——
只存访问令牌、不接续期，30 分钟后必须重新登录。后端有现成的 `POST /api/auth/refresh`，
前端接上它是十几行的事，但那属于体验优化，M2 不做。

## 面试会追问

**Q：为什么开发时用 Vite 代理，不在后端开 CORS？**
因为开了 CORS 之后**开发期是一种跨域配置、上线后通常又是同源部署，变成两套东西**，
而真正出问题（凭证不生效、预检请求被挡）往往只在其中一种环境下复现。
用代理，开发期就已经是「同源」，这个问题从一开始就不存在。
完整理由见 `vite.config.js` 的注释与设计稿 §6.3，代码里也留了同一段。

**Q：那上线之后代理就没了，前端是不是要改地址？**
不用改一个字。`client` 的 `baseURL` 写的是 `/api`（相对路径），
上线后前端静态文件与后端同源部署，`/api` 直接命中后端。写死 `http://localhost:8080`
才需要改，而「忘了改」的表现是请求全部 404。

**Q：登录失败时页面为什么没有跳走？**
因为拦截器是**按错误码判断**的，不是按 HTTP 状态码。`A0002`（未登录 / 过期）跳登录页；
`A0102`（用户名或密码错误）**留在原地把错误显示出来**。两者 HTTP 状态都是 401
（见 `ErrorCode`），只认状态码的话，用户在登录页输错密码会看到页面「刷一下」、
提示当场消失——像是坏了。

**Q：为什么两个 401 不能合并成一个 401？**
后端要合并的是**「用户名不存在」和「密码错误」**（防用户名枚举，理由见
`02-注册与登录.md`）；前端要分开的是**「令牌失效」和「凭证错误」**。
这是两个不同层面的「合」与「分」——后端那边合是为了不泄露「哪些用户名存在」，
前端这边分是为了把用户送到正确的下一步。

**Q：既然前端也写了校验规则，是不是可以少发一次请求？**
前端校验**只是体验，不是安全**，注释里写明了它拦得住的只有「用正常界面提交」这一种情况，
手改请求、直接调接口都绕得过去。真正说了算的永远是后端。两边规则写成一样的目的
是**别让用户被两套说法搞糊涂**——前端说可以、后端说不行的话，用户会以为是 bug。

**Q：路由守卫拦住了未登录，是不是安全就够了？**
不是，它是**体验，不是安全**。`isLoggedIn` 只看本地有没有令牌、根本不验证令牌有效性；
用户手改 `localStorage`、直接调接口、令牌过期而本地还没清，都能绕过去。
真正拦住越权的是后端的 `@PreAuthorize` 与资源归属校验。守卫的价值是
「别让用户填完一整篇帖子才告诉他没登录」。

**Q：登录成功之后为什么要请求两次（先登录、再 `GET /users/me`）？是不是可以省一次？**
省不掉，因为**登录响应里只有令牌、没有用户资料**。顺序也颠倒不得：`GET /users/me`
靠请求拦截器从 `useAuth()` 现取令牌带上，所以必须**先 `setToken` 再 `userApi.me()`**。
反过来会拿到 401，表现是「登录成功了但立刻被弹回登录页」——
一个看起来跟这两行顺序毫无关系的现象。

**Q：为什么不用 Pinia？**
登录态只有「令牌」和「当前用户」两个字段。为它装状态管理库，第一个要写的往往是
「把 `localStorage` 包一层」，收益为负。**模块级的 `ref`** 就够——
`useAuth()` 每次返回同一组 ref，一处改、全应用更新。真需要跨页面的复杂状态时再引入不迟。
（设计稿 §6.2 把 Pinia 列在「三个明确不引入」里。）

**Q：列表页为什么用 `watch(query, loadPosts)`，不在每个交互里调加载？**
因为「筛选条件变了要重新拉数据」这条规则如果散在翻页、切排序、点标签三处，
**漏调一处就是「点了没反应」**，而那种 bug 在页面上很难一眼看出。
让 `query` 变成唯一的触发点，就不存在「漏调」。

**Q：加载态和空状态为什么一定要有？**
没有加载态，用户点完不知道有没有反应；没有空状态，没数据的列表是**一片白**，
用户会以为加载失败。而且这两个条件是**互相排斥**的——`v-if="!loading && posts.length === 0"`，
少了 `!loading` 这一半，请求发出的一瞬间空状态会闪一下。
`loading` 还必须放在 `finally` 里关，否则请求一失败页面永远转圈——
**「一直转圈」比「显示一句错误」更糟**，它不给用户任何判断依据。

**Q：点赞为什么不做「乐观更新」（先改界面再等接口）？**
失败时会先看到数字跳一下又跳回去，**比「点完等一下」更让人困惑**。
所以这里等接口成功才动本地状态，代码里也顺手兜了计数不为负的下界。

**Q：帖子的正文是 Markdown，为什么不渲染 Markdown？**
M2 的范围里正文按 Markdown **文本**存，前端**按纯文本显示**，用 `{{ }}` 插值让浏览器
自动转义。引 Markdown 渲染库意味着把用户输入当 HTML 注入——**那就是一个 XSS 洞**。
换行靠 `white-space: pre-wrap` 保留。

**Q：前端拿到 401 后跳登录页，为什么用 `window.location.href` 而不是 `router.push`？**
两个理由，写在 `client.js` 里：`client` 是被 router **间接依赖**的，
反过来 import router 会形成**循环依赖**；而且这里也不需要「无刷新跳转」，
令牌失效本来就该重新来一遍。

**Q：刷新令牌后端都做好了，前端为什么不用？**
M2 的已知简化，写在 `useAuth.js` 的类注释里：只存访问令牌、**不接续期**，
30 分钟后需要重新登录。接续期是十几行的事，但属于体验优化，不是 M2 要交付的东西。
写在那里是为了让它看起来是「有意的取舍」而不是「漏掉了」。
