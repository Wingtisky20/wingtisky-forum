# 链路讲解 · 点赞与收藏

> 对着 M2 的真实代码讲一遍：一个人点一下帖子上的"赞"，后端做了什么。
> 只讲代码实际怎么走；设计上的"为什么"指向已有文档，不在这里复述第二遍。
> 帖子本身的读写见 `07-帖子读写链路.md`，标签计数的维护见 `09-标签链路.md`，本文不重复。

---

## 一句话

点赞与收藏是**同一套形状写两遍**（`InteractionService` 的四个方法长得几乎一样），它们的幂等**不是应用层"先查一查"实现的**——重复点赞靠 `INSERT IGNORE` 撞上 `(user_id, post_id)` 联合主键后安静跳过，取消点赞靠 `DELETE` 删 0 行也不报错，**幂等这件事整个交给了数据库**；而这条链路上最值得讲的一步是紧接着的那半行：`if (insertIgnore(...) > 0)`——**只有真的写进去了才动计数**，少了这个判断，同一个人点十次赞，帖子上的点赞数就是十，而且**不会报错**，只会显示一个没人看得出错在哪的数字；详情接口另带两个布尔字段 `liked` / `collected`，回答的是"**你**点过没"，所以未登录时恒为 `false`——前端在未登录时不能靠它判断"这条帖子没人点赞"。

## 数据怎么走

### 写一：点赞 `PUT /api/posts/{id}/like`

```
PostController.like(id, userId)
      │  userId 来自 @AuthenticationPrincipal（SecurityConfig 保证这个路径要登录）
      ▼
InteractionService.like(postId, userId)          ← @Transactional
      │
      ├─ requirePostExists(postId)               ← selectById 查不到 → 抛 A0201 帖子不存在
      │
      ├─ postLikeMapper.insertIgnore(userId, postId)
      │        INSERT IGNORE INTO t_post_like (user_id, post_id) VALUES (?, ?)
      │        返回值：插进去了 1 / 撞主键被忽略 0
      │
      └─ if (返回值 > 0)                           ← ★ 这一步是关键
             postMapper.addLikeCount(postId, 1)
                  UPDATE t_post SET like_count = GREATEST(like_count + 1, 0)
                  WHERE id = ? AND deleted = 0
```

### 写二：取消点赞 `DELETE /api/posts/{id}/like`

```
InteractionService.unlike(postId, userId)        ← @Transactional
      ├─ requirePostExists(postId)
      ├─ postLikeMapper.delete(userId, postId)
      │        DELETE FROM t_post_like WHERE user_id = ? AND post_id = ?
      │        返回值：删掉的行数（本来就点过 → 1；没点过 → 0）
      └─ if (返回值 > 0)
             postMapper.addLikeCount(postId, -1)
```

收藏 / 取消收藏（`PUT` / `DELETE /api/posts/{id}/collect`）走的是**同一条路**，只是把 `t_post_like` 换成 `t_post_collect`、`addLikeCount` 换成 `addCollectCount`。

### 读：详情里带"我点过没" `GET /api/posts/{id}`

```
PostController.detail(id, viewerId)
      │  viewerId 来自 @AuthenticationPrincipal —— 匿名访问时是 null
      ▼
PostService.getDetail(id, viewerId)
      │
      ├─ postMapper.selectById(id)              ← 查不到 → A0201
      ├─ postMapper.incrementViewCount(id)      ← 顺手把浏览数 +1（本接口是"读里带写"）
      ├─ userQueryService.findBrief(...)        ← 作者信息走跨域契约（ADR-0015）
      │
      └─ PostDetail.from(post, author,
             interactionService.liked(id, viewerId),      → boolean liked
             interactionService.collected(id, viewerId))  → boolean collected
                             │
                             ▼
                  InteractionService.liked(postId, userId)
                        return userId != null && postLikeMapper.exists(userId, postId) > 0;
                             │
                             ├─ userId == null（未登录）→ 直接返回 false，**连 exists 都不发**
                             └─ 否则 SELECT COUNT(*) FROM t_post_like WHERE user_id = ? AND post_id = ?
```

## 逐段讲代码

### 1. 幂等交给数据库，不是应用层"先查一查"

`PostLikeMapper.insertIgnore` 的 SQL 只有一行：

```xml
<insert id="insertIgnore">
    INSERT IGNORE INTO t_post_like (user_id, post_id)
    VALUES (#{userId}, #{postId})
</insert>
```

关键在于 `t_post_like` 的主键：

```sql
-- 联合主键**就是幂等保证**：重复点赞会撞主键，配 INSERT IGNORE 即可，
-- 不需要"先查有没有点过赞再插"——后者在并发下会插进两条。
PRIMARY KEY (user_id, post_id),
```

于是"重复点赞"会发生什么：第二次执行这条 `INSERT` 时，`(user_id, post_id)` 已经在表里了，主键冲突；而 `IGNORE` 让 MySQL **安静地跳过这一行**，不抛异常、也不改动任何数据。`InteractionService.like` 因此可以无条件地"先插一下"，不用自己判断有没有点过。

**为什么不能写成"先查有没有点过、没有就插"？** 因为它中间有窗口。两个请求几乎同时进来：

1. 请求甲 `SELECT` → "没点过"
2. 请求乙 `SELECT` → "也没点过"（甲的插入还没发生）
3. 请求甲 `INSERT` → 成功
4. 请求乙 `INSERT` → 如果主键存在就报错；如果主键不存在就是一个用户两条点赞记录

应用层的"查"和"写"是两步，中间隔着一段时间，并发请求能挤进去。数据库的主键约束是**一条语句内部**完成的判断，没有这个窗口。这正是 ADR-0017 选"两张专用表"的核心理由之一——联合主键让"这个人赞过这个帖，只有一条"成为**表结构层面的事实**，而不是靠代码每次都记得去查。为什么不做一张通用的 action 表、为什么主键要两列，见 ADR-0017，本文不重复。

取消点赞这一侧同理，只是换成了删除：

```xml
<delete id="delete">
    DELETE
    FROM t_post_like
    WHERE user_id = #{userId}
      AND post_id = #{postId}
</delete>
```

删 0 行不是错误——本来就没人点过赞，本来就没有东西可删。`DELETE` 对"没找到"的默认反应就是影响 0 行、不报错，所以它天然满足幂等。

顺带说一句这两张表的形状：它们是**全库唯一不带 `deleted` 列的表**。其他表（`t_user`、`t_post`、`t_comment`）都是逻辑删除，"删掉"= 标记 `deleted = 1`；而"取消点赞"的语义是**这件事没发生过**，留一行标记删除没有意义。`db/V2__init_content.sql` 里为此专门留了一段说明，见到它们没有 `deleted` 时不用怀疑是漏写。这对接口层也是可见的：点赞用 `PUT`（"把状态设置成这样"，天生幂等），取消用 `DELETE`，不是 `POST /like` + `POST /unlike`。

### 2. ★ 只有真的写进去了才动计数

四个业务方法长得一模一样，`like` 是这样：

```java
/** 点赞。已经点过就当无事发生（返回成功，计数不再加）。 */
@Transactional
public void like(Long postId, Long userId) {
    requirePostExists(postId);
    if (postLikeMapper.insertIgnore(userId, postId) > 0) {
        postMapper.addLikeCount(postId, 1);
    }
}
```

那一行 `if (... > 0)` 是整条链路里最值钱的一行。`insertIgnore` 的返回值是"**真的插进去了吗**"：

| 返回值 | 含义 | 该不该动计数 |
|---|---|---|
| `1` | 这次真的点上了 | 加 1 |
| `0` | 撞主键被忽略了（早就点过） | **一点都不加** |

**少了这个判断会怎样？** 代码变成无条件地 `postMapper.addLikeCount(postId, 1)`。第一次点赞：插入成功、计数 +1，看起来正常。第二次点赞：插入被忽略（表里还是一行，没有重复数据）、**但计数又 +1**。同一个人点十次，`t_post_like` 里始终只有一行，而 `t_post.like_count` 是 10。

这个 bug 最难的地方在于**它不会报错**。表数据是干净的（主键约束仍然在拦重复行），接口每次都返回成功，唯一的症状是界面上一个偏大的数字——而这个数字**没有任何东西和它对照**，所以没人看得出它错了。这就是为什么 `InteractionServiceTest` 里那条 `repeatedLikeDoesNotBumpCount` 是整个 Task 最要紧的断言：

```java
@Test
@DisplayName("★ 重复点赞：插入被忽略，**计数一点都不动**")
void repeatedLikeDoesNotBumpCount() {
    when(postMapper.selectById(POST_ID)).thenReturn(existingPost());
    // INSERT IGNORE 撞主键 → 返回 0
    when(postLikeMapper.insertIgnore(ME, POST_ID)).thenReturn(0);

    interactionService.like(POST_ID, ME);

    // 这一条是整个 Task 里最要紧的断言：没有它，同一个人点十次赞，
    // 帖子的点赞数就是十，而且看起来完全正常
    verify(postMapper, never()).addLikeCount(anyLong(), anyInt());
}
```

取消点赞那一侧是对称的，`unlike` 的注释把它为什么也要判断说得很直白：

```java
/** 取消点赞。本来就没点过也算成功（幂等），但**不能去减计数**。 */
@Transactional
public void unlike(Long postId, Long userId) {
    requirePostExists(postId);
    if (postLikeMapper.delete(userId, postId) > 0) {
        postMapper.addLikeCount(postId, -1);
    }
}
```

删 0 行还去减计数，减掉的就是**别人的赞**——把帖子的 `like_count` 减成一个比真实点赞人数小的数。`PostLikeMapper.delete` 的 Javadoc 用一句话点了这个后果："（减了就会把别人的赞算掉）"。

计数本身由 `PostMapper.xml` 里两条几乎一样的语句维护：

```xml
<!-- 点赞数 / 收藏数。与评论数同一套路（单语句、GREATEST 下限保护）。
     列名写死在这里而不是当参数传：能当参数传就意味着要拼 SQL，
     而那正是注入的口子。 -->
<update id="addLikeCount">
    UPDATE t_post
    SET like_count = GREATEST(like_count + #{delta}, 0)
    WHERE id = #{postId} AND deleted = 0
</update>

<update id="addCollectCount">
    UPDATE t_post
    SET collect_count = GREATEST(collect_count + #{delta}, 0)
    WHERE id = #{postId} AND deleted = 0
</update>
```

两处可以和上面连起来看：

- 增量的写法是 `like_count = like_count + #{delta}`——**单条语句**里做加法，并发安全；换成"先查出来、加一、再写回去"就会丢更新（同一张表的 `incrementViewCount` 注释讲了同一件事）。
- `GREATEST(..., 0)` 是下限保护：计数一旦变成负数，界面上是个没法解释的数字，排查时又很难判断它从哪来。
- `WHERE id = ? AND deleted = 0`：帖子已被删时不改计数。不过实际上走不到这里——`requirePostExists` 用的是同一个 `selectById`（同样带 `deleted = 0`），帖子不存在或已删会在更早一步抛 `A0201`。

`like_count` / `collect_count` 是**冗余计数**（不实时 `COUNT(*)`），为什么冗余见 ADR-0016，这里不复述。四个业务方法都带 `@Transactional`：插入被忽略、计数没动，是同一个事务里的两件事；`insertIgnore` 和 `addLikeCount` 必须一起成功或一起失败。

### 3. `liked` / `collected`：回答的是"**你**点过没"

详情接口的公开性决定了这两个方法要处理匿名访问。`InteractionService` 里：

```java
/**
 * 这个人点过赞吗。**未登录（{@code userId} 为 null）直接返回 false、不查库**——
 * 详情接口是公开的，匿名访问时没必要为了一个"你没登录"的结论去查一次数据库。
 */
public boolean liked(Long postId, Long userId) {
    return userId != null && postLikeMapper.exists(userId, postId) > 0;
}
```

`getDetail` 把 `viewerId` 原样透下来：

```java
// 未登录时 viewerId 为 null，InteractionService 会直接返回 false 且**不查库**
return PostDetail.from(post, author,
        interactionService.liked(id, viewerId),
        interactionService.collected(id, viewerId));
```

`PostDetail` 的两个字段名直接说明了它们的语义：

```java
/**
 * ...
 * @param liked  **当前登录的人**点过赞吗。未登录时恒为 {@code false}——
 *               所以前端在未登录时不能靠它判断"这条帖子没人点赞"
 * @param collected 同上，收藏
 */
```

**这里有个非常容易误用的点。** 一个名字叫 `liked` 的布尔字段，看起来像是在描述帖子，但它描述的是**你和帖子的关系**。这两种用法完全不同：

- ✅ 前端拿它决定"赞"按钮要不要高亮——登录用户 A 点过：`liked = true`；换 B 登录看同一条：`liked = false`。同一条帖子，不同的人看到不同的值，这正是按钮要的。
- ❌ 前端拿它判断"这条帖子没人点过赞"——未登录时它恒为 `false`，和"有人点过但不是我"是**同一个值**。判断一条帖子有没有人点赞要看 `likeCount`，那是另一个字段。

`exists` 的 SQL 就是一次 `COUNT(*)`：

```xml
<select id="exists" resultType="int">
    SELECT COUNT(*)
    FROM t_post_like
    WHERE user_id = #{userId}
      AND post_id = #{postId}
</select>
```

返回 0 或 1（联合主键保证最多一行）。而 `liked` 里那个 `userId != null &&` 短路，让**匿名访问详情时连这条查询都不会发**——`InteractionServiceTest.anonymousDoesNotQuery` 用 `verifyNoInteractions` 钉住了这一点。这既省了一次数据库往返，也避免了一件更麻烦的事：`exists` 的 SQL 里 `WHERE user_id = #{userId}` 传 `null` 进去，语义会变得没有意义。

### 4. 删帖**不删**这些记录——和标签的处理刚好相反

`InteractionService` 的类注释里记着这条约定：

```
删帖时这些记录不删（用户 2026-10-06 定的）：帖子上的"点赞数"只在
帖子可见时才有意义，而删掉的帖子不可见；记录留着反而保住了"以后恢复帖子"的可能
——这与本项目一律用标记删除而不是真删的思路一致。
```

它和标签的差别在最后一句括号里：

```
（注意这和标签不一样：标签的计数是**全站可见**的，所以删帖必须减。）
```

对比着看就很清楚。删帖时：

| | 标签（`09-标签链路.md`） | 点赞 / 收藏 |
|---|---|---|
| 删帖时做的事 | `tagService.detachAll(id)`——先把每个标签的 `post_count` 各 -1，再删关联 | **什么都不做** |
| 为什么 | `t_tag.post_count` 是**全站可见**的——标签页上写着"12 篇"，是所有帖子一起贡献的 | `t_post.like_count` 只跟着这一条帖子显示，帖子不可见它就没人看 |
| 记录留着还是删掉 | 关联必须删（否则计数对不上） | 记录留着，保住"以后恢复帖子"时点赞还在的可能 |

`PostService.delete` 里能看到这个差别：它只调 `tagService.detachAll(id)` 和 `postMapper.softDelete(id)`，**完全没有碰 `t_post_like` / `t_post_collect`**。而 `softDelete` 只是把 `t_post.deleted` 置 1（标记删除，不是真删行），所以那些点赞记录指向的帖子行还在，不是孤儿——这也和"记录不删"的选择是一致的。

## 走一遍场景

**场景一：同一个人点两次赞**

1. 第一次：`PUT /api/posts/1/like`。`like(1, 7)` → `requirePostExists(1)` 通过 → `insertIgnore(7, 1)`：`(7, 1)` 不在表里，插入成功，**返回 1** → 进 `if` → `addLikeCount(1, 1)`，`like_count` 从 3 变 4。
2. 第二次：同一个人再点。`insertIgnore(7, 1)`：`(7, 1)` 已在表里，主键冲突，`IGNORE` 跳过，**返回 0** → `if (0 > 0)` 不成立 → **`addLikeCount` 根本不会被调用**，`like_count` 还是 4。
3. 接口两次都返回成功，`t_post_like` 里始终只有一行。这就是"重复点不出错"的全部实现。

如果第 2 步少写了 `if (... > 0)`，`like_count` 会变成 5——**表面上完全正常**，前端不会报错，只是数字不对。这条由 `InteractionServiceTest.repeatedLikeDoesNotBumpCount` 钉住。

**场景二：两个人（或两个请求）几乎同时第一次点同一条帖子**

1. 请求甲和请求乙都执行 `INSERT IGNORE INTO t_post_like (user_id, post_id)`。若两人是**同一个用户**（比如同一个人双击了两次按钮），两边的 `(user_id, post_id)` 一模一样。
2. 数据库的主键约束拦下第二个：甲返回 1，乙返回 0。**乙不报错**，只是被忽略。
3. 甲进 `if` 给计数 +1，乙不进。最终 `t_post_like` 多一行、`like_count` 只 +1，**没有任何一行因为并发而丢失或重复**。
4. 若两人是**不同的用户**，主键不同，两边都插入成功、各返回 1，两边的计数各 +1——结果同样是正确的。

这两种情况都靠"主键 + 一条语句"完成判断，中间没有窗口——这正是它比"先查再插"可靠的地方。

**场景三：没点过赞就调取消点赞**

1. `DELETE /api/posts/1/like`。`unlike(1, 7)` → `delete(7, 1)`：表里没有 `(7, 1)` 这一行，`DELETE` 影响 **0 行**，返回 0。
2. **不报错**（`DELETE` 对"没找到"本来就不报错），也不进 `if` → **计数一动不动**。
3. 接口返回成功。这是幂等的：取消一个本来就没发生的动作，结果和"取消了"一样——什么都没变。

如果第 2 步没判断，`addLikeCount(1, -1)` 会把 `like_count` 减 1——**减掉的是别人的赞**。

**场景四：未登录的人看详情**

1. `GET /api/posts/1`（公开接口，`SecurityConfig` 里 `GET /api/posts/*` 已放行）。
2. `@AuthenticationPrincipal Long viewerId` 拿不到登录信息，**是 `null`**。
3. `getDetail(1, null)` → 走到 `interactionService.liked(1, null)` → `userId != null` 短路，**直接返回 `false`，连 `exists` 查询都不发**。
4. 响应里 `liked: false, collected: false`，同时 `likeCount: 4`（真实值）。**这两个 `false` 的含义是"你没登录"，不是"这条帖子没人点过赞"**——前端要判断有没有人点过，看的是 `likeCount`。

## 面试会追问

**Q：重复点赞为什么不用"先查有没有点过、没有就插"？**
那中间有窗口。两个并发请求都先 `SELECT`、都查到"没点过"，然后都 `INSERT`——如果主键不存在就会插进两条（或一条报错）。应用层的"查"和"写"是两条语句、隔着时间；而联合主键的冲突判断在**一条语句内部**完成，没有窗口。所以幂等交给 `INSERT IGNORE` + 主键（ADR-0017）。

**Q：那 `INSERT IGNORE` 有什么副作用？它会不会把别的错误也一起吞掉？**
`IGNORE` 会把插入过程中的**多种**警告/错误降级为"跳过"（不只是主键冲突）。本项目这两张表只有联合主键这一个唯一约束、字段全是 `NOT NULL` 且都有值，所以"被忽略"只可能是主键冲突。更复杂的表用 `INSERT IGNORE` 前要先想清楚它还可能忽略什么——这里可以放心是因为表足够简单。

**Q：`insertIgnore` 的返回值你用在哪了？**
用在"要不要动计数"这个判断上。返回值是"真的插进去了吗"：1 = 插进去了，0 = 撞主键被忽略。**只有 1 才给帖子点赞数 +1**。少了这个判断，同一个人点十次赞，帖子的点赞数就是十——而且不会报错，只是界面上一个没人看得出错在哪的数字。

**Q：为什么取消点赞也要判断删了几行？**
删 0 行说明这人根本没点过赞，此时去减计数减掉的就是**别人的赞**——`like_count` 会变成一个比真实点赞人数小的数。所以 `unlike` 里也是 `if (delete(...) > 0)` 才 `addLikeCount(postId, -1)`。

**Q：点赞数是每次实时 `COUNT(*)` 数出来的吗？**
不是，它是 `t_post.like_count` 这个**冗余列**，点赞时 +1、取消时 -1。为什么冗余、代价是什么，见 ADR-0016。这里只强调它和 `insertIgnore` 返回值的关系：冗余计数**必须**由"操作是否真的生效"来驱动，否则它会和真实行数悄悄对不上。

**Q：并发点赞同一条帖子，会不会把计数加错？**
不会。每个请求都是"插入判断 + 单条 `UPDATE ... SET like_count = like_count + 1`"的形式，`UPDATE` 在一条语句里做加法，不经过应用层读改写；而"该不该加"由各自主键插入的返回值决定，互不干扰。

**Q：计数会不会变成负数？**
不会。`addLikeCount` / `addCollectCount` 里都写了 `GREATEST(like_count + #{delta}, 0)`——一旦算出负数就取 0。这是下限保护：负的计数在界面上是个没法解释的数字，排查时很难判断它从哪来。

**Q：`like_count` 和 `t_post_like` 的行数会不会对不上？**
正常情况下不会——两者由同一个事务里的两步一起维护（`@Transactional`），而且计数只在"插入真的成功"时才动。历史上如果出现过对不上的数据，冗余计数只能靠重算修（ADR-0016）。

**Q：详情接口里的 `liked` 是什么？未登录时是什么？**
是"**当前登录的人**点过赞吗"。未登录时 `viewerId` 为 `null`，`InteractionService.liked` 直接返回 `false`，**且不查数据库**。所以前端在未登录时不能拿它判断"这条帖子没人点赞"——判断那个要看 `likeCount`；`liked` 只用来给"赞"按钮显示选中状态。

**Q：为什么未登录时不查库，直接返回 false？**
详情接口是公开的，匿名访问是常见情况。为了一个已知是"你没登录"的结论去查一次数据库是白花一次往返；而且 `exists` 的 SQL 是 `WHERE user_id = ?`，传 `null` 进去语义也没有意义。所以用 `userId != null &&` 短路掉（`InteractionServiceTest.anonymousDoesNotQuery` 钉住了"确实没查库"）。

**Q：对一条不存在的帖子点赞会怎样？**
抛 `A0201` 帖子不存在（`requirePostExists` 里的 `selectById` 查不到）。设计上刻意不"安静地往一张孤儿关联表里插一行"——那样会产生指向不存在帖子的点赞记录。注意 `selectById` 的条件是 `deleted = 0`，所以对**已删除**的帖子点赞也同样报不存在。

**Q：点赞用 `PUT`、取消用 `DELETE`，为什么不用 `POST /like` + `POST /unlike`？**
`PUT` 的语义是"把资源设置成这个状态"，天生幂等——重复调用结果相同，正好是点赞的语义；取消用 `DELETE`，删一个不存在的东西也返回成功，同样是幂等的。这样"重复点"这件事在 HTTP 语义和数据库语义两层都对得上（设计稿 §4）。

**Q：删帖的时候，帖子上那些点赞记录会一起删掉吗？**
不会。`PostService.delete` 只摘标签、标记删除帖子，**完全不碰 `t_post_like` / `t_post_collect`**。理由是帖子上的"点赞数"只在帖子可见时才有意义，而删掉的帖子不可见；记录留着反而保住了"以后恢复帖子"的可能。

**Q：那为什么标签在删帖时要减计数，点赞却不用？**
因为两者的可见范围不同：标签的 `post_count` 是**全站可见**的（标签页上写着"12 篇"），帖子删了必须减，否则数字永远虚高；而 `like_count` 只跟着这一条帖子显示，帖子不可见它就没人在看。所以删帖时标签要 `detachAll`（计数各 -1），点赞收藏什么都不用做。

**Q：为什么这两张表没有 `deleted` 列？全库就它们没有。**
因为"取消点赞"的语义是**这件事没发生过**，留一行 `deleted = 1` 没有意义；而且 `(user_id, post_id)` 这个唯一约束一旦配合逻辑删除，就退化成"要保证有效行唯一"，得改用更绕的方案。这是有意为之，不是漏写（`db/V2__init_content.sql` 里有完整说明）。

**Q：为什么没有 `PostLike` / `PostCollect` 实体类？**
这张表是 `(user_id, post_id)` 联合主键 + 一个时间戳，行本身没有值得建模的状态。所有操作用两个标量（`userId`、`postId`）就够了，建实体只会多一个没人真正需要的类型（`PostLikeMapper` 类注释）。

**Q：点赞和收藏为什么要分成两张表，它们的代码几乎一样？**
选两张专用表是 ADR-0017 的决定，理由（通用表唯一约束要拼四列、索引变宽、漏带类型条件会静默查错）本文不复述。代码看着重复是这份 ADR 明确接受的代价——`PostCollectMapper` 的类注释直接写了"与 `PostLikeMapper` 结构几乎一样，理由见那边的类注释"。两者的差别只有一个：收藏表多一个"按时间倒序看某人收藏了哪些帖子"的用途，`t_post_collect.create_time` 就是为它留的。

**Q：`InteractionService` 为什么不并进 `PostService`？**
`PostService` 已经管着发帖、改帖、删帖、列表、详情、标签六件事，再加点赞收藏它会变成"什么都管"的类，而且得同时认识三张表（`InteractionService` 类注释）。
