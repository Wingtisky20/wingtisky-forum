# 链路讲解 · 评论

> 对着 M2 的真实代码讲一遍：一条评论从"发出去"到"挂在某层楼下面"再到"被删掉"。
> 只讲代码实际怎么走；设计上的"为什么"指向 ADR 与设计稿，不在这里复述第二遍。

---

## 一句话

评论是**两级**的——顶层评论，和挂在它下面的回复，**不再往下嵌套**（ADR-0018）；表上用两个字段把这个结构钉死：`parent_id` 记"直接回复的是哪条"，`root_id` 记"属于哪一层楼"，于是"取第 2 页的顶层评论"和"取这一页所有楼的回复"都退化成**普通索引查询**，没有一处递归。发评论和回复走**同一个方法**（区别只在给不给 `parentId`），删顶层评论会连带删掉它下面的回复，而连带删掉的条数是从 SQL 的返回行数里直接拿的——**不多查一次计数，也不会让显示与计数对不上**。

## 数据怎么走

### 写：`POST /api/posts/{postId}/comments`（发评论 **或** 回复）

```
CommentController.create(postId, userId, CreateCommentRequest)
      │  带 parentId 就是回复；不带就是顶层评论——同一个请求形状
      ▼
CommentService.create(postId, authorId, parentId, content)   ← @Transactional
      │
      ├─ postMapper.selectById(postId) 为空 → POST_NOT_FOUND (A0201)
      │
      ├─ parent = (parentId == null) ? 0 : parentId
      │  root   = 0
      │
      ├─ if (parent != 0)                        ← 这是回复，不是顶层
      │       ├─ commentMapper.selectById(parent) 为空 → COMMENT_NOT_FOUND (A0202)
      │       ├─ 父评论的 postId ≠ 本次 postId → PARAM_INVALID（不许跨帖回复）
      │       └─ root = 父评论.isTopLevel() ? 父评论.id : 父评论.rootId   ← ★ 最关键的一行
      │
      ├─ commentMapper.insert(comment)
      │       ← useGeneratedKeys 把自增主键回填到 comment.id
      │
      └─ postMapper.addCommentCount(postId, 1)     ← 帖子评论数 +1
  返回 comment.getId()
```

插入评论和帖子评论数 +1 放在**同一个事务**里：分开的话，中间断掉就会出现"评论在、计数不对"，而这种偏差很难被注意到。

### 读：`GET /api/posts/{postId}/comments`（公开接口）

```
CommentController.list(postId, page, size)
      ▼
CommentService.page(postId, page, size)
      │
      ├─ 夹紧 page / size（复用 PostQuery.MAX_SIZE，不复制数字 50）
      │
      ├─ commentMapper.countTopLevel(postId)      ← 先 COUNT
      │        total == 0 就直接返回空页
      │
      ├─ commentMapper.selectTopLevelPage(postId, offset, safeSize)
      │        SELECT <Comment_Columns>           ← 不含 deleted
      │        FROM t_comment
      │        WHERE post_id = ? AND root_id = 0 AND deleted = 0
      │        ORDER BY id DESC LIMIT ? OFFSET ?  ← LIMIT 只作用在顶层评论上
      │        tops 为空（页码越界）→ 立即返回，**必须在这里返回**（见下）
      │
      ├─ commentMapper.selectRepliesByRootIds(rootIds)   ← 一次 IN，取回这一页所有楼的回复
      │
      ├─ userQueryService.findBriefs(authorIdsOf(tops, replies))
      │        ← 顶层与回复的作者**合在一起**去重，只查一次
      │
      └─ 按 root_id 分组 → 每层楼 CommentView.from(楼, 作者, 该楼的回复列表)
         返回 PageResult<CommentView>
```

### 删：`DELETE /api/comments/{id}`

```
CommentController.delete(id)
      │  @PreAuthorize("@commentAuthz.isOwner(#id) or hasAnyRole('MODERATOR','ADMIN')")
      │  ← 接口层只回答"你有没有资格删"，删除规则在 Service 里
      ▼
CommentService.delete(commentId)                            ← @Transactional
      │
      ├─ commentMapper.selectById(commentId) 为空 → COMMENT_NOT_FOUND
      │
      ├─ removed  = commentMapper.softDelete(commentId)          ← 这条本身，返回 1
      ├─ if (这条是顶层评论)
      │       removed += commentMapper.softDeleteReplies(commentId)  ← 连带删除，返回删掉几条
      │
      └─ postMapper.addCommentCount(postId, -removed)            ← 传负数就是减
```

## 逐段讲代码

### 1. 两个"父"字段：`parent_id` 记"直接回复谁"，`root_id` 记"属于哪一层楼"

```java
/** 顶层评论的 {@code parentId} 与 {@code rootId} 都是这个值。 */
public static final long NO_PARENT = 0L;
```

| 字段 | 含义 | 顶层评论的值 |
|---|---|---|
| `parentId` | **直接**回复的那条评论 | `0` |
| `rootId` | 所属的**顶层**评论 | `0` |

顶层评论两个都是 `0`——它不回复谁（`parent_id = 0`），自己就是一层楼（`root_id = 0`）。回复一条顶层评论时，`parent_id` 和 `root_id` 恰好是**同一个值**（那条顶层评论的 id）；回复一条**回复**时，两个才分叉：`parent_id` 指向那条回复，`root_id` 仍指向整层楼的楼顶。

**为什么非得两个字段**——理由见 `ADR-0018 §理由`。一句话版：只有 `parent_id` 的话，"取第 2 页的评论"要先知道哪些是顶层，而顶层判定得**递归**（顺着父链往上找），分页就无从谈起；有了 `root_id`，两个查询都变成普通索引查询。这条索引就是建表脚本里的：

```sql
-- 一个索引服务两个查询：
--   ① 顶层评论分页：WHERE post_id = ? AND root_id = 0
--   ② 某条顶层评论下的全部回复：WHERE root_id = ?
KEY idx_post_root (post_id, root_id, id)
```

`isTopLevel()` 就是"`root_id` 是不是 0"，它是全类里唯一判断层级的依据：

```java
/** 是不是一条顶层评论（它下面可以挂回复）。 */
public boolean isTopLevel() {
    return rootId != null && rootId == NO_PARENT;
}
```

### 2. 发评论和回复是**同一个方法**，区别只在 `parentId` 给不给

```java
@Transactional
public Long create(Long postId, Long authorId, Long parentId, String content) {
    if (postMapper.selectById(postId) == null) {
        throw new BizException(ErrorCode.POST_NOT_FOUND);
    }

    long parent = (parentId == null) ? Comment.NO_PARENT : parentId;
    long root = Comment.NO_PARENT;
    ...
```

请求体也是同一个形状，`parentId` 为 `null` 就是顶层评论：

```java
public record CreateCommentRequest(
        Long parentId,
        @NotBlank(message = "评论内容不能为空")
        @Size(max = 1000, message = "评论最多 1000 个字")
        String content
) {
}
```

不为"回复"单开一个接口，是因为它们在业务上是同一件事，只是"挂在哪"不同。两个接口会让前端发送逻辑分叉，而且业务规则（内容非空、帖子必须存在、计数维护）要写两遍。

进去之后先有一道**跨帖校验**：

```java
if (!parentComment.getPostId().equals(postId)) {
    throw new BizException(ErrorCode.PARAM_INVALID, "不能回复其他帖子下的评论");
}
```

拿另一条帖子下的评论 id 来回复，会让这条评论挂到一个和它上下文无关的楼层下。这类请求通常来自前端 bug 或手工构造，不拦的话数据会悄悄变脏。

### 3. ★ 最容易写错的一行：回复"一条回复"时 `root` 取**父评论的 `rootId`**，不是父评论的 `id`

```java
// ★ 两级模型的关键一行：
//   回复**顶层评论** → root 取被回复评论的 id（它自己就是这一楼）
//   回复**一条回复** → root 取父评论的 rootId（**不是父评论的 id**）
//   第二行取错的话，这条回复会变成一条新的顶层评论（root 指向一条回复的 id，
//   而列表只查 root_id = 0，于是它既不在任何楼里、也不会出现在顶层，
//   **直接消失**）。
root = parentComment.isTopLevel() ? parentComment.getId() : parentComment.getRootId();
```

举例。楼 `100` 下面已经有一条回复 `200`（`parent_id = 100`、`root_id = 100`）。现在有人**回复 200**：

- 正确：`root = parentComment.getRootId() = 100`。新评论 `parent_id = 200`、`root_id = 100`，挂在楼 `100` 下面，跟它的上下文在一起。
- 写错成 `parentComment.getId()`：`root = 200`。列表查回复走的是 `root_id IN (这一页的顶层评论 id)`，只可能有 `100`，**永远匹配不上 `200`**；查顶层又要求 `root_id = 0`，也不匹配。于是这条评论**既不在任何楼里、也不出现在顶层，直接从页面上消失**——数据还在库里，只是页面上找不到它。这种 bug 不会报错，要靠人去看才会发现。

所以这一行有专门的测试钉着（`CommentServiceTest`，用例名 `★ 回复一条回复：rootId 取**父评论的 rootId**，不是父评论的 id`）。ADR-0018 的"后果"一节也写明这条**必须有测试覆盖，不能靠"写的时候注意"**。

注意"回复的回复"是**允许**的，不是错误——它只是被**拍平**到同一层展示（不缩进第二层）。设计稿 §3.3 里那个原计划的错误码 `A0204 不能回复一条回复` 已经作废，因为"拍平"正是两级模型的定义。

### 4. 列表：`LIMIT` 只作用在**顶层评论**上，回复随楼一起返回

```java
int safePage = Math.max(page, 1);
int safeSize = Math.min(Math.max(size, 1), PostQuery.MAX_SIZE);
```

夹紧规则与帖子列表相同（页码 ≥1、每页 1~50），上限 50 这个数字**直接复用 `PostQuery.MAX_SIZE`**，不在评论这边复制一份。

分页的 SQL 把"哪些是顶层"直接写成了等值条件：

```xml
<select id="selectTopLevelPage" resultType="com.wingtisky.forum.forum.content.entity.Comment">
    SELECT <include refid="Comment_Columns"/>
    FROM t_comment
    WHERE post_id = #{postId}
      AND root_id = 0
      AND deleted = 0
    ORDER BY id DESC
    LIMIT #{size} OFFSET #{offset}
</select>
```

`root_id = 0` 这个条件正好用上 `idx_post_root (post_id, root_id, id)`——**这正是当初设 `root_id` 的目的**（ADR-0018）。

**页码超范围时必须提前返回**：

```java
List<Comment> tops = commentMapper.selectTopLevelPage(postId, offset, safeSize);
if (tops.isEmpty()) {
    // 页码超出范围（总共 5 条却要第 100 页）。**必须在这里返回**：
    // 往下走会拼出非法的 IN ()
    return new PageResult<>(List.of(), total, safePage, safeSize);
}
```

因为下一步要拿这一页的顶层 id 去查回复，拼成 `root_id IN (...)`。这一页如果一条顶层评论都没有，这个集合就是空的，`IN ()` 是**非法 SQL**，一执行就炸。而且它只在"页码恰好越界"时才会发生——正是最容易漏测的那一类。代码在调用批量查询**之前**就短路了。

### 5. 两处批量：回复一次取回，作者一次取回

**第一处：这一页所有楼的回复，一条 `IN` 取回**，不是每层楼查一次。

```java
// 一次取回这些楼的全部回复——不是每层楼查一次
Set<Long> rootIds = tops.stream().map(Comment::getId).collect(Collectors.toSet());
List<Comment> replies = commentMapper.selectRepliesByRootIds(rootIds);
```

```xml
<!-- 一次取回多个楼的全部回复。**这是替代 N+1 的那一条查询**——
     写成"每层楼查一次"，一条 100 楼的帖子就是 100 次查询。 -->
<select id="selectRepliesByRootIds" resultType="com.wingtisky.forum.forum.content.entity.Comment">
    SELECT <include refid="Comment_Columns"/>
    FROM t_comment
    WHERE deleted = 0
      AND root_id IN
    <foreach collection="rootIds" item="rootId" open="(" separator="," close=")">
        #{rootId}
    </foreach>
    ORDER BY id
</select>
```

"每条顶层评论查一次"就是 N+1：它不报错，只在一条热帖有上百层楼时表现为"评论页越来越慢"。注意回复按 `id` **升序**（先发的在前）——一个讨论串顺着读才通顺，这和顶层评论按 `id DESC`（最新讨论排前面）是两种不同的意图，XML 注释里都写了。

**第二处：顶层评论与回复的作者合在一起查，只查一次。**

```java
// 一次取回所有相关作者——顶层评论与回复的作者合在一起查，只查一次
Map<Long, UserBrief> authors = userQueryService.findBriefs(authorIdsOf(tops, replies));
```

```java
/** 顶层评论与回复的作者 id 合在一起，去重。 */
private static Set<Long> authorIdsOf(List<Comment> tops, List<Comment> replies) {
    return Stream.concat(tops.stream(), replies.stream())
            .map(Comment::getAuthorId)
            .collect(Collectors.toCollection(HashSet::new));
}
```

作者昵称头像不在评论表里，拿 `author_id` 去用户域的契约 `UserQueryService.findBriefs` 批量换回——这套路子和帖子列表完全一样，细节不再重复（见 `07-帖子读写链路.md` 第 4 段与 `ADR-0015`）。关键的用法是：**顶层和回复的 `author_id` 合成一个 `Set`**（同一个人既评论又回复会去重），所以整页只发一次用户查询，不是"每层楼一次 + 每条回复一次"。

拿到 `Map` 之后，按 `root_id` 分组，每层楼配上自己的回复：

```java
Map<Long, List<Comment>> repliesByRoot = replies.stream()
        .collect(Collectors.groupingBy(Comment::getRootId));

List<CommentView> items = tops.stream()
        .map(top -> CommentView.from(
                top,
                authors.get(top.getAuthorId()),
                repliesByRoot.getOrDefault(top.getId(), List.of()).stream()
                        .map(reply -> CommentReply.from(reply, authors.get(reply.getAuthorId())))
                        .toList()))
        .toList();
```

作者被逻辑删除（注销）时 `authors.get(...)` 返回 `null`，DTO 的 `author` 就是 `null`，前端显示"已注销用户"而不是崩掉。

### 6. 回复和顶层评论是**两个类型**，不是一个类型的自引用

`CommentView`（顶层评论，带 `replies` 列表）和 `CommentReply`（回复）是两个独立的 record。回复这个类型里**根本没有 `replies` 字段**：

```java
public record CommentReply(
        Long id,
        Long authorId,
        UserBrief author,
        String content,
        Long parentId,
        LocalDateTime createTime
) {
```

这是故意的：两个类型把"只有两级"这件事**写进了类型系统**——不可能有人给一条回复挂第三层，因为那个字段压根不存在。如果用一个自引用的 `CommentView`（`replies` 里还是 `CommentView`），"可以挂第三层"这个可能性就一直开着，只能靠 review 去发现有没有人用错。

`CommentView.replies` 有一条约定：**不会是 `null`**，没有回复时是空列表（上面 `getOrDefault(top.getId(), List.of())` 保证了这一点）。另外回复**不单独分页**——两级模型下一条顶层评论的回复通常是个位到几十条，跟着一起返回最省事；真出现"一楼几千条回复"再给回复单独开分页接口（现在不做，YAGNI）。

`CommentReply.parentId` 也值得看一眼：它指向的**可能是顶层评论，也可能是另一条回复**，后者说明这是一条"回复的回复"——被拍平到了同一层。字段注释里写明了这是允许的，不是错误。

### 7. 删顶层评论会连带删掉它下面的回复

```java
@Transactional
public void delete(Long commentId) {
    Comment comment = commentMapper.selectById(commentId);
    if (comment == null) {
        throw new BizException(ErrorCode.COMMENT_NOT_FOUND);
    }

    int removed = commentMapper.softDelete(commentId);
    if (comment.isTopLevel()) {
        removed += commentMapper.softDeleteReplies(commentId);
    }

    // 传负数就是减。SQL 里有 GREATEST(..., 0) 兜底，不会减成负数
    postMapper.addCommentCount(comment.getPostId(), -removed);
}
```

**为什么这么选**——理由见 `ADR-0018` 与 `CommentService` 的方法注释：回复脱离上下文后读不通（"他在回复什么？"），而连带删除让**显示与计数天然一致**——否则那些回复会挂在一个看不见的父评论下，永远不显示、却仍占着帖子的评论数。所以删一条回复**不**连带（`if (comment.isTopLevel())` 才会走连带分支），删顶层评论才连带。

连带删掉的条数是**从 SQL 的返回行数里直接拿的**：

```xml
<update id="softDeleteReplies">
    UPDATE t_comment
    SET deleted = 1
    WHERE root_id = #{rootId} AND deleted = 0
</update>
```

`softDeleteReplies` 返回删掉了几行，`removed += ...` 把这条顶层评论自己和它的回复加起来，一次 `addCommentCount(postId, -removed)` 就减到位——**不必再单独发一条 `COUNT(*)` 去数回复有几条**。这里能这么用，是因为 `softDelete` / `softDeleteReplies` 都带 `AND deleted = 0`，软删除是 `0 → 1` 的确定变化，所以"受影响行数"就等于"确实删掉了几条"，可信。

SQL 侧还有一处下限保护：

```xml
<!-- 评论数增减。delta 可能是负数（删评论）。
     GREATEST(..., 0) 是下限保护：计数一旦变成负数，界面上是个没法解释的数字，
     而且排查时很难判断它从哪来。 -->
<update id="addCommentCount">
    UPDATE t_post
    SET comment_count = GREATEST(comment_count + #{delta}, 0)
    WHERE id = #{postId} AND deleted = 0
</update>
```

### 8. 归属校验：`@commentAuthz.isOwner(#id)`（与帖子那套同一个套路）

删评论的"这是不是你的"由接口层的一个 Bean 回答，Service 里**不放鉴权**：

```java
@DeleteMapping("/comments/{id}")
@PreAuthorize("@commentAuthz.isOwner(#id) or hasAnyRole('MODERATOR', 'ADMIN')")
```

`CommentAuthzService`（Bean 名 `commentAuthz`）与帖子那边的 `postAuthz`、用户域的 `authz` **长得一样但管的资源不同**——三个 `isOwner` 的参数分别是**评论 ID / 帖子 ID / 用户 ID**，传串了不会报错，只会判错。它的实现是拿评论 ID 查出真实 `authorId` 再和当前登录用户比：

```java
public boolean isOwner(Long commentId) {
    Long currentUserId = CurrentUser.id();
    if (currentUserId == null || commentId == null) {
        return false;
    }
    Comment comment = commentMapper.selectById(commentId);
    return comment != null && currentUserId.equals(comment.getAuthorId());
}
```

"为什么不能直接复用 `@authz.isOwner`""为什么删帖给版主、改帖不给"这些在 `07-帖子读写链路.md` 第 6 段已经讲过，是同一个模式，这里只留结论：**判断"这东西是不是你的"，必须由拥有这份数据的域来做**。

## 走一遍场景

**场景一：匿名用户翻某帖的评论列表**

1. `GET /api/posts/7/comments?page=1&size=20`。这是公开接口，SecurityConfig 里单独放行了它：

   ```java
   .requestMatchers(HttpMethod.GET, "/api/posts/*/comments").permitAll()
   ```

   只放行 GET——同一个路径上的 POST（发评论）仍要登录。漏放行一个公开接口的表现是匿名访问 401（一眼能发现），比"漏列一个需要鉴权的接口导致它完全敞开"安全（设计稿 §4 的说明②）。

2. `CommentService.page`：夹紧参数 → `countTopLevel(7)`。总数为 0 就直接返回空页。
3. `selectTopLevelPage(7, 0, 20)`：`WHERE post_id = 7 AND root_id = 0 AND deleted = 0 ORDER BY id DESC LIMIT 20 OFFSET 0`，走 `idx_post_root`。拿回这一页的顶层评论（假设是楼 `100`、`105`）。
4. 把楼 id 收成集合 `{100, 105}`，`selectRepliesByRootIds` 发**一条** `... WHERE deleted = 0 AND root_id IN (100, 105) ORDER BY id`，取回这两层楼的全部回复。**这是 1 次查询，不是 2 次。**
5. `authorIdsOf(tops, replies)` 把顶层和回复的作者 id 合并去重，一次 `findBriefs(...)`。**又是 1 次查询。**
6. 按 `root_id` 分组，每层楼拼成 `CommentView{楼, author, replies}`，回复是 `CommentReply`（只有一条 `parentId`，没有更深的层）。返回 `PageResult`。

**场景二：有人回复"楼里的一条回复"**

1. `POST /api/posts/7/comments`，body `{"parentId": 200, "content": "..."}`。`200` 是楼 `100` 下面的一条回复（`parent_id = 100`、`root_id = 100`）。
2. `create` 先确认帖子 `7` 存在。
3. `parent = 200`，进 `if (parent != 0)` 分支：查出评论 `200`；`200.getPostId()` 等于 `7`，跨帖校验通过。
4. `200.isTopLevel()` 是 `false`（它的 `root_id = 100 ≠ 0`），所以 `root = 200.getRootId() = 100`。**如果这里写成了 `200.getId()`，新评论的 `root_id` 就是 `200`，将永远不在任何列表里出现。**
5. `insert` 一条 `parent_id = 200`、`root_id = 100` 的评论；`addCommentCount(7, 1)`。返回新评论 id。

**场景三：作者删掉楼 `100`（它下面有 3 条回复）**

1. `DELETE /api/comments/100`。`@commentAuthz.isOwner(100)` 先跑：查出评论 `100` 的 `authorId`，和当前登录用户比；不是作者就看有没有 `MODERATOR` / `ADMIN` 角色，都不是就 403。
2. 进 `CommentService.delete(100)`：`selectById(100)` 确认存在。
3. `softDelete(100)` 返回 `1`（评论 `100` 本身）；`100.isTopLevel()` 为真，`softDeleteReplies(100)` 发一条 `UPDATE ... WHERE root_id = 100 AND deleted = 0`，返回 `3` 并加到 `removed` 上，`removed = 4`。
4. `addCommentCount(7, -4)`：一条 `UPDATE ... SET comment_count = GREATEST(comment_count - 4, 0)`。**一次 UPDATE 到位，没有再发一条 `COUNT(*)` 去数回复。** 显示与计数天然一致。

**边界：请求第 100 页，但总共只有 5 条顶层评论**

`countTopLevel` 返回 5（不是 0），所以不会走"总数 0 直接返回"；`selectTopLevelPage(7, offset, 20)` 查到 `offset` 之后一条都没有，`tops.isEmpty()` 为真 → **在这里返回空页**。若跳过这个判断，下面会拿空集合去拼 `root_id IN ()`，非法 SQL 直接报错。

## 面试会追问

**Q：评论为什么用两个字段 `parent_id` 和 `root_id`，一个不够吗？**
不够。只有 `parent_id` 的话，"第 2 页的顶层评论"要先知道哪些是顶层，而顶层判定要**递归**（顺父链往上找），分页就无从谈起。有了 `root_id`，两个查询都是普通索引查询，正好用上 `idx_post_root (post_id, root_id, id)`（`ADR-0018 §理由`、设计稿 §2.4）。

**Q：`root_id` 是不是冗余字段？它和 `parent_id` 不是经常一样吗？**
回复顶层评论时两者确实相同，但**回复一条回复时就分叉了**：`parent_id` 指向那条回复，`root_id` 仍指向楼顶。这个"分叉"正是两级模型的关键；冗余换来的是一次索引查询就能取到"一层楼的某种东西"，不必递归。

**Q：回复"一条回复"时，`root_id` 取什么？取错会怎样？**
取**父评论的 `rootId`**（`CommentService.create` 里 `parentComment.isTopLevel() ? parentComment.getId() : parentComment.getRootId()`）。取错成父评论的 `id` 的话，新评论的 `root_id` 会指向一条**回复**：列表查回复是 `root_id IN (顶层评论 id)`，匹配不上；查顶层要求 `root_id = 0`，也匹配不上——这条评论**既不在任何楼里、也不出现在顶层，直接从页面上消失**（数据还在库里）。不报错，只能靠测试钉（`CommentServiceTest` 有专门用例）。

**Q：为什么不干脆做成无限级树？**
树形要递归查询、折叠展示、按根聚合分页，复杂度换来的表达力在本场景用不上——**掘金、牛客、Hacker News 实际展示的都是两级**。代价明确：回复的回复被拍平（展示在同一个楼里，不缩进第二层），原始指向存在 `parent_id` 里，将来真要树形，加一个 `depth` 就能重建，不用改已存的数据（`ADR-0018`）。

**Q：爬评论列表会不会 N+1？**
不会，两处都是批量的。回复用**一条** `selectRepliesByRootIds`（`root_id IN (...)`）取回整页所有楼的回复，而不是每层楼查一次；作者用**一次** `findBriefs` 把顶层和回复的 `author_id` 合在一起去重后查回（`ADR-0015`）。写 N+1 不会报错，只在数据多起来后表现为"评论页越来越慢"。

**Q：为什么"总数 0"和"页码越界"都要提前返回？**
两个是不同情况。总数 0 时连顶层列表都不用查；页码越界时列表查出来是空，但如果不在这里返回，下一步拿空集合去拼 `root_id IN ()`——**非法 SQL**，只在页码恰好越界时才炸，最难测。所以 `if (tops.isEmpty()) return ...` 这句必须在调批量查询之前。（同一类"空集合短路"在 `UserQueryServiceImpl.findBriefs` 里也有一份，见 `07-帖子读写链路.md`。）

**Q：删顶层评论为什么连带删回复？删掉的条数怎么算的？**
理由：回复脱离上下文读不通（"他在回复什么？"），而且连带删除让**显示与计数天然一致**，否则回复会挂在看不见的父评论下、永远不显示却仍占评论数。条数不用另查——`softDelete` 返回 1（这条本身），`softDeleteReplies` 返回它删掉几条，相加即 `removed`，一次 `addCommentCount(postId, -removed)`。能这么用是因为两条 UPDATE 都带 `AND deleted = 0`，软删除是 `0 → 1` 的确定变化，"受影响行数"可信（`CommentService` 方法注释、`CommentMapper` 注释）。

**Q：为什么删顶层连带，删一条回复却不连带？**
删回复时它下面本来就没有东西——两级模型里回复不能挂回复。连带逻辑写成 `if (comment.isTopLevel())`，只有顶层评论才会去删它的回复。

**Q：计数会不会减成负数？**
不会。`addCommentCount` 的 SQL 是 `SET comment_count = GREATEST(comment_count + #{delta}, 0)`，负数的 delta 是"减"，`GREATEST(..., 0)` 兜住下限。计数一旦变负，界面上是个没法解释的数字，排查时很难判断它从哪来。

**Q：`CommentView` 和 `CommentReply` 为什么是两个类型，而不是一个自引用类型？**
两个类型把"只有两级"写进类型系统——`CommentReply` **没有** `replies` 字段，第三层在类型上就不可能出现。自引用类型会让"能挂第三层"这个可能性一直开着，只能靠 review 发现有没有人用错。

**Q：能回复一条回复吗？设计稿里那个 `A0204 不能回复一条回复` 呢？**
能。回复的回复是**允许**的，只是被拍平到同一层展示（不缩进第二层），这正是两级模型的定义。设计稿 §3.3 里的 `A0204` **已作废**——初稿说它是错误，与 §2.4 / ADR-0018 的"拍平"直接矛盾，按 §2.4 处理，`ErrorCode` 里留了注释说明它为什么不存在。

**Q：为什么不把评论的 `content` 或作者昵称冗余进帖子表，省一次查询？**
作者信息走契约批量查、不做快照的理由见 `ADR-0015 §理由`（快照省一次查询的代价，是用户改昵称后历史内容永远停在旧值，且没有任何机制去修它）。本题的评论侧作者查询已经并进那次批量，没有额外开销。
