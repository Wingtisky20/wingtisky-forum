# 链路讲解 · 注册与登录

> 讲两条写链路：注册（`POST /api/auth/register`）和登录（`POST /api/auth/login`），
> 外加它们各自的下游——登录签发的那对令牌怎么用（刷新 / 注销）。
>
> 本文只讲**代码实际怎么走**。涉及"为什么这么设计"的取舍，凡是 ADR 或设计稿已写过的，
> 这里只指路不复述——复述会造出第二个事实源，改了代码却忘了改文档时，两个源就开始打架。

---

## 一句话

注册是**把用户写进库、把 BCrypt 哈希存进 `password` 列**，重名靠数据库唯一索引拦；
登录是**拿明文密码去比库里的哈希**，比错和不存在的用户返回一模一样的结果（防枚举），
比对了就签发一对令牌——**access 无状态、带 roles，refresh 有状态、只带 jti 并落 Redis**。

---

## 数据怎么走

**注册**

```
POST /api/auth/register
  └─ AuthController.register(@Valid RegisterRequest)
       └─ UserService.register(username, password, nickname)
            ├─ passwordEncoder.encode(rawPassword)        ← 明文变 BCrypt 哈希
            ├─ userMapper.insert(user)                    → t_user
            │     └─ 唯一索引 uk_username 冲突 → DuplicateKeyException
            │          └─ 捕获 → BizException(USERNAME_EXISTS)
            ├─ roleMapper.selectByCode("USER")            ← 取默认角色
            └─ userRoleMapper.insert(userId, roleId)      → t_user_role
  └─ Result.success(user.getId())                         ← 只回一个 id
```

**登录**

```
POST /api/auth/login
  └─ AuthController.login(@Valid LoginRequest)
       └─ AuthService.login(username, rawPassword)
            ├─ UserService.authenticate(username, rawPassword)
            │     ├─ userMapper.selectByUsername(username)  → t_user
            │     ├─ passwordEncoder.matches(raw, hashOrEqualizer)  ← 比对
            │     │     └─ 失败 → BizException(LOGIN_FAILED)  ← 两种失败同一个码
            │     └─ !user.isActive() → BizException(ACCOUNT_DISABLED)
            ├─ UserService.getRoleCodes(userId)             → t_user_role JOIN t_role
            └─ issueTokens(user, roles)
                  ├─ tokenProvider.issueAccessToken(id, username, roles)  ← roles 进载荷
                  ├─ tokenProvider.issueRefreshToken(id)                  ← 只有 jti
                  └─ refreshTokenStore.save(userId, refresh.jti())        → Redis
  └─ Result.success(LoginResult)   ← accessToken / refreshToken / 两个过期秒数
```

两条链路都不经过 HTTP 之外的任何东西：`UserService` 只做领域逻辑，`AuthService` 只管令牌，
`AuthController` 只管把 DTO 拆成参数、把实体折成返回值。

## 逐段讲代码

### 1. AuthController —— 参数的入口，只管转发

```java
@PostMapping("/register")
public Result<Long> register(@Valid @RequestBody RegisterRequest request) {
    User user = userService.register(request.username(), request.password(), request.nickname());
    return Result.success(user.getId());
}
```

它做的事只有三件：`@Valid` 触发 DTO 上的校验、把 record 拆成三个参数、把实体折成一个 id 返回。
`Result.success(user.getId())` 这一步很关键——**返回的是 id，不是 `User`**。
`User` 里有一个 `password` 字段（存的是哈希），直接返回实体会把它一起吐给前端。
这条约束不是靠自觉，是靠 Task 7 的测试钉住的：断言响应 JSON 里不含 `password` 字段。

注册接口**刻意不发令牌**，注释里写得很直白：

> 只返回新用户的 ID，**不顺手发令牌**——注册成功不等于要立刻登录，
> 让前端显式走一次登录流程，两条路径的代码就只有一条需要维护。

登录和刷新都是纯转发，没有分支逻辑：

```java
@PostMapping("/login")
public Result<LoginResult> login(@Valid @RequestBody LoginRequest request) {
    return Result.success(authService.login(request.username(), request.password()));
}
```

注销不一样，它要拿到"当前是谁"：

```java
@PostMapping("/logout")
public Result<Void> logout(@AuthenticationPrincipal Long userId) {
    authService.logout(userId);
    return Result.success();
}
```

`@AuthenticationPrincipal` 取的是过滤器塞进 `SecurityContext` 的 principal——就是 `userId`。
这是个 `Long`，不是 `UserDetails`，说明这里的认证主体从一开始就被设计成"一个用户 id"。
能走到方法体里就说明认证已通过（否则被拦在过滤器链外面），所以方法体里不需要判空。

### 2. 两个 DTO：校验放在边界，且故意不对称

`RegisterRequest` 上的注解很密：

```java
@NotBlank(message = "用户名不能为空")
@Size(min = 3, max = 32, message = "用户名长度需在 3~32 之间")
@Pattern(regexp = "^[A-Za-z0-9_-]+$", message = "用户名只能包含字母、数字、下划线、连字符")
String username,

@NotBlank(message = "密码不能为空")
@Size(min = 8, max = 64, message = "密码长度需在 8~64 之间")
String password,
```

`LoginRequest` 上就只有 `@NotBlank`：

```java
@NotBlank(message = "用户名不能为空")
String username,

@NotBlank(message = "密码不能为空")
String password
```

**登录刻意不校验密码长度。** 这段的不对称是有原因的，而且这个原因本身就是防枚举的一部分：
注册时要求至少 8 位，登录时不该重复这条规则。老用户的密码可能是规则变更前设的；
更要紧的是，**登录接口的校验信息会变成攻击者的探测工具**——如果登录时报"密码长度不足 8 位"，
攻击者就多了一个可观察的维度，能靠"格式错"和"密码错"两种反馈区分出不同情况，
而防枚举要做到的恰恰是"任何失败看起来都一样"。

### 3. PasswordEncoderConfig —— 一个 Bean，BCrypt

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

就一个 Bean，但它是后面时序均衡的前提。**BCrypt 为什么够用**，这段理由写在类的注释里，两点：

- **自带随机盐**，同一个密码每次编码结果都不同——数据库泄露后没法用彩虹表批量破解；
- **故意设计得慢**（可调代价因子）。正常登录多花约 100 毫秒无感，而暴力破解的尝试成本被抬高几个数量级。

反过来说，用 SHA-256 这类"快"哈希存密码是典型的错误：快哈希在正常场景下是优点，
存密码时正好变成缺点——攻击者用同样的快，对着一张泄露的表一秒钟能试几亿个。

注释末尾还有一条反向警告，容易被忽略但很实用：

> **不要把这里的编码器拿去哈希别的数据**（比如缓存 Key、幂等标识）。
> 它慢是特性不是缺陷，用在高频路径上会拖垮吞吐。

### 4. UserService.register —— 唯一性交给数据库

注册的骨架是这样：

```java
@Transactional
public User register(String username, String rawPassword, String nickname) {
    User user = new User();
    user.setUsername(username);
    user.setPassword(passwordEncoder.encode(rawPassword));
    user.setNickname(nickname);
    user.setStatus(User.STATUS_ACTIVE);

    try {
        userMapper.insert(user);
    } catch (DuplicateKeyException e) {
        log.debug("用户名已存在: {}", username);
        throw new BizException(ErrorCode.USERNAME_EXISTS);
    }

    Role defaultRole = roleMapper.selectByCode(RoleCode.USER.name());
    if (defaultRole == null) {
        log.error("默认角色 {} 未在 t_role 表中初始化，注册无法完成", RoleCode.USER);
        throw new BizException(ErrorCode.SYSTEM_ERROR);
    }
    userRoleMapper.insert(user.getId(), defaultRole.getId());

    log.info("新用户注册: id={}, username={}", user.getId(), username);
    return user;
}
```

几个点：

- **唯一性靠数据库唯一索引，不是"先查再插"。** `selectByUsername` 查不到就插入，这个写法在并发下有窗口：
  两个请求同时查到"没被占用"，然后都插入成功，库里出现两行同名。捕获 `DuplicateKeyException` 是唯一
  可靠的做法——把判断交给数据库，因为只有它持有真正的锁。
- **重名只记 `debug`。** 用户重复注册是正常的业务失败，不是系统故障。记成 warn/error 会让日志淹没在正常流量里。
- **默认角色查不到是部署问题，不是用户问题。** `t_role` 里没有 `USER` 说明建表脚本的角色初始化没跑，
  这是 `SYSTEM_ERROR`（500），细节只进日志不进响应——否则等于把内部表结构告诉调用方。
- **`@Transactional`** 让"插用户 + 插角色关联"要么都成要么都不成，不会留下一个没有角色的用户。

`insert` 之后紧接着用 `user.getId()` 建角色关联，这里有个隐藏前提——`UserMapper.xml` 里：

```xml
<insert id="insert" useGeneratedKeys="true" keyProperty="id">
    INSERT INTO t_user (username, password, nickname, avatar, email, status)
    VALUES (#{username}, #{password}, #{nickname}, #{avatar}, #{email}, #{status})
</insert>
```

`useGeneratedKeys="true" keyProperty="id"` 把自增主键回填到入参对象的 `id` 上。
**少了它 `user.getId()` 就是 `null`**，表现为"角色关联插入了 null"——这个报错离原因很远，不好查。

### 5. 唯一索引长什么样（V1__init_user.sql）

```sql
    PRIMARY KEY (id),
    -- 唯一索引建在 username 单列上，**不带 deleted**。
    -- 后果：用户被逻辑删除后，其用户名不会释放（别人不能注册同名）。
    -- 这是有意的取舍——若把 deleted 加进索引，同一个用户名可以存在多条
    -- "已删除"记录，反而要靠额外的清理逻辑才能保证唯一；而"用户名不释放"
    -- 对一个技术社区来说完全可以接受（多数平台都是这么做的）。
    UNIQUE KEY uk_username (username)
```

`t_user` 用的是逻辑删除（`deleted` 列），但**唯一索引只建在 `username` 单列上，不带 `deleted`**。
这个取舍值得记：加了 `deleted` 之后，同一个用户名可以同时存在一条"未删"和若干条"已删"，
唯一性反而要靠额外逻辑维持。代价是删掉的用户名不释放，别人不能注册同名——社区类产品接受这一点。

`password` 列也定死在这一步：

```sql
    password    VARCHAR(60)  NOT NULL COMMENT 'BCrypt 哈希，固定 60 字符。绝不明文，绝不进日志',
```

60 是 BCrypt 输出的固定长度（含盐与代价因子），列宽卡死 60 说明这一列**只可能存 BCrypt 哈希**。

### 6. UserService.authenticate —— 防用户名枚举全在这里

这是整条链路里最需要讲清楚的一段。

```java
public User authenticate(String username, String rawPassword) {
    User user = userMapper.selectByUsername(username);

    String hashToCompare = (user == null) ? TIMING_EQUALIZER_HASH : user.getPassword();
    boolean passwordMatches = passwordEncoder.matches(rawPassword, hashToCompare);

    if (user == null || !passwordMatches) {
        log.debug("登录失败: username={}", username);
        throw new BizException(ErrorCode.LOGIN_FAILED);
    }
    if (!user.isActive()) {
        throw new BizException(ErrorCode.ACCOUNT_DISABLED);
    }
    return user;
}
```

**措施一：两种失败返回同一个错误码。** `user == null`（用户名不存在）和 `passwordMatches == false`
（密码错）走的是同一个分支、抛同一个 `BizException(ErrorCode.LOGIN_FAILED)`。
`LOGIN_FAILED` 的定义在 `ErrorCode` 里：

```java
LOGIN_FAILED("A0102", "用户名或密码错误", HttpStatus.UNAUTHORIZED),
```

**"用户名不存在"和"密码错误"返回的 code、message、HTTP 状态三者完全相同**——`A0102` / "用户名或密码错误" / `401`。
`ErrorCode` 的注释解释了为什么：

> **注意：这个码同时用于"用户名不存在"和"密码错误"，是有意为之。**
> 若两者返回不同的错误码或文案，接口就变成了**用户名探测器**——攻击者
> 可以逐个试出哪些用户名真实存在，再对它们集中撞库。

道理很直接：如果"用户名不存在"给一个专门的提示，攻击者拿一份字典挨个打，
凡是返回"用户名不存在"的就划掉，剩下的就是真实存在的账号，再对这批账号集中撞库。
把两种失败压成一个响应，攻击者从响应内容上就区分不出来。

**措施二：抹平响应时间差。** 光有措施一不够。想绕过它，攻击者不需要看懂任何错误码——
**掐表就行**。BCrypt 比对是刻意慢的（约 100 毫秒），如果用户不存在时直接返回、跳过比对，
那"不存在的用户名"会快得多，光看耗时就能枚举出哪些用户名真实存在。所以：

```java
private static final String TIMING_EQUALIZER_HASH =
        new BCryptPasswordEncoder().encode(UUID.randomUUID().toString());
```

用户不存在时，拿这个 `TIMING_EQUALIZER_HASH` 去比一次。结果必然是 `false`，
**但耗时与真实比对一致**。两处都用无参构造的 `BCryptPasswordEncoder`（默认代价因子），
比对的工作量才可比——如果代价因子不同，耗时就又差回去了。

注意它是**随机串在类加载时现算**的，不是硬编码一个字面量。注释里给了理由：
硬编码的值容易被误认为"某个真实密码的哈希"，也容易在迁移中被当成测试数据删掉。

**顺序：先验密码，再看账号状态。** 这是第三个细节。如果先判断状态，那么"账号已被禁用"这个响应
本身就等于告诉攻击者"这个用户名存在"。先验密码则只要密码不对，返回的永远是同一个 `LOGIN_FAILED`；
只有密码对了、账号确实被禁用了，才返回 `ACCOUNT_DISABLED`——而此时对方已经知道密码了，
告诉他账号被禁用不泄露新信息。

**用户名的来源也顺带说一句**：`selectByUsername` 的 SQL 带 `AND deleted = 0`，
所以逻辑删除的用户等于"不存在"，走的也是 `LOGIN_FAILED` 那条路。

```xml
<select id="selectByUsername" resultType="com.wingtisky.forum.forum.user.entity.User">
    SELECT <include refid="Base_Column_List"/>
    FROM t_user
    WHERE username = #{username} AND deleted = 0
</select>
```

### 7. AuthService —— 校验归 UserService，发牌归自己

两个服务的分工写在类注释里：

> UserService 管"这个用户名密码对不对"，AuthService 管"对了之后发给谁什么令牌、怎么撤销"。
> 混在一起会让领域服务开始知道令牌这种传输层概念。

登录本体只有三行：

```java
public LoginResult login(String username, String rawPassword) {
    User user = userService.authenticate(username, rawPassword);
    List<String> roles = userService.getRoleCodes(user.getId());
    return issueTokens(user, roles);
}
```

`getRoleCodes` 走的是 `UserMapper.xml` 里那条 join：

```xml
<select id="selectRoleCodesByUserId" resultType="java.lang.String">
    SELECT r.code
    FROM t_user_role ur
             JOIN t_role r ON r.id = ur.role_id
    WHERE ur.user_id = #{userId}
</select>
```

`issueTokens` 是一对令牌的签发点：

```java
private LoginResult issueTokens(User user, List<String> roles) {
    IssuedToken access = tokenProvider.issueAccessToken(user.getId(), user.getUsername(), roles);
    IssuedToken refresh = tokenProvider.issueRefreshToken(user.getId());
    refreshTokenStore.save(user.getId(), refresh.jti());

    return new LoginResult(
            access.token(), refresh.token(),
            access.expiresInSeconds(), refresh.expiresInSeconds());
}
```

`LoginResult` 里放四个字段：两个 token 加两个过期秒数。**两个过期时间都回给前端**，
是为了让它能提前刷新，而不是等 401 了再补救——后者会让用户看到一次失败的请求。
`LoginResult` 同时也是"Service 不返回实体"这条原则的一处有意例外：
登录的结果本来就不是某个实体，而是"一对令牌 + 过期时间"这个组合概念。

### 8. JwtTokenProvider —— access 带 roles，refresh 只带 jti

这是"双令牌"两个令牌**内容不一样**的地方，也是最容易讲出差别的一段。

**访问令牌**：

```java
public IssuedToken issueAccessToken(Long userId, String username, List<String> roles) {
    Instant now = Instant.now();
    Instant expiry = now.plus(properties.getAccessTtl());
    String jti = UUID.randomUUID().toString();

    String token = Jwts.builder()
            .subject(String.valueOf(userId))
            .claim("username", username)
            .claim(CLAIM_ROLES, roles)
            .id(jti)
            .issuedAt(Date.from(now))
            .expiration(Date.from(expiry))
            .signWith(signingKey)
            .compact();

    return new IssuedToken(token, jti, properties.getAccessTtl().toSeconds());
}
```

**刷新令牌**：

```java
public IssuedToken issueRefreshToken(Long userId) {
    Instant now = Instant.now();
    Instant expiry = now.plus(properties.getRefreshTtl());
    String jti = UUID.randomUUID().toString();

    String token = Jwts.builder()
            .subject(String.valueOf(userId))
            .id(jti)
            .issuedAt(Date.from(now))
            .expiration(Date.from(expiry))
            .signWith(signingKey)
            .compact();

    return new IssuedToken(token, jti, properties.getRefreshTtl().toSeconds());
}
```

两者的差别是：**access 多带 `username` 和 `roles`，refresh 一个都不带。**
access 把 `roles` 写进载荷，是为了验签后直接构造权限、不用查库——这是无状态的价值所在，
也是拆服务时"本地验签"能成立的原因（**为什么值得这么做、代价是什么，见 ADR-0013 §理由，
这里不重复**）。refresh 只用来换新的访问令牌，权限那一刻重新查库取的是最新的；
把 roles 塞进 refresh 反而是把一个可能已过期的角色固化进去。

`IssuedToken` 是个 record，第三个字段是 `jti`：

```java
public record IssuedToken(String token, String jti, long expiresInSeconds) {
}
```

**为什么把 `jti` 一并返回**：刷新令牌的可撤销性靠它。服务端在 Redis 里记下"这个用户当前的 jti 是哪个"，
注销时删掉。只返回 token 字符串的话，调用方还得再解析一次才能拿到 jti。

密钥那段有个"启动即校验"的用法：

```java
this.signingKey = Keys.hmacShaKeyFor(properties.getSecret().getBytes(StandardCharsets.UTF_8));
```

密钥太短时 `hmacShaKeyFor` 抛 `WeakKeyException`——让它在这里失败，而不是等上线后被人穷举出来。
密钥本身来自 `JwtProperties.secret`（绑定 `wt.jwt.secret`），注释明确要求它**必须来自环境变量，
绝不写进配置文件**，越长越好的对称密钥用 `openssl rand -base64 48` 生成。两个有效期也在
`JwtProperties` 里，默认 `accessTtl = 30 分钟`、`refreshTtl = 7 天`。

最后是解析：

```java
public Claims parse(String token) throws JwtException {
    return Jwts.parser()
            .verifyWith(signingKey)
            .build()
            .parseSignedClaims(token)
            .getPayload();
}
```

注释特别提醒这里是 jjwt **0.12** 的写法，不是网上大量仍存的 0.11 旧写法
（`parserBuilder` / `parseClaimsJws` / `getBody` 那套，在 0.12 上编译不过）。
`parse` **不在内部捕获异常转成业务错误**：调用方的处理方式不同——过滤器选择"不设置认证、
让后续规则返回 401"，刷新接口选择"抛业务异常"。在这里吞掉会把两种场景抹平成一种。

### 9. RefreshTokenStore —— 整套认证里唯一有状态的地方

```java
public void save(Long userId, String jti) {
    redis.opsForValue().set(RedisKey.refreshToken(userId), jti, ttl);
}

public boolean isCurrent(Long userId, String jti) {
    return Objects.equals(jti, redis.opsForValue().get(RedisKey.refreshToken(userId)));
}

public void remove(Long userId) {
    redis.delete(RedisKey.refreshToken(userId));
}
```

就存三个操作：写、比、删。几个设计点：

- **存的是 jti，不是令牌串。** 令牌串等于凭据，存进 Redis 会让"Redis 泄露"直接等于"账号被盗"。
  存 jti 只能用来比对，泄露了也无法伪造令牌。
- **必须比对，不能"存在即有效"。** 否则用户注销后重新登录，注销前泄露出去的那张刷新令牌仍然能用——
  因为它对应的 jti 曾经存在过。
- **Key 按 userId 组织**：`RedisKey.refreshToken(userId)` 拼出来是 `wt:auth:refresh:{userId}`。
  这样"注销"就是 `DEL` 一个确定的 Key，不需要先查出令牌内容。代价是同一用户多端登录会互相顶掉
  （后登录的 `save` 覆盖先登录的），本项目接受。

**它是唯一有状态的地方，这件事本身就是要讲的重点**——无状态 JWT 不能撤回是它的固有代价，
这个项目不去对抗它，而是把"可撤销"这一份责任放到刷新令牌上、放到刷新那一刻，
让正常请求零查询。**完整的取舍见设计 §3.2 与 ADR-0013，此处不展开。**

### 10. AuthService.refresh —— 轮换与重新查库

```java
public LoginResult refresh(String refreshToken) {
    Claims claims = parseRefreshToken(refreshToken);

    Long userId;
    try {
        userId = Long.valueOf(claims.getSubject());
    } catch (NumberFormatException e) {
        throw new BizException(ErrorCode.UNAUTHORIZED);
    }

    if (!refreshTokenStore.isCurrent(userId, claims.getId())) {
        log.debug("刷新令牌已失效: userId={}", userId);
        throw new BizException(ErrorCode.UNAUTHORIZED);
    }

    User user = userService.getById(userId);
    if (!user.isActive()) {
        refreshTokenStore.remove(userId);
        throw new BizException(ErrorCode.ACCOUNT_DISABLED);
    }

    List<String> roles = userService.getRoleCodes(userId);
    return issueTokens(user, roles);
}
```

三个点：

- **失败对外都是同一句话 `UNAUTHORIZED`。** `isCurrent` 为假有三种情况——已注销、已被轮换掉、
  这个 jti 从来没发过。区分它们等于告诉攻击者"你偷的这张是不是最新的"，所以对外统一。
  `parseRefreshToken` 同理，把 jjwt 的过期/签名异常统一收成 `UNAUTHORIZED`，不把实现细节透出去。
- **用户角色与状态在这里重新查库**，不吃旧令牌里的信息。这样"改角色"和"封禁账号"能在刷新时
  （最长 30 分钟后）生效，而不是等 7 天。账号被封禁时顺手 `remove` 掉刷新令牌，不让它继续续期。
- **换新令牌就是轮换。** `issueTokens` 里的 `save` 会覆盖 Redis 里的旧 jti，旧刷新令牌当场作废。
  不轮换的话，一张刷新令牌在 7 天里能无限次使用，一旦泄露攻击者能一直续期而用户毫无察觉。

### 11. AuthService.logout —— 幂等的"关闸"

```java
public void logout(Long userId) {
    refreshTokenStore.remove(userId);
    log.info("用户注销: userId={}", userId);
}
```

删掉 Redis 里的刷新令牌，仅此而已。**它的效果是"拿不到新令牌"，不是"立刻踢下线"**——
手上那张访问令牌因为无状态，会一直有效到自然过期（最长 `access-ttl`，30 分钟）。
这是设计 §3.2 明确接受的代价，不是没想到。方法本身幂等：没登录过也能调，不报错。

## 走一遍场景

假设有个用户 `alice` 要注册、登录、用一阵子、注销。

**1. 注册成功。** 她提交 `POST /api/auth/register`，body 里 `username=alice`、`password=...`、`nickname=...`。
`@Valid` 先过一遍：用户名长度 3~32、字符集合法、密码长度 8~64，全过。
`UserService.register` 把密码 `encode` 成一段 60 字符的 BCrypt 哈希，`insert` 进 `t_user`
（`uk_username` 没冲突），拿到回填的自增 id，再给这个 id 挂上 `USER` 角色。响应是 `{"code":"0","data":1}`——
**只有 id，没有令牌**。

**2. 同名再来一次。** 另一个请求也注册 `alice`。`insert` 撞上 `uk_username`，
抛出 `DuplicateKeyException`，被捕获后转成 `USERNAME_EXISTS`。响应是 `409 / A0101 / 用户名已被占用`。
**如果两个 `alice` 的注册请求是同时到的，这个流程照样成立**——数据库的唯一索引是真锁，
后到的那个必然失败。这就是"先查再插"给不了的东西。

**3. 密码错误。** `alice` 登录但密码打错了。`authenticate` 查到 `alice` 这一行，
拿她的哈希比对，`passwordMatches=false`，抛 `LOGIN_FAILED`。
响应 `401 / A0102 / 用户名或密码错误`。

**4. 用户名不存在。** 攻击者试一个 `no_such_user_at_all`。`selectByUsername` 返回 `null`，
于是 `hashToCompare` 取 `TIMING_EQUALIZER_HASH`，照样比一次 BCrypt（约 100ms），结果 `false`，
抛的还是 `LOGIN_FAILED`。响应 **`401 / A0102 / 用户名或密码错误`——和上一步一字不差**（除 `traceId`）。
这两步必须完全一样，`api-smoke.http` 第 5、6 条就是专门按这个写的：

```
### 5. 密码错误
### 期望：401，code=A0102「用户名或密码错误」
...
### 6. 用户不存在
### 期望：**同样是 401 + A0102**，与第 5 条一字不差（除 traceId）
### 这两条必须完全一样——否则接口就成了用户名探测器
```

**5. 登录成功。** `alice` 密码对了，`authenticate` 返回 `User`。
`getRoleCodes` 查出 `["USER"]`。`issueTokens` 签出 access（载荷带 `sub=1`、`username=alice`、`roles=["USER"]`、`jti`）
和 refresh（载荷只有 `sub` 和 `jti`），并把 refresh 的 jti 写进 Redis 的 `wt:auth:refresh:1`。
响应 `data` 里是四个字段：`accessToken`、`refreshToken`、`accessExpiresIn=1800`、`refreshExpiresIn=604800`。

**6. 刷新。** 半小时后 access 过期，前端拿 refresh 打 `POST /api/auth/refresh`。
`parseRefreshToken` 验签通过，`claims.getSubject()` 是 `1`，`isCurrent(1, jti)` 为真，
重新查库确认 `alice` 还是 ACTIVE、角色还是 `["USER"]`，然后签出一对**新的**令牌——
`save` 覆盖 Redis 里的 jti，**旧的 refresh 此刻作废**。如果她手贱再拿旧 refresh 刷一次，
`isCurrent` 就是假，返回 `401`。这就是轮换。

**7. 注销。** `alice` 带 access 打 `POST /api/auth/logout`。过滤器验签通过，
`@AuthenticationPrincipal` 拿到 `userId=1`，`refreshTokenStore.remove(1)` 删掉 Redis 那个 Key。
**效果**：她再也换不到新令牌了；但手上那张 access 还能用到自然过期，**最长再活 30 分钟**。

## 面试会追问

**Q：密码为什么用 BCrypt？它"够用"在哪，为什么不用 SHA-256？**
BCrypt 自带随机盐、天然抗彩虹表，且代价因子可调、故意慢。慢在存密码这个场景下是优点：
正常登录多花约 100ms 用户无感，但暴力破解每次尝试都要付这个成本，整体被抬高好几个数量级。
SHA-256 这类快哈希反过来——快到攻击者可以对着一份泄露的表一秒试几亿个。理由见
`PasswordEncoderConfig` 的类注释，没写进 ADR，因为这是通用做法不是本项目的取舍。

**Q：为什么不存明文或者加密后存？**
加密能解回来，就等于库泄露时密码一起泄露；哈希单向，泄露了也还算不出来（前提是别用弱哈希）。
列宽卡死 60 也是这个意思——那一列只可能装 BCrypt 输出。

**Q：登录失败时"用户名不存在"和"密码错误"能不能给不同提示，方便用户？**
不能，代价太大。给了不同提示，接口就变成用户名探测器：攻击者拿字典挨个打，返回"不存在"的划掉，
剩下的就是真实账号，再集中撞库。所以两种情况返回同一个 `A0102` / "用户名或密码错误" / `401`。

**Q：光把错误码统一就够了吗？**
不够。攻击者不用看错误码，**掐表**就行——BCrypt 慢，如果用户不存在时跳过比对直接返回，
那这种请求会明显更快，光看耗时就能枚举出真实用户名。所以用户不存在时也要拿一个真实哈希
（`TIMING_EQUALIZER_HASH`）比一次，让耗时一致。两处都用默认代价因子的 `BCryptPasswordEncoder`，
工作量才可比。这就是为什么"防枚举"是两条措施，不是一条。

**Q：那个均衡哈希为什么是运行期随机生成，不硬编码一个字面量？**
硬编码的值容易被误认为"某个真实密码的哈希"，也容易在数据迁移中被当成测试数据删掉。
用 `UUID.randomUUID()` 在类加载时现算，既保证它是一个真实可比的 BCrypt 哈希，又不携带任何含义。

**Q：为什么先验密码再判断账号是否被禁用？**
反过来的话，"账号已被禁用"这个响应就等于告诉攻击者"这个用户名存在"——又把枚举的门打开了。
先验密码则密码不对永远返回同一个 `LOGIN_FAILED`；只有密码确实对了、账号确实被禁用，
才返回 `ACCOUNT_DISABLED`，而此时对方已经掌握密码，这个提示不泄露新信息。

**Q：重复注册怎么防？为什么不是先 `selectByUsername` 查一下再插？**
"先查再插"在并发下有窗口：两个请求同时查到"没被占用"，然后都插成功。
正确做法是把唯一性判断交给数据库——建唯一索引 `uk_username`，插入冲突时捕获
`DuplicateKeyException` 转成业务错误。只有数据库持有真正的锁，这个判断在并发下才可靠。
`api-smoke.http` 第 2 条"重复注册"顺带验证了这条索引真的存在。

**Q：用户被逻辑删除后，用户名能重新注册吗？**
不能。唯一索引只建在 `username` 单列、不带 `deleted`，所以删掉的用户名不释放。
这是有意的取舍：带上 `deleted` 会让同一个用户名存在多条"已删"记录、反而要额外的清理逻辑维持唯一；
"用户名不释放"对社区类产品完全可以接受。

**Q：为什么注册接口不直接发令牌，还要用户再登录一次？**
注册成功不等于要立刻登录。让前端显式走一次登录，两条路径的代码就只有一条需要维护（登录那条）。
代价是多一次请求，收益是不用维护两套发令牌的逻辑。

**Q：为什么不把 `roles` 放进刷新令牌？**
刷新令牌只用来换新 access，权限那一刻重新查库取的是最新的。放进刷新令牌反而会把一个可能
已经过期的角色固化进去。访问令牌才需要带 `roles`——为了验签后直接构造权限、不查库。

**Q：为什么 Redis 里存 jti 不存整条令牌串？**
令牌串等于凭据。存进 Redis 会让"Redis 泄露"直接等于"账号被盗"。存 jti 只能用来比对，
泄露了也无法伪造令牌。另外为什么要**比对**而不是"存在即有效"：否则用户注销后重新登录，
注销前泄露出去的那张刷新令牌仍然能用，因为它对应的 jti 曾经存在过。

**Q：注销后旧令牌还能用多久？为什么不做成立即失效？**
最长再活 access-ttl（30 分钟）。要让访问令牌立即失效，只能让每个请求都查一次黑名单，
那就等于用 JWT 的形式做了 Session 的事，还多背一份黑名单——拆服务时"本地验签"这个最大的简化
就没了。所以把"可撤销"挪到刷新令牌上，让正常请求零查询，接受 30 分钟的窗口。
**完整的方案对比见 ADR-0013，别在这里现编。**

**Q：为什么刷新时要轮换刷新令牌？**
不轮换的话，一张刷新令牌在 7 天里能无限次使用，一旦泄露攻击者能一直续期而用户毫无察觉。
轮换后，被偷的那张在用户下次刷新时就作废了。实现上就是每次刷新 `save` 覆盖 Redis 里的 jti。

**Q：多端登录会怎样？**
会互相顶掉。刷新令牌的 Key 按 `userId` 存（`wt:auth:refresh:{userId}`），后登录的覆盖先登录的，
先登录的那端刷不动了。本项目接受这个代价，换来的是"注销 = DEL 一个确定的 Key，不用先查令牌内容"。
