# 协作协议

> 本文件规定"我们怎么一起工作"。**用户参与机制优先级高于任何执行技能的默认行为。**
> 最后更新：2026-09-19

---

## 1. 会话开场流程

用户说「读文档，继续」时，按序读 **3 个文件**：

1. `CLAUDE.md`（自动加载，不用手动读）
2. `docs/STATUS.md` —— 唯一状态源，其中写明「当前上下文文件」清单
3. 本文件

**然后必须先向用户复述**：当前阶段 → 上次做到哪 → 本次要做什么 → 有哪些阻塞。**用户确认后才动手。**

> 这一步是防「AI 自信地跑偏」的关键闸门。漂移症状（中途换约定、推荐不在白名单上的库、重新实现已有工具类、与早先决策矛盾）全都发生在"没复述就直接开干"的对话里。

---

## 2. 用户参与机制（核心）

**判据：「面试可讲性」。** 面试官可能追问"为什么这么做"的决策，用户**必须参与**；纯机械改动（格式化、改错别字）不必打扰。

| # | 机制 | 做法 |
|---|---|---|
| 1 | **任务前置确认（Step 0）** | 每个任务动手前，用人话说清三件事，**等用户回应才动手**：① 这步做什么 ② 为什么现在做、不做会怎样 ③ 有哪几种做法 / 建议哪种 / 代价是什么 |
| 2 | **变更简报** | 每次改动后给「给人看」的简报：改了什么（人话）· 为什么 · **用户怎么自己验证** · 代价与风险 |
| 3 | **设计先于代码** | 设计型产物（模块划分、库表、接口、缓存策略）**先出文档给用户审，再写代码** |
| 4 | **不替用户拍板** | 影响设计的决定须写明「我建议 X，因为 Y」；用户未表态时**不得静默执行** |
| 5 | **暂停权** | 用户说"停，这里我先看看"即停 |

> ⚠️ `subagent-driven-development` 等执行技能默认「任务之间不停下确认，进度汇报是浪费用户时间」。**该默认在本项目失效。**
> 教训来源：2026-09-13 用 subagent 静默执行 Task 1，用户事后才知道 9 个模块已搭好，且说不出为什么。

---

## 3. 会话收场流程（五件事，缺一不可）

1. 更新 `docs/STATUS.md`（进度 + **证据等级** + 下一步 + 阻塞）
2. 更新 `docs/04-log/` 当前阶段的执行记录
3. 有新决策 → 写 ADR
4. `git commit`（严格格式，见 §5）
5. **向用户报告**：真实改了什么、验证到什么程度、遗留什么

---

## 4. 三条防矛盾铁律

| 铁律 | 说明 |
|---|---|
| **单一事实源** | 状态只在 `STATUS.md`；需求只在 PRD；决策只在 ADR。别处**只引用、不复制**——复制必然导致两份打架 |
| **变更留痕** | 推翻旧结论 → **必须新增 ADR** + 在 `STATUS.md` 标注。**禁止静默修改** |
| **里程碑闸门** | 每个里程碑结束打 tag（`m1-done`），可回滚、可对照、可讲 |

## 5. Git 标准

### 5.1 分支模型：GitHub Flow

```
main                          ← 永远可运行，禁止直接 push
 ├─ feature/m3-cache          ← 功能
 ├─ fix/m5-es-sync-timeout    ← 修复
 ├─ docs/adr-0012             ← 文档
 └─ chore/upgrade-nacos       ← 杂项
```

**流程**：切分支 → 小步提交 → **开 PR（哪怕自己合并）** → 自查清单 → **Merge commit（`--no-ff`）** → 删分支。

**为什么单人项目也走 PR**：PR 描述本身是**结构化的变更记录**（做了什么 / 为什么 / 怎么验证的 / 风险），是"可追溯、可讲述"的载体，面试时能说"我每个功能都走 PR 合并，PR 里附验证证据"。

**为什么用 Merge commit 而不是 Squash**（2026-09-19 修订，详见 ADR-0008）：

本项目的核心诉求是「**靠 commit 一步步看清迭代过程**」。而 Squash 会把分支上的提交压成一个——**过程在 main 上就消失了**，与诉求直接冲突。实测：`feature/m0-bootstrap` 领先 `main` 18 个提交，Squash 后 `main` 只多 1 个。

Merge commit 保留每个细粒度提交，同时用 merge 提交标出合并边界；要看干净的主线视图，用 `git log --oneline --no-merges`。

> 早期版本选 Squash，理由是"main 保持干净"。但那把「干净」放在了「可追溯」之上。对本项目而言，**可追溯优先**。

### 5.2 提交信息格式（四节，严格）

```
<type>(<scope>): <subject，≤50字符，祈使句，句末不加句号>

【为什么】
<问题是什么、为什么要改。必须能脱离上下文独立看懂。
写不出"为什么"，说明这个提交不该存在。>

【改了什么】
- <人的意图摘要，不是 diff 的复述>

【验证】
- `<命令>` → <真实结果>

【关联】
Refs: ADR-xxxx
```

| 字段 | 规则 | 可省 |
|---|---|---|
| `type` | `feat` `fix` `docs` `refactor` `perf` `test` `chore` `build` `ci` `revert` | ❌ |
| `scope` | 业务：`m<里程碑>-<域>`（如 `m3-cache`）；基建：`infra`/`build`/`ci`/`docs` | ❌ |
| 【为什么】 | 必填 | ❌ |
| 【改了什么】 | 必填；纯 docs/chore 可省 | ⚠️ |
| 【验证】 | 必填，**附实际执行的命令与真实输出** | ❌ |
| 【关联】 | 有 ADR / issue 时必填 | ✅ |

**禁止**：`fix bug` / `update` / `优化一下` / 空 body / **主体与 diff 不符**。

> **commit 与 ADR 的分工**：commit 说"我这么做了"，ADR 说"我为什么没选另一个方案"。**没有 ADR 的 commit 只有一半信息。**

### 5.3 提交频率与拆分

**一个「功能」应产生 3-8 个提交，而不是 1 个。** 一个工作日通常应有多次提交。

**参照范例**（某成熟 AI 协作项目的真实序列，单日 6 次提交围绕"JWT 认证"**一个**功能）：

| 提交 | 层次 |
|---|---|
| 新增登录注册 JWT 鉴权与认证观测日志 | 骨架 |
| 新增认证续期与用户资料接口契约 | **契约先行** |
| 实现刷新令牌与用户资料认证领域逻辑 | 领域实现 |
| 增强 JWT 双令牌与安全过滤配置 | 装配 |
| 补齐认证接口日志与令牌测试 | 测试 |

**这个顺序本身就是设计**：先定契约 → 再写领域 → 再装配 → 最后补测试。每一步都可独立读懂、独立回滚、独立讲述。

**拆分维度**（按需选用）：契约先行 · 领域与装配分离 · 测试独立 · **修复独立** · 文档独立

**拆分信号**：`【改了什么】` 中出现「并」「和」「顺便」「同时」连接两件不相关的事。

**反例**：
> `feat: 切换 DeepSeek 模型并外置 API Key，修复前端会话列表 Bug` —— 三件事一个提交，**三件都回滚不掉**
>
> `测试` / `更新一下api` —— 零信息量，在 `git log --oneline` 里等于空白

**⚠️ 高频 ≠ 提交半成品**：进入 `main` 的每个提交**都必须可编译**。feature 分支上允许 `wip:`；改用 Merge commit 后，这些 `wip:` 提交会**原样进入 `main`**——约束是"必须可编译"，不是"`main` 上不能有 wip"（ADR-0008）。

**⚠️ 两个改动落在同一文件时，必须「改一个、提交一次」**（2026-09-13 实际踩过）：

`git add <文件>` 会把该文件里**所有**未提交的改动一起暂存。如果先对同一文件做了两处不相关的修改、再一起 `add`，两件事就会挤进同一个提交——**提交信息只说了其中一件，diff 里却有两件**。

这正是闸门 4 要抓的失真，只不过方向相反：不是"说了没做"，是**"做了没说"**。后果一样——读 `git show` 的人不知道另一处改动从哪来、为什么改，也无法单独回滚它。

**做法**：改一处 → `git add` → `git commit` → 再改下一处。写文档时尤其容易犯（一份文档常在多处被改）。

### 5.4 提交前自查

**逐条对照 `git diff`**：确认每条 `【改了什么】` 都能在 `git show` 里找到对应改动。

> 依据：2026 年一项对 23,247 个 AI 提交 PR 的研究显示，**45.4% 存在"说明里声称的改动未实现"**。

### 5.5 回滚

| 场景 | 手段 | 说明 |
|---|---|---|
| 撤销未推送的提交 | `git reset --soft HEAD~1` | 保留改动 |
| 撤销**已推送**的提交 | `git revert <sha>` | **生成反向提交**，不改写历史 |
| 回退整个里程碑 | `git revert <merge-sha> -m 1` 或 checkout tag | 有 tag 锚点 |

**两条铁律**：
1. **`main` 上永不 force push**（公开仓库改写历史会破坏所有引用，是真实事故）。force push 只允许用于自己的 feature 分支。
2. **每次回滚必须留痕**：在 `docs/04-log/` 当前阶段文档中写清「为什么回滚、回滚到什么状态、后续怎么办」。

> 回滚记录本身就是面试素材——「我做过一次回滚，因为 X，回滚后改成了 Y」比「一路顺利」可信得多。

### 5.6 Tag 与 Release

每个里程碑打注解 tag：`git tag -a m1-done -m "..."` 并 push；GitHub 上发 Release（notes 从 `docs/04-log/` 汇总）。

好处：随时 `git diff m2-done m3-done` 即可看到"这个里程碑到底加了什么"——**面试前复盘靠这个**。

## 6. 工程迭代记录

**位置**：`docs/04-log/`（**按功能阶段分文件，非按日期**）

| 规则 | 说明 |
|---|---|
| **分文件** | 默认一个里程碑一份；功能块足够大时独立成篇；**单份超约 500 行即拆** |
| **精炼优先** | 这是给**人和面试官**看的，**不是全量日志。宁少勿多** |
| **上接指针** | 每份开头指向上一份 |

**结构**：

```markdown
# MX 执行记录 · <阶段名>

## 一句话总结
## 产出了什么          表格：产物 / 在哪 / 你怎么打开看
## 关键决策与理由      决策 · 为什么 · 备选 · 代价 · ADR 指针
## 你可以怎么验证      可复制的命令 + 预期输出
## 踩过的坑            真实的，不编
## 遗留与风险
## 回滚记录            无则写"无"
```

**四种追溯载体的分工**（互补，不重复）：

| 载体 | 回答的问题 | 粒度 |
|---|---|---|
| **commit** | 每一步具体改了什么、怎么验证的 | 最小单元 |
| **tag** | 里程碑边界在哪 | 阶段 |
| **ADR** | 为什么这么选、否决了什么 | 决策 |
| **04-log** | 这一阶段为什么这么做、**用户怎么自己验证** | 功能阶段 |

## 7. 防幻觉六道闸门

1. **证据制** —— 结论必附命令 + 真实输出；`STATUS.md` 标注 `[REAL]`/`[SYNTHETIC]`/`[UNVERIFIED]`/`[BLOCKED]`
2. **反验证剧场** —— 端到端必须真实数据（真实 HTTP / 真实 DB 行 / 真实消息）；亮点实测必须有**反面对照**，**单边数据不算证据**
3. **依赖防幻觉** —— 新依赖必须 Maven Central 真实存在 + `mvn dependency:tree` 可解析 + 版本收在父 POM `dependencyManagement`；**禁止**"我记得有个库叫…"
4. **提交与 diff 对账** —— 见 §5.4
5. **高危区点名** —— Spring Security 6 / Boot 3 的 `jakarta.*` / ES 8 Java API Client / Kafka KRaft / Redisson：**先读官方文档或本地 jar 源码，再写代码**；接入后第一关是启动验证
6. **文档-代码对账** —— `tools/check-doc-refs.sh`（文档引用的类必须真实存在）与 `tools/check-deps.sh`（依赖真实可解析），进 CI

## 8. 上下文卫生

- **一个对话一件事**。一个功能做完就收场，不在同一对话连做三个（"context collapse"的成因）
- 对话变长时**主动建议用户开新对话**，而非硬撑到输出质量下降
- 永远不要问「你怎么实现的」，而要告诉下游「我们的约定是什么」

---

## 9. 敏感信息

**密钥、密码绝不入库。**

- 敏感配置走**环境变量**，代码里只读 `${DB_PASSWORD}`
- 提供 `.env.example`（只有占位符），`.env` 进 `.gitignore`
- **万一误提交**：① 立刻改密码 / 吊销密钥 ② `git filter-repo` 清洗历史 ③ force push。**三步缺一不可**（只删文件再提交，历史里还在）
