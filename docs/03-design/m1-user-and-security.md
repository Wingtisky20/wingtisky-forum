## 1. 范围

### 做什么

| 块 | 内容 |
|---|---|
| 用户 | 注册、登录、注销、个人主页、资料修改 |
| 认证 | Spring Security 6 过滤器链 + JWT |
| 鉴权 | RBAC（角色）+ **资源级越权校验** |

### 验收闸门（spec §6.2，不达标不算完成）

1. 限流实测返回 **`429`**
2. **越权访问实测被拒**

## 2. 库表设计

### 2.1 用户表 `t_user`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 自增。**M8 秒杀才需要分布式 ID**，M1 用自增即可，不提前上雪花 |
| `username` | varchar(32) 唯一 | 登录名 |
| `password` | varchar(60) | **BCrypt 哈希**，固定 60 字符。绝不存明文，绝不进日志 |
| `nickname` | varchar(32) | 昵称 |
| `avatar` | varchar(255) | 头像 URL（走本地存储，spec §1.5 不做自建对象存储） |
| `email` | varchar(64) | 可空 |
| `status` | tinyint | 0 正常 / 1 禁用 |
| `create_time` / `update_time` | datetime | |
| `deleted` | tinyint | 逻辑删除 |

> **为什么用逻辑删除**：帖子、订单都会引用用户。物理删除会让历史数据变成孤儿。代价是唯一索引要处理"已删除的用户名还能不能重名"——本项目采取**删除后用户名不释放**（唯一索引加 `deleted` 会破坏唯一性约束，不值得为此引入更复杂的方案）。

### 2.2 角色表 `t_role` + 关联表 `t_user_role`

| `t_role` | | `t_user_role` | |
|---|---|---|---|
| `id` | PK | `user_id` | 联合主键 |
| `code` | `USER` / `MODERATOR` / `ADMIN` | `role_id` | |
| `name` | 普通用户 / 版主 / 管理员 | | |

三个角色来自术语表（`docs/01-requirements/glossary.md`），**不加第四个**。

### 2.3 为什么是两张表而不是三张

**决策点 ①：要不要 `t_permission` 权限表？**

| 方案 | 说明 | 代价 |
|---|---|---|
| **A（建议）** | **两表**：用户 → 角色。权限点写在代码里（`@PreAuthorize("hasRole('ADMIN')")`） | 加"谁能删帖"这种细粒度权限时要改代码 |
| B | 三表：用户 → 角色 → 权限，权限存库 | 多一套表和装配逻辑；但 spec §1.5 **明确不做复杂权限矩阵** |

**选 A。** 本项目只有三个角色，且 spec §1.5 把"复杂权限矩阵"列为不做的事。三张表在这里是**为了显得专业而引入的复杂度**——面试官问"你为什么要权限表"，答案会是"网上都这么建"，这比不做更糟。

**升级路径写清楚**：真需要细粒度时，改动集中在"把角色展开成 `GrantedAuthority` 集合"这一处，业务代码里的 `hasRole` 换成 `hasAuthority` 即可，不用重构。

## 3. 认证方案（JWT 双令牌）

### 3.1 决策点 ②：单令牌还是双令牌

| 方案 | 说明 | 代价 |
|---|---|---|
| A | 单 JWT | 过期时间两难：设短了用户天天重新登录，设长了被盗后长期有效 |
| **B（建议）** | **双令牌**：`accessToken`（短，30 分钟）+ `refreshToken`（长，7 天） | 多一个接口、多一份存储 |

**选 B。**

### 3.2 注销怎么做——无状态 JWT 的固有难题

**这是本方案里最值得讲的一个点，也是面试必问的。**

JWT 是**自包含**的：签出去之后，服务端手里没有它的记录，因此**无法在到期前撤回**。想撤回就得存状态，而存了状态就不再是"无状态"。

**我的选择是不去对抗这个矛盾，而是把它放到该放的地方：**

| 令牌 | 是否可撤销 | 存放 |
|---|---|---|
| `accessToken` | **不可撤销**（纯无状态） | 只在客户端；服务端靠签名本地验签，**不查库不查缓存** |
| `refreshToken` | **可撤销** | **存 Redis**，注销时删除它 |

**注销的实际效果**：`refreshToken` 当场失效 → 拿不到新的 `accessToken`；手里那个旧的 `accessToken` **最多再活 30 分钟**。

**这个代价是明确接受的**，不是没想到：30 分钟的窗口对技术社区够用；要压到零就得让每个请求都查一次黑名单，那样拆分服务时"本地验签"这个最大好处就没了——而 ADR-0010 拆分服务的简化**正是建立在这点上**（spec §12 开放问题 #3）。

> **面试话术**：*"无状态 JWT 不能撤回是它的固有代价，我不去对抗它——我把'可撤销'放在 refresh token 上：access 保持无状态、短命，refresh 有状态、可删。这样注销的窗口从 7 天压到 30 分钟，而正常请求仍然不查任何存储。"*

### 3.3 令牌细节

- **签名算法**：HS256（对称）。理由：本机单进程，M9 才多服务；HS256 只需一个密钥。若将来要第三方验签再换 RS256。
- **密钥**：`JWT_SECRET` **环境变量**，不进仓库（spec §10.9）。提供 `.env.example` 占位。
- **载荷**：`sub`(userId) / `username` / `roles` / `iat` / `exp` / `jti`
  - **`roles` 放载荷里**，是为了本地验签后直接构造权限，不用查库 —— 这正是无状态的价值
  - 代价：改了角色要等 token 过期才生效。30 分钟可接受。
- **Redis key 规范**：`wt:auth:refresh:{userId}` → 值存 `jti`

## 4. 鉴权方案

### 4.1 两层，别混在一起

| 层 | 回答的问题 | 手段 |
|---|---|---|
| **RBAC** | "你**有没有资格**做这类事" | `@PreAuthorize("hasRole('ADMIN')")` |
| **资源归属** | "**这件事的东西**是不是你的" | 查数据比 `authorId` |

**RBAC 管不了资源归属**——管理员和作者都能删帖，但普通用户不能删**别人的**帖。这是两个问题。

### 4.2 决策点 ③：越权校验写在哪

| 方案 | 说明 | 代价 |
|---|---|---|
| A | 每个 Service 方法里手写 `if (!owner.equals(current)) throw ...` | 重复、易漏，**漏一处就是一个越权漏洞** |
| **B（建议）** | 抽 `@PreAuthorize("@authz.isOwner(#id)")`，把归属判断收进一个 Bean | 要多写一个 Bean，且 SpEL 参数要写对 |

**选 B。** 理由不是为了"优雅"，是**为了不漏**：方案 A 的失败模式是静默的——漏写一个 if 不会有任何报错，直到被人利用。收进一处后，新增接口时"忘了加校验"会变成显式的遗漏（能在 code review 或测试里发现）。

**M1 需要校验归属的资源**：用户资料（改自己的）、后续 M2 的帖子、M7 的订单。

## 5. 亮点 5：Redis ZSet 滑动窗口限流

### 5.1 为什么是 ZSet

| 方案 | 问题 |
|---|---|
| 固定窗口计数器（`INCR` + 过期） | **窗口边界能放过接近 2 倍流量**：00:59 打满 100 次，01:00 又打满 100 次，跨边界的 2 秒内实际过了 200 次 |
| **ZSet 滑动窗口（选中）** | 没有边界问题：score 存时间戳，每次只统计"最近 N 秒内"的成员 |
| 令牌桶 / 漏桶 | 允许突发，更适合"限速"而非"防刷"——本项目要的是防刷 |

### 5.2 结构

```
key    = wt:rate:{维度}:{值}:{接口}
member = 请求唯一标识（时间戳-随机数）
score  = 当前时间戳(ms)
```

一次判定 = 一个 Lua 脚本，**原子完成**四步：

1. `ZREMRANGEBYSCORE` 清掉窗口外的
2. `ZCARD` 数窗口内的数量
3. 未超限 → `ZADD` 本次请求 + `EXPIRE`；超限 → 直接返回
4. 返回当前计数与是否放行

**为什么必须用 Lua**：这四步如果分开发，两次请求之间会插进来别的请求，`ZCARD` 的结果就不是原子的——限流会漏。这和秒杀扣库存是同一类问题（亮点 6）。

### 5.3 决策点 ④：限流器自己坏掉时怎么办

限流依赖 Redis 记录计数。**Redis 挂了，限流器就失去了判断依据**——此时只有三种处理方式，不是两种：

| 选项 | 做法 | 效果 |
|---|---|---|
| **fail-open** | 放行 | 限流暂时失效，可能被刷 |
| **fail-closed** | 拦住所有请求 | **整个站点不可用** |
| **降级到本地内存** | 退回单机内存计数 | 精度下降，但**仍有保护** |

#### 判断依据：不是"哪个更安全"，而是两个问题

**问题一：限流在这里是不是"正确性防线"？**

**不是。** 限流是**防滥用**，不是保证正确性。这个区分决定了整个决策：

| 要防的事 | 真正靠什么防 | 靠限流吗 |
|---|---|---|
| 优惠券超卖 | Redis Lua 原子扣减（亮点 6） | ❌ |
| 重复下单 / 重复扣款 | 幂等（`eventId` + 唯一索引） | ❌ |
| 订单状态错乱 | 状态机 + 本地消息表（ADR-0011） | ❌ |

**正因为正确性另有保障，限流失效才不会让钱算错。** 这是"支付场景也能 fail-open"的底气所在——不是因为支付不重要，而是因为**限流本来就不是它的安全绳**。

**问题二：两种失败的代价，哪个更大？**

- fail-open 的后果：限流失效，**可能**被刷
- fail-closed 的后果：**Redis 抖一下，全站 502**

本机 Redis 是**单点**，没有哨兵没有集群。用"可能被刷"换"全站不可用"不划算。

#### 所以：按接口分类，不搞全局一刀切

| 接口 | 降级策略 | 为什么 |
|---|---|---|
| 普通业务接口 | **fail-open** | 限流失效的代价 < 全站不可用的代价 |
| 秒杀 / 支付 | **fail-open** | 正确性由 Lua 扣减与幂等兜底，限流只负责减压 |
| **登录 / 注册** | **降级到本地内存限流** | 不能放行（**防撞库是这类限流的唯一目的**，放行等于把门打开）；也不该全拦（谁都登不进来）。退回单机内存计数，精度差但还有保护 |

> **为什么"本地内存兜底"是个真选项**：M1–M8 只有**一个进程**，本地内存计数与 Redis 几乎等价——它只在多实例时才失真。
> **但 M9 拆成多实例后，本地兜底会变成"每个实例各限一份"**（N 个实例放行 N 倍）。这个时间点要重新评估：要么给 Redis 上哨兵，要么登录接口改成 fail-closed（牺牲可用性换安全）。**现在不做**（YAGNI），但记在这里。

#### 实现上要注意

- 三种策略应当是**可配置的**（按接口路径配），而不是硬编码在漏桶逻辑里——否则将来调整要改代码
- 无论走哪条降级路径，**都要记日志**：fail-open 记 WARN/ERROR 并计数（这是"限流正在失效"的唯一信号），降级到本地记 WARN

> **面试话术**：*"Redis 挂了的时候我选 fail-open——但这个选择有前提，我把它拆成了两个问题。第一，限流在这里是不是正确性防线？不是，超卖靠 Lua 原子扣减、重复下单靠幂等，所以限流失效不会让钱算错。第二，两种失败的代价哪个大？Redis 是单点，fail-closed 等于全站 502，比可能被刷更糟。但登录接口我不用 fail-open，而是降级到本地内存——因为防撞库是那个限流的唯一目的，放行等于把门打开。"*

### 5.4 限流维度、阈值与降级策略

| 接口 | 维度 | 阈值（初始值） | Redis 挂掉时 |
|---|---|---|---|
| 登录 | IP | 10 次 / 分钟 | **降级到本地内存** |
| 登录 | 用户名 | 5 次 / 分钟（防单账号被撞库） | **降级到本地内存** |
| 注册 | IP | 10 次 / 分钟 | **降级到本地内存** |
| 普通接口 | 用户 ID（未登录则 IP） | 100 次 / 分钟 | fail-open |

**阈值是初始值，M10 压测时校准**——现在写死一个"看起来合理"的数字没有依据。

> **登录按 IP 和用户名各限一次，不是重复**：按 IP 挡的是"同一台机器狂试很多账号"，按用户名挡的是"很多台机器试同一个账号"（撞库的经典形态）。两种攻击的形态不同，只限一个都会漏。

#### ⚠️ 实现进度：用户名维度的限流**本里程碑未做**

M1 实际落地的规则是：登录/注册按 **IP** 限 10/分钟，普通接口按**用户**限 100/分钟。

**用户名维度被推迟了**，原因具体、不是"来不及"：

- 用户名在**请求体**里，而限流拦截器（`HandlerInterceptor.preHandle`）运行在 Controller **之前**。
  要拿到它必须先读请求体，而请求体是一次性的——读完后续 `@RequestBody` 就拿不到数据了，
  必须加一层 `ContentCachingRequestWrapper` 把请求包起来。
- 而它挡的那种攻击（多台机器打同一个账号）**已经被别的机制部分覆盖**：
  后端的 BCrypt 比对本身就限速（每次约 100ms），且账号锁定策略是 M1 之后可加的更直接手段。

**建议的做法（留待 M2 或 M7）**：与其在拦截器里读请求体，不如把用户名维度的限流放进
`AuthService.login`——那里用户名已经解析好了，不需要任何请求包装。
代价是限流逻辑从"统一拦截器"里分出来一部分，需要在代码注释里说清为什么分家。

**这条是有意留的缺口，不是漏掉的**：写在这里，是为了下一个人（或下一个对话）看到
设计文档时知道它没实现在哪、为什么。

> **✅ 2026-10-06 补记：M2 的 Task 9 已经按上面"建议的做法"把它实现了。**
> 位置就在 `AuthService.login` 的最前面（**在密码校验之前**——再往下就是 BCrypt 比对，
> 放在后面限流就来得太晚了）。阈值 5 次/分钟，配置项 `wt.rate-limit.login-username`。
>
> **顺带记一处与原建议的差别**：原设计稿给这段配置写了 `fallback` 字段，
> 实现时**去掉了**——这一维度只有"退回本地内存"一条路可走（放行等于把门打开、
> 全拒又谁都登不进来），留一个永远不会被改成别的值的配置项只是噪音。
>
> 实现细节与验证证据见 `docs/03-design/m2-content-core.md` §5 与
> `db/../docs/05-interview/05-限流-ZSet滑动窗口与降级.md` 的"M2 扩展"一节。

## 6. 公共设施

### 6.1 统一响应体

```java
Result<T> { String code; String message; T data; String traceId; }
```

- 成功 `code = "0"`；失败用业务错误码
- `traceId` 回给前端，便于用户报错时定位日志

> **`code` 用 `String` 而不是 `int`**（本节初稿写的是 `int`，与 §6.2 的 `A0001` 分段格式冲突，已修正）：
> 带字母前缀的分段码**可读、可 grep**——排查线上问题时 `grep 'A01'` 就能捞出用户域的全部报错，
> 而纯数字做不到这一点。前端做 `switch` 比较字符串与比较整数没有差别。

### 6.2 错误码

**分段**，不用一长串枚举：

| 段 | 含义 |
|---|---|
| `A0001`~`A0099` | 通用（参数错误、未登录、无权限、系统异常） |
| `A0100`~`A0199` | 用户域 |
| （后续里程碑按域续段） | |

### 6.3 全局异常处理

`@RestControllerAdvice` 统一兜底，**把异常映射成错误码**，避免把堆栈直接吐给前端（既是安全问题也是体验问题）。

### 6.4 日志与 traceId

- 每个请求生成 `traceId`，放进 **MDC**，日志格式里带上
- 这样一次请求跨多个类/多个服务的日志能串起来——**M9 拆服务后这条更重要**

### 6.5 合规与安全（不是可选项）

| 项 | 做法 |
|---|---|
| 密码 | **BCrypt**（自带盐），绝不明文、绝不进日志、绝不返回给前端 |
| 响应体 | `password` 字段永不出现；用 DTO 而不是直接返回实体 |
| JWT 密钥 | 环境变量 `JWT_SECRET`，**不入库**；提供 `.env.example` |
| 日志脱敏 | 登录参数记录时打码，异常堆栈不返回给前端 |
| 越权 | 每个涉及资源的接口都要过归属校验（§4） |

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/api/auth/register` | 注册 | 无（限流：IP） |
| POST | `/api/auth/login` | 登录 → 返回双令牌 | 无（限流：IP + 用户名） |

| GET | `/api/users/me` | 当前用户信息 | 已登录 |
| ~~PATCH~~ | ~~`/api/users/me`~~ | ~~改自己的资料~~ | **已改为下面那行**，理由见下 |
| PATCH | `/api/users/{id}` | 改指定用户的资料 | 已登录 + **归属校验**（`@authz.isOwner(#id) or hasRole('ADMIN')`） |
| GET | `/api/users/{id}` | 个人主页（公开信息） | 无 |

> **为什么把 `PATCH /me` 改成 `PATCH /{id}`**：`/me` 的路径里没有资源标识，
> 也就**没有"改错人"这种可能**——归属校验永远不会失败，等于没写。
> 而 M1 的验收闸门恰恰是"越权访问实测被拒"，需要一个能真的失败的路径。
>
> 前端不受影响：它本来就从 `GET /me` 拿到了自己的 id。
> **代价**：前端需要多存一个 id，而不是直接调 `/me`。
> 若将来觉得这个代价不值，可以两者都提供（`/me` 作为 `/self-id` 的便捷别名），
> 但**不要只留 `/me`**——那样等于把归属校验从接口层拿掉了。

## 8. 一个 spec 排期上的遗漏，需要现在补

**持久层选型（MyBatis vs MyBatis-Plus）在 spec §12 开放问题表里写的决策时点是「M2」，但 M1 就要写用户表了。**

**决策点 ⑤。建议：MyBatis（不用 Plus）。**

| 方案 | 代价 |
|---|---|
| **MyBatis（建议）** | CRUD 要手写 SQL。但 M6 的亮点 4（Deferred Join 深翻页）**本来就是手写 SQL 优化**并配 `EXPLAIN` 对比，Plus 在这块帮不上忙，反而绕开了亮点 |
| MyBatis-Plus | 省掉基础 CRUD，但面试官对"只会调 Plus 的 API"普遍有偏见，且会削弱 M6 的讲法 |

**这个决策要写 ADR**（涉及"引入/排除了一个依赖"），并回填 spec §12 的时点。

## 9. 怎么验收（对应闸门）

| 闸门 | 怎么测（M1 收尾时执行） |
|---|---|
| 限流 `429` | 循环打同一接口超过阈值 → 断言返回 `429`；**并附反面对照**：阈值内应全部正常 |
| 越权被拒 | 用 A 用户登录，改 B 用户的资料 → 断言 `403`；**反面对照**：改自己的应成功 |

> **反面对照是硬要求**（spec §9 闸门 2）：只测"被拒绝"证明不了什么——一个永远返回 403 的系统也能通过。必须同时证明"该通过的确实通过"。
