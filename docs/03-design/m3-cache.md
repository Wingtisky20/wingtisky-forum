## 1. 范围

### 做什么

| 块 | 内容 |
|---|---|
| 三级读缓存 | `Caffeine(L1) → Redis(L2) → MySQL`，只作用于**帖子详情**这一条读路径 |
| 防击穿 | Redisson 锁 + **锁内 double-check** |
| 防穿透 | 空值墓碑（短过期时间） |
| 防雪崩 | 过期时间加随机抖动 |
| 跨节点失效 | Redis 发布订阅广播 → 各节点清自己的 L1 |
| 写一致性 | Cache-Aside：**先更新数据库，再删缓存** |
| 浏览数改造 | 从"每次读都 UPDATE 一次库"改成 **Redis 计数器 + 定期回写**（收 M2 埋的伏笔） |
| 首次引入 Redisson | 白名单内的 3.52.0，M3 是它第一次真被用上 |
| 闸门实验 | 命中率 / 延迟对比 · 100 并发仅 1 次回源 |

### 不做什么（YAGNI）

- ❌ **不给列表页、标签页、评论列表加缓存** —— 先把一条读路径做透。
  一条能讲清楚的三级缓存，比五条半成品有价值。
- ❌ **不引布隆过滤器**防穿透 —— 空值墓碑够了。布隆过滤器要先解决"数据怎么预热进它"
  这个问题，而那是个新问题，不是这个问题。
- ❌ **不引 Caffeine 之外的 L0**（比如本地静态 Map）—— 那是重复造 L1。
- ❌ **不做"缓存永不过期的强一致方案"** —— 那是分布式事务，本项目的选择见 §4。
- ❌ **不改 M6 的深翻页、不为 M6 铺路** —— 那是另一个亮点，混在一起两件都讲不清。
- ❌ **不做缓存预热** —— 没有真实流量，预热给谁看？
- ❌ **不引入 Spring Cache 的 `@Cacheable`** —— 它把"什么时候删、删哪个 key"
  藏进注解里，而这个项目的亮点恰恰是**把失效规则显式写出来**（§3.3 那张清单就是交付物）。
  用注解等于把这个亮点删掉。

### 验收闸门（spec §6.2，不达标不算完成）

| 闸门 | 具体要求 |
|---|---|
| 命中率 / 延迟对比 | 同一份代码，**缓存开 / 关两组**，比命中率与 P99 延迟 |
| **100 并发仅 1 次回源** | 100 个并发请求同一帖，**回源 MySQL 恰好 1 次** |

反面对照（spec §9 闸门 2：单边数据不算证据）见 §9.3 —— 闸门 2 要求亮点实测
**必须有反面对照**，本设计的反面对照是"把锁拿掉，同样 100 并发，回源次数应当大于 1"。

## 2. 缓存什么

### 2.0 决策点 ①：缓存粒度 —— 只缓存"帖子详情"，不缓存"帖子"

| 方案 | 说明 | 代价 |
|---|---|---|
| **A（选这个）** | 缓存**详情接口的返回内容**，key 是帖子 id | 列表页不受益 |
| B | 缓存**帖子实体**（`Post` 那一行），列表与详情共用 | 列表是分页查询，缓存单行对列表几乎没有帮助；而列表要的是"按页缓存"，那是另一个问题（且翻页缓存很容易做错） |
| C | 缓存整个接口响应（含用户态） | 见 §2.2，命中率会崩 |

**选 A。** 理由是"缓存的粒度应当对齐**复用点**"：详情是真被反复读的（一个人刷新、
一百个人看同一篇），而列表每次的查询条件都不同、缓存意义小得多。
把两件事混在一个缓存里，失效时就得猜"这次改动影响列表还是详情"——而那个问题是自找的。

### 2.1 决策点 ②：缓存对象里放哪些字段 —— 按"变化频率"分层

`PostDetail`（`dto/PostDetail.java`，它已经是个 `record`）一共 17 个字段。
把它们按**"多久变一次"**分成三层：

| 层 | 字段 | 归属 | 为什么 |
|---|---|---|---|
| **几乎不变** | `id`、`title`、`content`、`authorId`、`author`、`tags`、`top`、`featured`、`createTime`、`updateTime` | **进缓存** | 只有"编辑"和"后台治理"会动它们——都是低频写 |
| **变得比较多** | `likeCount`、`collectCount`、`commentCount`、`offline` | **也进缓存** | 点赞、评论会动它们。但仍然远低于读的频率（见下方代价说明） |
| **每次读都在变** | `viewCount` | **不进缓存**，走 Redis 计数器 | 它被**这一次读**改变——放进缓存的话，缓存永远从存在那一刻就是脏的 |
| **因人而异** | `liked`、`collected` | **不进缓存** | 见 §2.2 |

**判据一句话**（这句是这一节真正要记的）：

> **这个值会不会因为一次「读」而改变？**
> 会 → 它不能进缓存，得走计数器。
> 不会 → 它能进缓存，由**写**负责删（§3.3）。

**第二层的代价要诚实写下来**：点赞 / 评论会删掉详情缓存。一条很热的帖子被人不断点赞，
缓存就会被不断删掉 —— 这是真实的损失。之所以仍然这么选：

1. 论坛是典型的**读多写少**，读:写在 100:1 量级。一次写删一次缓存，下一个读再回源一次，
   命中率仍然很高。
2. 另一条路（把三个计数也赶出缓存对象）的代价是**每次读都要多查一次库**——
   而那恰好要在闸门"100 并发仅 1 次回源"上留下 100 次查询，把闸门本身弄脏。
3. **升级路径已留**：如果 M10 压测发现"热帖被频繁点赞"真的是瓶颈，
   把三个计数拆成独立的短过期缓存即可（`dto` 不动、`PostService` 的组装处改一行）。
   本期不做，是因为**没有证据证明它是瓶颈**。

### 2.2 决策点 ③：`liked` / `collected` 不进缓存

这两个字段是"**这个人**点过赞没有"，**因人而异**。

| 方案 | 后果 |
|---|---|
| **A（选这个）**：不进缓存，每次照旧查库 | 详情命中缓存时仍有 2 次很轻的索引查询（`t_post_like` / `t_post_collect` 的唯一索引上查"有没有这一行"）。**未登录时一次都不查**——M2 已经是这么写的 |
| B：整条详情都缓存，key 带上浏览者 id | ① 每个用户一份缓存，**命中率会难看到没法交差**（100 个人看同一帖 = 100 份缓存）② 一次点赞要失效"所有人"的缓存 —— 而失效只能按 key 删，你删不完 |

**选 A。** 还有一种更"聪明"的做法 —— 公共部分一个 key、用户态一个 key（key 带 userId），
但那是在为同一个问题维护两套过期规则。**先把简单的做对。**

> **面试会追问的点**：那"我点过赞没有"就不缓存了？——对，而且**这是有意的**。
> 它是**用户私有状态**，不是**公共内容**。把用户私有状态塞进公共缓存，
> 是"命中率"和"越权风险"两样一起赔。（缓存串号 = 别人看到你点过赞 = 越权。）

### 2.3 决策点 ④：浏览数不进缓存，改成 Redis 计数器

M2 的代码里已经留了话（`PostService.java:141`）：

> 这是个"读接口里带写"的方法：它会给浏览数 +1。……
> **M3 会把它换成 Redis 累加 + 定期回写**，那时只改这一行。

M3 收这个尾。做法：

| 项 | 做法 |
|---|---|
| 计数器 key | `wt:cache:post:view:{id}`，存**绝对值**（不是增量） |
| 每次读 | Lua 原子执行：**key 不存在 → 先装载种子；然后 `INCR`；返回新值** |
| 种子从哪来 | 计数器不存在时（Redis 冷启动 / 首次访问 / 键过期）**单独查一次库**取当前值。这是一次单列查询，很轻 |
| 回写 | 定时任务（`@Scheduled`，默认 30 秒）把 Redis 里的**绝对值** `UPDATE` 回 `t_post.view_count` |
| 一致性 | **弱一致，而且是有意接受的** —— architecture.md §2.1 明写 `forum-service` 的一致性要求是"最终一致可接受（**浏览数**、热度）"。Redis 挂掉会丢最近一段增量，可接受 |

**为什么是"绝对值"而不是"增量"**：增量方案要在回写时把增量清零，于是
"展示值 = 库里基准 + 增量"——两个数一加，还得保证回写的瞬间两边同时对，复杂。
绝对值方案下 Redis 一个数就是答案，回写是**幂等**的（重复写同样的值，结果一样）。

**代价**：浏览数**不再精确**。这条要写进 README / 讲解文档，而不是假装它精确。

## 3. 三级缓存怎么运作

### 3.1 读路径

```
getDetail(id, viewerId, isModerator)
  │
  ├─ 1. L1（Caffeine）查 wt:cache:post:detail:{id}
  │     命中 → 跳到 5
  │
  ├─ 2. L2（Redis）查同一个 key
  │     命中 → 回填 L1 → 跳到 5
  │     命中"空值墓碑" → 直接 404（防穿透）
  │
  ├─ 3. 未命中 → 抢 Redisson 锁 wt:lock:cache:post:{id}
  │     抢到 → 【double-check：再查一次 L2】→ 仍无 → 回源 MySQL → 写回 L2 + L1 → 放锁
  │     抢不到 → 短暂自旋等 L2 出现（默认 50ms × 最多 10 次，共 500ms）
  │               等不到 → 回源 MySQL（降级，宁可多查一次库也不能卡死请求）
  │
  ├─ 4. **可见性判定**（用缓存对象里的状态字段，仍然必须做）
  │
  └─ 5. 组装返回：缓存对象 + 浏览数（Redis 计数器 INCR）+ liked/collected（查库）
```

**三个不显眼但重要的点**：

1. **第 3 步的 double-check 不是可选的**。拿到锁之后**必须**再查一次 L2 —— 因为
   在你等锁的那段时间里，前一个持有者很可能已经把值写进去了。不查的话，
   所有排队的请求会**依次各回源一次**，锁白加。
   （这条正是 §9.3 反面对照要证伪的东西。）
2. **第 4 步：缓存的是数据，不是权限判定的结果。** 命中缓存也**必须重新做可见性判定**，
   否则已下架的帖子被缓存之后，匿名用户也能拿到 —— 那是越权，不是缓存问题。
   所以缓存对象里必须带上判定所需的字段（`deleted`、`status`）。
3. **第 5 步的浏览数走计数器，读接口里没有 `UPDATE` 了** —— 这是 M2 那行注释的兑现。

### 3.2 写路径：Cache-Aside

```
写操作（编辑 / 删帖 / 后台治理 / 点赞 / 收藏 / 评论）
  │
  ├─ 1. 更新 MySQL（在事务内）
  ├─ 2. 事务提交后：删 L2（DEL）→ 删本机 L1 → 发布订阅广播"这个 key 失效了"
  └─ 3. 其它节点收到广播 → 删自己进程内的 L1
```

**顺序不能反**（先更新库再删缓存），理由与被否决的三个方案见 §4。

**为什么是"删"而不是"改"缓存**：改缓存要**按新值重算**，而重算需要的输入
（比如 `UserBrief` 作者信息、`tags`）往往要再查库 —— 那就成了"写路径也要承担读路径的成本"。
删掉更省事，而且把"重新算"推迟到真正有人读的时候。spec §5.1 也是这么定的。

### 3.3 失效清单 —— 「缓存一致性」这道题的答案

**这张表是本次交付物里最该被记住的一件。** 面试官问"你怎么保证缓存和数据库一致"，
答案不是一个形容词，是这张表：

| 写操作（方法） | 为什么它要动缓存 |
|---|---|
| `PostService.update` | 改了 title / content / tags |
| `PostService.delete` | 逻辑删除，`deleted` 变了 → 可见性变了 |
| `PostService.administrate` | 置顶 / 加精 / **下架**——`top`、`featured`、`offline` 都在缓存对象里 |
| `InteractionService.like` / `unlike` | `likeCount` 在缓存对象里 |
| `InteractionService.collect` / `uncollect` | `collectCount` 在缓存对象里 |
| `CommentService.create` / `delete` | `commentCount` 在缓存对象里 |

**没有漏项，靠的不是仔细，是这个规则**：

> **凡是能改变缓存对象里任何一个字段的写操作，都必须删这个 key。**

**注意 `TagService` 不在表里** —— M2 的标签只有"新增 / 关联"，
没有改名或合并（`TagService.listByPost` 是只读的）。
将来若加了"标签改名"，**这张表就要加一行**，而"标签名变了但缓存没删"是典型的
静默错误：不报错，只是页面上的标签名永远是旧的。

**幂等写不重复删**：M2 的点赞是幂等的（`INSERT IGNORE` + 只在真写入时动计数，
见 ADR-0017）。所以"连点 3 次赞"只会删 1 次缓存 —— 重复请求不会造成重复失效。
这是 M2 的幂等设计在 M3 顺带拿到的收益。

### 3.4 三防

| 问题 | 做法 | 参数（初始值，M10 校准） |
|---|---|---|
| **击穿**（热点 key 过期瞬间，大量请求同时回源） | Redisson 锁 + **锁内 double-check** | 等锁最多 500ms |
| **穿透**（查一个根本不存在的 id，每次都绕过缓存打库） | **空值墓碑**：缓存一个特殊标记，**过期时间取短** | 墓碑 60 秒 / 正常 5 分钟 |
| **雪崩**（大批 key 同时过期） | 过期时间加随机抖动 | L2 = 5 分钟 + `random(0, 60秒)` |

**墓碑为什么必须是"短"过期时间**：正常的 5 分钟是"值不太会变，可以放久一点"；
墓碑是"这个 id 现在没有，但它**随时可能被创建**" —— 一个新 id 被创建后，
如果墓碑还留着，新帖子会被当成不存在。所以墓碑必须短。

**墓碑怎么存**：缓存值在 Redis 里是 JSON 字符串，而 JSON 的 `null` 与"这个 key 不存在"
**没法区分**（`GET` 返回空串和返回 `"null"` 是两回事，而序列化很容易把它俩弄混）。
所以用一个**显式哨兵**：字符串 `"__NULL__"`。选它而不是"包装类"的理由是：
在 RedisInsight 里能一眼看出来是个墓碑，而包装类在可视化工具里只是一坨看不出所以然的 JSON。

### 3.5 跨节点失效：发布订阅，以及"单进程下怎么证明它真的能工作"

**做**。通道 `wt:cache:evict`，消息内容是失效的 key；每个节点订阅，
收到后删自己进程里的 L1。

**这里有一个必须正面回答的问题**：M0–M8 是**单进程**，只有一个节点 ——
广播出去只有自己收得到。**"跨节点失效"这件事当前无法在真实部署下验证。**
spec §5.1 自己也写着"多实例后 Pub/Sub 跨节点失效从假变真"。

所以 M3 的验证方式是：**在一个测试里放两个互相独立的 L1 实例**（模拟两个节点），
订阅同一个通道，然后断言"广播一发，**另一个实例**的本地缓存真的被清掉了"。

> **为什么不做成"只写代码、不验证"**：那正是 spec §9 闸门 2 点名的"验证剧场"——
> 代码看起来对，但从 M3 到 M9 这段时间里它**从没生效过**，谁也不知道它是不是对的。
> 用一个测试把它跑起来，代价很小，而它把"写了"变成"能工作"。

**消息里要带发送方的实例标识**：收到自己发的消息直接跳过。
（清两次本地缓存本身无害，但带上标识之后，日志里才看得出来"这条消息是谁发的、
有没有真的跨节点" —— 单进程下如果不带，日志会让人误以为跨节点生效了。）

**已知缺陷（spec §5.1 已写，这里只引用不重复）**：发布订阅不可靠，
订阅者掉线期间的消息会丢。兜底是 **L1 的过期时间设短（30–60 秒）** ——
即使失效消息丢了，脏数据最多活一个 L1 的过期时间。

## 4. 决策点 ⑤：为什么是"同步删缓存"（含被否决的四个方案）

**结论**：M3 的写后失效走 **先更新数据库 → 再同步删缓存**。这是 2026-10-06
用户确认的决定，本文把它落成正式设计。

**这是一次"有时点的决定"，不是永久结论。** 复查的触发条件：

> **M4 的 Kafka 链路建好之后**，用真实数据回头比一次"同步删"与"等事件异步失效"
> （对比项见 spec §5.6 第 2 条：同步删除强一致但写路径耦合缓存；
> 等 Kafka 事件异步失效解耦，但有延迟窗口）。比完再决定是否换。

ADR 必须按下面这张表写——**只写"我选了同步删"而没有被否决的方案，等于只写了一半**：

| 方案 | 它是什么 | 为什么不用（面试问的就是这个） |
|---|---|---|
| **先删缓存，再更新库** | 反过来做 | **并发下有经典的不一致窗口**：A 删缓存 → B 读，未命中，读到**旧值**并写回缓存 → A 才更新库。缓存里从此**永久**是旧的（直到过期）。而"先更新库再删缓存"的窗口极窄，且下一次读会纠正它 |
| **延迟双删** | 更新库 → 删缓存 → **睡一会儿** → 再删一次 | ① "睡多久"没有依据，只能靠赌 ② 它治的是"主从复制延迟"场景下的一次具体竞态，而本项目**没有 MySQL 主从** ③ 一次写请求被**刻意拖慢**几百毫秒，是拿确定的代价换一个不确定的收益 |
| **订阅 binlog（Canal 那类）** | 从数据库日志里捕获变更来失效缓存 | 要为它再装一套中间件 + 它自己的高可用。**引入的东西比解决的问题重**。而且 binlog 方案的价值在"多写入口"场景（很多服务都在写这张表），本项目只有一个写入口 |
| **等 Kafka 事件异步失效** | 发个事件，消费者删缓存 | 解耦确实好，但 Kafka 要到 M4 才有——**M3 现在没有这条路可走**。M4 复查时再评 |
| **给缓存设很短的过期时间，不做主动失效** | 全靠过期兜底 | 过期时间短到能兜住一致性的程度（几秒），缓存就等于没做——命中率回到零 |

**"先更新库再删缓存"也有它自己的窗口，要诚实说**：

> 读请求 A 未命中 → 回源读到**旧值** → 此时写请求 B 更新库并删了缓存 →
> A 才把**旧值**写回缓存。缓存里从此是旧的。
>
> 这个窗口存在，但**下一次写会纠正它**，且 L2 有过期时间兜底。
> 想彻底关掉它，得让"回源 + 写回"这一步进锁（本设计的锁只管防击穿，
> 但**写回也在锁内**——见 §3.1 第 3 步，这顺带把这个窗口压得很小）。
> 完全消除需要分布式事务，spec §1.5 明确不做。

## 5. 决策点 ⑥：Redisson 为什么在 M3 就引入

**先说一件必须先说的事：这个决定与一处现成文档冲突。**

| 出处 | 怎么说的 |
|---|---|
| spec §5.1（亮点 1） | 防击穿用 **Redisson 的锁** |
| `docs/03-design/architecture.md` §5 | 亮点 1 = 「…**Redisson 防击穿**」 |
| `docs/STATUS.md` 待核实表 | 「Redisson 3.52.0 × Redis 5.0.14.1 的运行时兼容性 —— **M3** 实测」 |
| **`wt-infra/pom.xml` 的注释** | 「Redisson 的强项是分布式锁与分布式对象，**留给 M8 的亮点 7**」 |

**三份说 M3 用，一处注释说不给用。** 那处注释写于 M1（当时为登录/限流选了 Lettuce），
之后 spec 的亮点设计一直按 Redisson 写。**本次以 spec 为准，M3 引入**，
并**改掉 `wt-infra/pom.xml` 那段注释**（在改动处写清为什么改，遵守「变更留痕」）。

**为什么 M3 用 Redisson 的锁，而不是自己用 `SETNX` 写一把**：

| 自己写要处理的事 | Redisson 怎么做 |
|---|---|
| 锁**到期了业务还没做完**怎么办（业务慢于锁的过期时间，第二个请求进来了） | 看门狗自动续期 |
| 释放锁时**删掉了别人的锁**（自己的锁刚过期，别人刚拿到，自己才执行 `DEL`） | 用"锁的值 = 自己的标识"来校验 |
| 可重入（同一线程再进一次） | 支持 |
| 获取锁失败怎么办（自旋还是等待） | 有现成的等待/超时语义 |

这四件事**每一件写错都是一个 bug，而且都不会立刻暴露**。用 Redisson 不是"图省事"，
是**不重复解决一个已经有人解决好的问题**。

**代价（必须写下来）**：

1. 从 M3 起**两个 Redis 客户端共存** —— Lettuce（`StringRedisTemplate`，管令牌、限流、
   缓存读写）与 Redisson（只用于锁）。**要能说清各自为什么在这儿**：
   锁有"续期、可重入、安全释放"这些语义，Redisson 是专门做这个的；
   而简单的读写与 Lua，`StringRedisTemplate` 够用且更直接。
2. **`redisson-spring-boot-starter` 会不会动到现有的 Lettuce 连接工厂** ——
   这是**高危区**（CLAUDE.md 防幻觉闸门 5 点名了 Redisson）。
   Redisson 的 Spring Boot starter 会装配自己的连接工厂，**有可能顶掉 M1/M2 在用的那个**，
   而后果是隐蔽的：令牌刷新、限流这些已经跑通的功能可能因此出错。
   **所以 M3 的 Task 1 就是这件事**：加依赖 → 启动 → **回归登录 / 刷新 / 限流三个已有功能**。
   若冲突，改用 `redisson` 核心包 + 手动装配客户端 Bean（只拿 `RedissonClient`，
   不碰连接工厂）。
3. 待核实表里的 **Redisson 3.52.0 × Redis 5.0.14.1 运行时兼容性**在同一次实测里验掉。
   若报 `ERR unknown command`，降版本并写 ADR 修订。

## 6. 模块落点（机制 vs 策略）

边界线沿用 architecture.md §4.3：**`wt-infra` 只管连接、序列化、Key 规范、重试；
缓存存多久、哪些事件幂等、索引怎么映射，属业务模块。**

### 6.1 `wt-infra`（机制）

| 放什么 | 职责 |
|---|---|
| Redisson 客户端装配 | 连接、序列化（见下方"序列化"） |
| `TwoLevelCache` | 只做三件事：**查 L1 → 查 L2 → 未命中则加锁回源并回填**；以及 `evict(key)` = 删 L1 + 删 L2 + 广播。**它不知道缓存的是什么业务对象** |
| 发布订阅的收发原语 | 订阅、广播、以及"忽略自己发的消息"这层处理 |
| `RedisKey` 的扩展 | 加缓存相关的 key 生成方法（沿用 `wt:<业务域>:<用途>:<标识>`，见该类注释） |

**`TwoLevelCache` 的接口长这样**（业务侧提供一个"回源函数"和一个过期时间）：

```java
// 伪代码，只表达职责
V get(K key, Duration ttl, Supplier<V> loader);  // 三级查找 + 回源 + 回填
void evict(K key);                               // 删两级 + 广播
```

**为什么"加锁回源"属于机制**：它回答的是"**怎么**安全地回源"，与"回源取什么"无关。
换成 M7 的商品详情，这套逻辑一个字都不用改。

**序列化**：缓存值用 **JSON 字符串**（复用 Spring 已装配的 `ObjectMapper`）。
不用 JDK 序列化 —— 理由是它在 Redis 里是一坨二进制，出问题时**肉眼看不见内容**，
排查成本高。（现在用的是 `StringRedisTemplate`，本来就存字符串，方向一致。）

### 6.2 `forum-content`（策略）

| 放什么 | 职责 |
|---|---|
| `CachedPostDetail`（新 `record`） | 缓存对象的**形状**。它是 `PostDetail` 去掉"因人而异"与"每次都在变"的字段之后的子集（§2.1 的那张表） |
| `PostDetailCache` | 缓存**策略**：过期时间取多少、key 怎么生成、调 `TwoLevelCache` |
| `PostService.getDetail` 的改造 | 组装：缓存对象 + 浏览数 + 用户态 |
| §3.3 那张失效清单上的每一处调用 | 写完之后调 `evict` |

### 6.3 为什么不做更泛化的抽象

**不做**：注解驱动的 `@Cached`、SpEL 表达式拼 key、缓存穿透的自动布隆过滤器、
"多级缓存管理器"注册中心……

理由与 §1「不做什么」里那条一致：**这些抽象的价值来自"有很多种用法"，
而 M3 只有一种用法**。抽出来的通用层没人验证过第二条路径，
等真出现第二种用法时，多半会发现抽象的方向不对。
（M7 的商品详情出现时再抽第二版——那时有两个真实样本。）

## 7. 缓存对象的并发安全（一个容易被忽略的坑）

**L1 存的是对象引用，不是副本。** 如果 `CachedPostDetail` 里的某个字段是可变的
（比如 `List<TagView>`），那么"从缓存取出来的对象"和"缓存里存着的对象"是**同一个**——
调用方一改，缓存就被改了，而且**没有任何代码删过这个 key**，日志里也查不出来。

做法两条，**都必须做**：

1. **缓存对象设计成不可变的**：`record` + 字段本身不可变。`PostDetail` 已经是 `record`，
   新加的 `CachedPostDetail` 照做。
2. **`List` 字段在构造时用 `List.copyOf(...)` 拷一份**，而不是把外部传进来的
   可变列表直接存进去。（`PostDetail` 现有的 `from` 方法已经在兜 `tags` 的 null，
   M3 顺手把"拷贝"也一并做对。）

## 8. 新增配置项

放进 `application.yml` 的新段（**全部可关**，这是闸门实验"缓存开 / 关两组"的开关）：

```yaml
wt:
  cache:
    post-detail:
      enabled: true          # ← 闸门实验的开关：关掉它 = "纯 MySQL" 那一组
      l1-ttl: 45s            # spec §5.1：L1 取 30–60 秒，短过期时间是 Pub/Sub 丢消息的兜底
      l2-ttl: 5m             # 基准值
      l2-ttl-jitter: 60s     # 雪崩防护：实际 TTL = 5m + random(0, 60s)
      null-ttl: 60s          # 空值墓碑（必须短，见 §3.4）
      lock-wait: 500ms       # 抢不到锁时最多等多久，超时则降级回源
    view-count:
      flush-interval: 30s    # 浏览数回写数据库的间隔
```

**为什么这些数字进配置而不是写死在代码里**：它们是**初始值**，M10 压测时才校准。
写死的话，改一次要重新编译 —— 而校准是"试几组值比一比"的活，要能改得动。
（与 `application.yml` 里限流那段的做法一致。）

## 9. 怎么验收（闸门实验设计）

### 9.1 实验一：命中率与延迟对比

| 组 | 做法 |
|---|---|
| **对照组**「纯 MySQL」 | `wt.cache.post-detail.enabled = false` —— **同一份代码**，只翻开关 |
| **实验组**「三级缓存」 | 同上，开关打开 |

**为什么用同一个开关、而不是"缓存代码 vs 旧代码"**：两组必须只差一个变量。
拿改前改后的两份代码比，比出来的差值里混着"代码重构"的影响，说明不了缓存的作用。

要记录的数字：

- **L1 命中率 / L2 命中率 / 回源率** —— Caffeine 用 `recordStats()` 直接拿；
  L2 的命中要在 `TwoLevelCache` 里自己打点计数
- **P99 延迟**（两组各打同样的请求量）
- **回源次数**（对照组 = 请求数，实验组应远小于）

### 9.2 实验二：100 并发仅 1 次回源（含反面对照）

| 步 | 做法 | 期望 |
|---|---|---|
| 1 | 清空 L1 与 L2，使该帖**完全没有缓存** | —— |
| 2 | **100 个线程同时**请求同一帖详情 | 全部 `200` |
| 3 | 数"回源 MySQL 的次数" | **恰好 1** |
| 4 | **反面**：把锁关掉（或去掉锁内的 double-check），重复第 1–3 步 | **远大于 1** |

**第 4 步是本设计的证据核心。** 第 3 步单独看，只能证明"数字是 1"；
加上第 4 步，才证明**是那把锁让它变成 1**（而不是碰巧、不是别的原因）。
spec §9 闸门 2 要求"亮点实测必须有反面对照，单边数据不算证据"——这条就是照它做的。

回源次数怎么数：在 `TwoLevelCache` 的回源路径上放一个 `AtomicLong` 计数器
（仅测试环境下暴露）。

### 9.3 反面对照清单（本设计一共要出几组）

| # | 正面 | 反面 | 证明了什么 |
|---|---|---|---|
| 1 | 命中缓存时**不查帖子主体** | 关掉缓存后**每次都查** | 缓存真的在挡流量 |
| 2 | 100 并发 → **1 次回源** | 去掉锁 → **> 1 次** | 锁真的在防击穿 |
| 3 | 查不存在的 id → **只回源 1 次**（墓碑生效） | 去掉墓碑 → **每次都回源** | 墓碑真的在防穿透 |
| 4 | **广播一发，另一个 L1 实例被清空** | 不订阅 → 另一个实例仍是旧值 | Pub/Sub 真的能跨"节点"工作（§3.5） |
| 5 | 改帖后再读 → **读到新内容** | 改帖后**不删缓存**的对照组（测试里手工跳过 evict）→ 读到旧内容 | 失效清单不是摆设 |
| 6 | **未登录读已下架帖 → 404**（即使该帖已在缓存里） | —— | **缓存没有绕过鉴权**（§3.1 第 2 点） |

第 6 条没有反面 —— 它是**安全性断言**，只有"必须成立"这一种结果。

## 11. 决策结论

| # | 决策 | 结论 | 被否决的方案 |
|---|---|---|---|
| ① | 缓存粒度 | **只缓存帖子详情** | 缓存帖子实体（B）、缓存整个响应（C） |
| ② | 缓存对象字段 | **按"会不会被一次读改变"分层**；计数进缓存，浏览数不进 | 全部进缓存 / 全部不进缓存 |
| ③ | `liked` / `collected` | **不进缓存**，每次查库 | key 带 userId（命中率崩 + 越权风险） |
| ④ | 浏览数 | **Redis 计数器（绝对值）+ 定时回写**，接受弱一致 | 继续每次 `UPDATE`（M2 现状）；增量方案 |
| ⑤ | 写后失效 | **先更新库 → 再同步删缓存**（**有时点的决定**，M4 后复查） | 先删后更、延迟双删、订阅 binlog、Kafka 异步 |
| ⑥ | Redisson | **M3 引入**（以 spec 为准，改掉 `wt-infra/pom.xml` 的冲突注释） | 自己写 `SETNX` 锁；留到 M8 |
| ⑦ | 抽象层度 | **薄抽象放 `wt-infra`**，不做注解驱动 / SpEL | `@Cacheable` / 通用缓存管理器 |
| ⑧ | 序列化 | **JSON**，不用 JDK 序列化 | JDK 序列化（Redis 里不可读） |

> 上表答的是"我在候选方案里选了哪个"；**§13 答的是另一种问法**——
> "你为什么不直接上逻辑过期 / single-flight / 版本号 / 键空间通知"，那些是同样主流的做法。
> 两者合起来，才算把"缓存设计"这道题答完。

## 13. 被评估过的主流替代方案（面试会问"你为什么不用 X"）

上面各节已经写了"我选了什么"，这一节写**"我为什么没选那些同样主流的做法"**。
这些是缓存领域最常见的几种方案，答不上来会显得没调研过。

| 主流做法 | 它是什么 | 本设计为什么不用 |
|---|---|---|
| **逻辑过期**（热点 key 物理上永不过期，值里带一个逻辑过期时间；读到过期的值就**先返回旧值**，同时异步起线程刷新） | 治击穿的另一种主流解法，去掉锁、只去掉"过期瞬间的并发回源" | ① 它**会把旧数据返回给用户**。浏览数那种弱一致字段我们已单独拆成计数器；而**帖子正文**改了之后还返回旧正文，是用户一眼能看见的错误 ② 要多一个异步线程池 + 任务合并，等于多一份并发正确性要证明。**留作 M10 压测后的备选**：若实测发现"热点帖子被锁串行化"真是瓶颈，再上它 |
| **本地 single-flight**（Caffeine 的 `get(key, loader)`：同一进程内同一个 key 只放一个线程去加载，其余等待） | 进程内的去重 | 它**只在本进程内去重**，多实例下每个实例仍会各回源一次。本设计的锁是**跨进程**的。两者**不冲突、可叠加**——而且 Caffeine 的 `get(key, loader)` 本身就带这个语义，本设计顺带就有，不需要额外配置 |
| **epoch / 版本号失效**（写时把版本号 +1，读时发现版本变了就重新加载） | spec §5.1 已列为"被评估过的替代方案" | 它把"失效"从"删 key"变成"读时发现"，省掉广播，但**每个读都要多一次版本号查询**——用一次额外的 Redis 往返，换掉一次广播。在写少读多的场景里，广播更划算 |
| **用 Redis 的键空间通知替代发布订阅**（key 被删时 Redis 自动发通知） | 省掉"自己发广播"这一步 | ① 送达保证与发布订阅**一样弱**（一样会丢）② 要**改 Redis 服务端配置**才能开启，而本项目的部署形态是"沿用本机已装好的 Redis"——为应用的需要去改中间件配置，会给开发环境留下一个说不清的差异 ③ 会收到大量与本缓存无关的 key 通知 |
| **把浏览数与各种计数搬进 Redis，让 Redis 当唯一权威** | 计数不落库 | `t_post` 的计数列是 ADR-0016 定的**冗余存储**，列表页按热度排序要用它；Redis 一丢，这些数就全没了，而 Redis 对持久化没有承诺。**DB 必须是权威，Redis 只能是缓冲** |
| **Spring Cache 的 `@Cacheable` / `@CacheEvict`** | 注解驱动，一行搞定 | 见 §1「不做什么」：它把"什么时候删、删哪个 key"藏进注解里，而这个亮点恰恰靠**把失效规则显式写出来**（§3.3 那张清单就是交付物）。用注解等于把这个亮点删掉 |

## 附：文档闸门（闸门 6）在本文上的实测结果 —— 以及它的一处盲区

**实测**：`bash tools/check-doc-refs.sh` → `[check-doc-refs] 通过。`（exit 0）

**起草时我预期的相反**：本文提到 `TwoLevelCache`、`PostDetailCache`、`CachedPostDetail`
三个**此刻还不存在**的类（它们正是 M3 要建的），我以为会像 M2 设计稿那样被闸门拦下。
**实际没有。** 查了 `tools/check-doc-refs.sh` 的匹配规则才明白：

> 它只检查两类引用：`com.wingtisky.*` 形式的全限定名，
> 以及以 **`Application` / `Service` / `Mapper` / `Controller` / `Config` / `Util` / `Test`**
> 结尾的类名（脚本注释写明："只检查这两类，是为了让误报率接近零"）。

上面三个名字**一个都不匹配**，所以闸门根本没看它们。

**这既是好事，也是一处已知盲区**，两件事都要记：

| 面 | 说明 |
|---|---|
| 好 | 设计稿不会把 PR 弄红 —— 不必像 M2 那样等代码落地才转绿 |
| **盲区** | 将来谁把 `TwoLevelCache` 改名或删掉，**这个闸门抓不到**。它守护的是带那几个后缀的名字，不是"所有被引用的类" |

**本期的处理**：不擅自扩大闸门的检查范围（那会让误报率上升，而脚本注释说明了当初为什么收窄）。
这条盲区记在这里，供 M10 整理工具链时一并评估。

> **顺带一个教训**（留在这里，因为它比结论本身有用）：
> 我在附录里先把"会报红"写成了结论，**跑命令之前就写好了**。
> 实测一跑，两句都是假的。这正是本项目闸门 1（证据制）要拦的东西 ——
> **结论要先跑命令再写，不能先写再跑。**
