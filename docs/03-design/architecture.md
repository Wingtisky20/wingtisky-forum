## 1. 业务域与数据流转

产品定位：**技术社区 + 付费内容**（参照 CSDN 形态）。两个业务域通过"内容 → 付费内容 → 交易"形成闭环。

```mermaid
flowchart LR
    A[用户写帖子/专栏] --> B[专栏可设为付费]
    B --> C[上架为商品]
    C --> D[运营配置优惠券]
    D --> E[用户秒杀抢券]
    E --> F[创建订单]
    F --> G[模拟支付]
    G --> H[解锁专栏内容]
    H --> A
```

**闭环成立**：每个域都有真实的上下游，不存在"拼贴"进来的孤立模块。

## 2. 服务拆分

### 2.1 三个服务

| 服务 | 职责 | 流量特征 | 数据一致性要求 |
|---|---|---|---|
| `forum-service` | 用户/认证、帖子、评论、专栏（内容侧）、检索、通知 | 读多写少 · 平稳 | 最终一致可接受（浏览数、热度） |
| `trade-service` | 商品、订单、支付（模拟）、内容解锁凭证 | 写多 · 对账敏感 | **较强**——订单状态不能错 |
| `seckill-service` | 优惠券库存、Lua 扣减、异步下单、防刷 | **平时 0 QPS，瞬时脉冲** | 最终一致（允许库存回补） |

### 2.2 拆分理由：**故障域隔离**

> 秒杀是瞬时脉冲，会打满 Tomcat 线程池与数据库连接池。**若秒杀与交易同进程，秒杀被打挂 = 用户下不了单。**

这条理由**不依赖流量大小**，是结构性的——因此在本机这种无真实流量的环境里**依然成立**，且**可以实测**（见 §2.5）。

### 2.3 为什么不用其他理由

| 常见理由 | 为什么不用 |
|---|---|
| "性能" | ❌ 本机没有真实流量，性能论证必然站不住 |
| "独立伸缩" | ❌ 本机不部署到云，无弹性伸缩场景 |
| "团队分工" | ❌ 单人项目，无此需求 |
| "微服务是主流" | ❌ 这不是理由，是跟风 |

**面试话术**：能说出"我考虑过用性能论证拆分，但那在本项目站不住，所以我用的是故障域隔离"，比背一堆微服务好处更有说服力。

### 2.4 关键约束：**先画逻辑边界，后做物理拆分**

| 阶段 | 做法 |
|---|---|
| **M1–M8** | 全部在**一个进程**内开发，但模块边界严格按三个服务划分，**由 ArchUnit 强制**（`trade-*` 不得依赖 `forum-*` 的 internal 包，反之亦然） |
| **M9** | 物理拆分 + 执行 §2.5 的对照实验 |

**为什么这么做**：拆分决策的正确性此时无法证明。先画边界后拆进程，使"拆"与"不拆"都只差一次模块搬运，**不押注在未经验证的判断上**。

### 2.5 拆分验证实验（M9 必做）

> 用 JMeter 打满秒杀接口，**同时**测量订单查询接口的 P99。

| 组 | 预期 |
|---|---|
| A 组：秒杀与交易**同进程** | 订单接口 P99 显著劣化（线程池/连接池被抢占） |
| B 组：秒杀**独立进程** | 订单接口 P99 基本不受影响 |

**A/B 差值即为拆分决策的硬证据。** 若差值不显著 → 退回两个服务，并在 ADR-0010 中记录修订。

> 这条实验的价值：绝大多数简历项目写"我拆了 N 个微服务"，但没有一个能回答"拆了之后好了多少"。

## 3. 模块清单

```
wingtisky-forum/                       父 POM（聚合）
├─ wt-common/           统一响应体 / 错误码 / 异常体系 / 工具 / 注解
├─ wt-domain/           领域模型 + 跨服务与跨模块接口契约（只放契约）
├─ wt-infra/            中间件基础设施（机制，不含业务策略）
│
├─ forum-service/       内容域（自身为 Maven 聚合模块）
│  ├─ forum-user/           用户、认证、JWT、RBAC
│  ├─ forum-content/        帖子、评论、标签、专栏
│  ├─ forum-search/         ES 索引、同步、检索
│  ├─ forum-notify/         通知
│  └─ forum-app/            启动模块（唯一 main）
│
├─ trade-service/       交易域
│  ├─ trade-product/        商品（付费专栏/课程）
│  ├─ trade-order/          订单、状态机
│  ├─ trade-payment/        模拟支付、内容解锁凭证
│  └─ trade-app/            启动模块
│
├─ seckill-service/     秒杀
│  ├─ seckill-coupon/       券、库存、Lua 扣减、防刷
│  └─ seckill-app/          启动模块
│
├─ gateway/             API 网关
├─ frontend/            Vue3 独立工程
├─ scripts/  tools/  docs/
```

**边界线仍是「机制 vs 策略」**（见 spec §4.3）：`wt-infra` 只管连接、序列化、Key 规范、重试；缓存存多久、哪些事件幂等、索引怎么映射，都属业务模块。

## 4. 技术选型增补

### 4.1 引入

| 组件 | 理由 |
|---|---|
| **Nacos** | 多实例部署后**服务地址不再固定**（2 个 forum 实例端口不同），静态配置失效。**这是引入注册中心的真实理由，不是"微服务都该有"** |
| **Gateway** | 统一入口 + **限流前移**——在网关挡掉无效流量，比在每个服务里挡更省资源（可延至 M9） |

### 4.2 **明确不引入**（这部分比"引入什么"更值钱）

| 组件 | 不引入的理由（面试话术） |
|---|---|
| **Sentinel** | **它会抢戏**。限流亮点是自己实现的 ZSet 滑动窗口；换成 Sentinel 就变成"调了个 API"，面试价值归零 |
| **Seata** | 跨服务一致性用**本地消息表 + MQ 最终一致**。秒杀场景下 **2PC 的同步阻塞会拖垮吞吐**，最终一致既够用又快。"我评估过 Seata 但没用"比"我用了 Seata"更能讲 |
| **RocketMQ** | 已有 Kafka。换中间件**没有收益，只有学习成本** |
| **Docker** | 本机无 Docker、Win10 Home 无 WSL2（ADR-0004） |

## 5. 亮点体系

| # | 亮点 | 所属 | 说明 |
|---|---|---|---|
| 1 | 高频读：Caffeine → Redis → MySQL + Pub/Sub 失效 + Redisson 防击穿 | forum | **多实例后 Pub/Sub 跨节点失效从"假"变"真"** |
| 2 | 异步写：Kafka 自定义分区 + 手动 Ack + Redis 幂等 | forum / 共用 | |
| 3 | 检索：ES + 增量/全量同步 + IK 扩展 | forum | |
| 4 | DB 治理：Deferred Join 深翻页 | forum / trade | **秒杀订单列表是真实深翻页场景** |
| 5 | 安全限流：RBAC + Redis ZSet 滑动窗口 | gateway / forum | **限流前移至网关** |
| **6** | **秒杀一致性：Lua 原子扣减 + 异步下单 + 库存回补** | seckill | 新增 |
| **7** | **分布式锁：Redisson 跨实例互斥** | seckill | 新增 |
| **8** | **最终一致性：本地消息表 + 定时对账** | trade / seckill | 新增 |

**秒杀是收口**：亮点 1、2、4、5 在它身上从"各自成立的技术点"变成"一个系统里互相咬合的部件"。

## 6. 部署形态与资源预算

### 6.1 本机资源预算

| 组件 | 内存 | 何时需要 |
|---|---|---|
| MySQL | 0.5 G | 全程 |
| Redis | 0.05 G | M3 起 |
| Kafka（1G 堆） | 1.2 G | M4 起 |
| ES（1G 堆） | 1.5 G | M5 起 |
| forum-service | 0.7 G | 全程 |
| trade-service | 0.7 G | M7 起 |
| seckill-service | 0.7 G | M8 起 |
| Nacos | 0.5 G | M9 起 |
| Gateway | 0.5 G | M9 起 |
| IDEA + 浏览器 + 系统 | 4.5 G | 全程 |
| **最坏情况（M9 全开）** | **≈ 10.9 G / 16 G** | |

### 6.2 三条硬性纪律

1. **按需启动**：做内容域时只起 `forum-service` + MySQL + Redis（≈ 1.25 G），**不需要全开**
2. **JVM 堆收紧**：每服务 `-Xmx384m`（默认值会让三个服务吃掉 4 G+）
3. **中间件堆受限**：ES 与 Kafka 各压到 1 G

### 6.3 明确不做

❌ 公网部署（ADR-0006）· ❌ Docker（ADR-0004）· ❌ 多实例常驻（仅在 M9 做实验时启动）

## 7. 跨服务一致性方案

**不用 Seata，采用「本地消息表 + MQ 最终一致」**（详见 ADR-0011）。

以"秒杀成功后创建订单"为例：

```
seckill-service                         trade-service
     │                                        │
     ├─ 1. Redis Lua 原子扣库存 + 记录购买者
     ├─ 2. 本地事务：写消息表(status=待投递)
     ├─ 3. 发送 Kafka 消息（订单创建请求）
     │                                        │
     │                              4. 消费 → 幂等校验(eventId)
     │                              5. 本地事务：创建订单 + 写消息表(status=已处理)
     │                              6. 手动 Ack
     ├─ 7. 定时任务：扫描超时未确认的消息 → 重投 / 触发库存回补
     └─ 8. 定时对账：Redis 库存 vs DB 订单数 → 修正差异
```

**关键点**：
- **步骤 2 与 3 的顺序**：先写本地消息表再发消息，保证"消息一定会发出去"（否则扣了库存却丢了消息）
- **步骤 4 幂等**：复用亮点 2 的 `eventId` + `SETNX`
- **步骤 7 库存回补**：这是最终一致的兜底——**允许短暂不一致，但必须自愈**
- **步骤 8 对账**：把"最终一致"从口号变成**可运行的检查**
