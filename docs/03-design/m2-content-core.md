## 1. 范围

### 做什么

| 块 | 内容 |
|---|---|
| 帖子 | 发帖、编辑、删除、详情、列表（分页 / 标签筛选 / 排序） |
| 评论 | 两级评论（评论 + 回复）、删除 |
| 标签 | 自由输入、标签列表 |
| 点赞收藏 | 帖子点赞 / 收藏，计数维护 |
| 后台 | 内容治理：置顶、加精、下架（**接口，不做页面**） |
| **补 M1 遗留** | 限流的**用户名维度**（M1 有意留的缺口，见 M1 设计 §5.4） |
| 前端 | Vue3 工程 + 4 个核心页面 |

### 不做什么（YAGNI，spec §1.5）

- ❌ **专栏** —— 见 §2.7。`architecture.md §3.1` 把专栏列在 `forum-content` 下，
  但**付费专栏属交易域 M7**，M2 做一个免费专栏会在 M7 重复建模一次。
  （**spec 侧无需改动**——它的 M2 行本来就没提专栏。）
- ❌ 富文本编辑器（正文按 Markdown 文本存，前端只做纯文本域 + 预览）
- ❌ 关注 / 私信 / 通知 —— `forum-notify` 是独立模块，M2 不碰
- ❌ 图片上传 —— 走本地存储的接口留到需要时，M2 正文只存文本
- ❌ 全文检索 —— 列表页的搜索框先走 **MySQL `LIKE`**，ES 是 M5 的事

### 验收闸门（spec §6.2，不达标不算完成）

**真实 HTTP 走通 `发帖 → 评论 → 列表`。**

反面对照（spec §9 闸门 2 的硬要求，单边数据不算证据）：

| 对照 | 期望 |
|---|---|
| 未登录发帖 | `401` |
| 登录后改 / 删**别人的**帖 | `403`；改 / 删**自己的** | `200` |
| 对同一帖**重复点赞** | `200` 且计数**不变**（幂等） |
| 同一用户名连续登录超过阈值 | 前 N 次 `401`，第 N+1 次起 `429` |

## 2. 库表设计

> **两个全局约定**（沿用 M1）：
> 1. **不加外键约束**，字段只是逻辑引用（与 `t_user_role` 一致）。跨表一致性由业务保证。
> 2. 表名 `t_` 前缀、`utf8mb4`、`create_time`/`update_time` 默认值同上。

### 2.0 决策点 ①：点赞与收藏，两张表还是一张

| 方案 | 说明 | 代价 |
|---|---|---|
| **A（建议）** | **两张专用表**：`t_post_like`、`t_post_collect` | 结构相似的两张表 |
| B | 一张通用表 `t_user_action(user_id, target_type, target_id, action_type)` | 索引从 2 列变 4 列；每次查询都要带 `target_type`，漏带就静默查错；外键式的唯一约束表达力变弱 |

**选 A。** 通用表的卖点是"将来给评论也能点赞"——但 spec §1.5 的 minimal 原则下，
**为了一个还不存在的需求把索引做宽**是亏的。真要做时再加 `t_comment_like`，
两张变三张的成本远低于现在把一张表做复杂。

### 2.1 帖子表 `t_post`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 自增 |
| `author_id` | bigint | 作者，逻辑引用 `t_user.id` |
| `title` | varchar(100) | |
| `content` | mediumtext | 正文（Markdown 文本） |
| `summary` | varchar(255) | **列表页展示的摘要**，发帖时截取 |
| `status` | tinyint | 0 正常 / 1 下架（版主隐藏，可恢复） |
| `top_flag` | tinyint | 是否置顶 |
| `featured_flag` | tinyint | 是否加精 |
| `view_count` | int | 浏览数，默认 0 |
| `like_count` | int | 点赞数，默认 0 |
| `comment_count` | int | 评论数，默认 0 |
| `collect_count` | int | 收藏数，默认 0 |
| `create_time` / `update_time` | datetime | |
| `deleted` | tinyint | 逻辑删除：0 未删 / 1 已删 |

**索引**：
- `KEY idx_author_create (author_id, create_time)` —— 个人主页"他的帖子"、按时间倒序
- `KEY idx_status_top_create (deleted, status, top_flag, create_time)` —— 列表页主查询

> **⚠️ 2026-10-05 更正（写建表脚本时改了本行的两处）**：
> 1. **去掉 `DESC`**——列表页的 `ORDER BY top_flag DESC, create_time DESC` **两列同向**，
>    一个纯升序索引**反向扫描**就能满足，写 `DESC` 是多余的。
> 2. **把 `deleted` 提到最前**——列表查询的过滤条件恒为 `deleted = 0 AND status = 0`，
>    两个都是等值条件。**都放进索引，"过滤 + 排序"才能全靠索引完成、不必回表**；
>    `deleted` 不进索引的话，每读一行都要回表检查它——而"少回表"正是 M6 要讲的那件事。
> 3. 删掉了原来列的 `KEY idx_create_time (create_time)`：它与 `idx_status_top_create`
>    的后缀高度重合，而列表查询**永远带 `deleted = 0 AND status = 0`**，
>    单独一条 `create_time` 索引基本用不上——**多一条索引就多一份写入成本**。
>
> 三处都已同步到 `db/V2__init_content.sql`，两份文档不再有分歧。

#### 为什么 `status` 和 `deleted` 要分开

它们回答的是两个不同问题：

- `deleted` —— **这条记录还在不在**（作者删帖）
- `status` —— **这条记录能不能被看见**（版主下架，是治理动作，**可撤销**）

合成一个字段省不了多少事，代价是"版主误下架"和"作者删帖"再也分不开——
恢复路径不同，责任也不同。分开之后，列表页的过滤条件恒为 `deleted = 0 AND status = 0`。

### 2.2 决策点 ②：计数用冗余字段还是实时 `COUNT`

点赞数、评论数、收藏数、标签下帖子数——**列表页每一行都要显示它们**。

| 方案 | 说明 | 代价 |
|---|---|---|
| A | 每次 `SELECT COUNT(*) FROM t_post_like WHERE post_id = ?` | 一页 20 篇帖子就是 20 次 COUNT；`GROUP BY` 也快不了多少，且点赞表会最大 |
| **B（建议）** | **在 `t_post` 上冗余计数字段**，写的时候同事务更新 | 要靠业务保证一致；热点帖的 `UPDATE` 会争同一行 |

**选 B。** 三个理由，第三个最重要：

1. 列表页是**最高频的读**，实时 COUNT 把成本压在最贵的地方
2. `UPDATE t_post SET like_count = like_count + 1 WHERE id = ?` 是**单语句原子操作**，
   不需要显式加锁；并发正确性由数据库保证
3. **这是 M3 的钩子。** M3 的亮点 1（多级缓存）要缓存的就是"帖子的展示信息"——
   如果计数字段在这里不存在、每次现算，M3 就没有一个**明确的缓存对象**可讲。
   现在把字段留下，M3 才是"缓存这些字段 + 处理一致性"，而不是"先想办法算出数来"。

> **一致性边界要写清**：冗余计数允许**短暂**不一致（点赞成功但计数 +1 失败）。
> 但这两个操作在**同一个事务**里，正常路径下不会不一致；只有进程崩溃在两次写之间才会。
> 对计数这类展示性数据，这个代价可以接受——M3 会引入缓存，一致性的讨论在那里才真正展开。

### 2.3 标签表 `t_tag` + 关联表 `t_post_tag`

| `t_tag` | | `t_post_tag` | |
|---|---|---|---|
| `id` | PK | `post_id` | 联合主键 |
| `name` | varchar(32) **唯一** | `tag_id` | |
| `post_count` | int，冗余计数（同 §2.2 论证） | | |
| `create_time` | | | `KEY idx_tag_id (tag_id)` |

**`idx_tag_id` 是反查用的**："这个标签下有哪些帖子"。联合主键的顺序是 `(post_id, tag_id)`，
查不了反方向——这和 `t_user_role` 上那条 `idx_role_id` 是同一个理由。

#### 决策点 ③：标签是自由输入还是预置

**建议自由输入**：用户在发帖页填标签，后端规范化（trim、去重、单帖最多 5 个），
**但不做小写化**。

理由：技术标签里 `Redis` 比 `redis` 好看，**小写化会把这个信息永久丢掉**。
而不做小写化也不会产生重复标签——`t_tag` 用的是 `utf8mb4` 的默认排序规则
`utf8mb4_0900_ai_ci`，其中 `ci` 就是 case-insensitive：**`Redis` 与 `redis` 会撞上
`name` 的唯一索引，被判为同一个标签**，保留的是首次写入的那个大小写。
两头的便宜都占到了。

> ⚠️ **大小写不敏感这条要写进验证用例**：Post `Redis` 与 `redis` 两帖 → `t_tag` 只能有一行。
> 否则这段推理只是"应该如此"，没被证实过。

代价与应对：两个人同时第一次用同一个新标签，会**并发插入同一个 `name`**。
`name` 上的唯一索引会拦下第二条，此时**捕获唯一键冲突并回头重查**即可——
这是"先查后插"在并发下必然遇到的问题，用唯一索引兜底是最省心的做法。

预置标签的代价更大：得先有个标签管理后台，且用户想用的标签常常不在预置列表里。

### 2.4 评论表 `t_comment`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `post_id` | bigint | 所属帖子 |
| `author_id` | bigint | 评论者 |
| `parent_id` | bigint | 直接父评论；**顶层评论为 0** |
| `root_id` | bigint | 所属顶层评论；**顶层评论为 0** |
| `content` | varchar(1000) | |
| `create_time` | datetime | |
| `deleted` | tinyint | |

**索引**：`KEY idx_post_root (post_id, root_id, id)`

> **`t_comment` 不设 `like_count`**：M2 范围里**没有"评论点赞"**（§1 的范围表与 §4 的接口清单都没有它）。
> 初稿按帖子的样子抄了一列过来，是一处**没有写入方的悬空字段**——
> 留着它，读代码的人会去找"谁在维护这一列"，然后找不到。
> 按 minimal 原则去掉；将来真要做评论点赞，需要的是**两样东西**——
> 一张 `t_comment_like`（按 ADR-0017 的"专用表"模式）**和**这一列 `like_count`
> （计数的载体）。两样都只是一条 DDL，没有数据迁移。
> **说明这一点，是为了不让 §2.0 的"再加 `t_comment_like`"与这里的"加回这一列"看起来像两条打架的路线**——
> 它们是同一件事的两半。

#### 决策点 ④：评论做几级

| 方案 | 说明 | 代价 |
|---|---|---|
| A | 一级（帖子下平铺） | 无法表达"回复某条评论"，而这在技术社区是基本需求 |
| **B（建议）** | **两级**：评论 + 回复，回复一律挂在顶层评论下 | 需要 `parent_id` 与 `root_id` 两个字段 |
| C | 无限级树 | 查询要递归（CTE 或应用层多次查），展示还要做折叠——复杂度换来的表达力，本场景用不上 |

**选 B**，和掘金 / 牛客的实际形态一致。

**`root_id` 是"两级"能高效分页的关键**：一条帖子的评论要分页，
如果只按 `parent_id` 组织，取"第 2 页的评论"必须先知道哪些是顶层，
而顶层判定要递归。有 `root_id` 之后：

- 取顶层评论：`WHERE post_id = ? AND root_id = 0` —— 直接分页
- 取某条评论的回复：`WHERE root_id = ?` —— 一次查完，不用递归

代价是**回复的回复会被拍平**（回复 A 的回复，展示在 A 下面，而不是缩进第二层）——
这正是"两级"的定义，主流产品的做法一致。

### 2.5 点赞表 `t_post_like` / 收藏表 `t_post_collect`

两张表结构相同：

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | bigint | |
| `post_id` | bigint | |
| `create_time` | datetime | 收藏列表按时间倒序用它 |
| **PRIMARY KEY** | `(user_id, post_id)` | **天然幂等**：重复点赞会撞主键 |
| `KEY idx_post_id (post_id)` | | 查某帖的点赞数 / 哪些人点赞了 |

#### 两个要写清的取舍

**① 取消点赞是物理删除，不用 `deleted` 逻辑删。**
"取消点赞"的语义是**这件事没发生过**，保留一行 `deleted=1` 没有意义；
而且 `(user_id, post_id)` 这个唯一约束一旦配合逻辑删，就变成"要保证有效行唯一"，
得改用更绕的方案。所以这两张表**是全库唯一不带 `deleted` 的表**——这是有意的。

**② 幂等靠主键冲突，不靠"先查再插"。**
"先查有没有点过赞，没有就插入"在并发下会插进去两条（或报错），
而 `INSERT IGNORE` / 捕获重复键异常让数据库来保证——和 M1 的用户名唯一索引同一个套路。

### 2.6 决策点 ⑤：正文与帖子同表，还是拆到 `t_post_content`

| 方案 | 说明 | 代价 |
|---|---|---|
| **A（建议）** | **同表**，正文就是 `t_post.content` | 单行更宽 |
| B | 拆出 `t_post_content(post_id, content)` | 详情页多一次 join；列表页本就不查 `content`，拆表换不来列表页的收益 |

**选 A。** 关键事实是：**MySQL 的 `TEXT` 本来就行外存储**——正文超过一定长度后，
数据存在溢出页里，主表行只留一个 20 字节左右的指针。也就是说，
**只要查询不 SELECT `content` 这一列，它就不会被读出来**。拆表想省的正是这个成本，
而同表 + 不查那一列已经省掉了。

于是真正要立成规范的不是"拆表"，而是这条：

> **列表 / 分页查询必须显式列出需要的列，禁止 `SELECT *`。**
> `SELECT *` 会把 `content` 一起捞出来，前面说的"行外存储所以便宜"当场失效。

这条会和 M6 的深翻页（亮点 4）直接对上：M6 要演示的正是"先查主键再回表取需要的列"，
如果这里养成了 `SELECT *` 的习惯，M6 要讲的那个优化就没有对照物了。

### 2.7 决策点 ⑥：专栏（`column`）M2 不做

`architecture.md §3.1` 的模块清单把**专栏**列在两处：`forum-content`（"帖子、评论、标签、专栏"）
与 `trade-product`（"商品（付费专栏/课程）"）。**付费才是这个项目里专栏存在的理由**——
它是 M7 内容解锁的对象。

> **更正（2026-10-05）**：本节初稿写的是"spec §6.2 的 M2 行后面还有「专栏」"，
> **这是错的**——spec 的 M2 行只有"帖子、标签、评论、点赞收藏、后台；Vue3 工程 + 核心页面"，
> **没有专栏二字**（核验命令：`grep -n '专栏' spec §6.2 所在文件的里程碑表`）。
> 真正的来源是 `architecture.md §3.1` 的模块清单，被我记串了。
> 于是当时往 spec 里加的那条指针**已撤回**（spec 没有这个说法，加指针等于改原文的意思）。
> 结论本身不变，只是**依据换了**。

M2 做一个免费专栏，M7 要为付费再建一次模型（价格、购买、解锁凭证挂在哪），
两次建模之间还会有一堆"免费专栏要不要也能买"的边界问题。

**结论：M2 不做专栏，延后至 M7 与付费内容一并设计。**
（spec 侧**不需要**改动——它本来就没承诺过 M2 做专栏。）

## 3. 跨模块契约：`wt-domain` 的第一次真实落地

**M2 会撞上第一个真正的跨域问题：帖子上要显示作者昵称和头像，而作者信息在 `forum-user` 里。**

按 architecture.md §3.1，`forum-content` **不得依赖** `forum-user`——ArchUnit 会拦。
两者只能通过 `wt-domain` 的契约通信。`wt-domain` 目前是个空壳，M2 是它第一次被真正用上。

### 3.1 契约长什么样

```
wt-domain
└─ com.wingtisky.forum.domain.user
   ├─ UserBrief                —— id / nickname / avatar（只读投影）
   └─ UserQueryService         —— 接口
        Map<Long, UserBrief> findBriefs(Collection<Long> userIds)
```

- **实现放 `forum-user`**（`UserQueryServiceImpl`），Maven 依赖方向是
  `forum-user → wt-domain`、`forum-content → wt-domain`，两边都只依赖契约。
  `app` 模块同时依赖两者，Spring 注入时自然装配起来。
- 契约里**只放跨域需要的最小信息**。`UserBrief` 不含 `email`、更不含 `password`——
  把 `User` 实体放进 `wt-domain` 等于把用户域的内部结构变成了公共 API。

### 3.2 决策点 ⑦：作者信息是"查契约"还是"在帖子上冗余一份"

| 方案 | 说明 | 代价 |
|---|---|---|
| **A（建议）** | 每次展示时通过 `UserQueryService` **批量**取 | 列表页多一次查询（但是一次批量的，不是 N 次） |
| B | 发帖时把昵称 / 头像**快照**进 `t_post` | 列表页零额外查询，但**用户改了昵称，历史帖子还是旧昵称** |

**选 A。** 方案 B 表面更快，代价却是**一处永远修不好的不一致**——
用户改昵称之后，只有新帖子显示新昵称。这类"看起来是缓存、实际是数据错误"的设计，
在面试里很难替它辩护。

**批量方法是必须的**：列表页一页 20 篇帖子，若一篇查一次就是 20 次查询（N+1）。
`findBriefs(Collection)` 一次拿回来，这也不是提前优化——**分页列表天然就是这个形状**。

> **这个方法还是 M3 的第一个缓存对象**：用户信息**读多写少**、
> 且"改昵称"是个明确的失效事件——正是亮点 1 要讲的那种数据。
> 现在把它放在契约接口上，M3 加缓存时只需要在实现里加，调用方一行不改。

### 3.3 错误码

按 `ErrorCode` 里已经写明的分段约定（`A02xx 内容域`），M2 新增：

| 码 | 含义 | HTTP |
|---|---|---|
| `A0201` | 帖子不存在 | 404 |
| `A0202` | 评论不存在 | 404 |
| `A0203` | 标签数量超出限制 | 400（**M2 Task 6 建标签时才加**） |
| ~~`A0204`~~ | ~~不能回复一条回复~~ | **已作废，不要实现**（见下） |

> **⚠️ 2026-10-06 更正：`A0204` 作废。**
>
> 本节初稿列了「不能回复一条回复」，但同一份文档的 §2.4（以及 ADR-0018）写的是
> **"回复的回复会被拍平展示"**——也就是**允许**回复一条回复，只是不缩进第二层。
> 两处直接矛盾：一处说这是错误，另一处说这是模型的正常表现。
>
> 按 §2.4 处理：**允许回复一条回复**，"拍平"是两级模型的定义，不是错误。
> 掘金、牛客也都能对一条回复再点"回复"。所以这个错误码不建，
> `ErrorCode` 里留了一段注释说明它为什么不存在（免得后人看到设计稿的旧表以为漏了）。

> `A0201` 与 M1 的 `A0103`（用户不存在）是同一个模式：**资源不存在用 404 而不是 403**——
> 但要注意，对"别人的私密资源"仍应返回 404 而不是 403，避免泄漏"这个 id 存在"。
> 本项目帖子是公开的，所以直接用 404 即可。

## 4. 接口清单（M2 范围）

| 方法 | 路径 | 说明 | 鉴权 | 限流维度 |
|---|---|---|---|---|
| POST | `/api/posts` | 发帖 | 登录 | 用户 |
| GET | `/api/posts` | 列表：`page` / `size` / `tagId` / `sort` | 公开 | IP |
| GET | `/api/posts/{id}` | 详情 | 公开 | IP |
| PATCH | `/api/posts/{id}` | 编辑 | **归属校验** | 用户 |
| DELETE | `/api/posts/{id}` | 删除 | 归属校验 **或** 版主 | 用户 |
| POST | `/api/posts/{id}/comments` | 评论 / 回复（带 `parentId`） | 登录 | 用户 |
| GET | `/api/posts/{id}/comments` | 评论列表（顶层分页，回复随附） | 公开 | IP |
| DELETE | `/api/comments/{id}` | 删评论 | 归属校验 **或** 版主 | 用户 |
| PUT | `/api/posts/{id}/like` | 点赞（幂等） | 登录 | 用户 |
| DELETE | `/api/posts/{id}/like` | 取消点赞 | 登录 | 用户 |
| PUT | `/api/posts/{id}/collect` | 收藏（幂等） | 登录 | 用户 |
| DELETE | `/api/posts/{id}/collect` | 取消收藏 | 登录 | 用户 |
| GET | `/api/tags` | 标签列表（按 `post_count` 倒序） | 公开 | IP |
| GET | `/api/users/{id}/posts` | 某人的帖子（个人主页用） | 公开 | IP |
| PATCH | `/api/admin/posts/{id}` | 置顶 / 加精 / 下架 | `MODERATOR` / `ADMIN` | 用户 |

### 几处要说明的取舍

**① 点赞用 `PUT` / `DELETE` 而不是 `POST /like` + `POST /unlike`。**
`PUT` 的语义是"把资源设置成这个状态"，天生幂等——重复调用结果相同。
点赞恰好就是这个语义，用 `PUT` 之后"重复点赞"不需要任何额外处理。

**② 需要登录的路径要在 `SecurityConfig` 里逐个放行公开接口。**
M1 用的是 `anyRequest().authenticated()`（漏列 = 完全敞开）。M2 新增的
**公开**接口（列表、详情、标签、评论列表）必须显式加进 `PUBLIC_ENDPOINTS`，
漏一个的表现是"匿名用户访问 401"，一眼能发现——这比反过来安全。

**③ 列表页的搜索先走 `LIKE`。** spec 里 ES 是 M5，M2 用
`WHERE title LIKE ? OR summary LIKE ?` 顶一下即可。**要在这里标注"这是 M5 要替换掉的实现"**，
否则 M5 时没人知道为什么有两套检索。

## 5. 补 M1 遗留：限流的用户名维度

M1 设计 §5.4 明确留了这个缺口，并写下了建议做法。**M2 要补上**（用户已确认）。

### 5.1 为什么放在 `AuthService.login`，不放进拦截器

`RateLimitInterceptor` 运行在 Controller 之前，**拿不到请求体里的用户名**。
要在拦截器里拿，必须加一层 `ContentCachingRequestWrapper` 把请求包起来——
而请求体是一次性的，读完后续 `@RequestBody` 就拿不到了。

`AuthService.login` 里用户名**已经被解析成参数**，直接用它做 Key 即可，
不需要任何请求包装。代价是限流逻辑从"统一拦截器"分出一点到业务层，
**这个分家的理由要写进代码注释**，否则下一个人会以为是随手写的。

### 5.2 具体做法

- 配置新增一段（**与 `rules` 并列，不混进按路径匹配的规则里**）：

  ```yaml
  wt:
    rate-limit:
      login-username:
        limit: 5
        window: 1m
        fallback: local
  ```

- 实现复用现成的 `SlidingWindowRateLimiter`（`wt-infra`）与 `LocalRateLimiter`（降级），
  Key 用 `RedisKey.rateLimit("username", username, "/api/auth/login")`。
- **计数放在密码校验之前**——否则撞库请求已经打到 BCrypt 了，限流就晚了。
- 阈值 `5 / 分钟` 是初始值，和 M1 那些数字一样，**M10 压测时校准**。

### 5.3 两处必须写清的理由

**阈值为什么是 5 而不是更严**：正常用户输错密码 5 次要被等 1 分钟，这是可接受的上限。
压到 3 次会有很多误伤（记不清密码的人第一轮就会撞上），而撞库者本来就在用字典，
少限两次挡不住他——**这一维度的价值在于给"同一账号被多台机器打"设一道闸**，
不在于精确拦截。

**它和 IP 维度不是重复**：按 IP 挡的是"同一台机器试很多账号"，
按用户名挡的是"很多台机器试同一个账号"。这是撞库的两种形态，**只限一个都会漏**。

## 6. 前端范围（最小，但排版要达到合理水准）

### 6.1 什么叫"最小"

**页面数量少，不是质量差。** 只做 4 个页面，但每个页面都要是**能给人看的**：

| 页面 | 内容 | 质量底线 |
|---|---|---|
| 登录 / 注册 | 表单 + 切换 | Element Plus 表单校验；错误提示直接用后端 `Result.message` |
| 帖子列表 | 首页 | 卡片列表、分页控件、加载态、**空状态**（无内容时不能是一片空白）、标签筛选 |
| 帖子详情 | 帖子 + 评论区 | 信息层级清楚：标题 / 作者 / 时间 / 正文 / 标签 / 点赞收藏按钮 / 评论区；回复缩进一级 |
| 发帖 | 表单 | 标题、正文、标签输入（最多 5 个）；提交前的校验提示 |

**统一布局**：顶部导航栏（站名 + 登录态 + 发帖入口）+ 居中的内容容器（限制最大宽度）。
所有页面共用同一套间距与字体，不各写各的。

### 6.2 技术选型（白名单内）

Vue3 + Vite + Element Plus + `vue-router` + `axios`。

**三个明确不引入**（YAGNI）：

- ❌ **Pinia** —— 登录态与用户信息用 `localStorage` + 一个 `useAuth` 组合式函数足够。
  引入状态管理库之后，第一个要写的往往是"把 localStorage 包一层"，收益为负。
- ❌ **组件库二次封装** —— 4 个页面还没到需要抽象"业务组件"的规模
- ❌ **SSR** —— 与项目目标无关

### 6.3 联调

Vite dev server 配 `proxy` 把 `/api` 转发到 `localhost:8080`——
**不要在后端开 CORS**：同源代理让前后端在开发期就是同源的，
既省掉 CORS 配置，也让"上线后同源部署"这件事提前成立。

**2026-10-05 用户授权：按下列建议执行。**

| # | 决策点 | 结论 | 落在哪 | 在哪一节 |
|---|---|---|---|---|
| ① | 点赞 / 收藏：两张专用表还是一张通用表 | **两张专用表** | **ADR-0017** | §2.0 |
| ② | 计数字段：冗余在 `t_post` / `t_tag` 上，还是实时 `COUNT` | **冗余字段** | **ADR-0016** | §2.2 |
| ③ | 标签：自由输入还是预置 | **自由输入** + 唯一索引兜并发 | 本文档 | §2.3 |
| ④ | 评论级数：一级 / 两级 / 树形 | **两级**（`parent_id` + `root_id`） | **ADR-0018** | §2.4 |
| ⑤ | 帖子正文：同表还是拆 `t_post_content` | **同表**，另立"禁止 `SELECT *`"的规范 | 本文档 | §2.6 |
| ⑥ | 专栏：M2 做还是延后 | **延后到 M7**（依据 `architecture.md §3.1`；spec 无需改动） | 本文档 | §2.7 |
| ⑦ | 作者信息：查 `wt-domain` 契约还是冗余快照 | **批量查契约** | **ADR-0015** | §3.2 |
| ⑧ | 浏览量 `view_count`：M2 就做还是不做 | **M2 就做**（详情页 `+1`，作为 M3 的钩子） | 本文档 | §2.1 |
| ⑨ | 后台：只做接口还是连页面一起 | **只做接口**，不做后台页面 | 本文档 | §1、§4 |
| ⑩ | 列表排序：只做最新，还是也做"最热" | **两个都做**，热度用初始公式并标注 M6 校准 | 本文档 | 见下 |

**四条有独立 ADR 的**（① ② ④ ⑦）是"面试官可能追问为什么"的那一类；
其余六条属于设计取舍，记在本节与 `STATUS.md` 的决策轨迹里，不单独立 ADR——
**ADR 立太多会让索引失去信号**，判断标准见 `docs/02-decisions/README.md` 的开头。

### 关于 ⑩ 的补充说明

spec §1.5 写了「首页用时间 + 热度分，不做协同过滤」。M2 把它落成：

- `sort=latest` —— `ORDER BY top_flag DESC, create_time DESC`
- `sort=hot` —— `ORDER BY top_flag DESC, (comment_count * 3 + like_count * 2 + collect_count) DESC`

**这个系数是拍出来的，不是算出来的**，所以要在文档和代码里都标注：
**它是初始公式，M6 用真实数据与 `EXPLAIN` 校准**。

顺带一件事：`hot` 排序 + 深分页，**正是 M6 亮点 4（Deferred Join）要的那个真实场景**——
按非主键排序、翻到第 5000 页。M2 把它建起来，M6 才有对照物可测。

> **⑧ 与 ⑩ 都是我主动往 M2 里加的**（spec §6.2 的 M2 行没写）。理由是同一条：
> **M3 和 M6 需要一个真实的、有数据量的表才能测出东西**，
> 而"浏览量计数"和"热度排序"恰好是这两个亮点各自最自然的切入点。
> 若你觉得这是超前，砍掉 ⑧ 或 ⑩ 都能讲得通——只是 M3 / M6 要另找切入点了。
