# ADR-0016: 内容计数冗余存表，不实时 COUNT

- **状态**：已接受
- **日期**：2026-10-05
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

帖子列表的**每一行**都要显示点赞数、评论数、收藏数；标签列表要显示每个标签下的帖子数。

这是全站**最高频的读**：首页一页 20 行，就是 20 组计数。而它们全都来自别的表——
点赞数在 `t_post_like`、评论数在 `t_comment`。

## 候选方案

### 方案 A：每次实时算
`SELECT COUNT(*) FROM t_post_like WHERE post_id = ?`，或用 `GROUP BY` 一次算一页。

- 优点：**永远准确**，没有一致性问题，没有"忘了更新"的风险
- 缺点：成本压在最贵的地方；`t_post_like` 会是全库最大的表

### 方案 B：在内容表上冗余计数字段，写的时候同事务更新（**选中**）
`t_post.like_count` / `comment_count` / `collect_count`、`t_tag.post_count`。

- 优点：列表页读极快；计数字段就是 M3 要缓存的东西
- 缺点：一致性由业务代码保证；热点行会争锁

## 决定

采用**方案 B**：计数冗余在内容表上，写操作与计数更新放在同一个事务里。

## 理由

### 一、实时 COUNT 把成本压在了最贵的地方

列表页是**读最多**的接口，点赞表是**行最多**的表。让最贵的读去扫最大的表，
是把这个系统里两件最费资源的事凑到了一起。

`GROUP BY` 能缓解（一页只查一次而不是 20 次），但缓解不了"扫全表再分组"这件事本身。

### 二、`UPDATE ... + 1` 是原子的，不需要额外处理并发

```sql
UPDATE t_post SET like_count = like_count + 1 WHERE id = ?
```

这是**单条语句**，原子性由数据库保证。它不需要"先读出来、加一、再写回去"——
那种写法在并发下必然丢更新（两个请求都读到 10，都写回 11，实际应该是 12）。

所以方案 B 的并发正确性**不需要显式加锁**，这是它比想象中好做的地方。

### 三、最重要：这是 M3 的钩子

亮点 1（多级缓存）要缓存的是**"帖子的展示信息"**。如果计数字段在这里不存在、
每次现算，M3 就没有一个**明确的缓存对象**可讲——它会变成
"先想办法把数算出来"，而不是"缓存这些字段并处理一致性"。

**现在把字段留下，M3 的题目才是那道题。**

## 后果

- **正面**：
  - 列表页读极快（全部字段在同一行，一次查询搞定）
  - M3 有明确的缓存对象与失效事件（点赞、评论）
  - 计数可以单独重建（写一条对账 SQL 重算即可，见下）
- **负面**：
  - **一致性由业务保证**：每个改动计数的地方都得记得更新，漏一处的表现是"计数偏了"而不是报错
  - **热点行的锁竞争**：爆款帖被大量点赞时，`UPDATE t_post` 会争同一行。这是 M3（缓存承接读）与 M8（分布式锁）要处理的问题，M2 先接受
  - 计数错了只能重算，没有自动修复

### 允许短暂不一致，边界要说清

写点赞行与 `+1` 在**同一个事务**里，正常路径下不会不一致；
只有进程崩溃在两次写之间才会。对**展示性**计数，这个代价可以接受。

**这个取舍之所以成立，是因为计数不参与任何判断**——它只被显示。
一旦某个计数参与业务判断（比如"点赞过 100 才能解锁"），它就必须是权威数据源，
那时正确的做法是查实际表，而不是读这个字段。**这条界线要一直守住。**

### 重算 SQL（不是装饰，是出事时的补救手段）

```sql
UPDATE t_post p SET p.like_count =
  (SELECT COUNT(*) FROM t_post_like l WHERE l.post_id = p.id);
```

## 被否决方案为何不选

**方案 A 在另外两类场景下是对的，本项目不是那两类：**

1. **计数必须绝对准确时**——例如"剩余库存"（M8）。那时不能有"短暂不一致"，
   做法也不是 COUNT，而是 Lua 原子扣减。
2. **写多读少时**——实时算反而更省，因为不用维护冗余字段。

本项目的计数是**展示性的**：它错了不会让谁的钱算错，只会让界面数字不好看，
而且随时可以重算。**把它当权威数据来看待，是用错了工具。**

> 面试时这条界线值得主动讲：*"我把计数分成两类——展示性的用冗余字段，
> 参与判断的必须查权威来源。混在一起的后果是，某天有人拿点赞数做了业务规则，
> 而它还带着'允许短暂不一致'的前提。"*
