# ADR-0003: 前端形态（Vue3 + Vite + Element Plus，前后端分离）

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

项目需要一个能展示社区形态的前端：帖子列表、发帖、评论区、登录注册，后期还有付费下单与秒杀页面。

目标是 **Java 后端 / AI Agent 应用开发**岗位，前端不是卖点，但**必须存在且能跑**——

- 没有界面，"技术社区"就只是一个接口集合，面试时无法演示
- 但投入过多时间在前端，又会挤占后端亮点（缓存、异步、检索、秒杀）的时间

所以真正要定的是"**用最低的边际成本换来一个像样的界面**"。

## 候选方案

### 方案 A：Vue3 + Vite + Element Plus，前后端分离（**选中**）
- 优点：国内 Java 后端岗位最常配套的前端栈，关键词匹配度高；Element Plus 是现成的企业级组件库，表格/表单/分页/弹窗开箱即用；前后端分离让后端接口可以被独立测试（`.http` 脚本直接打）
- 缺点：多一个独立的 Node 工程要维护；本地开发要处理跨域

### 方案 B：React
- 优点：生态最大，若将来想转全栈/前端岗位更有用
- 缺点：对"Java 后端"这个目标岗位**收益不明显**，学习成本换不来面试加分

### 方案 C：无构建静态前端（原生 HTML + fetch）
- 优点：零构建、零依赖，改完刷新就能看
- 缺点：拿不到任何前端框架关键词；页面一多就难以维护；M11 的对话界面（流式渲染）几乎做不动

### 方案 D：Thymeleaf 服务端渲染
- 优点：不用起 Node，模板与后端在同一个工程里
- 缺点：与"前后端分离"的产品要求相悖；而且**与旧项目同质**——本项目要重新推导设计，不做复刻

## 决定

采用**方案 A**：Vue3 + Vite + Element Plus，作为**独立工程**（`frontend/`）与后端分离。

## 理由

**优先对齐目标岗位的技术栈生态。** Java 后端岗位的招聘描述里，配套前端十有八九写的是 Vue；用 Vue3 + Element Plus，面试官看到的是"熟悉主流组合"，而不是"这个人前端学过什么"。

**Element Plus 把 CRUD 页面的成本压到接近零。** 本项目前端的绝大部分页面（帖子列表、后台管理、订单列表）都是标准 CRUD，用组件库拼装，产出速度与手写 CSS 不是一个量级。

**前后端分离让后端有独立可信的证据。** 接口能用 `.http` 脚本直接打，这样"发帖 → 评论 → 列表"这条端到端链路才有**真实 HTTP 数据**可记录——这是防「验证剧场」闸门的前提（spec §9 闸门 2）。

**为 M11 留位。** 二期的 RAG / 多轮对话需要一个能流式渲染消息的界面，Vue3 的响应式模型天然适配；Thymeleaf 那种服务端渲染方案届时会很难受。

## 后果

- **正面**：界面产出快；后端接口可独立测试；M11 的对话界面不需要换技术栈
- **负面**：多一个 Node 工程要维护（依赖升级、构建产物）；本地开发需要处理跨域（M1 起就要配 CORS 或 Vite 代理）；本机 Node 装在 `D:\aaaSoftware`，需确认版本与 Vite 的要求匹配

## 被否决方案为何不选

- **方案 B（React）**：技术上是等价选择，但**对本项目服务的目标岗位没有收益**。选型的判据是"这个决定服务谁"，不是"哪个更主流"
- **方案 C（静态前端）**：省下的构建成本，换来的是必须手写所有交互。而且它会削弱 M11 —— 流式对话界面用原生 JS 写是自找麻烦
- **方案 D（Thymeleaf）**：与旧项目同质。本项目明确要**重新推导一遍设计**，沿用旧项目的形态会让"为什么这么选"这个问题没有新答案
