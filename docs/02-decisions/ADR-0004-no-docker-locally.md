# ADR-0004: 本地不使用 Docker

- **状态**：**已修订**（2026-10-07 由 ADR-0020 修订——见文末「修订记录」；
  原文保留，**内存约束与"不用 Docker"这两条结论仍然有效**，被取代的只是「中间件承载在 Windows 原生进程」）
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

项目要跑四个中间件（MySQL、Redis、Kafka、ES），加上未来的三个服务进程。用什么方式把它们在**开发机上**跑起来，是一个必须现在决定的问题——它会一路影响 CI（ADR-0007）、交付形态（ADR-0006）和日常开发的每一分钟。

本机实测约束（2026-09-13）：

| 项 | 实测值 |
|---|---|
| 内存 | ≈ 15.4 GiB |
| CPU | AMD Ryzen 5 4500U，6 核 6 线程 |
| 磁盘 | C 盘剩 ~19 GB（**不可用于安装**）/ D 盘剩 ~229 GB |
| Docker / WSL2 | **均未安装**，且系统为 Win10 Home（**不支持 WSL2 后端**） |

## 候选方案

### 方案 A：本机原生部署中间件（**选中**）
中间件全部装在 `D:\aaaSoftware`，用 .bat 脚本固化启停参数。

- 优点：**内存完全可控**——每个中间件的堆大小能按项目预算精确压（ES 与 Kafka 各 1 G）；出问题时能直接翻原生日志与配置文件
- 缺点：环境不可复现，换台机器要重装一遍；中间件版本被 Windows 生态限制（如 Redis 只能停在 5.0.14.1）

### 方案 B：Docker Desktop + Docker Compose
- 优点：环境一键复现；中间件版本不受 Windows 原生构建的限制
- 缺点：**Win10 Home 没有 WSL2**，Docker Desktop 只能走 Hyper-V 后端；16 G 内存上再叠一层虚拟化，与"ES + Kafka + 三个服务 ≈ 11 G"的预算直接冲突

## 决定

采用**方案 A**：本机原生部署，**不使用 Docker**。

## 理由

**内存是硬约束，不是偏好。** 项目的资源预算已经很紧张（architecture.md §6.1：M9 全开约 10.9 G / 16 G）。Docker 的虚拟化层不是免费的——在 Win10 Home 走 Hyper-V 后端的情况下，它要先占掉一块固定的内存，再让每个容器各占一份。**预算里没有这块余量。**

**C 盘只剩 19 G，而 Docker 的镜像与虚拟磁盘默认落在 C 盘。** 即便前面的内存问题能忍，磁盘这一关也过不去——把 Docker 的数据目录改到 D 盘是可行的，但那是又一层与工具搏斗的成本。

**源码级可控对本项目有实际价值。** 调试 ES 的分词器配置、Kafka 的 KRaft 参数、Redis 的 Lua 行为时，直接改原生配置文件、看原生日志，比"进容器里 exec 一下"直接得多。本项目的亮点（缓存、秒杀 Lua）恰好都在这些地方。

**保留条款：这个决定只约束"本项目自己的开发环境"，不约束使用者。** 架构上保证**配置外置**（数据库地址、端口、中间件连接串一律走配置文件而非硬编码），GitHub 上的使用者如果本机有 Docker，**可以自己用 Docker Compose 把中间件跑起来**，不必装原生版本。本项目的交付文档需要说明这一点，但不把 Docker Compose 作为默认路径。

## 后果

- **正面**：内存占用可控且可精确调参；中间件行为可直接观察；不需要为 Docker 本身排障
- **负面**：
  - **环境不可复现**：README 无法做到"一条命令跑起来"，只能写"先装这四个中间件，再改这些配置"（这一成本由 ADR-0006 的交付形态一并承担）
  - **集成测试无法用 Testcontainers**（见 ADR-0007），集成测试只能在本地跑，不进 CI
  - 中间件启停参数需要自己写成脚本固化（M0 Task 8 的 `scripts/start-es.bat` / `start-kafka.bat`）

## 被否决方案为何不选

- **方案 B（Docker Compose）**：这是**当前社区的标准做法**，本项目不用它，不是因为不认可，而是因为**这台机器不适合**——无 WSL2、内存贴近上限、C 盘只剩 19 G。三个约束任缺其一，这个决定都可能反过来。把"为什么不用标准做法"写清楚，比强行套用标准做法更能说明问题

## 修订记录

### 2026-10-07 · 状态改为「已修订」

**由**：ADR-0020（本地 Kafka 改用 WSL2 承载）
**原因**：本 ADR 的前提**对 Kafka 不成立**。原文把取舍算在「内存」与「C 盘空间」两笔账上，
并隐含了一个当时**没有写出来、也无法预见**的假设：**中间件在 Windows 原生下能正常工作**。
对 MySQL 与 Redis 这个假设成立；**对 Kafka 不成立**——Kafka 官方不把 Windows 列为 broker 的
受支持平台，凡需回收磁盘（删日志段、删主题）即崩溃，相关工单至今 Open。

**变更**：

- **原文全部保留，继续有效**。特别是这两条今天依然成立、后续决策必须继续遵守：
  1. **内存是硬约束**（M9 全开约 10.9 G / 16 G），这条判断没有变；
  2. **本地不使用 Docker**——本 ADR 被修订**不是**因为要改用 Docker。
     本机为 Win10 **Home**，装不了 Docker Desktop（无 Hyper-V 后端；C 盘也只剩 32 GB），
     这一点与原文记录一致。
- **被取代的部分**：只有「中间件的承载方式」这一项。中间件由
  **Windows 原生进程** 改为 **WSL2 内的原生进程**（不是 Docker 容器）。
- **"保留条款"不受影响**：原文承诺的「配置外置、使用者可用 Docker Compose 自建环境」仍然有效，
  且随着 ADR-0020 把 Kafka/ES 移入 WSL2，这一承诺更容易兑现。
- **新的负面后果**：首次安装 WSL2 需要管理员权限与一次重启，CLI 做不了；
  发行版虚拟磁盘需从默认的 C 盘迁到 D 盘。详见 ADR-0020「后果」。
