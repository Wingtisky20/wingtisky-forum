# ADR-0011: 跨服务一致性采用「本地消息表 + MQ 最终一致」，不用 Seata

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

拆分出 `seckill-service` 与 `trade-service` 后（ADR-0010），出现跨服务写操作：

> 秒杀扣减库存成功后，需要在交易域创建订单。**扣库存与建订单必须同生共死。**

这是典型的分布式事务场景。

## 候选方案

### 方案 A：Seata（AT 模式）
- 优点：对业务代码侵入小，注解即可；简历上是"标准微服务组件"
- 缺点：**同步阻塞**——全局锁持有到分支事务提交，在秒杀这种高并发场景下会把吞吐拖垮；多一个组件（+0.5 G 内存 + 运维复杂度）

### 方案 B：本地消息表 + MQ 最终一致（**选中**）
- 优点：无同步阻塞，性能好；实现完全可控，可讲清每个环节；复用已有的 Kafka 与幂等机制（亮点 2）
- 缺点：**最终一致**——存在短暂的不一致窗口，需要补偿与对账

### 方案 C：TCC
- 优点：性能优于 2PC
- 缺点：每个参与方要实现 Try/Confirm/Cancel 三套逻辑，**开发成本与出错面显著放大**，对本项目的业务复杂度属过度设计

## 决定

采用**方案 B**。链路如下：

```
seckill-service                              trade-service
  1. Redis Lua 原子扣库存 + 记录购买者
  2. 本地事务：写消息表(status=待投递)
  3. 发送 Kafka 消息（订单创建请求） ──────────→
                                              4. 消费 → 幂等校验(eventId)
                                              5. 本地事务：建订单 + 写消息表(status=已处理)
                                              6. 手动 Ack
  7. 定时任务：扫超时未确认消息 → 重投 / 触发库存回补
  8. 定时对账：Redis 库存 vs DB 订单数 → 修正差异
```

## 理由

**秒杀场景下，一致性方案的选择标准是"能不能扛住吞吐"，而不是"强不强"。**

Seata AT 的全局锁会让秒杀接口的响应时间随并发上升而恶化——这与秒杀"削峰"的设计目标直接冲突。反过来说，本业务**完全可以容忍短暂不一致**：库存扣了但订单还没建，几秒后补上，用户无感知。

三个设计要点：

1. **步骤 2 必须在 3 之前**：先写本地消息表再发消息。否则"扣了库存却丢了消息"会造成永久不一致。**这是本方案唯一不能颠倒的顺序。**
2. **步骤 4 复用亮点 2 的幂等**：消息会重投，消费端必须幂等
3. **步骤 7、8 是兜底而非补丁**：**允许不一致，但必须能自愈**——这是"最终一致"的完整含义。只讲 MQ 不讲补偿，等于只讲了一半

## 后果

- **正面**：无同步阻塞，吞吐不受一致性方案拖累；可复用的组件多（Kafka、幂等机制）；**"我评估过 Seata 但没用"是一个能展开讲五分钟的面试答案**
- **负面**：需要额外实现消息表、定时补偿、对账任务——**约 1 周工作量**，且这些不是"业务功能"，是纯粹的一致性成本

## 被否决方案为何不选

- **方案 A**：公平地说，Seata 本身没有问题，**问题是它用错了地方**。若本项目是订单-支付这种低频强一致场景，Seata 是正确选择。**但它与秒杀的性能目标是冲突的**——选型要看场景，不是看组件名气
- **方案 C**：TCC 的价值在于把锁的粒度从"数据库行"降到"业务资源"，代价是三套逻辑。本项目没有需要如此细粒度资源预留的场景
