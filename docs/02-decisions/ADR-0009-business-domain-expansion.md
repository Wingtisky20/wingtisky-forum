# ADR-0009: 业务域从「纯论坛」扩展为「技术社区 + 付费内容」

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

原定位是纯技术社区（帖子、评论、标签、检索），预计工期 4-6 个月。用户提出两个新诉求：

1. **要体验分布式**，并提出秒杀场景
2. 认为"一个论坛撑不起微服务拆分"

这两个诉求指向同一个问题：**项目业务太薄，撑不起一个分布式项目的体量。**

## 候选方案

### 方案 A：保持纯论坛 + 秒杀券
- 优点：改动最小，工期只增约 3 周
- 缺点：秒杀是硬塞进社区的功能，业务关联牵强；项目体量仍偏薄

### 方案 B：多业务域拼贴（如"二手交易 + 校园趣事 + 技术论坛"）
- 优点：业务看起来丰富
- 缺点：**三个域之间没有数据流转**——面试官问"它们怎么交互"答不上来；没有交互就不是一个系统，是三个系统塞进一个仓库；每个域都做浅；工作量 ×3 而技术收益 ×0

### 方案 C：沿现有业务纵深扩展 ——「技术社区 + 付费内容」（**选中**）
- 优点：业务关联真实（内容 → 付费内容 → 交易），数据流转闭环；两个域的流量特征与一致性要求天然不同，为拆分提供正当理由；AI 演进的语料更丰富（帖子 + 专栏都是知识库）
- 缺点：工期增加约 4-6 周

## 决定

采用**方案 C**。产品定位为「技术社区 + 付费内容」，参照 CSDN 形态：社区内容可转为付费专栏，付费专栏上架为商品，通过优惠券秒杀购买。

## 理由

**核心判据是"数据流转是否真实"。** 方案 B 的问题不在于"业务多"，而在于**域之间没有上下游关系**——没有关系的域放在一起，不会让系统更复杂，只会让仓库更乱。

方案 C 的闭环（内容 → 付费 → 交易 → 解锁 → 回到内容）**每个环节都有真实的读写**，因此：
- 面试官问"它们怎么交互"，有完整链路可答
- 跨服务一致性有了**真实的业务场景**，而不是为了演示技术而生造
- 秒杀的位置自然（卖课发券），不是硬塞

## 后果

- **正面**：项目体量足以支撑分布式设计；业务故事连贯；AI 演进的语料来源从"只有帖子"扩展到"帖子 + 专栏"
- **负面**：工期增加 4-6 周，总计约 8.5 个月。用户已确认采用**分两期交付**（一期 M0-M10 形成可投递项目，二期 M11 AI 演进）

## 被否决方案为何不选

- **方案 A**：不改定位的话，秒杀与社区缺乏业务关联，属于"为了用技术而造需求"，面试时容易被问穿
- **方案 B**：见上——域之间无数据流转，是拼贴而非系统。**这是本次决策中最重要的排除项**：判断一个业务域该不该加，标准不是"技术含量高不高"，而是"它和现有域有没有真实的数据往来"
