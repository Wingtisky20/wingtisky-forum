# ADR-0001: 技术栈基线（JDK 17 + Spring Boot 3 + ES 8 + Kafka 3.9 KRaft）

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

从零建一个新项目，需要先钉死技术栈基线，后续所有里程碑都在这条线上走。

两个约束把它变成了真正的选择题：

1. **本机已装的东西是"旧"的**：MySQL 8.0.41、Redis 5.0.14.1、Kafka 2.8.1（带 ZooKeeper）、ES 6.8.23 —— 都来自上一个已完成的项目。
2. **上一个项目用的是 JDK 11 + Spring Boot 2**，而本项目二期（M11）要演进出 RAG / Agent 能力。

也就是说：沿用旧栈最省事，但可能把返工推到后面；现在就上新栈要付出环境成本，但一次到位。

## 候选方案

### 方案 A：全套沿用旧栈
JDK 11 + Spring Boot 2 + ES 6.8 + Kafka 2.8（含 ZooKeeper），MySQL / Redis 不动。

- 优点：**零环境成本**，中间件都已装好、都已跑通过，第一天就能写业务代码
- 缺点：二期必须大返工；且 ES 6.8 只能用早已废弃的 `TransportClient`

### 方案 B：半现代（Boot 3 + ES 8，Kafka 2.8 不动）
- 优点：省下 Kafka 的迁移成本（Kafka 在 Win10 上安装是本次最容易卡住的一环）
- 缺点：**两头都不彻底**——Kafka 2.8 仍要带一个 ZooKeeper 进程，而 KRaft 才是 3.x 的主流形态；等于把最麻烦的那件事推迟，而不是解决

### 方案 C：JDK 17 + Spring Boot 3.5.16 + ES 8.x + Kafka 3.9 KRaft（**选中**）
MySQL 8.0 与 Redis 5.0.14.1 沿用（无升级空间，理由见下）。

- 优点：技术栈关键词全部对齐当前主流；二期 AI 演进不需要返工
- 缺点：本机要新装 ES 8 与 Kafka 3.9，多占约 1.5 G 内存，环境成本约半天

## 决定

采用**方案 C**。

## 理由

**决定性理由是二期。** Spring AI / LangChain4j 这类库硬性要求 **Java 17+**。如果沿用 JDK 11，M11 的 AI 演进要么做不了，要么先把整个项目升到 17 —— 而那时的升级会牵动 Boot 2 → 3 的 `javax.*` → `jakarta.*` 全局改名。**这笔账现在付只要半天，放到二期付要重跑所有测试。**

**ES 是被 Boot 3 反推着必须升的**：Spring Boot 3.x 官方的 ES 客户端只面向 ES 7.17 / 8.x，而 ES 6.8 时代的 `TransportClient` 在 ES 8 里已被彻底移除。想用新客户端，就只能升 ES。

**Kafka 用 KRaft 是为了少一个进程**：3.9.x 的 KRaft 模式不再需要 ZooKeeper，本机 16 G 内存、ES 与 Kafka 各压 1 G 堆的预算下，少一个常驻 JVM 是实打实的收益。

**MySQL 与 Redis 沿用，不是"懒得升"**：
- MySQL 8.0.41 本来就够新，没有升级理由
- Redis 停留在 5.0.14.1 是 **Windows 平台的天花板**——更高版本的官方 Windows 原生构建早已停止，而本机无 Docker/WSL2（ADR-0004）。这是一条被环境锁死的约束，不是偏好

**为什么不是 JDK 21**：JDK 21 的虚拟线程是简历加分点，spec §12 曾把它列为"决策时点 M0 前"的开放问题。这里明确记为**不升级**——本机已装 17.0.16，Spring Boot 3.5 对两者都支持，而虚拟线程的收益集中在 IO 密集的压测场景，**本项目现在没有可验证它的手段**。等 M10 压测若显示线程池确实是瓶颈，再评估；那才是有数据支撑的升级，而不是为了关键词而升。

## 后果

- **正面**：拿到当前主流的 Java 后端技术栈；二期 AI 演进不需要返工；KRaft 模式让本机少一个常驻进程
- **负面**：本机需新装 ES 8 与 Kafka 3.9，约多占 1.5 G 内存；Win10 上安装这两个中间件有踩坑风险。**对策已写入 spec §11：环境卡超 1 天即降级到 ES 7.17**，并把降级决策记回本 ADR

## 被否决方案为何不选

- **方案 A（沿用旧栈）**：把一个确定会发生的返工推到了二期。而且本项目是"重新推导一遍设计"，沿用旧栈等于把旧项目的技术债一起继承
- **方案 B（半现代）**：Kafka 2.8 + ZooKeeper 意味着多一个进程要管、多一套过时的配置体系（`zookeeper.connect` 那套）。既然 ES 那边已经要装新东西了，"省下 Kafka"省不了半天

## 修订记录

### 2026-09-13 · 更正补丁版本号

**变更**：Spring Boot 补丁版由 `3.5.3` 更正为 **`3.5.16`**，结论本身不变。

**原因**：本 ADR 初稿用 solr 的 `core=gav&rows=N` 查询版本，**它按发布时间排序而非版本号**，把 `3.5.3` 排在了前面，于是被误判为最新。后改为读 `maven-metadata.xml` 核实。

**遗留的通用教训**：版本核查一律用 `maven-metadata.xml`；也**不要读 `<release>` / `<latest>` 字段**——它们可能指向 milestone 版本（实测该字段返回 `4.2.0-M1`）。

### 待办 · Redisson 与 Redis 5 的运行时兼容性（M3 验证）

Redisson **3.52.0** 目前**只做过编译期验证**（依赖能解析、代码能编译）。本机 Redis 是 5.0.14.1，Redisson 3.x 的部分功能可能用到 Redis 6+ 才有的命令。

**M3 首次真正接入 Redis 时必须实测**：若运行时报 `ERR unknown command`，则降级 Redisson 到兼容版本，并把结论追加到本节。

**同理不采用 4.x 线**：Redisson 4.x 可能要求 Redis 6+，与本机被锁死的 Redis 5 直接冲突。
