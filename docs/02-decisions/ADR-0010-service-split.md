# ADR-0010: 按故障域拆分为三个服务，且「先画逻辑边界，后做物理拆分」

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）
- **取代**：ADR-0005（明确不采用微服务）
- **修订**：ADR-0002（架构形态）

## 背景

ADR-0005 曾明确不做微服务，理由是"本机 16G/6 核跑不动，且非项目亮点，属过度设计"。

引入付费内容与秒杀（ADR-0009）后，前提变了：**项目出现了两个流量特征与一致性要求截然不同的业务域**。需要重新判断是否值得拆分。

## 候选方案

### 方案 A：维持单体多实例
不拆进程，只跑两个实例。
- 优点：资源占用最低（≈ 6.2 G），复杂度最低
- 缺点：秒杀与交易仍在同一进程，**故障域未隔离**；简历上缺少服务治理相关实践

### 方案 B：拆分并立即物理隔离（**选中，附加约束**）
拆为 `forum-service` / `trade-service` / `seckill-service`，M1 起即分进程开发。
- 优点：边界从第一天就是硬的
- 缺点：**押注在一个尚未验证的判断上**——若拆分收益不显著，返工成本高；且开发期资源占用高

### 方案 C：完整微服务（网关 + 注册中心 + Sentinel + Seata）
- 优点：简历关键词最全
- 缺点：**面试官必问"一个技术社区你为什么要全套微服务"，答不好是减分项**；大量精力耗在服务治理而非业务；本机内存逼近上限

## 决定

采用**方案 B 的拆分边界**，但附加一条关键约束：

> **M1–M8 全部在一个进程内开发，模块边界由 ArchUnit 强制；M9 才做物理拆分，并执行对照实验验证拆分收益。**

## 理由

**拆分理由是「故障域隔离」，不是「性能」也不是「微服务是主流」。**

秒杀是瞬时脉冲，会打满 Tomcat 线程池与数据库连接池。若与交易同进程，**秒杀被打挂 = 用户下不了单**。这条理由**不依赖流量大小**，是结构性的——因此在本机这种没有真实流量的环境里依然成立。

**明确不用性能论证拆分的理由**：本项目没有真实流量，任何性能论证都会被追问到站不住。能说出"我考虑过用性能论证，但那在本项目站不住"，比背微服务的好处更有说服力。

**"先边界后进程"这一约束的价值**：拆分决策的正确性此时无法证明。先画边界使"拆"与"不拆"只差一次模块搬运，**不押注在未经验证的判断上**。

## 后果

- **正面**：拿到故障域隔离与完整的服务化实践；拆分决策有 A/B 对照实验数据兜底
- **负面**：M9 资源占用约 10.9 G / 16 G，不宽裕；必须执行"按需启动"纪律（做内容域时只起 forum + MySQL + Redis）

## 被否决方案为何不选

- **方案 A**：秒杀与交易的故障域无法隔离，秒杀把进程打挂会连带影响下单——这正是本项目最想验证的分布式问题
- **方案 C**：拆分的正当性只存在于有真实业务边界的地方。给三个服务配齐注册中心、网关、Sentinel、Seata，**大部分组件的引入理由会是"微服务都该有"而非"我需要它"**——这正是本项目一直在防的过度设计

## 后续验证（M9 必做）

用 JMeter 打满秒杀接口，同时测量订单查询接口的 P99：

| 组 | 预期 |
|---|---|
| A 组：同进程 | 订单接口 P99 显著劣化 |
| B 组：独立进程 | 订单接口基本不受影响 |

**若 A/B 差值不显著 → 退回两个服务，并在本 ADR 追加修订记录。**
