# ADR-0005: 明确不采用微服务

- **状态**：已废弃
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）
- **取代**：ADR-0010（按故障域拆分为三个服务）

## 背景

项目定位是技术社区（对标掘金 / 牛客），要判断是否需要微服务架构。

约束：

- 一个人做，没有团队分工与独立部署的需求
- 本机 16 G / 6 核，无 Docker（ADR-0004）
- **没有真实流量**，也没有多实例部署的场景

## 候选方案

### 方案 A：不使用微服务（**当时选中**）
单体 + 模块化边界（边界规则见 ADR-0002）。

- 优点：资源集中投给业务与亮点；架构复杂度与项目规模匹配
- 缺点：简历上不会有服务治理相关的实践（注册中心、网关、链路追踪）

### 方案 B：微服务
按业务拆成若干独立服务，配注册中心、网关、配置中心。

- 优点：简历关键词最全
- 缺点：**"为什么上微服务"这个问题答不上来**

## 决定

**不采用微服务。**

## 理由

**"微服务"不是一个可以独立成立的决策，它必须由某个具体问题驱动。** 常见的驱动有三类，本项目一类都不满足：

| 常见理由 | 本项目是否成立 |
|---|---|
| 独立伸缩（某个模块压力大） | ❌ 没有真实流量 |
| 团队分工（多个团队各管一块） | ❌ 一个人 |
| 故障隔离（某模块挂了不拖垮别的） | ❌ 当时的业务里没有这种模块 |

**更重要的是：面试官一定会问"什么条件下你才会拆微服务"。** 能回答这个问题，比真的拆了微服务更能说明你懂。本 ADR 当时给出的判据是：

> **出现两个流量特征截然不同的业务域，且其中一个域出故障会直接拖垮另一个域时，才值得拆。**

这条判据当时用不上，但它把"不拆"从一个印象变成了一个有条件的判断。

**还有资源上的硬约束**：本机 16 G 内存，无 Docker。拆成多个进程后，每个 JVM 各自吃一份堆内存，加上中间件，会逼近上限——开发体验会明显变差。

## 后果

- **正面**：资源与注意力集中在业务与亮点上；架构复杂度与"一个人的项目"相匹配
- **负面**：**简历上缺少服务治理相关的实践**（注册中心、网关、配置分发）。当时接受了这个代价，并把它记在这里——如果后来发现这是硬伤，应该回到本 ADR 重新评估，而不是悄悄推翻

## 被否决方案为何不选

- **方案 B（微服务）**：如前所述，三条常见驱动一条都不成立。**加上一个自己都讲不出理由的架构，是负分项**——面试官问"为什么"，答"因为微服务是主流"，比不拆更糟

## 废弃记录（2026-09-13）

### 2026-09-13 · 状态改为「已废弃」

**由**：ADR-0010（按故障域拆分为三个服务，且先画逻辑边界后做物理拆分）

**原因**：本 ADR 的推理前提变了——业务域从"纯论坛"扩展为"技术社区 + 付费内容 + 秒杀"（ADR-0009）后，**出现了两个流量特征截然不同的域**：

| 域 | 流量特征 |
|---|---|
| 交易域 | 平稳写入，对账敏感，一致性要求较高 |
| 秒杀域 | 平时 0 QPS，瞬时脉冲 |

而且故障关系是单向的、结构性的：**秒杀是瞬时脉冲，会打满线程池与数据库连接池；若与交易同进程，秒杀被打挂 = 用户下不了单。**

**关键点：本 ADR 当初写下的判据被满足了。** 它写的是"出现两个流量特征截然不同的业务域，且其中一个域出故障会直接拖垮另一个域时才值得拆"——引入秒杀后，这个条件刚好成立。所以结论被改判，不是因为当初想错了。

> **"不是当初判断错了，而是当初的约束变了"——这个区分在面试时很有用。**
> 前者说明判断力有问题，后者说明判断是**有条件的**、并且知道条件是什么。能讲出"我在什么条件下会推翻自己"，比"我一开始就选对了"更可信。

**变更**：

- **被取代的部分**："完全不拆进程"这一结论失效。按故障域拆出三个服务边界（`forum` / `trade` / `seckill`），M9 做物理拆分
- **仍然有效的部分**：
  1. **"不做全套微服务"的克制仍然保留**——只拆三个服务，不配 Sentinel / Seata（理由见 architecture.md §4.2 与 ADR-0011）
  2. **"微服务不是可以独立成立的决策，必须有具体问题驱动"这条方法论不变**
  3. **资源约束仍然是真实的**：M9 全开约 10.9 G / 16 G，因此必须执行"按需启动"纪律（architecture.md §6.2）
