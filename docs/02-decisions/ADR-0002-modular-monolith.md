# ADR-0002: 架构形态（模块化单体）

- **状态**：已修订
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）
- **修订**：ADR-0010（架构形态由「模块化单体」修订为「多服务 + 先画逻辑边界后做物理拆分」）

## 背景

新项目起手要先定架构形态。可选的光谱很宽：从"一个模块里分几个包"，到"拆成一堆独立进程"。

约束是清楚的：

- **一个人做**，没有团队分工的需求
- **本机 16 G / 6 核**，中间件已经要占掉一大块（architecture.md §6.1）
- **没有真实流量**——任何性能论证都是空谈
- 上一个项目（已完成，只读参考）是个单体

## 候选方案

### 方案 A：模块化单体（**选中**）
Maven 多模块，模块边界按业务域划，边界由构建期与测试期双重强制。

- 优点：边界是**真实存在**的（不是包名约定）；进程只有一个，部署与调试简单
- 缺点：模块边界靠工具强制而非语言强制，需要额外写测试；多模块的 POM 与构建时长都比单模块麻烦

### 方案 B：单模块分层
一个模块内按 `controller` / `service` / `mapper` 分包。

- 优点：结构最简单，新人一眼看懂
- 缺点：**边界只活在包名和文档里**，没有任何机制阻止 `controller` 直接调 `mapper`

### 方案 C：微服务
按业务拆成若干独立进程 + 注册中心 + 网关。

- 优点：简历关键词最全
- 缺点：针对本项目，成本立刻发生、收益无法证明

## 决定

采用**方案 A**：Maven 多模块的模块化单体。模块划分（当时的命名）：

```
forum-common    通用（响应体 / 错误码 / 异常 / 工具 / 注解）—— 不依赖任何业务模块
forum-domain    契约（领域模型 + 跨域接口）—— 只放契约，不放实现
forum-infra     基础设施（连接 / 序列化 / Key 规范 / 重试）
业务模块        按业务域切分
forum-boot      唯一有 main() 的启动模块
```

## 理由

**核心是这两个问题的难度不对称：「知道怎么解耦」和「知道什么时候不解耦」。** 前者查得到答案，后者只能靠判断，而且**后者才是面试官更想听的**。

具体到本项目，解耦的前提一个都不成立：一个人做，没有团队边界要维护；没有真实流量，没有独立伸缩的需求；本机资源紧张，多跑一个进程就多吃一份内存。**在这种情况下拆进程，付出的是确定的成本，换来的只有"看起来更专业"。**

**但"不拆进程"不等于"不划边界"。** 模块化单体保留了模块化最关键的那部分收益——**边界是写在代码结构里的**：`common` 不依赖任何业务模块、`domain` 只放契约、业务模块不互相依赖。这些规则不是靠自觉，而是靠两道闸门强制：

1. **构建期**：Maven 的模块依赖关系（不该有的依赖根本解析不到）
2. **测试期**：ArchUnit 规则（拦住"跨模块直接调内部类"这类 Maven 拦不住的情况）

**为什么边界按业务域切，而不是按技术分层切。** 技术分层的 `controller` / `service` / `dao` 在"将来要拆"的时候，**每一层都要动**——你要把三层的相关部分各切一块出来。按业务域切则是：拆分边界已经画好了，搬目录就行。**边界画在哪里，取决于你将来可能从哪里切。**

## 后果

- **正面**：模块边界真实、可测、可讲；只有一个进程，调试与部署简单；将来看清楚该怎么拆了，拆分成本很低
- **负面**：
  - **Maven 拦不住所有越界**——它能拦住"业务模块 A 依赖业务模块 B"，拦不住"A 引用了 B 的 internal 包"。后者必须靠 ArchUnit 补，也就意味着要多维护一份规则
  - **多模块的构建配置繁琐**：模块数一多，POM 数量、建构建时长、IDE 索引时间都随之上涨
  - 模块边界需要人来维护——新增模块时若不更新 ArchUnit 规则，规则会慢慢失效

## 被否决方案为何不选

- **方案 B（单模块分层）**：它没有边界，只有"分包的希望"。而且它把将来的拆分成本推高了：真到要拆的时候，先得把业务代码按域重新组织一遍
- **方案 C（微服务）**：**面试官会问"一个技术社区你为什么要全套微服务"**——答不好是减分项。而且本项目没有真实流量，任何"为了性能"的论证都会被追问到站不住

## 修订记录（2026-09-13）

### 2026-09-13 · 状态改为「已修订」

**由**：ADR-0010（按故障域拆分为三个服务，先画逻辑边界后做物理拆分）

**原因**：业务域扩展（ADR-0009）后，项目从"纯论坛"变成"技术社区 + 付费内容 + 秒杀"，**出现了两个流量特征截然不同的域**。本 ADR 当初的推理前提（"一个人的项目、没有需要隔离的故障域"）不再成立——拆分理由从"跟风"变成了**故障域隔离**，而故障域隔离这条理由是结构性的，不依赖流量大小。

**变更**：

- **被取代的部分**：架构形态由「模块化单体」变为「**多服务 + 先画逻辑边界后做物理拆分**」。模块清单也随业务域扩展由 9 个重排为三域 12 模块（见 `architecture.md` §3.1），模块命名相应变更：
  | 本 ADR 原文 | 现名 |
  |---|---|
  | `forum-common` | `wt-common` |
  | `forum-domain` | `wt-domain` |
  | `forum-infra` | `wt-infra` |
  | `forum-boot` | `app`（M9 时拆为 `forum-app` / `trade-app` / `seckill-app` + `gateway`） |

- **仍然有效的部分（这是本节存在的理由）**：**模块边界规则一条都没变**——
  1. `common` 不依赖任何业务模块，不含业务逻辑
  2. `domain` 只放契约，不放实现
  3. 业务模块之间不互相依赖，跨域走 `domain` 的契约
  4. 只有一个启动模块（M9 之后是三个 app，各域仍是"本域唯一入口"）
  5. 边界由 Maven 依赖 + ArchUnit 双重强制
  6. 边界线画在「机制 vs 策略」上

> **ADR-0010 修订的是"要不要拆进程"，不是"要不要划边界"。** 面试官看到「已修订」时，第一反应往往是"那你原来的设计是不是错了"——这一节就是给这个问题准备的答案：**边界的设计没有错，且正是它让后来的拆分变得便宜**（M9 拆分时业务模块一行不改）。
