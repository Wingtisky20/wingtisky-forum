# ADR-0006: 交付形态（GitHub 公开 + 本地可复现，不做公网部署）

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

这是一个要投秋招简历的项目。交付形态回答的是：**面试官以什么方式看到它、怎么判断它是真的。**

可选的方式大致三类：让面试官点开一个网址就能用、让面试官把代码拉下来自己跑、或者只把代码放上去。三者的成本与效果差别很大，而这个项目的时间预算只有 4-6 个月。

## 候选方案

### 方案 A：GitHub 公开仓库 + 本地可复现（**选中**）
公开仓库 + 一套能让陌生人在干净环境跑起来的文档，**不做公网部署**。

- 优点：无服务器成本、无运维负担；时间全部投向业务与亮点；文档本身就是加分项
- 缺点：面试官**点不开看**，只能靠 README、架构图、实测数据与截图建立印象

### 方案 B：公网部署（云服务器 + 域名）
- 优点：面试官点开就能用，第一印象最直观
- 缺点：多 1-2 周（买机器、配环境、部署、备案）；持续产生成本；**4 G 内存的入门云主机跑 ES + Kafka 会非常吃力**

### 方案 C：只放代码，不写文档
- 优点：最省时间
- 缺点：面试官看不到"为什么这么设计"——而**本项目最大的产出恰恰是这套推理过程**

## 决定

采用**方案 A**：GitHub 公开仓库，README + `docs/` 保证本地可复现，**不做公网部署**。

## 理由

**这个项目的交付物不是"一个网站"，是"一套能讲清楚的工程过程"。** 面试官不会真的注册一个账号去发帖，他会问"你的缓存为什么这么设计""拆分前后差多少"。答得上这些问题靠的是文档与实测数据，不是一台在跑的服务器。

**公网部署的时间成本会直接吃掉亮点的时间。** 多出的 1-2 周如果投到亮点 1（多级缓存）或亮点 6（秒杀一致性）上，换来的是面试时能讲深的东西；投到部署上，换来的是一个"哦，能打开"。

**而且部署本身会引入一类新问题**：线上环境的日志、重启、资源监控，每一项都要时间，但都不是本项目想讲的。

**保留条款：架构上保证配置外置。** 数据库地址、端口、中间件连接串一律走配置文件，不硬编码。**后期若真要上云，不需要返工**——这条让"现在不部署"从"放弃"变成了"推迟"。

## 后果

- **正面**：时间集中投向亮点；没有服务器与运维成本；文档质量成为可展示的加分项
- **负面**：
  - 面试官**无法直接访问**，简历上只能给仓库链接。需要用截图、架构图、实测数据表来补足第一印象
  - **README 的质量被抬到了很高的位置**——这是面试官唯一能看到的东西。M10 的闸门因此定为"**干净环境按 README 能跑起来**"，不是"写完 README 就行"
  - 受 ADR-0004 影响，README 无法写成"一条命令跑起来"，只能写成"装这四个中间件 + 改配置"

## 被否决方案为何不选

- **方案 B（公网部署）**：**4 G 内存跑不动 ES + Kafka 是关键。** 要跑得动就得买更大的机器，成本再上一档；而即便跑起来了，面试官也多半只是点开看一眼列表页——拿不到本项目最想展示的东西
- **方案 C（只放代码）**：这等于主动放弃了本项目相对"培训班项目"的最大区别。仓库里那套 ADR、执行记录、实测数据，本身就是"这个人知道自己在做什么"的证据
