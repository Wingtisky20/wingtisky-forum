# ADR-0008: 分支模型（GitHub Flow + Merge commit）

- **状态**：已接受
- **日期**：2026-09-13
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

这是一个人做的项目——没有团队、没有 code review 的对手方。按常识，分支模型似乎没什么可选的：一个人直接往 `main` 提交不就行了？

但本项目的核心诉求把这件事变成了真问题：**要能靠 commit 历史一步步看清迭代过程**，而且每个功能都要**可追溯、可讲述**——面试时能说"我每个功能都走 PR 合并，PR 里附验证证据"。

也就是说，分支模型不只是协作工具，它是**产出物的载体**。

## 候选方案

### 方案 A：GitHub Flow（**选中**）
`main` 永远可运行 + 短生命周期的功能分支 + PR + 合并后删分支。

- 优点：模型简单，一个人能完整走通；PR 天然产出结构化的变更记录
- 缺点：单人项目里 PR 的"评审"环节是空的，只有自查

### 方案 B：Git Flow
`main` / `develop` / `release/*` / `hotfix/*` / `feature/*` 多分支并行。

- 优点：能同时维护多个发布版本，有明确的发布周期
- 缺点：**这套模型是为"有发布节奏 + 多版本并行"的团队设计的**，本项目没有发布分支的概念，`main` 随时可运行

### 方案 C：直接 push `main`
- 优点：最省事，零流程成本
- 缺点：**没有 PR 就没有结构化的变更记录**，也没有分支保护这道物理闸门

## 决定

采用**方案 A**：GitHub Flow，`feature/m<里程碑>-<主题>` 分支 → PR → **Merge commit（`--no-ff`）** → 删分支。

## 理由

**为什么单人项目也走 PR。** 没人评审，PR 的价值不在"评审"，而在**PR 描述本身是一份结构化的变更记录**——做了什么 / 为什么 / 怎么验证的 / 有什么风险。这份东西和 commit message 不重复：commit 说"每一步具体改了什么"，PR 说"这一整块功能是什么、怎么验的"。面试前复盘靠它，面试时讲述也靠它。

**为什么不用 Git Flow。** `develop`、`release/*`、`hotfix/*` 的存在前提是"有发布周期、可能同时维护多个版本"。本项目 `main` 永远可运行、没有版本并行，多出来的分支层级只会变成需要记住的规矩，换不来任何东西。**判断标准是"这套模型的每个分支在这个项目里对应什么"，而不是"它是否专业"。**

**为什么不用直接 push `main`。** 一是丢掉上面那层变更记录；二是丢掉分支保护这道物理闸门——"禁止直接 push main"写在文档里是约定，配在 GitHub 上才是约束。

**为什么合并方式用 Merge commit 而不是 Squash**（**2026-09-19 修订**）。这是本 ADR 里唯一被改过的结论：

- 最初选 Squash，理由是"让 `main` 的历史干净"
- 但这个理由与项目的核心诉求**直接冲突**——本项目要的恰恰是"**靠 commit 一步步看清迭代过程**"，而 Squash 会把功能分支上的全部提交压成一个，**过程在 `main` 上就消失了**
- 实测数据：`feature/m0-bootstrap` 领先 `main` **18 个提交**，若 Squash，`main` 上只会多 **1 个**提交。18 步的过程压缩成 1 步，复盘时什么都看不到
- Merge commit（`--no-ff`）保留每一个细粒度提交，同时用 merge 提交标出合并边界；要看干净的主线视图，用 `git log --oneline --no-merges`

**这里有一个通用教训**：Squash 本身没错，它解决的是"分支上有一堆 `fix typo` 想清理掉"的问题。**但它与"保留过程"这个目标天然对立**——选它之前要先想清楚，你要的到底是"干净的历史"还是"完整的过程"。本项目要后者。

## 后果

- **正面**：`main` 上保留完整的迭代轨迹，可用于复盘与讲述；`git log --oneline --no-merges` 可随时切出主线视图；PR 描述成为结构化的功能级记录
- **负面**：
  - `main` 上的提交数变多，直接 `git log` 时噪音更大（需要靠 `--no-merges` 过滤）
  - **功能分支上的 `wip:` 提交会原样进入 `main`**——Merge commit 不做压平，这是它保留过程的代价。因此约束变为"**进入 `main` 的每个提交都必须可编译**"，而不是"`main` 上不出现 wip 提交"
  - 单人项目的 PR 自查容易流于形式，需要靠 spec §9 闸门 4（提交与 diff 对账）兜底

> **这条已于 2026-09-19 明确**：允许 `wip:` 提交随合并进入 `main`，约束是**每个进入 `main` 的提交都必须可编译**。理由与措辞统一见下方修订记录。

## 被否决方案为何不选

- **方案 B（Git Flow）**：为不存在的需求引入复杂度。单人项目用 Git Flow，多出的分支不是工程实践，是仪式
- **方案 C（直接 push `main`）**：省下的时间要以"失去全部变更记录"为代价。而本项目的简历价值相当一部分就建立在这些记录上
- **Squash merge**：曾经采用，2026-09-19 推翻。理由与实测数据见上——**这不是"当初想错了"，而是"当初把'干净'排在了'可追溯'前面，后来发现排序反了"**

## 修订记录

### 2026-09-19 · 合并方式由 Squash 改为 Merge commit

**原因**：核心诉求是"靠 commit 一步步看清迭代过程"，而 Squash 会把分支上的提交压成一个，过程在 `main` 上消失。实测 `feature/m0-bootstrap` 领先 `main` 18 个提交，Squash 后 `main` 只多 1 个。

**变更**：

- **仍然有效**：GitHub Flow 的分支模型、`main` 永远可运行、禁止直接 push `main`、走 PR、PR 作为变更记录载体、每个功能 3-8 个提交的粒度要求——全部不变
- **被取代**：仅"合并方式"一项，由 Squash merge 改为 Merge commit（`--no-ff`）
- **连带影响**：`wip:` 提交的约束需同步调整（见下方「明确 `wip:` 提交的约束」一节）

**同步已改写的文档**：spec §10.2、spec §10.4（WIP 例外行）、`CLAUDE.md`、`collaboration.md` §5.1、本 ADR 索引行。

### 2026-09-19 · 明确 `wip:` 提交的约束

**决策**：允许 `wip:` 提交随合并**进入 `main`**，约束落在"**每个进入 `main` 的提交都必须可编译**"，而不是"`main` 上不能出现 wip 提交"。

**为什么**：spec §10.2 原有的表述是"`wip:` 提交仍只允许出现在 feature 分支上"，这句话在 Merge commit 下已经失效——分支上的提交会原样进 main。

要不要改成"合并前把 wip 整理掉"？**不选，因为它自相矛盾**：Merge commit 不做压平，这正是选它的理由；如果再要求手工 rebase 压一遍，等于**把刚刚为了保留过程而放弃的压平，用手工再做一次**。既然选择了"可追溯优先于干净"，就应该承认这个代价，并把闸门落在真正重要的那条约束上——**可编译**。

**另一条不改**：`wip:` 仍然只允许出现在 feature 分支上，不允许直接在 `main` 上提交。这条与合并方式无关。

**同步已改写的文档**：spec §10.2、`collaboration.md` §5.3。
