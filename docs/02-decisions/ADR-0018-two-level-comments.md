# ADR-0018: 评论用两级模型（parent_id + root_id）

- **状态**：已接受
- **日期**：2026-10-05
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

M2 要做帖子评论。评论的层级深度是必须现在定的——它决定表结构，
而表结构一旦有了数据再改，代价高得多。

## 候选方案

### 方案 A：一级平铺
所有评论都直接挂在帖子下，没有回复关系。

- 优点：最简单，一个 `post_id` 就够
- 缺点：**无法表达"回复某条评论"**，而这是技术社区的基本需求

### 方案 B：两级（**选中**）
评论 + 回复。回复一律挂在**顶层评论**下，不继续嵌套。

- 优点：查询不递归，分页天然；展示简单
- 缺点：需要两个字段；**回复的回复会被拍平**

### 方案 C：无限级树
- 优点：完整保留讨论结构
- 缺点：查询要递归（CTE 或应用层多次查询）；展示要做折叠/展开；分页困难

## 决定

采用**方案 B**：`t_comment` 上有 `parent_id`（直接父评论）与 `root_id`（所属顶层评论），
**顶层评论两者都为 0**。

## 理由

### 一、一级不够，而树形是过度

一级表达不了"回复"；树形的复杂度（递归查询 + 折叠展示 + 分页要按根聚合）
换来的表达能力，在本场景用不上——
**掘金、牛客、Hacker News 实际展示的都是两级**，深层的讨论照样能进行。

### 二、`root_id` 是"两级"能高效分页的关键

**只有 `parent_id` 是不够的。** 问题出在分页上：

一条帖子有 200 条评论，要分页展示。如果只有 `parent_id`，
那么"第 2 页的评论"指的是**顶层评论**的第 2 页——
可是**哪些评论是顶层，需要递归才能判断**（没有父的才是顶层）。

加上 `root_id` 之后，两个查询都变成普通索引查询：

```sql
-- 顶层评论：直接分页
SELECT * FROM t_comment WHERE post_id = ? AND root_id = 0 ORDER BY id LIMIT ?, ?;

-- 某条顶层评论下的全部回复：一次查完，不用递归
SELECT * FROM t_comment WHERE root_id = ? ORDER BY id;
```

索引 `idx_post_root (post_id, root_id, id)` 正好同时服务这两个查询。

**代价明确**：回复的回复会被拍平——回复 A 的回复，展示在 A 下面而不是缩进第二层。
这正是"两级"的定义，不是缺陷。原始指向存在 `parent_id` 里，要还原时有据可查。

## 后果

- **正面**：
  - 查询不递归，两个查询都是普通索引查询
  - 评论分页天然成立（按顶层评论分页，回复随附）
  - 前端展示简单：一层缩进
- **负面**：
  - **两个字段要保持一致，且这里容易写错**：回复"某条回复"时，
    新评论的 `root_id` 应该取**父评论的 `root_id`**，而不是父评论的 `id`——
    取错的话，回复会挂到错误的根下，**表现是"评论跑到别的楼里去了"**。
    这条必须有测试覆盖，不能靠"写的时候注意"
  - 层次信息有损：无法直接还原"回复的回复"的原始缩进关系
  - 分页粒度是顶层评论——一条顶层评论下若有 500 条回复，那一页里会带出 500 条

## 被否决方案为何不选

- **方案 A（一级）**：表达不了回复关系。技术社区里"针对某条评论回一句"是常见动作，
  没有它，讨论就只能是各说各的。
- **方案 C（无限级树）**：它的优势在"几万条评论的深度讨论"这类场景
  （论坛的老帖、Reddit 的深层楼中楼）。本项目是技术社区，
  **评论深度天然浅**——为罕见的深层讨论让所有评论查询都变得复杂，不划算。

> 如果将来真需要树形，升级路径是：`parent_id` 已经存着完整的指向关系，
> 加一个 `depth` 字段就能重建任意深度的展示，**不需要改已存的数据**。
> 这是选 B 而不是 A 的另一个好处——数据里保留了升级所需的信息。
