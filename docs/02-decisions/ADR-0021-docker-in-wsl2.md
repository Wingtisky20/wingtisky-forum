# ADR-0021: Kafka 与 ES 用 Docker 跑在 WSL2 里（修订 ADR-0020 的承载方式，并推翻 ADR-0004 的「不用 Docker」）

- **状态**：已接受
- **日期**：2026-10-08
- **决策者**：Wingtisky（决策） / Claude（建议）
- **关联**：修订 [ADR-0020](ADR-0020-wsl2-for-kafka.md) 的**承载方式**；推翻 [ADR-0004](ADR-0004-no-docker-locally.md) 的**「本地不使用 Docker」**；
  与 ADR-0001（技术栈白名单）、ADR-0007（集成测试不在 CI 跑）有关

## 背景

[ADR-0020](ADR-0020-wsl2-for-kafka.md) 定的是「Kafka 迁进 WSL2」，但**没定怎么装**。
执行时先走了「在 WSL2 里手工装原生 Kafka」这条路，**装成了、也能收发消息**，
但在继续推进时暴露了三个问题：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **不可复现** | 为了让 WSL2 能出去下 Kafka，我手工改过 DNS、关过 IPv6、改过 listener 的 IPv4 绑定、改过数据目录——**这些步骤散在我的执行历史里，换台机器或重装 WSL 就得重来一遍，而且我不会记得每一步** |
| 2 | **WSL2 出网本身就不稳** | 实测 WSL2 里 DNS 解析失败（`Temporary failure in name resolution`），`networkingMode` 还报了回退到 Consomme 的警告。手工装要靠它下载 |
| 3 | **与社区主流脱节** | 网上关于「本地起 Kafka」的资料**绝大多数是 Docker Compose 写的**；走手工装，等于每次遇到问题都要自己翻译一遍 |

**同时用户提出一个明确要求：Docker 尽量装在 D 盘。** 这一条下面的方案天然满足（见「D 盘」一节）。

### 一个关键的认知纠正

ADR-0004 否决 Docker 的理由是「本机是 Win10 **Home**，装不了 Docker Desktop」。
**这句话本身没错，但结论下早了**——它漏了一种装法：

> **Docker Desktop 是一个 Windows 程序，家庭版装不了。
> 但 Docker 的引擎（`docker.io` 这个 Linux 包）可以装在 WSL2 里，
> 那里是 Linux，跟 Windows 是哪个版本无关。**

实测确认：`apt install docker.io` 成功，Docker 29.1.3 + Compose 2.40.3 跑起来了。
**所以「家庭版」这个限制，绕得过去。**

## 候选方案

### 方案 A：WSL2 里手工装原生 Kafka（**执行过，后放弃**）
- 优点：无 Docker 这一层；二进制直接可见可改
- 缺点：**不可复现**（见背景的三个问题）；改配置的地方多且隐蔽
- 结论：**放弃**。它不是不能用，是**留不下东西**——下一个接手的人（包括几个月后的我）拿到的是"一堆手工改过的状态"，不是"一份能跑起来的定义"

### 方案 B：Docker Desktop
- 缺点：**家庭版装不了**（ADR-0004 已记录），且 C 盘只剩 35 GB，它的镜像与虚拟磁盘默认落 C 盘
- 结论：否决（客观限制，不是偏好）

### 方案 C：WSL2 里装 Docker 引擎 + Docker Compose（**选中**）
- 优点：
  1. **绕开家庭版限制**（Docker 引擎跑在 Linux 里，与 Windows 版本无关）
  2. **可复现**：整个 Kafka 的配置就是一份 compose 文件，**可以提交进仓库**
  3. **可重置**：`docker compose down -v` 删掉数据卷即回到干净状态——正对 2026-10-07 那次「Windows 原生上凡是删日志段就崩」的痛
  4. **容器内是 Linux 文件语义**：那个失败模式在内核层面就不存在（不是绕开）
  5. **与社区资料对齐**：以后搜到的问题，答案基本能直接照用
  6. **兑现 ADR-0004 的保留条款**：那份 ADR 承诺过"使用者可用 Docker Compose 自建环境"，**而仓库里一直空着**，这次把它补实
- 缺点：
  1. **多了一层**（WSL2 → Docker → 容器）。排障时要知道自己在哪一层
  2. 镜像拉取依赖**第三方加速站**（官方 registry 在国内连不上，见下）
  3. 内存开销比"进程直接跑"多约 0.5 G（容器本身的固定开销）
  4. 需要用户会两条命令（`docker compose up -d` / `down`）——**本项目会把它们包进脚本**，让日常使用不必记
- 结论：**选中**

## 决定

**采用方案 C：Kafka 用 Docker Compose 跑在 WSL2 里。**
**ES 走同一条路**（M5 要用，一次配好，不再为它单独排一次）。
**MySQL 与 Redis 留在 Windows 原生，不动。**

### 范围：为什么只动 Kafka 与 ES

| 中间件 | 怎么办 | 理由 |
|---|---|---|
| **Kafka** | ✅ 进 Docker | Windows 原生上不可用（ADR-0020）；这次是被逼的 |
| **ES** | ✅ 进 Docker（M5 前完成） | 同属"在 Windows 原生上本来就别扭"的一类；**趁这次一次配好，免得 M5 再来一遍今天这一轮** |
| **MySQL** | ❌ 留在原生 | 现在跑得好好的、还是常驻服务。**没有理由去动没坏的东西** |
| **Redis** | ❌ 留在原生 | **它是启动期硬依赖**（ADR 相关记录：M3 起不起 Redis 应用直接起不来）。动它的风险远大于收益 |

**判据不是"能不能 Docker 化"，而是"动它值不值"。** 这次改动的起因是一个坏掉的东西（Kafka），
所以只动它、和跟它同类的东西（ES）；**不顺手把没坏的也换掉**。

### 具体承载方式

| 项 | 决定 | 理由 |
|---|---|---|
| Docker 装在哪 | **WSL2 里的 `docker.io`（引擎）+ `docker-compose-v2`** | 绕开家庭版限制；不装 Docker Desktop |
| 镜像从哪来 | **`apache/kafka:3.9.1`** 官方镜像，经**国内加速站** `docker.m.daocloud.io` 拉取 | 官方 registry 在国内直连不通（实测超时）。这引入了一个第三方依赖，见「后果」 |
| Kafka 数据目录 | **容器内的数据卷**（Docker volume），物理落在 WSL2 的 ext4 里 | **不放 `/mnt/d`**——那是跨文件系统访问，性能差，且可能把 Windows 的坑请回来 |
| 对外端口 | `localhost:9092`（业务）/ 容器内 9093（控制器） | **Windows 侧应用一行不用改**，仍是 `localhost:9092` |
| 编排方式 | **`docker-compose.yml`，提交进仓库** | 这是本决定的**核心产出**；ADR-0004 承诺过的那份文件，现在补上 |
| 启动方式 | 包进 `scripts/start-kafka.bat`（转发到 WSL2 执行 compose 命令），**脚本前台挂住不退出** | 保持"一个脚本起一个中间件"的既有习惯，**调用方式对项目其他部分不变**；挂住前台是为了阻止 WSL2 空闲关机（见下一节） |

### 关于「Docker 装在 D 盘」（用户明确要求）

**这一条天然满足，不需要额外配置。** 理由是 WSL2 的架构决定的：

```
WSL2 这台"隐形 Linux 电脑"的整块硬盘 = 一个文件
D:\aaaSoftware\wsl\Ubuntu-22.04\ext4.vhdx      ← 它在 D 盘

WSL2 里面的一切都落在这个文件里：
  ├── apt 装的 Docker 引擎
  ├── Docker 的镜像（Kafka 563 MB）
  ├── 容器
  └── 数据卷（Kafka 的日志目录）
```

**所以不需要给 Docker 单独指定 `data-root`**——那样反而多一层间接，且容易和 WSL2 的磁盘管理打架。
C 盘只占 WSL 程序本身（`C:\Program Files\WSL`）与 `.wslconfig` 两个小文件。

**已实测确认**：C 盘在本次全部操作后仍剩 35 GB。

### 一个执行中才暴露的前提：WSL2 空闲会自己关机

**这条不影响"选不选 Docker"，但影响"怎么用"，而且它一度让验证失败了好几次，必须记下来。**

**现象**：Kafka 容器起来、验证通过之后，**只要不再敲 WSL 命令，约 1~2 分钟内整个虚拟机就关掉**，
容器跟着死，Windows 侧 `localhost:9092` 变成连不上。表现是**"时好时坏"**——
刚验证完是通的，过两分钟再试就不通了。

**据此排除掉一个误判**：一开始看容器状态反复显示 `Up 2 seconds`，我以为是"容器在反复重启"。
把系统日志拉出来才看清真相：

```
Oct 08 01:04:12  Daemon shutdown complete
-- Boot ... --                          ← 整台虚拟机重启了，不是容器重启
Oct 08 01:12:37  Docker ... Engine Starting
```

**根因**：WSL2 默认在最后一个会话结束后自动关机（本机实测约 1 分钟）。
**而 Kafka 是常驻服务，不能被这样关掉。**

**试过但没用的办法**：在 `.wslconfig` 里写 `vmIdleTimeout=86400000`（24 小时）。
**本机的 WSL 版本（3.0.1.0）不认这个设置**——写完重启，虚拟机照样关。
这一行仍留在 `.wslconfig` 里并加了注释，说明它在本机无效，**不让后来者以为它生效了**。

**采用的办法**：**让 `scripts/start-kafka.bat` 在前台挂住**——
脚本启动容器后不退出，持有 WSL 会话，窗口开着服务就在；关窗口即停止。

**为什么这么选，而不是挂一个隐藏的后台常驻进程：**

1. **和项目原来的使用习惯一致**——原生版 Kafka 也是这样：开一个窗口跑着，关窗口就停
2. **状态可见**——窗口开着就是服务在跑，不用猜
3. 隐藏后台进程的做法，出问题时**没人知道它还在跑**，反而更难排查

**实测验证**：脚本启动后安静观察 5 分钟（期间不执行任何 WSL 命令），**端口探测 15 次全通、0 次断**。
（修复前同样的观察：12 次全断。）

### 内存账（这是本次改动最需要盯的一项）

`.wslconfig` 里的 `memory` 由 **4 GB 抬到 6 GB**（2026-10-08 改），原因是容器有额外开销：

| 项 | 大小 |
|---|---|
| WSL2 上限（新） | **6 GB** |
| 其中：Kafka 容器（1 G 堆） | ~1.2 GB |
| 其中：ES 容器（1 G 堆，M5 起） | ~1.5 GB |
| 其中：Docker 引擎与容器开销 | ~0.5 GB |

**与 architecture.md §6.1 的预算对照**：

```
MySQL (0.5) + Redis (0.05)      + WSL2 (6.0) + Windows/IDE/浏览器 (4.5)
  = 约 11 G / 16 G
```

**结论**：M5（Kafka + ES 都开）时约 11 G，**M9 全开（再加三个服务进程与 Nacos/Gateway）会超预算**。
→ 这条**记进「后果」**，M9 之前必须重新算一次账，不能沿用。

## 理由

**一、真正的问题是"留不下东西"，不是"用哪种装法"。**

在 WSL2 里手工装 Kafka，我改过：DNS、IPv6 开关、listener 的 IPv4 绑定、数据目录、heap。
**这些改动没有一处写进任何可提交的文件里**——它们只存在于"我这台机器现在的状态"里。

而这次改动之所以要谨慎，正是因为它**跨对话**：下一个接手的人（或几个月后的我）
打开仓库，**看到的应该是一份能跑起来的定义，而不是一句"Kafka 装在 /root/kafka"**。

Docker Compose 的价值就在这里：**Kafka 的全部配置变成一份可以审、可以 diff、可以提交的文件。**

**二、这条路的正确性有实测支撑，不是"理论上更好"。**

2026-10-07 在 Windows 原生上，Kafka **凡触发删日志段或删主题必崩**（当天崩 16 次）。
换到 Docker 之后，同样两件事**主动测了**：

| 主动制造的场景 | Windows 原生 | Docker（本次） |
|---|---|---|
| 删一个主题 | ❌ 崩 | ✅ 正常 |
| 建 2 秒保留期的主题，逼它删日志段 | ❌ 崩 | ✅ 删得干净，容器零重启、日志零 ERROR |

**这不是"跑起来了"，是"把当初打崩它的那个动作重做了一遍"。**

**三、为什么推翻 ADR-0004 而不是绕开它。**

ADR-0004「本地不使用 Docker」的**两条理由今天依然成立**（内存硬约束、C 盘紧张），
但它的**结论**已被证伪——不是因为它错，是因为**它当时不知道 Docker 还能装在 WSL2 里**。

按 `collaboration.md §4` 铁律 2，**推翻旧结论必须留痕**：ADR-0004 原文全部保留，
末尾追加修订记录，写清哪一条被取代、哪一条仍然有效。**不修改原文。**

## 后果

- **正面**：
  - Kafka **真正可用**：能删段、能删主题、能回收磁盘，无需任何绕行配置
  - **可复现**：Kafka 的配置就是一份 `docker-compose.yml`，进仓库
  - **可重置**：`docker compose down -v` 一句话回到干净状态
  - **兑现了 ADR-0004 对使用者的承诺**——那份 Compose 文件从"口头承诺"变成"仓库里真有"
  - ES 一次配好，**M5 不必重演今天这一轮**
- **负面**（诚实写全）：
  - **多一层**：WSL2 → Docker → 容器。排障时要先想清"问题在哪一层"
  - **引入第三方依赖**：镜像拉取走 `docker.m.daocloud.io`（国内加速站）。
    官方 registry 直连不通（实测超时）。**若该站失效，需换源**——
    换源方法写在 `docs/06-runbook/troubleshooting.md`
  - **内存多约 0.5 G**（容器开销）；**M9 预算需重算**（见上）
  - **WSL2 出网不可靠**（DNS 解析失败、`networkingMode` 回退到 Consomme）。
    本次靠"镜像在 WSL2 内部拉取 + 镜像站可达"绕过了，但这条**仍是个已知的不稳定因素**
  - 需要会 `docker compose` 两条命令——**本项目用脚本包住**，日常不必记
  - **两套历史安装暂时都保留着**（`D:\aaaSoftware\kafka-3.9.1` 与 WSL2 里的 `/root/kafka`），
    磁盘上多占一点。**等这套稳定跑过一个里程碑再清理**，理由见下

### 为什么不立刻删掉旧的

**这次改动本身没被"跑一个里程碑"验证过。** 旧的（原生 Windows 那套）虽然坏了，
但 Linux 手工装那套（`/root/kafka`）**是能工作的**——它是这次改动失败时的退路。

**验证通过一个里程碑（M4 做完）之后再清理。** 这跟 2026-10-07 的教训一致：
**别在没验证新方案之前，先拆掉旧的。**

## 被否决方案为何不选

- **方案 A（WSL2 手工装）**：不是不能用，是**留不下东西**（见「理由 一」）。
  它让 M5、M9 以及任何换机场景都要重来一遍今天这些手工步骤。
- **方案 B（Docker Desktop）**：本机为 Win10 **Home**，装不了。**客观限制，不是偏好。**
  若将来换机或升到 Pro，本决策可重新评估——**届时 Docker Desktop 与"WSL2 里装引擎"可共存，
  但两者不必都装**，选一即可。
- **四个中间件全部 Docker 化**：MySQL 与 Redis 现在**工作正常**，且 Redis 是启动期硬依赖。
  **改动的收益（统一）小于风险（把好的搞坏）。** 判据是"值不值"，不是"齐不齐"。
