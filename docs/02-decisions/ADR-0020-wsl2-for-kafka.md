# ADR-0020: 本地 Kafka 改用 WSL2 承载（修订 ADR-0004 的「本地不使用 Docker」）

- **状态**：已接受（**承载方式已被 [ADR-0021](ADR-0021-docker-in-wsl2.md) 修订**——见文末「修订记录」；
  本 ADR 的**核心结论「Kafka 必须离开原生 Windows」不变**，被取代的只是"在 WSL2 里怎么装"）
- **日期**：2026-10-07
- **决策者**：Wingtisky（决策） / Claude（建议）
- **关联**：修订 ADR-0004；被 ADR-0021 修订；受 spec §1.5「不做的事」与 ADR-0001 技术栈白名单约束

## 背景

M4（亮点 2 · Kafka 异步写）开工前第一件事是把本机 Kafka 起起来。**这一步失败了**，
而且失败得比预期严重：**broker 在 2026-10-07 当天先后崩了 16 次**，每一次的性质都一样。

先把事实摆清楚（全部 `[REAL]`，命令与原文见 `docs/06-runbook/troubleshooting.md` 同日条目）：

| 观察到的事实 | 证据 |
|---|---|
| **只要触发一次日志段的删除/替换，broker 必定崩溃退出** | 16 次启动，10 次因"有东西要删"而崩；未触发的 6 次都没崩 |
| 与数据新旧**无关** | 全新主题、全新小消息（69 字节）照样崩 |
| 与日志目录新旧**无关** | 换一个**全新格式化**的目录后，只要触发删除**照样崩** |
| 与杀毒软件**无关** | 把 `D:\aaaSoftware\kafka-3.9.1` 加进 Windows Defender 排除项后，18 秒后照样崩 |
| 与保留期长短**无关** | 把 `log.retention.hours` 设为 `-1`（永不按时间删除）**仍然崩** |
| 与日志压缩清理器**无关** | `log.cleaner.enable=false` 后**仍然崩** |
| 崩溃的**直接动作**永远是**改名**：`xxx.timeindex` → `xxx.timeindex.deleted`，报 `另一个程序正在使用此文件` | 每次崩溃的栈都落在 `AbstractIndex.renameTo` → `Files.move` |
| **删主题也必崩** | 删主题同样是改目录名，一样触发 |
| **换新目录只是"还没捅刀"** | 新目录一开始"稳定"，一旦被逼触发删除立刻崩——**这条推翻了当天此前的错误结论** |

**结论：在这台机器的原生 Windows 上，Kafka broker 一旦需要回收磁盘就会自毁。**
让它不崩的唯一办法是让它永不触发删除（保留期无限 + 关清理器），**而那等于放弃 Kafka 的磁盘治理能力**——
本地开发尚可苟活，但它同时意味着**「删主题」这个日常动作做不了**；更关键的是，
**这条路只是个绕行方案，不是使 Kafka 变得可用**。

### ⚠️ 一处**仍未解释**的矛盾（写下来，不假装已经闭环）

**失败的动作是"改名"，可我单独写程序测"改名"，它是成功的。**

我写了个独立的 Java 程序复现 Kafka 那一个动作：把一个文件做内存映射、
**且用强引用把映射对象握住不放**，然后改名。实测：

| 我对独立文件做的动作 | 结果 |
|---|---|
| 改名（含 `ATOMIC_MOVE`、含目标已存在） | **成功** |
| **删除** | **失败**：`AccessDeniedException` |

也就是说：**"Windows 上映射文件不能改名"这个流传很广的说法，本机复现不出来**——
真正常见的现象是**不能删除**。而 Kafka 崩在**改名**上。

**这个矛盾我没有解决。** 可能的解释（**都未验证**）：Kafka 的索引对象在删除路径上
除了映射还持有别的句柄；或者它走的是另一条 `atomicMoveWithFallback` 分支。
**我不打算在 ADR 里编一个机制出来凑数。**

**好在这个决定不依赖它**：无论底层是"改名失败"还是"某个句柄没释放"，
问题都出在 **Windows 的文件语义**上，而**换到 WSL2 就整体绕开了这一整类失败模式**——
这也是本决定选 WSL2 而不是继续在 Windows 上抠配置的原因。

> **教训（这条比 Kafka 本身值钱）**：当天我先做了一个"内存映射"实验，
> 结论是"改名能成功"，据此推出"一定有别的进程抓着文件"，**方向就偏了**。
> 后来回看代码才发现那个实验本身写错了——**`map()` 的返回值没接住，
> 映射立刻被垃圾回收，等于压根没测到"映射还活着"的情况。**
> **"我以为我测过了"和"我真的测到了"之间，差一个返回值。**
> 详见 `docs/06-runbook/troubleshooting.md` 2026-10-07 那条。

### 与官方态度的对照（解释为什么这不是"我配错了"）

查过 Apache 官方工单库，同一现象至少有三个工单**至今 Open**：

| 工单 | 标题 | 状态 |
|---|---|---|
| KAFKA-1194 | The kafka broker cannot delete the old log files after the configured time | Resolved / **Abandoned** |
| KAFKA-6983 | Error while deleting segments - The process cannot access the file... | **Open** |
| KAFKA-7086 | Kafka server process dies after try deleting old log files under Windows 10 | **Open** |
| KAFKA-6059 | Kafka cant delete old log files on windows | **Open** |

同现象下也有一个工单被以 `Not A Bug` 关闭（KAFKA-6901），提交者的结论是"杀毒软件问题"——
**但本次实测加排除项无效**，所以那不能解释我们这一台。

**Apache 从未把 Windows 列为 broker 的受支持生产平台。** Kafka 能删映射文件的假设建立在
POSIX 语义上（Linux 下 unlink 一个仍被映射的文件是合法的），Windows 不满足这个前提。

## 候选方案

### 方案 A：继续原生 Windows + 绕行配置（保留期无限、关清理器）
- 优点：零新增依赖；ADR-0004 不动
- 缺点：**Kafka 变成一个只能进不能出的黑盒**——磁盘只涨不减；**「删主题」必崩**；
  每个里程碑重置环境都要手动清目录；而且这个绕行方案**从未被长期验证过**（当天只观察到 50 秒不崩）
- 结论：**否决**。它把一个基础设施组件变成了随时会响的地雷，而 M4 之后还有 M5（ES 增量同步复用同一条总线）、M8（秒杀异步下单）都要长期依赖它

### 方案 B：Docker Desktop 起 Kafka
- 优点：社区标准做法；一条命令；环境与 CI 一致；**容器内是 Linux 文件语义，本类问题不存在**
- 缺点：**本机装不了**。实测：本机为 Windows 10 **Home**（build 19045），
  没有 Hyper-V 后端所需的 Pro/Enterprise（ADR-0004 已记此项）；Docker Desktop 的
  WSL2 后端又要求先有 WSL2；且 **C 盘仅剩 32 GB**，而 Docker Desktop 的镜像与虚拟磁盘默认落 C 盘
- 结论：**否决**（不是不认可，是这台机器装不了）

### 方案 C：WSL2 里跑 broker（**选中**）
- 优点：
  1. **从根上消掉问题**：WSL2 里是真正的 Linux 内核，`unlink` 一个被映射的文件是合法的——
     这类"文件被另一个进程占用"的失败模式**在内核语义层面就不存在**，不是被绕过去了
  2. 不需要 Hyper-V（WSL2 用的是 VirtualMachinePlatform，Home 版支持）
  3. **原生 Windows 侧的 Java 应用照旧连 `localhost:9092`**，业务代码一行不改
  4. 顺带解决 M5 的 ES：同样可以放进 WSL2，而 ES 在 Windows 上的已知问题也不少
- 缺点：
  1. **首次安装需要管理员权限**（`wsl --install` 要装 Windows 可选功能、要重启）——
     本项目的 CLI 会话是**非提权**的，这一步只能由用户手动完成
  2. **C 盘只剩 32 GB**：WSL2 的发行版与虚拟磁盘**默认落在 C 盘**。
     必须在 `.wslconfig` 里把发行版迁到 D 盘、并限制内存上限，否则会吃掉本就紧张的 C 盘
  3. 首次下载发行版约几百 MB，需要走代理
  4. 引入了一层新的"环境不可复现"因素（与 ADR-0004 的负面后果同类，但更轻）

### 方案 D：Linux 虚拟机
- 优点：最接近生产，文件语义正确，与项目其他部分完全隔离
- 缺点：虚拟机常驻要吃 2 G+ 内存，而本项目 M9 全开预算已到 10.9 G / 16 G；且需要手动装系统
- 结论：否决——**WSL2 在"正确性"上已等价于 Linux，但内存与安装成本低得多**

---

## 决定

**采用方案 C：把 Kafka broker 迁移到 WSL2 中运行，原生 Windows 侧的应用通过
`localhost:9092` 连接，与现在完全一致。**

**并同时修订 ADR-0004：其「本地不使用 Docker」的结论改为「本地不使用 Docker，
但中间件承载在 WSL2 中」——原文按变更留痕规程保留，末尾追加修订记录。**

### 具体承载方式（写下是为了让下一个人能照做）

| 项 | 决定 | 理由 |
|---|---|---|
| WSL2 是否当作 Docker 用 | **不**。只把它当"一台本地 Linux"，在其中**原生安装** Kafka/ES 的官方发行包 | 避开 Docker Desktop 这个装不上的东西，同时保住 Linux 文件语义 |
| Kafka 数据目录位置 | **WSL2 自己的文件系统内**（如 `~/kafka/kraft-logs`），**不放 `/mnt/d/...`** | `/mnt/*` 是跨文件系统访问，性能差且行为与 Linux 原生命令不同；放进 `/mnt/d` 等于把 Windows 的坑请回来 |
| 内存上限 | `.wslconfig` 里 `memory` 显式限制 | 本机 16 G，不能让 WSL2 默认吃一半 |
| 磁盘位置 | 发行版虚拟磁盘迁到 D 盘 | C 盘仅剩 32 GB |
| Windows 侧连法 | `localhost:9092` | WSL2 有 localhost 转发；`advertised.listeners` 保持 `PLAINTEXT://localhost:9092` |
| 启动脚本 | `scripts/start-kafka.bat` 改为转发到 WSL2（`wsl -d <distro> -e bash -lc '...'`） | 保持"一个脚本起一个中间件"的既有习惯，调用方式不变 |
| 该脚本的 Git 归属 | **提交**，跟随仓库 | ADR-0004 记录过 `scripts/*.bat` 曾因忽略规则被挡在仓库外，后来专门放行 |
| 原有端口 | 仍是 9092（客户端）/ 9093（控制器） | 业务代码与配置不改 |

## 理由

**一、这不是"换个环境试试"，而是在修正一个前提错误。**

ADR-0004 选原生部署的理由是**内存**（还有 C 盘空间）。那两条理由今天依然成立——
本 ADR 并不推翻它。但 ADR-0004 有一个**当时无法预见的前提**：
它假设"中间件在 Windows 原生下能正常工作"。**对 MySQL 和 Redis，这个假设成立。
对 Kafka，它不成立**——而且这是 Kafka 自己承认的（官方不支持 Windows 跑 broker，
相关工单至今 Open）。

**原决策的代价被低估了。** ADR-0004 在「负面」里写的是"环境不可复现、集成测试不能用
Testcontainers"，这些都是**可接受的**代价。而实际代价是**一个核心中间件直接不可用**——
这不在当时的评估里，因为它当时还不知道。

**二、WSL2 是"修前提"，不是"绕问题"。**

今天的排查反复出现同一个模式：**每一个绕行方案都只是把刀挪开，而不是把刀拿走**。
关清理器、保留期无限、换新目录——它们都让问题**暂时不出现**，而磁盘回收能力、
删主题能力则永久丧失。WSL2 不一样：它换掉了操作系统内核，**那个失败模式在内核层面
不存在**。这是本项目一贯的判据（见 architecture.md 的取舍风格）：**宁可换掉错误的前提，
不要堆叠绕行配置**。

**三、为什么不是 Docker（虽然 Docker 更主流）。**

社区标准答案确实是 Docker Compose。本机装不上，这是硬事实（Home 版 + C 盘 32 GB）。
**但决策理由不能写成"因为装不上所以退而求其次"**——WSL2 在正确性上并不比 Docker 差：
两者都提供 Linux 文件语义，差异只在"容器编排"与"进程隔离"这些本项目当前用不到的能力上。
**对"在本地跑一个 Kafka 给应用连"这一个需求，WSL2 与 Docker 等价。**

**四、内存预算是可控的。**

WSL2 默认按物理内存的一半分配，可以在 `.wslconfig` 里压到 1～1.5 G
（Kafka 本身按 ADR-0001 的预算就是 1 G 堆）。这比 Docker Desktop 的固定开销更省，
与 architecture.md §6.1 的预算表仍能对上。

## 后果

- **正面**：
  - Kafka 在这台机器上**真正可用**：能删段、能删主题、能回收磁盘，不再需要任何绕行配置
  - **M5 的 ES 可以顺手一起搬进去**，一次解决两个 Windows 原生坑
  - 与生产环境（Linux）的行为更接近，本地验证过的结论更可信
  - `.bat` 脚本的调用方式不变，开发习惯不变
- **负面**（诚实写全）：
  - **首次安装需要用户手动以管理员身份执行**（`wsl --install`），这一步 CLI 做不了
  - 需要额外搬迁发行版到 D 盘并设置内存上限，多一层环境配置
  - **需要重启一次系统**
  - 引入一个新依赖（WSL2），与 ADR-0004 原「负面」项同类但更可控
  - **原生的 Kafka 3.9.1 安装与 `scripts/start-kafka.bat` 会被废弃**，
    但**不删除**——保留到 WSL2 方案跑通并稳定运行一个里程碑之后再考虑清理，
    理由与今天的教训一致：**留证据比清理干净重要**
  - 本 ADR 的决策**尚未执行**（截至 2026-10-07 收盘）：WSL2 还没装，
    Kafka 还没迁。**执行完毕前，M4 处于阻塞状态**

## 被否决方案为何不选

- **方案 A（原生 + 绕行配置）**：它让 Kafka 失去磁盘治理能力，且**删主题必崩**。
  更要命的是，这类"看起来能跑"的配置**不会被任何测试发现有问题**——直到某天磁盘满了、
  或者某人删了一个主题。今天的 16 次崩溃里，有 5 次结论是错的，其中两次正是
  "看起来解决了"。**对一个要连续支撑 M4/M5/M8 三个里程碑的组件，不能建立在绕行配置上。**
- **方案 B（Docker Desktop）**：本机为 Win10 **Home**，无 Hyper-V 后端；
  且 C 盘剩 32 GB，装不下其镜像与虚拟磁盘。**不是技术偏好问题，是装不上。**
  （若将来换机或系统升级到 Pro，本决策应重新评估——WSL2 与 Docker 可共存，
  届时亦可改为 Docker，见「修订记录」的预留说明。）
- **方案 D（Linux 虚拟机）**：内存开销（常驻 2 G+）与 M9 的 10.9 G 预算冲突，
  而它相对 WSL2 的额外收益（完全隔离、可快照）对本项目没有实际用武之地。

## 修订记录

### 2026-10-08 · 承载方式改为「Docker Compose」

**由**：ADR-0021（Kafka 与 ES 用 Docker 跑在 WSL2 里）
**原因**：本 ADR 定的是「Kafka 迁进 WSL2」，**没定怎么装**。执行时先走了「在 WSL2 里手工装原生 Kafka」，
装成了也能用，但暴露三个问题：

1. **不可复现**——为了让它跑起来，我手工改过 DNS、IPv6 开关、listener 的 IPv4 绑定、数据目录、heap。
   **这些改动没有一处写进任何可提交的文件**，换台机器或重装 WSL 就得重来一遍
2. **WSL2 出网不稳**——实测 DNS 解析失败、`networkingMode` 回退到 Consomme。手工装要靠它下载
3. **与社区资料脱节**——网上讲"本地起 Kafka"的绝大多数是 Docker Compose 写的

**变更**：

- **本 ADR 的核心结论完全保留**：**「在这台机器上，Kafka 不能跑在原生 Windows」**——
  这条被 16 次崩溃与九轮排除实验支持，**没有变，也不需要变**。
- **被取代的只有「承载方式」这一项**：由「WSL2 里手工装原生 Kafka」改为
  **「WSL2 里用 Docker Compose 跑 Kafka」**。
- **对 ADR-0004 的修订关系不变**：本 ADR 仍然修订 ADR-0004，只是修订后的形态从
  "中间件跑在 WSL2 里（手工装）"变成"中间件跑在 WSL2 的容器里"。ADR-0004 的
  「内存是硬约束」与「不用 Docker Desktop」两条**仍然有效**——ADR-0021 用的不是 Docker Desktop，
  而是装在 WSL2 里的 Docker 引擎。
- **仍然有效的一条警告**：本 ADR 记录的**「一处仍未解释的矛盾」**（改名在独立实验里成功、
  Kafka 却崩在改名上）**至今没有闭合**。它不影响任何决策——无论底层机制是什么，
  问题都出在 Windows 的文件语义上，换 Linux 内层即整体绕开。**留着，不编机制。**
- **新增的一个前提**（ADR-0021 记录的）：WSL2 空闲约 1 分钟会自动关机，容器跟着死。
  所以启动脚本要**前台挂住**。这条是我当初没想到的。
