# ADR-0017: 点赞与收藏用两张专用表，不做通用 action 表

- **状态**：已接受
- **日期**：2026-10-05
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

M2 要给帖子做**点赞**与**收藏**。两件事结构几乎一样：都是一个用户对一个对象做了一次动作。

于是有个现成的"聪明"做法：既然结构一样，为什么不合并成一张表？

## 候选方案

### 方案 A：两张专用表 `t_post_like` / `t_post_collect`（**选中**）
每张表两列：`(user_id, post_id)` 联合主键 + `create_time`。

- 优点：表结构自解释；**联合主键本身就是幂等保证**；索引窄
- 缺点：两张几乎一样的表；将来点赞对象每多一种就多一张

### 方案 B：一张通用表 `t_user_action(user_id, action_type, target_type, target_id)`
- 优点：加对象类型不用加表；跨类型的聚合查询（"这人一共产生过多少互动"）一次查完
- 缺点：**唯一约束要拼四列**，语义弱；每次查询都得带 `target_type`，漏带不报错只会查错

## 决定

采用**方案 A**：两张专用表。

## 理由

### 一、通用表的卖点是一个**还不存在**的需求

B 的好处理由是"将来给评论也能点赞、给用户也能关注"。但 M2–M10 的规划里，
**点赞对象只有帖子一种**（评论点赞不在 spec §6.2 的任何里程碑里）。

spec §1.5 的 minimal 原则针对的正是这种情况：**为一个想象中的需求，现在就付出真实的复杂度**。

真需要时加一张 `t_comment_like` 的成本（照抄现有表），
**远低于**现在把一张表做复杂之后、每个读它的人都要多理解一层抽象的成本。

### 二、专用表的联合主键就是幂等保证

`PRIMARY KEY (user_id, post_id)` 让"重复点赞"在数据库层就撞车，
配 `INSERT IGNORE` 或捕获重复键异常即可，**不需要"先查再插"**——
而"先查再插"在并发下会插进两条（或报错），是有名的坑。

在通用表里，这个约束要写成 `(user_id, action_type, target_type, target_id)` 四列联合主键。
它**能**工作，但读代码的人得先想清楚这四列各自是什么，
而专用表的主键一眼就懂：**这个人赞过这个帖，只有一条**。

### 三、索引宽度是有实际代价的

专用表的查询是 `WHERE post_id = ?`，走 `idx_post_id`。
通用表要写成 `WHERE target_type = 'POST' AND target_id = ?`——
索引从 2 列变 4 列，且**一旦有人漏写 `target_type`，查出来的就是别的类型的互动**，
不报错，只是数据不对。

## 后果

- **正面**：
  - 表结构自解释，读代码不用先理解一层抽象
  - 唯一约束即幂等，不需要应用层去重
  - 索引窄，查询条件短
- **负面**：
  - 点赞对象每增加一种（评论、用户）就多一张结构几乎相同的表
  - 跨类型的统计要 `UNION ALL` 几张表——如果将来要做"用户互动总览"，这是笔要还的债
  - 表数量随功能线性增长

## 被否决方案为何不选

**方案 B 在多态聚合上是明确更优的**：如果这个项目有一张"互动动态流"
（点赞、收藏、关注混在一个时间线里），通用表的优势会立刻压倒专用表——
那种查询正是它擅长的。

本项目没有这个需求：点赞与收藏是**分别展示**的（帖子详情页两个按钮、
个人主页两个列表），从不需要混在一起查。

> **判据是"查询会不会跨类型"，不是"结构像不像"。**
> 两张表结构像，但它们的查询从不合并；通用表结构统一，
> 却要为每次查询付出"带上类型条件"的代价。
