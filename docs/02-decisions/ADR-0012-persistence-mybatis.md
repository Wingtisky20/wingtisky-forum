# ADR-0012: 持久层选型（MyBatis，不用 MyBatis-Plus）

- **状态**：已接受
- **日期**：2026-09-29
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

M1 要写用户表，必须选一个持久层。但 spec §12 的开放问题表把"持久层：MyBatis vs MyBatis-Plus"的**决策时点写成了 M2**——而 M1 就要读写数据库。

**这是 spec 的一处排期遗漏**：它把持久层归到了"内容域核心"那一档，忽略了 M1 的用户域同样是数据库操作。所以这个决策不是在 M2 从容评估的，而是在 M1 开工时被**倒逼**做出的。

## 候选方案

### 方案 A：MyBatis（**选中**）
SQL 手写在 XML 里，接口只声明方法签名。

- 优点：SQL 完全可控可调；M6 的亮点（深翻页优化）本来就要手写 SQL；面试官对"能手写 SQL"的认可度明显高于"会调 API"
- 缺点：基础 CRUD 要手写，比 Plus 多写不少样板

### 方案 B：MyBatis-Plus
在 MyBatis 之上封装了通用 CRUD、条件构造器、分页插件等。

- 优点：单表 CRUD 几乎零代码，开发快
- 缺点：**与本项目的亮点 4 冲突**

## 决定

采用 **MyBatis**，SQL 写在 XML 映射文件里。

## 理由

**决定性理由是 M6。** 亮点 4 是"Deferred Join 解决深翻页"，它的交付物是一组**手写 SQL 的性能对比**（普通 `LIMIT offset` vs 延迟关联 vs Keyset），配 `EXPLAIN` 前后的执行计划。这件事：

- Plus 的分页插件**帮不上忙**——它封装的是常规分页，而亮点要的恰恰是绕过常规分页
- 更糟的是，用 Plus 会让这个亮点被"绕开"：既然分页交给插件了，就不会有人去手写那个优化

**用 Plus 的代价不是"性能差一点"，是"把最大的一个亮点关掉了"。**

**第二个理由是本项目自己的判断标准。** 前面几条 ADR 反复出现的模式是"这个决定服务谁"——而这里的服务对象是**面试**。手写 SQL 是一个可以讲的东西（"为什么这样写更快、执行计划怎么变的"），调用 Plus 的 API 不是。

**关于"写得更慢"这个代价，实际影响比想象中小**：本项目每个模块的表都不多，M1 只有三张表、不到十个查询。省下的那点样板代码，换不来 M6 的一个亮点。

## 后果

- **正面**：SQL 可见可控；M6 的亮点有实现基础；不额外引入一个封装层
- **负面**：
  - 基础 CRUD 要手写，`UserMapper` 这类接口会有不少样板
  - 表结构变更时，实体、XML、接口三处都要改（Plus 只需改实体）
  - 复杂的动态 SQL（`<if>` / `<set>`）可读性不如 Java 代码，写错时的报错也比较笼统

## 被否决方案为何不选

- **方案 B（MyBatis-Plus）**：它在"快速搭一个 CRUD 后台"这类场景下是更好的选择——本项目不是那个场景。**选型要看项目要交付什么**，而不是哪个更省事。

## 修订记录

### 2026-09-29 · 补记 spec 的排期遗漏

本 ADR 的决策时点是 **M1**，而 spec §12 记为 M2。**已在 spec §12 中更正**，并注明原因（M1 就要写用户表）。留下这一节，是因为"计划里写的时点与实际不符"本身值得被记住——它说明排期表也会有盲区，不能当成不可质疑的输入。
