# ADR-0015: 跨域取用户信息走 wt-domain 契约，不冗余作者快照

- **状态**：已接受
- **日期**：2026-10-05
- **决策者**：Wingtisky（决策） / Claude（建议）

## 背景

M2 的帖子列表要显示**作者昵称与头像**，而作者信息在 `forum-user` 里。

按 `architecture.md §3.1`，`forum-content` **不得依赖** `forum-user`（ArchUnit 会拦），
两者只能通过 `wt-domain` 的契约通信。而 `wt-domain` 从 M0 建立至今**一直是个空壳**——
M2 是它第一次被真正用上，所以这次定下的形状会成为后续所有跨域调用的模板。

同时要解决一个现实问题：**列表页一页 20 篇帖子，就是 20 个作者**。

## 候选方案

### 方案 A：每次展示时通过 `UserQueryService` 批量取（**选中**）
`wt-domain` 定义接口，`forum-user` 实现，`forum-content` 注入使用。

- 优点：昵称改了全站立刻一致；契约稳定，用户域内部怎么改都不影响内容域
- 缺点：列表页多一次查询；多一层"接口与实现分离"的间接性

### 方案 B：发帖时把昵称 / 头像**快照**进 `t_post`
- 优点：列表页零额外查询，读最快
- 缺点：**用户改了昵称，历史帖子永远显示旧昵称**

## 决定

采用**方案 A**：`wt-domain` 定义 `UserBrief` 与 `UserQueryService`，
`forum-user` 提供实现，`forum-content` 只依赖契约。

## 理由

### 一、B 的代价不是"慢一点"，是"一处永远修不好的不一致"

快照看起来只是"省一次查询"，但它把一个**会变的值**复制到了一个**不会自动更新**的地方。
用户改昵称之后，只有新帖子显示新昵称，历史帖子停在旧昵称——而且**没有任何机制会去修正它**。

这类设计在面试里很难辩护，因为它不是缓存：**缓存可以失效，快照不能**。
缓存的一致性由 TTL 或显式失效兜底，快照没有兜底。

### 二、批量查询是必须的，不是提前优化

分页列表天然就是这个形状：一页 N 条 → N 个作者 → **一次批量查询**。
如果契约只提供 `findBrief(Long id)`，列表页必然写成 N+1，
而 N+1 问题最麻烦的地方是**它不会报错**，只在数据量上来之后表现为"列表越来越慢"。

所以契约里直接放 `Map<Long, UserBrief> findBriefs(Collection<Long> ids)`——
**把正确的用法设成最省事的用法**，比事后靠 code review 拦 N+1 可靠。

### 三、它同时是 M3 的第一个缓存对象

用户信息**读多写少**，而且"改昵称"是一个**明确的失效事件**——
这正是亮点 1（多级缓存）要讲的那种数据。

把它放在契约接口上，M3 加缓存时**只需要在实现里加，调用方一行不改**。
如果现在让每个调用方自己去查库，M3 就要到处改。

### 四、契约里只放跨域需要的最小信息

`UserBrief` 只有 `id` / `nickname` / `avatar`——**不含 `email`，更不含 `password`**。

把 `User` 实体放进 `wt-domain` 等于把用户域的内部结构变成公共 API：
此后用户表加一个字段，就得考虑"会不会影响内容域"。

## 后果

- **正面**：
  - 昵称改了全站立刻一致，不存在"历史数据停在过去"的问题
  - 依赖方向清晰：两边都只指向 `wt-domain`，`forum-user` 与 `forum-content` 互不认识
  - M3 加缓存时调用方零改动
- **负面**：
  - 列表页多一次批量查询（**是一次，不是 N 次**）
  - 多一层接口与实现分离的间接性——读代码时要在两个模块之间跳一次
  - `app` 模块必须同时依赖两者才能装配起来，这层"看不见的连线"不在 Maven 依赖图里

## 被否决方案为何不选

**方案 B（冗余快照）本身不是错的**——它在另一个场景里恰恰是**正确**的做法：

> **订单里的收货地址就该是快照。** 用户改了默认地址，三个月前的订单必须还显示当时填的那个，
> 否则那笔交易"寄到哪了"就说不清了。

两者的区别是这个值**代表谁的当前状态**：

| | 帖子的作者昵称 | 订单的收货地址 |
|---|---|---|
| 它反映的是 | **用户此刻是谁**（活人的当前状态） | **下单那一刻发生了什么**（已发生事实的记录） |
| 所以应该 | 跟着用户变 | **冻结住** |
| 冗余快照 | ❌ 错 | ✅ 对（M7 会这么做） |

**判据是"这个值描述的是当前状态还是历史事实"，不是"哪个更快"。**
把它当成性能问题选，就会在帖子这一侧选错。

## 面试话术

> *"作者昵称我不用快照，走跨域契约实时批量取。快照的代价不是慢一点，是用户改昵称之后历史帖子永远停在旧昵称，而且没有任何机制会去修它——这不是缓存，因为缓存可以失效，快照不能。*
>
> *但快照在订单里是对的：收货地址必须冻结在下单那一刻，否则那笔交易寄到哪就说不清了。判据是——这个值描述的是用户的当前状态，还是已经发生的事实。*
>
> *另外契约里我直接放的是批量方法，因为分页列表就是 N 条对应 N 个作者，给单个查询的接口必然被写成 N+1，而 N+1 不会报错，只会在数据量上来之后表现为列表越来越慢。"*
